# 复用优化 — 工具盘点、两层检测、三分法与抽取沉淀

复用优化的主文档，按生命周期组织：盘点（动手前）→ 检测（发现重复）→ 判定（三分法）→ 抽取 → 验收。

核心立场：**改动前先盘点既有工具代码，能复用不新写；重复逻辑抽成可测试的工具/静态方法，让工具层随每次改动持续沉淀。**

## 为什么方向是「抽成工具/静态方法」

- **可测试性**：无副作用的静态方法可脱离调用上下文直接单测，测试不再依赖搭建业务场景。
- **改动范围小**：逻辑收敛到一处，修复和演进只动工具本身，diff 集中、回归面可控。
- **可沉淀**：工具层是下次盘点的检测基础——工具越全、归类越清晰，未来「能复用」的命中率越高，形成正循环。所以每次改动都要让工具层变得更好找，而不是更分散。

## 步骤 0：工具盘点 [MANDATORY 前置]

fix 模式在确定范围后、审查前必须执行；未经盘点不得提议新写任何工具函数。

1. **找**：项目里的 utils/helpers/shared/common/lib 目录、静态工具类、基类 helper。读 exports 和调用方，不靠目录名下结论。
2. **建清单**：每个工具能力一句话 + 位置。大项目范围 = 通用 utils 全量 + 与本次改动同域的模块工具；小项目全量。
3. **用**：清单进入审查上下文与最终报告；后续每个要写/要改的逻辑先过清单，再走三分法。

## 步骤 1：两层重复检测 [MANDATORY]

**必须走两层**：第一层确定性工具打底（全量、无遗漏的文本/token 级克隆），第二层纯 LLM 补语义级重复（工具结构性漏掉的部分）。只靠肉眼读文件找重复 = 未完成。

### 第一层：确定性工具（先跑）

| 场景 | 工具 | 命令 |
|------|------|------|
| 默认（多语言一把梭，224 种格式） | jscpd | `npx jscpd <dir> --min-lines 5 --min-tokens 50 --ignore "**/node_modules/**,**/dist/**,**/build/**"` |
| JS/TS 项目补语义档 | fallow | `npx fallow dupes`（阈值分 strict/mild/weak，默认偏保守，可用 weak 提召回） |
| Java 项目 | PMD CPD | `pmd cpd --minimum-tokens 50 --dir <dir> --language java` |
| 顺带：死代码/未用导出（JS/TS） | knip | `npx knip` |

规则：

- 工具缺失、语言不支持、安装失败 → **记录跳过原因并报告**，直接上第二层，不阻塞流程。网络受限时 jscpd/fallow 都可 `npx` 免安装直跑，失败先查网络再放弃。
- 报告量大时用 JSON reporter（如 `npx jscpd <dir> --reporters json`）再用脚本聚合成簇，主 agent 只看聚合结果，**不逐条读原始报告**（省 context）。
- 工具输出是「克隆对」，不是结论。要把克隆对归并成下文的「重复簇」格式。

### 第二层：纯 LLM 语义级检测（必做）

工具只认文本/token 相似，以下类别结构性漏检，由 LLM 层负责：

- **近似复制**：同结构但变量名/字面量不同，且差异超出工具阈值。
- **同算法不同载体**：同一算法作用在不同数据类型/结构上（如对数组做一遍、对 Map 又做一遍）。
- **横切散点**：同样的重试、错误包装、序列化、参数校验、日志模式散落在多处，每处单独看都「合理」。
- **手写重实现**：标准库、既有 utils、维护良好的第三方包已有该能力。
- **同语义不同抽象层级**：一处调用 helper，另一处把 helper 的内联展开手写了一遍。

方法：按目录/模块分域并行 subagent（对齐 `scan-candidates.md` 的「广泛扫描」，域按目标项目目录结构动态划分）。每个 agent 产**重复簇**，不产逐条重复——逐条清单无法支撑抽取决策。

### 产出格式：重复簇

两层结果统一归并成簇，一簇一条：

```
簇 #n: <共同语义一句话>
成员: file:line ×N（列全，漏一个调用点 = 抽取后留残留）
差异点: <要参数化什么：变量、字面量、数据类型、错误处理策略>
来源: 工具 / LLM / 两者（两者都命中 = 高置信）
建议: 直接复用 X / 扩展 X 后复用 / 新抽工具 → <归宿>（判定规则见下方三分法）
```

聚合与误报：

- 主 agent 合并两层结果：同簇合并、丢弃误报、消除冲突建议。
- **消假差异、留真差异**：形式同构且语义同构才可合并；概念域或变化轴不同的「长得像」是真差异，保留并在报告中说明理由，不为凑数硬抽。
- 低置信簇（只有 LLM 单源且语义判据模糊）降级为 TODO/提案，不进 fix 清单。

## 步骤 2：三分法（每个逻辑先分类再动手）

| 判定 | 条件 | 动作 |
|------|------|------|
| 直接复用 | 既有工具完全满足 | 调用它，删手写实现 |
| 扩展后复用 | 既有工具差一点（参数化/泛化一步即可覆盖） | 扩展工具本身，**不在调用点打补丁** |
| 归类待抽 | 无现成工具，但属通用能力 | 归入同类组；组内 ≥2 处即抽取 |

「扩展后复用」的扩展本身也受行为不变铁律约束：扩展后既有调用点行为必须不变（新能力走新参数/新重载，默认值保持旧行为）。

## 步骤 3：抽取时机

- **第二次出现即抽**（rule of two）：重复簇有 ≥2 个成员即满足抽取条件。
- 单处不抽——再通用也是投机泛化；单处但明显通用 → 记 TODO 归入对应组，等第二处出现。
- 例外：用户显式要求抽取单处时以用户为准。

## 步骤 4：沉淀位置决策

| 逻辑性质 | 归宿 |
|---------|------|
| 无副作用、无领域语义（字符串/日期/集合/编解码等） | 静态方法/工具类，进通用 utils |
| 带领域语义（订单状态流转、会话生命周期等） | 领域模块内的静态方法或领域服务 |
| 禁止 | 领域逻辑下沉通用 utils（污染工具层，破坏盘点的可发现性） |

**归类原则：同变化轴放一起。** 都是字符串处理归一处、都是某协议编解码归一处——即使现在每组只有两三个方法，清晰的归类是未来合并成更强工具层的结构基础。避免按「从哪个文件抽出来的」组织。

## 步骤 5：抽取工作流

1. **差异点参数化**：把簇内成员的差异（变量、字面量、类型、策略）变成参数，不改语义。
2. **命名按能力不按来源**：名字说「做什么」（`normalizeKey`），不说「从哪抽的」（`orderPageHelper`）。
3. **逐个迁移调用点**：一次迁移一个，每步跑测试/构建，失败回滚该步——成员清单漏一个 = 旧实现残留。
4. **验收（量化闭环）**：
   - 测试通过（证明行为不变）；
   - 重复检测前后 delta：抽取前后各跑一次第一层工具，报告重复行数/重复率下降；
   - 旧实现无残留：全仓搜旧代码片段，命中数为 0。

## 报告要求

复用类发现在报告中额外标注：**三分法判定、归宿（文件/类）、影响调用点数、预期重复行 delta**。低置信或需行为决策的保持提案形态，等用户拍板。
