# Workflow — code-simplify 主流程（fix 模式）

被 `code-simplify` 触发后先判模式：用户只要找简化候选（"找机会"/"找死代码"/"清理重复"）→ 读 `scan-candidates.md` 走 scan 模式，只产候选不改码。否则按本文件执行。**全程先报告、确认后改。**

## 步骤 1：确定范围

见 `scaling.md` 的「范围确定」一节。确定文件清单并估算负载指标（代码量、文件数、架构复杂度）。

## 步骤 1.5：工具盘点 [MANDATORY]

**必读 `reuse-optimization.md` 步骤 0**，产出工具清单（既有工具能力 + 位置）。清单进入审查上下文：后续每个审查者发现的手写逻辑先过清单判三分法，未经盘点不得提议新写工具函数。

## 步骤 2：选择执行策略

见 `scaling.md` 的「自适应策略」一节。根据负载指标选择 L1/L2/L3 及拆分维度。
用户可强制指定策略（"用单 agent" / "全部按文件并行拆"），以用户为准。

## 步骤 3：审查

按所选策略执行审查。每个审查者（无论单 agent 还是并行的一个）都扫描 `review-signals.md` 中的信号。

**并行原则**：真正的洞察来自"拆解职责 + 并行 + 完整上下文 + 聚合去误报"。
- L2 按问题类别拆：并发发起 3 个 agent（复用 / 质量 / 效率），各拿完整 diff，互不等待。复用 agent 额外**必读 `reuse-optimization.md`（两层检测 + 三分法 + 沉淀位置）**；效率 agent 额外**必读 `perf-signals.md`**（局部性能信号 + A/B 行为分档 + 测量护栏）。
- L3 按文件/模块拆：把文件分组，每组一个 agent 并行；组与组有交叉逻辑时，用"按问题类别"补一轮。
- 聚合阶段：等所有 agent 完成后统一进行，由主 agent 合并发现、丢弃误报、消除冲突建议。

## 步骤 4：报告（先报告，确认后改）

- 按文件分组列举发现：**文件、位置、类型、问题、建议改法、为什么更易懂**。
- 复用类发现额外标注：**三分法判定、归宿（文件/类）、影响调用点数、预期重复行 delta**（见 `reuse-optimization.md`）。
- 性能类发现额外标注：**A/B 档、预期收益量级、测量方式**（无测量手段的性能候选只列不改，见 `perf-signals.md`）。
- 标注严重度 / 置信度（高置信可改，低置信需用户判断）。
- **结尾问用户：哪些要应用？** 等用户明确确认（可全选/单选/忽略）。确认前一律不动文件。

## 步骤 5：确认后应用（增量、验证）

- **一次只做一个简化**，每步后跑测试/构建（有的话）；失败就回滚这一步。
- **重构与 feature 分开提交**——不要边简化边加功能。
- **大型重构（>500 行）**：优先用 codemod / AST 工具 / 脚本自动改，别手改。
- 完成后汇报：改了什么、行为如何保持不变、diff 干净可审。
- 性能优化类改动：测试通过只证明行为不变，收益需基准 / profile 证据；B 档（行为敏感）改动必须经用户确认行为差异后才可应用。
- 抽取复用类改动：验收走量化闭环——测试通过 + 重复检测前后 delta（重复行数下降）+ 旧实现零残留（见 `reuse-optimization.md` 步骤 5）。

## 关键检查点

- [MANDATORY] 范围外的代码一概不动（除非用户明确要求扩范围）。
- [MANDATORY] 任何改动前先想清楚行为如何保持；要改测试才能过的简化 = 改变行为，撤销。
- [MANDATORY] 未获确认前不应用任何修复。
