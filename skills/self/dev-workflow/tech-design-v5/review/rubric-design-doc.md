# 设计文档审查清单（对抗式）

> **本清单是 `tech-design-direction-review`（方向审）、`tech-design-review-v5`（主审）、`tech-design-impact-review`（影响面审）、`tech-design-simplicity-review`（简洁审）四个 agent 的共同审查依据，分工见下。** 基调是**对抗式**——默认怀疑方案不成立，除非被证据说服。每一项都要主动找反例、攻击点，逼方案自证。
>
> **为什么必须对抗式**：设计文档最贵的错误（运行时断言靠推理、方案不解决根因、关键事实编造、前提不成立）在中立审查下会蒙混过关。本清单的全部检查项，都来自真实案例里被对抗审查（多轮独立攻击 + 实测）才逼出来的问题。中立 = 放过 = 实施期翻车。
>
> 原则层（七原则 P1-P7 与产物表规格）对应 `references/principles.md`；准则编号对应 `references/design-principles.md`；反例对照 `anti-patterns.md`。本清单只承载方向级与方案级判据——结构/表达/验收完备类判据在 T1 自检拦截。

---

## 审查纪律

1. **默认怀疑**：拿到文档先假设"这方案有问题"，逐项找证据反驳自己，反驳不了才放行
2. **事实必须验证 + 火力聚焦**：声称"事实错误/API 不存在"前，必须 `read` 源码核实，不得臆断。只报影响核心决策的问题——核心决策是否成立、决策依赖的事实证据是否真实、表达是否妨碍读者理解决策。编号/序号错乱、行号偏移、笔误、格式措辞等**不改变语义的机械性细节不报**：不进 Findings 表、不计数；确有现成证据时至多报告末尾一句话 INFO 带过。不平均用力
3. **只报告不修复**：发现问题给修复方向，不代写方案
4. **每个判定有依据**：引用具体检查项编号（D-N / P0-N / P1-N）+ 文档位置（章节号/行号），不凭感觉
5. **守护单一登记豁免 + 语义核对**：决策块守护登记表与正文 {{Gx}} 引用处展开全文并存是单一登记（准则 14）的目标形态——同一可执行内容在渲染视图多处出现是登记展开的结果，不按"重复"报；对账 guards 类修复或 {{Gx}} 引用点时读 s3-solution.json 的 decisions[].guards，核对登记处 id/text 与引用点语义一致，引用指向存在但内容不对 = must-fix（引用存在性机器可查，语义一致性只有审查能抓）。主审（tech-design-review-v5）按此条执行，其余席位通读覆盖

## 审查分工（方向审先行 + 三 reviewer 分工）

审查分两阶段：**第一道门 = 方向审**（`tech-design-direction-review`，攻击前提层与终态层——must-fix = 方向级打回，回 T1 重做含 Step D 诊断期，不派三 reviewer）；通过后三个独立 agent **并行**执行深审，本清单按分工划分，各自只判自己的条目：

| reviewer | 负责检查项 |
|---|---|
| **方向审**（`tech-design-direction-review`，先行门） | D1 ~ D5 |
| **主审**（`tech-design-review-v5`） | P0-7 ~ P0-12、P0-27 |
| **影响面审**（`tech-design-impact-review`） | P0-19、P0-20、P0-21 |
| **简洁审**（`tech-design-simplicity-review`） | P0-22、P0-23、P1-6 |

方向审通过后同一文档产出三份报告，修复时合并处理（见 `flow/write.md` Step 8）。任何一方发现他方职责范围的线索时，标 INFO 交接，不重复判定。

## D 系列 方向审（第一道门，must-fix = 方向级打回）

> 审的是「方案的前提与终态是否成立」——三审审的是方案做得对不对，审不出「前提是假的、终态是虚的」：文档的前提由写作者自己核实、自己声明，在文档内部看起来总是自洽的；建立在被击穿前提上的设计可以被三审打磨得很精致，精致感还会让所有人更确信前提对。攻击职责、身份设定与流程见 `agents/tech-design-direction-review.md`，判据本体如下。must-fix 的修复方向通常是「打回 T1 重跑 Step D」「先行裁决待裁决项」「重写公理清单」，不是局部修补。

### D1 分型正确

| 编号 | 检查项 | 怎么查 | 不通过形态 |
|---|---|---|---|
| D1 | **设计分型声明缺失或错误** | 文档头部必须有分型声明（终态型 / 演进型，与功能分级、风险分并列）。终态型：逐条核对触发依据——用户显式要求（终态 / 长期合理 / 不计成本 / 「反复出问题」）、修复史判定表输出「未修到」、设计对象为架构级（跨模块 / 状态权威变更 / 协议变更 / 新子系统），三条一条不占 = 分型拔高。演进型：验「为什么不需要终态视角」的辩护成色——读修复史判定表，同一问题域修过多次仍出问题、fix 集中在接口形状返工、修复后有回摆，任一条成立而文档仍称「窄修够用」= 辩护不成立 | 无分型声明；终态型无触发依据；演进型无辩护或辩护不被修复史判定表支撑；分型理由与修复史判定表结论矛盾 |

### D2 前提可击穿

| 编号 | 检查项 | 怎么查 | 不通过形态 |
|---|---|---|---|
| D2 | **前提清单（增强版）可被击穿** | 攻击对象 = §2 末前提清单（增强版，规格见 `references/principles.md` P5）。否定性断言（「无 X」「没有任何 Y」）逐条攻击：先枚举「谁可能在写、谁可能在持有」（跨进程 / 跨包 / 磁盘 / 内存 / 派生视图 / 定时任务 / 启动脚本 / 数据迁移代码），再逐个找写者侧反例——只查读侧不算核实。✅ 条目抽样复核实：亲自 read 它声称的源码位置，验证核实动作真实发生过且该内容支撑这条前提。⏳ 待裁决项逐条判「是否影响方向」：待裁决项若动摇方案主干依赖的现状理解（数据在哪、谁在写、上游行为如何），不能带着它进三审 → 升级 must-fix 先行裁决；与方向无关的放行 | 任一否定性断言被写者侧反例击穿；任一 ✅ 核实动作虚假（声称读了某位置而该位置不含支撑内容——整份清单可信度随之折损，剩余条目逐条升级复查）；方向级待裁决项未处理就往下走 |

### D3 终态有效（终态型专用，演进型跳过）

| 编号 | 检查项 | 怎么查 | 不通过形态 |
|---|---|---|---|
| D3 | **公理清单与终态-现状差距表不构成有效终态** | 公理清单（§3.1）逐条判别：这条陈述是系统在任何实现形态下都必须成立的不变量，还是当前实现的形状？判别法 = 假设把当前实现推翻重建，这条陈述还必须成立吗？不成立 = 实现细节混进公理。终态-现状差距表逐维对照现状查漏项：拿公理清单 + 终态形态逐维对照（数据权威归属 / 进程边界 / 协议形状 / 失效判定……每一维问「终态与现状在这维差多少、入表了吗」），漏掉的差距 = 迁移路径会漏掉的工作量与风险。迁移波次逐波问「这波结束时系统是否仍满足全部公理？是否引入了后续波次才能消除的中间态（两份权威并存的过渡期、临时开关、新旧路径双轨并存）」 | 公理混入实现细节（终态失去参照作用——所谓终态只是现状换个说法）；差距表漏项；波次制造新差距 |

### D4 产物表完整且真实

| 编号 | 检查项 | 怎么查 | 不通过形态 |
|---|---|---|---|
| D4 | **触发的产物表缺失、漏行或填表不实** | 完整性：按文档内容判定哪些原则被触发（触发条件见 `references/principles.md` 各原则），触发的产物表必须存在——状态副本清单 / 信号-蕴涵表 / 修复史判定表（§2 现状与问题）、前提清单（§2 末）、公理清单 + 终态-现状差距表（§3.1，终态型）、上游依赖清单（§2 末或 §3.3）。查漏行：状态副本清单漏持有者（跨进程 / 跨包 / 磁盘 / 内存 / 派生视图逐一问过去）、信号-蕴涵表漏信号（§3 方案里每个「以 X 变化触发 Y」的机制都该有一行）、上游依赖清单漏接触点。真实性（行级抽样攻击）：随机挑行 read 源码验证——状态副本清单验「同步手段」列与实际代码一致（表里写「事件广播同步」而源码是轮询对账 = 填表不实），信号-蕴涵表验「实际蕴涵」列，上游依赖清单验接触点真实存在 | 缺表；任一表有漏行；行内容与源码不符（行级证伪一次，全表可信度重审） |

### D5 问题定义忠于真问题

| 编号 | 检查项 | 怎么查 | 不通过形态 |
|---|---|---|---|
| D5 | **问题定义不忠于用户真问题** | §1 定义的问题是用户描述的现象，还是根因？文档有没有识别出用户没明确表达、藏在描述背后的深层问题？文档主体是不是探明问题的手段——加日志观察、加探针复现、「先收集数据再定方案」的步骤占设计主体（例外仅限探针体系本身复杂到需要设计且独立成章）。问题定义有没有被现状实现污染——问题定义里内嵌现状机制名、把现状实现当需求 | 只接住现象、没挖根因；探明手段占设计主体；问题定义内嵌现状机制名 |

### 对抗式核心三问（最重要）

| # | 检查项 | 怎么查 | 准则 |
|---|---|---|---|
| P0-10 | **方案是否真正解决目标问题** | 回溯 §1 问题定义 → §3 方案的因果链：方案实现了，问题真的解决吗？解决的是根因还是表象？只让症状消失、根因还在 = 不通过。**三种显式形态**（准则 12 设计决策序）：①**兜底替代根治**——§2 病症/根因明确，方案主体是掩盖问题类（catch 吞掉/降级遮蔽/重试自愈/轮询对账/缓存遮蔽），判别法：删掉补偿机制病因仍在；②**架构级问题逐个打补丁**——§2 显示多症状共点或根因在共享路径，§3 却只修单症状不在架构层做统一修复，「直接解决 vs 架构优化」决策未显式进方案对比；③**非功能设计无必要性论证**——掩盖问题类机制未回答「日常高频是否已覆盖、极端场景破坏性×概率×可检测性」、未过三档裁决（不做/简单/复杂）就上强自愈/强兜底/对账；复杂档未证「复杂度<事故代价」、未写升级到复杂档的条件。回收层兜底豁免条件（三者齐备）：极端情况而非正常路径 + 正常路径已根治 + 触发可观测 | 0/12/对抗 |
| P0-11 | **影响决策的关键事实错误** | 文档引用的 API/字段名/类型/方案成立依赖的事实，`read` 源码逐一核实；错误**影响决策或架构** → P0；行号偏移/编号序号等不影响决策的机械性细节 → 不报（审查纪律 2）。**含外部 API 时序/返回形态**（可 await、fire-and-forget、超时行为）——只看函数名不读实装签名 = 命中此项。**运行时断言与实施期事实的两态判定**：只能实施期核实的运行时/环境/宿主行为（CI 运行形态、构建产物、真机表现），合格登记形态唯一 = ⏳ 前提 + 实施期探针——前提登记完备（逐条带来源与不成立影响、挂探针）即该域合格，「文档没给出实施期才知道的运行时结论」不是缺陷、不得据此打 must-fix；本项只打两态——①断言失实（推断、未核实、未尝试的查询被写成事实或 ✅，含核实动作不完整却标 ✅）②前提登记有实质缺口（影响决策的信息缺失）。可静态核实的断言（读码/API 查询/文档核对）不适用 ⏳——未核实就写成事实按 ① 打 | 对抗 |
| P0-12 | **是否有副作用/遗漏** | 改 A 是否影响 B？有无遗漏连带改动（schema 变了没提 migration）？边界场景/迁移/向后兼容是否覆盖？**接管/替换既有流程的决策**：read 被接管的原实现，逐段核对"接管点之后的内部步骤"是否被静默绕过且接管方未复刻/未声明放弃（入口复用 ≠ 全程复用）。涉及外部共享状态写入时联动 P0-19 | 对抗 |

## 判定四态

对每个检查项，输出下列四态之一（必须有依据）：

| 判定 | 含义 | 何时用 |
|---|---|---|
| **通过** | 该项达标 | 需引用文档里达标的证据位置 |
| **不通过** | 该项违反，必须修 | 需解释违反点 + 引用对应准则 + 指出导致的失败模式 |
| **可能不完整** | 存疑，证据不足以判定 | 列出还需要什么信息才能定论 |
| **不适用** | 本项不适用于本次设计类型 | 说明为什么（如层敏感准则对纯需求规格不适用） |

**核心纪律**：不凭感觉。每个"不通过"都要能指向具体准则 + 失败模式（对照 `anti-patterns.md` 的 3 病根：认知懒惰/视角错位/结构失序）。

---

## 审查输出格式

```markdown
## Summary
<must-fix 数量> must-fix.

## Findings

| 优先级 | 位置 | 维度 | 描述 | 影响决策 | 影响交付 | 修复方向 |
|--------|------|------|------|---------|---------|----------|
| MUST_FIX | §3.2 | P0-10 对抗 | 方案只解决表象，未触及§2根因 | 是——§3 方案主干方向错（掩盖问题） | 开发——按此实施病因存续，交付后问题复发 | 重新设计要打到根因层 |
| MUST_FIX | §3.2 | P0-11 事实 | 引用的 API 签名与源码不符，方案成立依赖该 API 的行为 | 是——该决策建立在不存在的 API 行为上 | 开发——实施者按错误签名写出错误代码 | read 源核准后修正或改方案 |
```

- 优先级：MUST_FIX（唯一报告级别）/ INFO（他方职责的线索交接，不计数、不进 problems）。本清单不设更低报告级别——凡值得报告的问题按 must-fix 对待；修复方处置时按三态分流（fixed 修复 / deferred 登记不修 / archived 归档，见 `flow/write.md` Step 8.1）
- 每条 finding 带锚点编号（形态随 agent 模板：方向审 = Findings 行首锚点列 review-direction#N；三审 = 报告每条问题的小节标题带锚点 review-<dimension>#N）——problems[].ref 原样引用它
- **「影响决策 / 影响交付」两列必填**（每条 finding 必填，缺列视同无效报告——修复方按"影响决策"定处理级别、按"影响交付"定修复落点，两列细则见 agents/ 各模板）

并附 structured-output JSON：`{ "report_file": "<路径>", "must_fix": <数>, "problems": [ { "ref": "<锚点>", "title": "<一句话标题>" } ] }`——problems 条目无 level 字段（唯一报告级别是 must-fix，无需分级字段；条数须与 must_fix 一致，消费方以清单派生计数为准）。方向审字段名用 camelCase（`reportFile` / `mustFix`，另含 `oneliner`），见 `agents/tech-design-direction-review.md`。
