# 六边形分层分析（hexagonal architecture / clean architecture 作分析视角）

用六边形架构的概念体系**判定任意代码的性质与依赖方向，映射到项目现有结构**。五圈层在这里是**判定坐标系，不是目录模板**——三层架构、端口-适配器、事件驱动、单体 CRUD 项目同样用这套坐标系分析，分析产出记录「这段逻辑是什么性质、现在位于项目哪一层、依赖方向如何」，不产出「应该重组到哪里」的建议（分析不改造纪律见 SKILL.md）。

## 圈层定义（判定坐标系，内 → 外）

| 圈层 | 性质判据 | 典型内容 |
|------|---------|---------|
| 1 领域核心（domain core） | 业务规则所在地 | 实体 / 值对象 / 领域服务 / 领域事件（= 领域建模的产出） |
| 2 应用层（application） | 用例编排：取数据、按序调用、发事件，无规则 | use case / service 编排逻辑 |
| 3 端口（ports） | 内外边界的接口 | repository / 外部服务网关 / 事件发布器等接口 |
| 4 适配器（adapters） | 外部世界的形态 | DB / 第三方 API / 消息队列实现；HTTP / CLI / UI 入口 |
| 5 组装根（composition root） | 装配接线 | 依赖注入与启动 |

**横切关注点**（cross-cutting：日志 / 配置 / 度量 / 鉴权）不是圈——按项目现有的工具层或切面机制定位。

## 性质判定四问（拿到一段功能 / 文件）

1. **含业务规则或不变量吗？**（钱怎么算、状态能否转移、谁能做什么的规则本体）→ 领域核心
2. **只是编排？**（取数据、按序调用、发事件，无规则）→ 应用层
3. **是外部世界的形态？**（协议、存储、第三方 SDK、UI 组件）→ 适配器；被内圈性质的逻辑使用的外部能力，其接缝（接口 / client / driver，无论形态）视为端口性质
4. **是装配接线？**（创建实例、注入依赖、启动）→ 组装根

四问都不沾 → 横切工具或配置。判定结果连同依据记入圈层性质映射表（格式见文末）。

一个文件常混装多种性质（Service 里既有规则又有编排又有 SQL）——如实按「混合」记录并拆列各性质所在行号段，这正是分析的价值输出（供 code-domain-review 核对不变量、供 code-arch-review 审查素材），不是整改清单。

## 依赖方向记录

分析范围内的 import / 调用关系按事实记录（谁依赖谁），不预设方向合法性。涉及外部依赖时附**依赖类别标签**（判断接缝处替换成本、「值不值得放接缝」的输入）：

| 类别 | 含义 | 替换成本 |
|------|------|---------|
| in-process | 进程内依赖（自身代码） | 低：重构即换 |
| local-substitutable | 本地可替换（文件系统、内存实现、本地工具） | 中：实现可换协议稳定 |
| ports & adapters | 需真实适配器（DB、第三方 API、消息队列） | 高：跨边界，值得显式接缝 |
| mock | 只能 mock（无法真实替换的外部） | 高：接缝处测试只能 mock，须标注 |

记录后对照两类观察：

- **普遍性健康风险**（与六边形无关地成立）：业务规则直接依赖 IO / 框架 / 协议细节——影响是规则无法脱离基础设施测试与复用。记入映射表「观察」列，附影响说明
- **形态偏差**（仅相对参考形态而言）：没有显式接口接缝、装配散落多处等——**只记录不评判**；项目自己的架构约定（AGENTS.md / 架构文档）才是评判依据，本项目约定有裁决时从其约定

## 参考形态（仅供理解与零起点项目）

判定结果完整落位时长的样子——**零依赖任何既有结构的新项目可参考此形态起步**；存量项目分析**不输出**「改造成此形态」的建议：

```
src/
  orders/                     # 限界上下文：订单
    domain/                   #   领域核心性质
      order.ts                #   聚合根
      order-line.ts           #   实体
      address.ts              #   值对象
      order-events.ts         #   领域事件
    application/
      place-order.ts          #   编排
    ports/
      order-repository.ts     #   接缝（接口定义）
    adapters/
      sqlite-order-repo.ts    #   外部形态（实现接缝）
  inventory/                  # 另一上下文，同构
  shared/                     # 跨上下文共享（值对象 / 基础类型，最小化）
  composition/                # 装配
```

目录结构与领域模型登记的对应关系：`docs/domain-model.md` 的每个上下文对应一个内聚单元；四性质子目录让判定结果可直接机械落位。存量项目的「上下文 ↔ 包」对应关系按现状记录（一个上下文横跨多个包、一个包混多个上下文都如实记）。

## 观察信号（记录用语，非整改清单）

| 信号 | 性质 | 记录用语 |
|------|------|---------|
| 业务规则 import DB / HTTP / 框架类型 | 普遍健康风险 | 记入观察列 + 影响说明（测试须带基础设施、规则复用受锁） |
| 编排逻辑内嵌 SQL / 直接 new 外部客户端 | 普遍健康风险（同类上一条） | 同上 |
| 界面 / 入口直接调数据访问（跳过编排） | 形态偏差：多数项目约定不允许，按项目约定判 | 项目约定禁止 → 按约定记风险；无约定 → 只记录 |
| 接缝定义由实现方持有 | 形态偏差 | 只记录 |
| 装配散落多处 | 形态偏差 | 只记录 |
| 跨上下文直引对方内部实体 | 普遍健康风险（耦合越界，多数架构思想共判） | 记入观察列；行为面问题通报 code-domain-review（类别 context-boundary） |

## 圈层性质映射表格式

| 功能 / 文件 | 性质判定（四问结果） | 项目现有层 / 目录 | 依赖方向 | 观察 |
|------------|---------------------|------------------|---------|------|
| 订单金额计算（order-service.ts:88-120） | 领域核心 | Service 层 | import 数据库客户端 | 业务规则依赖 IO：无法脱库测试（影响说明） |
| 订单持久化（order-repo.ts） | 适配器 | Repository 层 | 被 Service 依赖 | — |
| 下单流程编排（order-service.ts:12-60） | 应用层（混合，见上） | Service 层 | — | — |

- **性质判定**：五性质之一 / 横切 / 混合（混合须拆行号段）
- **项目现有层 / 目录**：按项目自己的分层与命名记录（不映射成六边形术语）
- **依赖方向**：事实记录（依赖了什么；外部依赖附类别标签）；无特殊观察时记「—」
- **观察**：仅两类——普遍性健康风险（附影响说明）或按项目约定判定的风险；纯形态偏差不入此列
