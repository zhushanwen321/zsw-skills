# 六边形分层判定（hexagonal architecture / clean architecture）

判定每个功能 / 文件归属哪个圈层、端口放哪、包目录怎么组织。核心只有一条硬规则：**源码依赖指向内**（外圈 import 内圈，内圈不 import 外圈）——其余判定都从它推导。

## 圈层定义（内 → 外）

| 圈层 | 职责 | 内容 | 禁止 |
|------|------|------|------|
| 1 领域核心（domain core） | 业务规则所在地 | 实体 / 值对象 / 领域服务 / 领域事件（= 领域建模的产出） | import 任何外圈；含 IO / 协议 / 框架细节 |
| 2 应用层（application） | 用例编排 | use case：取聚合 → 调领域逻辑 → 经端口持久化 / 发事件 | 业务规则；直接触碰适配器实现 |
| 3 端口（ports） | 内外边界的接口 | repository / 外部服务网关 / 事件发布器等接口，**定义权在内圈** | 任何实现细节 |
| 4 适配器（adapters） | 外部世界的形态 | 被驱动适配器（driven：DB / 第三方 API / 消息队列，实现端口）；主适配器（driving：HTTP / CLI / UI，调用应用层） | 业务规则 |
| 5 组装根（composition root） | 装配 | 依赖注入与启动接线，**唯一知道所有具体实现的地方** | 业务逻辑 |

端口 = 依赖倒置的接缝：内圈声明「我需要什么」（接口），外圈提供「怎么给」（实现）。端口跟着需求方走：领域核心需要的能力，端口定义在领域侧；应用层需要的能力，端口定义在应用侧。

**横切关注点**（cross-cutting：日志 / 配置 / 度量 / 鉴权）不是圈——按基础设施工具层或切面处理，不进领域核心；领域核心确需日志时注入 logger 接口（它也是一种端口）。

## 归属判定四问（拿到一个功能 / 文件）

1. **含业务规则或不变量吗？**（钱怎么算、状态能否转移、谁能做什么的规则本体）→ 领域核心
2. **只是编排？**（取数据、按序调用、发事件，无规则）→ 应用层
3. **是外部世界的形态？**（协议、存储、第三方 SDK、UI 组件）→ 适配器；该外部能力需要被内圈使用时，**先在内圈定义端口**，适配器实现它
4. **是装配接线？**（创建实例、注入依赖、启动）→ 组装根

四问都不沾 → 横切工具或配置。判定结果连同依据记入圈层归属表（格式见文末）。

## 包目录组织

推荐**按上下文分包、上下文内再分圈层**（package by context）——聚合内聚优先于技术分层内聚；纯技术分层（全仓一层 domain/ 一层 infra/）会把一个聚合撕到多个目录。

```
src/
  orders/                     # 限界上下文：订单
    domain/                   #   领域核心
      order.ts                #   聚合根
      order-line.ts           #   实体
      address.ts              #   值对象
      order-events.ts         #   领域事件
    application/
      place-order.ts          #   用例
    ports/
      order-repository.ts     #   端口（接口定义）
    adapters/
      sqlite-order-repo.ts    #   被驱动适配器（实现端口）
  inventory/                  # 另一上下文，同构
  shared/                     # 跨上下文共享内核（值对象 / 基础类型，最小化）
  composition/                # 组装根（装配与启动）
```

目录结构与领域模型登记一一对应：`docs/domain-model.md` 的每个上下文对应一个顶层包；上下文内目录名固定 `domain / application / ports / adapters`，让归属判定结果可直接机械落位。

## 常见违规形态（存量核对清单）

| 违规 | 信号 |
|------|------|
| 领域核心含 IO | 实体 / 领域服务 import DB、HTTP、文件系统或框架类型 |
| 应用层绕过端口 | 用例里写 SQL / 直接 new 外部客户端 |
| UI 直调仓库 | 界面层 import repository / 数据层（跳过应用层） |
| 端口定义权外移 | 接口定义文件放在适配器目录旁、由实现方持有 |
| 组装散落 | 多处 new 具体实现、依赖图无单点装配处 |
| 跨上下文直引 | orders 包 import inventory 包的内部实体（应经端口或共享内核） |

存量分析时逐项核对，命中项进圈层归属表「违规预警」列（如实登记，不默认现状合法）。

## 圈层归属表格式

| 功能 / 文件 | 圈层 | 包目录 | 端口归属 | 违规预警 |
|------------|------|--------|---------|---------|
| 订单金额计算 | 领域核心 | orders/domain/order.ts | — | 现实现位于 services/order-service.ts（贫血模型信号） |
| 订单持久化 | 适配器 | orders/adapters/sqlite-order-repo.ts | orders/ports/order-repository.ts（应用层定义） | — |

- **圈层**：五圈之一或「横切」
- **端口归属**：该功能涉及 / 新增的端口及其定义方（哪一圈声明）
- **违规预警**：现实现与本表的偏差 + 偏差类型（对照违规形态清单）
