# 领域建模协议（DDD）

从需求叙述与现有代码中提炼领域模型：统一语言 → 概念分类 → 聚合划分 → 上下文划分 → 落登记。

## 概念与判别式

| 概念 | 英文锚定 | 判别式 | 例 |
|------|---------|--------|----|
| 实体 | entity | 有身份标识；属性变了仍是同一个 | 用户、订单（改名后还是该用户） |
| 值对象 | value object | 无身份、靠全部属性判等；不可变 | 收货地址、金额、时间区间 |
| 聚合 | aggregate | 一致性边界：必须一起满足不变量的最小对象组 | 订单 + 订单行 |
| 聚合根 | aggregate root | 聚合的唯一外部入口；外部改聚合内成员必须经过它 | 订单 |
| 领域服务 | domain service | 不归属单一实体的领域操作 | 汇率换算、跨聚合规则裁决 |
| 领域事件 | domain event | 领域中已发生的事实，过去式命名 | 订单已支付 |
| 限界上下文 | bounded context | 模型与语言保持一致的边界；同一词跨边界含义漂移即分界信号 | 订单上下文 / 库存上下文 |
| 统一语言 | ubiquitous language | 业务与技术共用的词表，单一上下文内无歧义 | CONTEXT.md 词条 |

### 实体 vs 值对象判别

问「改了属性之后，它还是不是同一个东西」：收货地址整条替换后订单无感（值对象）；用户改名后仍是该用户（实体）。拿不准时**先按值对象建模**——实体是身份的代价（要管生命周期、要可追踪），需要时再升级。

### 聚合根判定三问

1. 外部要修改聚合内成员，是否**必须**经过它？（绕过它就能改 = 边界画错了）
2. 删除它之后，成员是否还有独立业务意义？（有 = 成员可能自成聚合）
3. 不变量跨越哪几个对象？（跨对象不变量所在的最小对象组 = 聚合范围）

### 上下文切分信号

- **语言漂移**：同一词在不同流程段含义不同（「商品」在目录 / 购物车 / 库存三处指不同模型）
- **变化原因聚类**：一批概念的变更原因与其他部分不同（各自独立演化 → 各自上下文）
- **团队 / 流程边界**：不同团队或业务流程段各自维护各自的语言

上下文间关系在登记中写明：谁调谁、经什么端口；外部模型渗入风险高时加防腐层（anti-corruption layer，上下文间的一层翻译隔离，把外部模型转换为本上下文自己的概念）。

## 建模步骤

1. **采集叙述**：需求文档 / 用户故事 / issue 原话 / 现有代码命名——业务原话优先，不擅自润色改义
2. **提取名词建词表**：候选概念全部列出，同义词合并（一词多义与多词一义都要收敛），形成统一语言草表——**词条名用项目现有命名**（代码里叫 `orderService` 就登记 orderService / 订单服务），不造新名贴合 DDD 术语
3. **逐个分类**：过「实体 vs 值对象判别」与领域服务 / 领域事件定义；分类存疑的概念标「待裁决」进登记，不硬塞
4. **聚合化**：按「聚合根判定三问」聚类，定根，**逐聚合写不变量清单**（每条可核对，外部审查与实现测试直接消费）
5. **划上下文**：按「上下文切分信号」划分，写上下文间关系
6. **落登记**：统一语言 → `CONTEXT.md`；结构 → `docs/domain-model.md`（格式见下）

## 领域模型登记格式（docs/domain-model.md）

```markdown
# 领域模型登记

## 上下文：<名称>

### 边界
- 负责：<一句话业务能力>
- 不负责：<显式排除项>
- 相邻关系：<调谁 / 被谁调，经什么端口；有无防腐层>

### 聚合：<聚合根名>
- 根：<聚合根>
- 成员：<实体 / 值对象清单>
- 不变量：
  - <规则语句，外部可核对，如「订单支付后金额不可再改」>
  - <如「订单行数量必须 > 0；整单金额 = 各行金额之和」>
- 唯一入口：<外部只能经 <根> 的哪些操作触达聚合内部>

### 领域事件
- <事件名（过去式）>：<何时发生，谁消费>
```

统一语言词条格式（CONTEXT.md）：`**术语**：1-2 句定义（定义它 IS 什么）+ _Avoid_: 别名列表`。只收项目特有概念，通用编程概念不收；CONTEXT.md 是纯词表，不写实现细节。

## 反模式

反模式是**识别与理解现状的观察视角，不是自动整改清单**——命中时如实记录观察与影响，是否改、怎么改由用户裁决（本技能分析不改造，见 SKILL.md 定位纪律）。

| 反模式 | 信号 | 影响 |
|--------|------|------|
| 贫血模型（anemic model，实体只剩数据字段） | 业务规则散在应用层 / 服务函数里，实体只有字段 | 不变量无人守护、规则与数据分离难以追踪（记录为观察，不要求重构成充血模型） |
| 巨型聚合 | 一个根带全部成员 | 并发冲突面巨大，不变量形同虚设 |
| 跨聚合直改 | 外部直接改聚合内实体（绕过根） | 不变量旁路，一致性破坏 |
| 上下文过碎 | CRUD 级简单域硬拆多上下文 | 概念税大于收益（对齐 code-overdesign-audit 投机抽象判据） |
| 投机建模 | 为想象中的未来需求建概念 | 无现实击中证据的抽象，登记时不予通过 |

## 纪律

- 聚合越小越好：只包住不变量必需的成员；跨聚合只引用对方聚合根的 id，不直持对象
- 一次事务一个聚合：跨聚合一致性走领域事件 + 最终一致，不靠大事务
- 术语先登记后使用：分析产物里出现的每个领域概念都必须已在统一语言登记（SKILL.md 关键纪律）；登记用项目现有命名
- **模型登记描述业务事实，不规定代码组织**：聚合清单与不变量是行为核对基准（供 code-domain-review 消费），现有代码用 Service / 函数 / 类的什么形态承载不变量，按项目现状记录，不要求改成聚合形态
