# Architecture Clean Domain Design（领域建模 + 架构分析）

设计期技能，一个入口两步分析，回答「业务上有什么、边界在哪」与「代码上这些逻辑各是什么性质、放在项目现有结构的哪一层」：

1. **领域建模**（DDD，domain-driven design 领域驱动设计）：统一业务语言、划限界上下文、识别实体 / 聚合根 / 值对象、登记聚合不变量
2. **架构分析**（六边形架构 / clean architecture 作分析视角）：判定每段功能 / 文件的圈层性质（业务规则 / 编排 / 外部形态 / 装配）、记录依赖方向、映射到项目现有结构

**定位纪律（最高优先）**：DDD 与六边形在本技能中是**建模思想与分析视角，不是目标形态模板**——用来理解、描述、评估任意形态的项目（三层架构、端口-适配器、事件驱动、单体 CRUD 均适用），分析产出映射到**项目现有结构**（现有分层、现有目录、现有命名）。本技能不输出把项目改造成 DDD / 六边形形态的设计（那类整体改造是 tech-design 流程的设计任务）；分析中发现的健康风险只如实记录为观察，是否改、怎么改由用户裁决。

两步的关系：领域建模产出 = 圈层性质判定中「领域核心」的内容清单（业务规则、不变量）；架构分析负责其余性质的判定与整体依赖方向记录。典型顺序：先域后层；存量分析时可两步并行输出对照表。

## 关键纪律

- [MANDATORY] **分析不改造**：不建议重命名现有模块 / 目录以贴合 DDD 或六边形术语；不建议新建 domain / application / ports / adapters 式目录结构；不把「现状与标准形态不符」表述为问题或错误（表述为「性质映射 + 观察」）；新代码落位建议遵循项目现有结构约定（六边形性质判定只用于回答「这段逻辑是什么性质」，落位按现状惯例）。项目确需整体改造时走 tech-design 流程，本技能只提供现状分析输入
- [MANDATORY] 概念必须先在统一语言登记再使用：分析过程中引入的每个领域概念（实体 / 值对象 / 聚合根名）都进 CONTEXT.md 词条，未登记概念不得出现在分析产物里；登记用项目现有命名
- [MANDATORY] 聚合不变量必须可核对：每条写成「外部可对照 diff / 测试验证的规则语句」（如「订单支付后金额不可再改」），不写「保持一致性」类不可检验表述。不变量是**行为核对基准**（供 code-domain-review 消费），不要求代码组织成聚合形态——现有 Service / 函数形态照样承载不变量
- [MANDATORY] 依赖方向如实记录：分析范围内的 import 关系按事实记录（谁依赖谁）；「业务规则直接依赖 IO / 框架」这类普遍性健康风险记入观察列（附影响说明），其余形态偏差只记录不评判
- 简单域不硬套：CRUD 级领域按「实体 + 数据访问」最小形态处理，不为方法论完整度强拆聚合与上下文（对齐 code-overdesign-audit 的投机抽象判据）
