# T1 写设计文档流程

> 引导主 agent 按 tech-design 方法论写出设计文档（Step 0 → Step D 诊断期 → Step 1-7，Step 7 = 业务用例走查），审查循环协议见 Step 8（T2 执行细节见 `flow/review.md`），T3 实施计划见 `flow/plan.md`。结构标准见 `references/doc-structure.md`，章节 JSON 字段的权威规格见 `references/design-doc-schema.md`，写作原则见 `references/design-principles.md`，思维原则（P1-P7）与产物表规格见 `references/principles.md`——本文件只给流程步骤与落点约定，原则本体不重复。

> **产物路径约定 [MANDATORY]**：设计文档的权威源 = 设计目录 `~/.agents/skill-data/tech-design/<slug>/<name>/`——目录内六个章节 JSON（`meta.json` / `s1-context.json` / `s2-status.json` / `s3-solution.json` / `s4-accept.json` / `s5-breakdown.json`），长文本（背景 / 现状 / 终态形态 / 文件地图等）为字段值，字段规格见 `references/design-doc-schema.md`；渲染产物 `<name>.rendered.md`（`node <tech-design-v4 技能根>/scripts/render-design-doc.mjs <设计目录>` 生成）是阅读视图，**非权威、禁止手改——每次章节 JSON 修改后重跑渲染脚本**。`<slug>` = 单仓形态的 project-slug 或工作区形态的 ws-slug，由寻址检测探针按 projectRoot 自动派生、不手拼；双形态判定与路径约定见 `skill-data-addressing.md`（`<zsw-skills 检出根>/skills/self/dev-workflow/references/skill-data-addressing.md`）。设计文档是 tech-design-v4 → dev-flow-v4 的**过程产物，不进项目 docs/**——落 HOME 下 `~/.agents/skill-data/`，天然不入 git。审查报告、探针等伴生产物同落设计目录（T2 报告在 `round-N/` 子目录，见 review.md）。新设计的起步模板见 `resources/templates/design-doc/`（六章节 JSON 最小样例）。

> **meta.json skillVersion 写入 [MANDATORY]**：T1 创建 `meta.json` 时写入 `skillVersion` 字段，值 = 本技能 SKILL.md frontmatter 的 `version`（技能版本唯一权威，读文件取真实值，不凭记忆写）——产物溯源字段，回答「本设计包由哪个技能版本产出」；只读溯源，不参与任何执行裁决。字段规格见 `references/design-doc-schema.md` §3（可选字段，semver 形态；机器检查有则查形态、无则放行——存量设计目录零影响）。

> **ADR 登记 [MANDATORY]**：项目存在 ADR 登记处（如 `docs/adr/decisions.md`，路径以项目 AGENTS.md 索引为准）时，设计中拍板的重要决策须登记或更新——设计文档可弃，决策必须活在其权威登记处。登记的新写文本同样过词表自查（ADR 是面向项目长期读者的产出物，判据同「没有背景知识的读者第一遍能否准确理解」）。

> **用语规范 [MANDATORY]**：动笔写设计文档**前**必须加载 meta-words-guidance skill 并读其词表——zcode 用 Skill 工具加载；pi / 无 Skill 工具环境直接 Read `~/.agents/skills/meta-words-guidance/SKILL.md`（词表与判据在其中）。写出的文档必须遵守其用语规范：
>
> - 四张词表逐条适用（已裁决替换表照替换 / 带条件保留表按条件用 / 白名单可用 / 观察名单同样避免），全文自查
> - 自造词、领域词先解释再使用；抽象概括配具体例子；命名用自然句不用四字压缩
> - 引用存量文档（ADR / 既有设计文档 / 代码注释）原文时，引文里的压缩词与未定义领域词同样按词表处理：改写为平实表达，需保留可追溯的括注原词——禁止裸引未消化的原文进新文档（引文是产出物的一部分，词表扫描对引文块同样适用；存量文档本体不因被引用而修改，其清扫是独立任务）
> - 判据 = 没有背景知识的读者第一遍能否准确理解
> - 文档完稿后按该 skill 的扫描指引跑词表自查（word-scan），命中逐项修后再进 T1 确认

## Step 0：问题定义先行（设计前必做，禁止跳过）

**交付体系入口门（先于本步一切内容）**：本设计属于三技能交付体系时（用户目标 = 设计并实现 / 修复 /
开发），必须已有已批准的验收包——`node ~/.agents/skills/delivery-v4/scripts/delivery-gate.mjs
evaluate --task-dir <taskDir>` 的 state 为 `design`（已批准、待方案）。该判据仅对应 verdict-rules
`requireDesignApproved` 默认 true 的任务——`requireDesignApproved=false` 的任务 state 不落 design
（delivery-gate 状态路由跳过 design 分支，直接落到 acceptance-approved）：该策略下设计阶段非裁决
前置，不得按「未批准」误判回 delivery-v4，仍需推敲方案时按用户明确要求进入（照常走三阶段并
record-design-approved）。通过后把 `acceptanceBinding`
（taskDir + acceptanceVersion + acceptancePackageSha256）写进 `meta.json`；验收版本此后变化
（delivery-v4 递增 acceptanceVersion 重批）时，本设计包须重新过影响审查——对照新版本
acceptance.json 与 increments.json 逐条比对设计包是否仍覆盖（判据缩窄 / 新增需求逐条核对
设计章节与 impl-plan 归属），需要改动的回 T1 修订并按所处阶段重走 T2/T3，重批后更新
meta.json acceptanceBinding 再进下游。无任务目录或未批准 → 停止，回 delivery-v4 走验收设计；用户明确不走
交付体系的独立设计（用 tech-design-v1 通道）不经本门。**判据与验收设计的关系**：验收包定义
「什么算对」，本技能的 §4 验收章节与验收判据对齐并细化可执行的验证场景——发现判据遗漏或缩窄，
回 delivery-v4 递增版本，不在设计文档内改判据。

动笔前先过**前置探明门**，再过**产品最小形态三问**，最后回答三个问题：

**前置探明门**：问题是否已探明——症状、触发条件、复现路径三者清楚？未探明 → **先做调研再回来**：复现实验、日志采集、探针观察都是前置步骤，产物落 `.tmp/` 留档，不进设计文档。把「加日志看看再定方案」写成设计内容 = 问题未探明的设计，不合格。例外：探针体系本身复杂到需要设计（多探针编排/结果归因），独立成章并论证复杂度。

**产品最小形态三问**（问题探明后、动笔 §3 前必答，答案写进文档）：

1. **核心价值**：这个功能最核心的价值是什么（一句话，以项目产品定义文档为锚）？达成该价值的**最少技术投入**是什么形态？——这个形态就是 §3 方案的主干
2. **增量收益**：最小形态之上，哪些**较少投入换明显收益**的项？逐项独立裁决（投入/收益/不做会怎样），未裁决的不得混入主干
3. **扩展支持**：只保留有**已发生证据**支持的扩展点（已有第二个使用方/已发生的变化原因）；为想象未来预留的抽象砍掉

判别法：**从产品核心价值出发描述这个功能，再对照现状实现——现状复杂度里天然不包含的部分，每项论证「为什么保留」，砍掉是默认候选**。从最小形态倒推设计，不从现状实现倒推。

三个问题：

1. **用户描述的问题是什么？** 用自己的话复述，确认理解无误
2. **这是不是真正的问题？** 用户描述的现象可能只是症状（例：用户说"命令太慢"，真问题可能是"每次都全量重算"）
3. **背后有没有隐藏的、用户未明确表达的根本性问题？** 常见信号：用户直接给了方案而不是问题；触发场景描述得太窄；跳过因果链中间层直接说结论

发现"可能有隐藏问题"时的做法：**先提问澄清，不猜**——提问聚焦"根本问题是什么"，不聚焦方案细节；grill 机制（grilling 盘问式 / research 查证式，可多轮追问）；**不带未答问题往下写**；被用户第二次追问「为什么 X」时，主动列出「本设计默认为真的前提清单」请用户裁决。

写方案前最后自问：**这个方案解决的是根本问题，还是只让表面症状消失？** 掩盖问题的典型形态：加 try-catch 掩盖报错、自动重试/自愈、定时轮询对账补偿、降级/缓存遮蔽。判别法：删掉方案里的补偿机制，病因还在不在？还在 = 不合格。

**分型信号登记**：用户消息出现以下显式信号时逐条登记（原文摘录，随工作记录保留）——要求终态 / 长期合理 / 不计成本 / 「反复出问题、修过多次」。这些是设计分型（演进型 / 终态型，定义见 Step D）「用户显式」一条的输入；本步只登记不判定，分型判定在 Step D。

## Step D：诊断期（Step 0 之后、动笔之前）

本步回答两个问题：**现状理解是否正确、设计方向是否成立**。与 Step 0 前置探明门职责不同——探明门管「问题是否可复现」（探针 / 复现类调研按 Step 0 走，本步不吸收），本步管原则触发与证据采集。四个子步依序：D.1 设计分型判定 → D.2 原则触发扫描 → D.3 执行触发原则的执行步骤 → D.4 产物表落盘。

投入按设计规模分档：纯文案 / 参数调整类只触发 P5（推断核实，七条中唯一全量强制的地基原则），本步近乎零成本；架构类设计全触发（考古 + 枚举 + 审讯）。

### D.1 设计分型判定（本步第一件事）

分型二选一：**演进型**（默认：现状问题 → 方案对比 → 推荐）或**终态型**（公理 → 终态形态 → 差距 → 迁移）。判终态型的依据三条，任一成立即触发：

1. **修复史判定表定性「未修到」**：先做 P4 触发扫描（触发条件见 `references/principles.md` P4）——问题域有 ≥3 次修复记录或用户表述「反复出现 / 修过多次」→ 执行 P4 考古（对该问题域 git log 与 PR 的全样本回溯取证；merge 双亲 diff = 该 merge 两个父提交之间的真实差异，取证一律用它、不信 PR 描述），产出修复史判定表；其定性列输出「未修到」（历次修复都没触及根因）→ 判终态型
2. **用户显式信号**：Step 0 登记的信号（要求终态 / 长期合理 / 不计成本 / 反复出问题）任一存在 → 判终态型
3. **设计对象为架构级**：跨模块 / 状态权威变更 / 协议变更 / 新子系统 → 判终态型

判定结论与理由（命中哪条依据 + 一句话判定过程）写入 `meta.json` 的 designType / typeRationale 字段，与功能分级（priority）、风险分（riskScore / riskRationale）并列——渲染视图头部表同源呈现。判演进型时同步写一句辩护：为什么窄修够用、不需要终态视角（修复史判定支撑）——T2 方向审按「分型是否正确」攻击此判定。两型的 Step 3 骨架差异见 Step 3 变体。

### D.2 原则触发扫描

逐条对照 `references/principles.md` 七条原则（P1 终态优先 / P2 权威唯一 / P3 蕴涵审讯 / P4 历史模式 / P5 推断核实 / P6 防护网 / P7 上游约束）各自的「触发条件」，判定本次设计适用哪些——P1 的触发 = 分型为终态型（D.1 已判，直接沿用）；P4 若已在 D.1 扫过，沿用其结论。产出触发清单落 `<runDir>/principles-triggered.md`：每行 = 原则编号 + 触发依据一句话。触发了的原则必须执行其执行步骤并产出对应产物表；未触发的不执行、不产出、不补空表。

### D.3 执行触发原则的执行步骤

按触发清单执行各原则的执行步骤（步骤本体见 `references/principles.md`，本步只约定执行方式）：

- **采集类动作可派 subagent 分批**：P4 考古（按时间分批、双亲 diff 取证）、P2 状态副本清单（按包 / 进程分批）、P3 蕴涵审讯（按信号清单分批）——批间无依赖时并行派发
- **关键结论主 agent 抽查核实后才采信**（P5 执行步骤③）：subagent、记忆、外部会话给出的结论，进设计文档前主 agent 亲自核实一次；抽查不通过的整批退回重做
- **探针 / 复现类调研不走本步**：那是 Step 0 前置探明门的职责

### D.4 产物表落盘

Step D 生成的产物表写入 `s2-status.json` 对应字段：修复史判定表 → `artifactTables.repairHistory`、状态副本清单 → `artifactTables.stateCopies`、信号-蕴涵表 → `artifactTables.signalImplications`、上游依赖清单 → `artifactTables.upstreamDeps`、前提清单（增强版）→ `assumptions`——字段规格见 `references/design-doc-schema.md` §5（落点总表与列级语义见 `references/principles.md` 末尾「产物表落点表」）。公理清单 + 终态-现状差距表（P1）与断言-红灯映射表（P6）在写作期生成（分别见 Step 3 / Step 4）。前提清单（增强版）写作期持续更新，其余 Step D 产物表随 §2 写作定稿；章节 JSON 定稿后重跑渲染脚本。

## 前置：判断层性质

动手前先定五件事：

0. **产品边界核对**：项目存在产品愿景文档（如 `docs/PRODUCT.md`）→ read 并核对不偏离产品定位；冲突时停下向用户澄清
1. **本次设计的"当前层 → 下一层"是什么？** 文档开头显式声明（不跨 2 层）
2. **下一层产物性质？** 套 `doc-structure.md` 层敏感调节表确定 §3 侧重点
3. **是否涉及运行时行为 / 数据流 / 错误处理？** 是 → 准则 5/6/7 全部 P0 适用
4. **领域术语与视觉层核对（条件触发）**：新术语 → 项目术语表对齐；涉及 UI → 项目视觉设计权威对齐，路径以项目 AGENTS.md 索引为准
5. **本次设计触及的功能分级（P 级）与风险分是多少？** [MANDATORY] 落 `meta.json`（priority / riskScore / riskRationale——渲染视图头部表呈现）：项目存在功能分级登记（如 `docs/FEATURE-PRIORITIES.md`）→ 查表取涉及模块/用例的**最高 P 级**；不存在 → 按「挂掉后果」判据现场评估（P0=项目对用户毫无价值 / P1=大体能用但体验非常差 / P2=基本可用稍可忍受 / P3=影响很少或特定人群）。**风险分（1-10）= P 级基数（P0=9 / P1=7 / P2=4 / P3=2）+ 可逆性修正（数据迁移/协议变更/不可逆操作 +1）+ 新颖度修正（仓内无先例机制 +1）**，clamp 1-10——3.2 对比表「风险」栏与一句话主要风险来源参考它，分数一次产生下游不重打（一致性审查按分级核对错误处理策略——P0/P1 fail-fast、P2/P3 接入点降级边界）

## Step 1：背景目标

SCQA 开篇 + 系统是什么 + 设计目标（从使用者体验倒推）+ in/out scope。受众假设：会用系统但不懂内部背景的开发者。本章产出写 `s1-context.json`：background（SCQA 开篇 + 系统是什么，长文本字段值）/ goals（目标数组，使用者视角陈述）/ outOfScope——字段填写要求见 `references/design-doc-schema.md` §4。

## Step 2：现状与问题分析（禁止跳过）

使用者视角现状（真实例子，**取自代码不编造**）+ **端到端大流程图**（§2 开头，全文坐标系）+ 真实失败模式 + 根因分析 + **前提清单节**（「本设计默认为真」的假设逐条列，增强版规格见下方产物表落字段段）。问题点条目以「**环节**：<大流程> → <环节名>」开头锚定。禁止上来讲"哪个文件哪个函数怎么改"。本章产出写 `s2-status.json`：currentBehaviour / flowDiagram（长文本字段值）/ problems（stage 字段做环节锚定）/ assumptions / artifactTables——字段规格见 `references/design-doc-schema.md` §5。

**Step D 产物表落字段 [MANDATORY]**：Step D 触发生成的产物表写入本章对应字段——修复史判定表 → `artifactTables.repairHistory`、状态副本清单 → `artifactTables.stateCopies`、信号-蕴涵表 → `artifactTables.signalImplications`（列级规格见 `references/principles.md`、字段定义见 `references/design-doc-schema.md`；触发了才有行，未触发的表为空数组、不补空表行）。前提清单用 **assumptions 字段**（**前提清单（增强版）**形态，P5 产物）：每条前提标注分类（事实 / 推断 / 知识 / 决策）与状态——✅ **必须附核实动作**（读了什么文件的什么位置、跑了什么探针；留空 = 未核实，未核实的推断不得作为设计依据）；⏳ 待裁决附「若不成立的影响」；**否定性断言**（「无 X」「没有任何 Y」形态）另附排除记录：先枚举「谁可能在写、谁可能持有」（跨包跨进程、含写者侧），再逐个排除留档——只查读侧不算核实；排除记录落 `assumptionExclusions` 字段（字段规格见 `references/design-doc-schema.md`）。**穷举断言可复算（字段声明制）**：断言属穷举（「唯一 / 全集 / 限于」式前提、排除已覆盖全部候选）时，该行声明 `exhaustive: true` 并在 `searchCmd` 字段登记取得该断言的检索命令（含路径范围）与命中清单——穷举而缺 searchCmd 的行被 check-design-doc.mjs 判 warning（规则 8，不阻塞），方向审按 must-fix 处置；R2+ 方向审重跑 searchCmd 登记的命令对账新增命中。

**领域与架构现状加载 [MANDATORY]**：本 Step 动笔前加载 architecture-clean-domain-design（zcode 用 Skill 工具；pi / 无 Skill 工具环境直接 Read `~/.agents/skills/architecture-clean-domain-design/SKILL.md` 及其 references）——该技能以 DDD 与六边形为**分析视角**（不改项目结构）：按其领域建模协议梳理现状的领域模型（统一语言、上下文边界、聚合不变量），按六边形性质判定产出圈层性质映射（现状逻辑的性质与依赖方向，映射到项目现有分层）；梳理结果作为 §2 现状素材与 §3 方案的领域/分层依据，**不得据此输出改名、目录重组等结构改造建议**（确需整体改造属 §3 方案设计，须用户裁决）。项目已有 `docs/domain-model.md` 与 `CONTEXT.md` 登记时先消费再增补（登记优先于现场重建）；本次改动不触及领域模型与模块归属时（纯流程/配置类改动）可跳过并在 Step 6 自检记一句跳过理由。

## Step 3：解决方案

分型（Step D 判定）决定本步骨架：**演进型**走方案形态定型序（默认），**终态型**走终态变体。两型都以 3.4 人工审核导航收尾。本章产出写 `s3-solution.json`：演进型 = options + decisions（不得有 terminalForm / migrationWaves）；终态型 = terminalForm + options + decisions + migrationWaves——字段规格见 `references/design-doc-schema.md` §6。

### 演进型（默认）

**方案形态定型（动笔前过设计决策序）**：第 0 步最小形态终态先行 → ①定级（独立/偶发 vs 同类/架构级）→ ②路线（直接解决 vs 架构优化，显式进 3.2 对比）→ ③直接解决（方案落病因环节；掩盖类不作主体）→ ④非功能后置（必要性三问 + 三档裁决，档位连验收）。

- 3.1 终态：最小形态终态先行，增量项随后各带独立裁决；完整交互对话样例（成功 + 失败路径带恢复指引）；终态在实现机制之前讲
- 3.2 多方案对比（强制）：≥2 候选，各评「长期架构合理性 / 短期实现成本 / 风险」，给明确推荐；不采用方案用完整自然句说明理由
- 3.3 关键决策与权衡：每条决策以「环节」锚定（stage 字段）+ 选择 + 不采用 + 证据；运行时断言附探针。**每条决策按 `references/review-guide-rubric.md` 定审核级别（A/B 两级；C 级 = 局部实现细节，不进 decisions 数组——落在相应长文本字段）**：level 字段标级别（渲染视图条目带（A 级）/（B 级）标记），条目 impact 字段填六维评估（只填非「无」维度，A 级命中判据编号落 meta.json reviewNav 行的 criteria 字段）
  - 决策对象 = 用户可见行为 × 系统状态的有限组合（按钮形态 / 消息呈现 / 恢复行为）、且现状行为分散无单一文档可引时，先按 `references/enumeration-matrix.md` 生产穷举矩阵（涉及视觉元素时配 HTML demo）呈用户逐格裁决——纯文字方案描述无法支撑此类裁决；矩阵事实作为 3.2 对比与推荐的证据

### 终态型变体（Step D 判终态型时走此变体）

- 3.1 终态形态：**公理清单**（P1 产物，列级规格见 `references/principles.md`）先行立骨——每条 = 不变量陈述 + 推导依据，不写实现细节；随后写终态形态（结构 / 不变量 / 职责归属，从「假设历史包袱为零的理想形态」倒推，不从现状缝补；推导与校准执行步骤见 P1）；附**终态-现状差距表**（每条差距标注由哪一步消除）
- 3.2 迁移路径对比（强制）：候选至少覆盖「一次到位」与「分波次」（迁移拆成多期，每期独立交付且至少消除一条差距）两型，逐路径评三件事：每步消除哪条差距、中间态边界（该期完成后系统处于什么形态、下期开工的前置条件）、有无制造新差距。**成本只呈现，不作推荐依据**——推荐按差距消除的完备性与不制造新差距判定；成本信息如实列出供用户知悉（「不计成本」裁决的落地）
- 3.3 差距-波次映射决策：终态-现状差距表逐条映射到波次——每条差距必须有归属波次，每波次至少消除一条差距；决策条目形态与定级机制同演进型 3.3（「环节」锚定 + A/B 定级 + 五件套）。波次标注目标 dev 版本的跨版本语义见 Step 5

**守护登记（两型共用，条件触发）**：决策含守护 / 命令 / 正则类可执行内容（同一内容会被多个章节引用的）→ 在该决策的 `guards` 字段单一登记（id / text / note，字段规格见 `references/design-doc-schema.md` §6.3），消费处的文本字段内联完整标记 `{{Gx}}` 引用——渲染自动展开为登记全文，人读层不损失就近可读；修复守护只改登记一处、重渲染即全档生效（机器通道，对应 `references/design-principles.md` 的单一登记准则——该文件准则 14，与 SKILL.md 核心红线清单第 14 条「单波次交付」同号不同义，按文件名+准则名定位）。`{{Gx}}` 的 Gx 是占位符——写作时替换为登记的真实守护 id，照抄字面量会被保留语法校验拦下（凡 {{...}} 一律按引用校验，指向的 id 不存在即 exit 1）。

### 3.4 人工审核导航回写 [MANDATORY]（两型共用）

3.3 定级完成后回写 `meta.json` 的 reviewNav 数组——每条 A/B 级决策一行（decisionId / anchor / level / title / criteria / impact，行内字段规格见 `references/design-doc-schema.md` §3；定级判据见 `references/review-guide-rubric.md`）；reviewNav 的 decisionId 集合必须与 s3 decisions 的 id 集合**完全一致**（A/B 级决策不得缺导航行——机器校验对账）；渲染视图把导航表渲染在正文之前（含 A/B 级标记），确认点呈现时另声明「导航表外内容为局部实现细节，可不审」（见 Step 7.4）

## Step 4：验收（禁止跳过）

真实场景验证（非单测非 mock）；三要素（场景/步骤/通过标准）；每场景回溯 §1 目标；具体业务例子不用抽象断言；按改动大小匹配投入。本章产出写 `s4-accept.json`：scenarios（每条 goalRefs 回溯 s1 目标）/ assertionRedlights / e2eImpact / criterionMechanisms / verificationBindings——字段规格见 `references/design-doc-schema.md` §7。V4 交付任务逐条读取验收包 assertions 与 adversarialForms：每条断言与 s3 机制对账，检查是否存在满足机制却违反断言的反例；每个反例场景绑定实际测试，写明入口、初始状态、操作、时序和断言位置。机器校验由 `check-quality-contract.mjs` 执行，语义等价由 T2 主审与业务用例走查判定。

**断言-红灯映射表（条件触发，P6 产物）**：设计含运行时行为断言（触发判定见 `references/principles.md` P6）时，本章 assertionRedlights 数组逐行登记：设计依赖的每条运行时假设 × 假设被破坏时哪个机器检查变红（测试名 / CI 步骤 / 探针，写具体名字）× 无对应检查时的补建项（挂进 T3 验收计划）。没有变红通道的运行时假设 = 未来的一次线上事故——变红通道填「无」的行必须登记补建项。

**e2e 影响面评估**为 §4 固定子节（e2eImpact 字段承载），渲染视图小节标题逐字为「e2e 影响面评估」（下游 T3 按标题检索继承，措辞漂移会检索失败——渲染脚本固定输出该标题，保证由字段必填兜底）：列出受影响的现有 e2e/真实进程/真实 LLM 测试资产清单，圈定开发阶段需跑子集（执行准则 SSOT = 项目 AGENTS.md 测试节；能 mock/fixture 等价覆盖的标单测化路径）。无受影响项时 items 为空数组且 noneReason 填依据——禁止留空或省略字段，空集会被下游静默继承为零验证节点。

圈定范围不限于 e2e 资产：项目自有的其他既有检查轨同样按改动影响面核对——unit 级域测试套件（如扩展包测试三连）、机器对比类检查（如界面截图与基准图的像素比对）在改动触及对应目录/层时必须列入需跑子集并写明命令，经 impl-plan 验收计划在开发阶段执行；设计期未圈定到的由 CI 兜底暴露，不要求本地前置全量。

## Step 5：下一层拆分

实施路径 + 单元拆分清单 + 每项 justification + 文件改动地图 + 待验证检查点。每个拆分说明"为什么这么拆"；拆分呼应 Step 4（单元可独立验收）；设计阶段无法确定的诚实标"待验证"。本章产出写 `s5-breakdown.json`：units（拆分单元数组，被 s3 decisions 的 unitRefs 引用）/ fileMap（文件改动地图，长文本字段值）——字段规格见 `references/design-doc-schema.md` §8。

**终态型波次与跨版本队列语义**：终态型设计的拆分单元 = 迁移波次（来自 3.3 差距-波次映射）。波次允许标注目标 dev 版本，形成跨版本队列；约定四条：

1. 一份设计文档对应一份 impl-plan——波次跨版本不拆成多份设计、不重走设计流程
2. 各期共用同一设计文档与同一审查终态（final.json 只落一次，不按版本重开）
3. T3 确认点一次性批准分期映射；后续版本按波次执行，不逐版重过设计确认
4. 差距表逐版本核对：每个版本收尾时对照终态-现状差距表核对剩余项，全部清零才算设计交付完毕

中间态边界（3.2 迁移路径中声明的进入/退出条件）由 Step 7 走查覆盖——分期间衔接场景（前一版本结束态 + 下一版本操作）入边界用例。

## Step 6：自检（双层）

交付前过两层检查。**机器项全绿 = T2 进场门槛**：机器可判定的写作完备性问题在 T1 拦截，不带进 T2 消耗审查轮次。

### 6.1 机器层（脚本判定）

跑机器校验脚本：`node <tech-design-v4 技能根>/scripts/check-design-doc.mjs <设计目录>`。脚本按十条规则判定：六文件完整与枚举合法 / id 全局唯一 / 导航对齐 / 跨章节引用与守护引用存在 / 分型一致 / 产物表触发完备 / 内容形态合法 / 穷举断言声明（warning 不阻塞）/ 渲染产物过期（warning 不阻塞）/ 守护单一登记——其中导航对齐 = reviewNav 与 decisions 的 decisionId 集合对账；跨章节引用与守护引用存在 = gapRefs / unitRefs / axiomRefs / goalRefs 指向的 id 必须在被引用数组中存在、{{Gx}} 守护引用指向的 guards id 必须在 decisions[].guards 登记中存在；内容形态合法 = 分型理由不重复前缀、文件条目括号配对；穷举断言声明 = 穷举断言行缺 searchCmd 登记时告警；守护单一登记 = guards 文本全局唯一，可执行内容跨字段逐字重复只告警不阻塞（提示收敛为 guards 登记 + 引用）。exit 非 0 时按 stdout 报告逐项修复对应章节 JSON 后重跑，至 exit 0 才进 6.2；exit 0 时仍要读 stdout 的 warning 行——单一登记类 warning 按其中的收敛建议处置（收敛为 decisions[].guards 登记 + {{<守护 id>}} 引用，或按准则 14 在决策节登记全部登记点清单）后再进 6.2。**机器项全绿 = T2 进场门槛**不变。每次章节 JSON 修改后同步跑渲染脚本 `node <tech-design-v4 技能根>/scripts/render-design-doc.mjs <设计目录>` 刷新 `<name>.rendered.md`（阅读视图非权威，审查与走查读它）。

### 6.2 语义层（一页清单）

- **失败路径全覆盖**：核心场景之外，失败路径 / 空数据与极端数据 / 并发与中断 / 权限越界 / 状态残留与重入，各有验收或显式豁免
- **验收真实场景与投入匹配**：§4 逐场景是真实场景（非单测非 mock），投入与改动大小匹配
- **错误恢复指引**：每个失败路径给具体恢复动作（不是「请检查」）
- **代价四要素**：已接受代价逐条核对量级 / 恢复路径 / 重审触发条件 / 显式判定（可接受 + 依据）
- **受众假设**：每写一段问「不懂内部背景的开发者能读懂吗」（表达类准则：金字塔 / 自包含 / 使用者视角 / 术语锚定，见 `references/design-principles.md`）
- **决策定级自查**（对照 `references/review-guide-rubric.md`）：关键决策每条已定级（标题带 A/B 级标记、六维只填非「无」）；无 C 级条目滞留关键决策节；对照 A 级触发判据无「应 A 标 B」的压低（重点核对含时间类机制 / 权威源变更 / 持久化格式变更的决策）
- **一句话复述**（T1 写作者自检，不派 agent）：能否用一句话向不带上下文的开发者复述本设计的核心问题与方案主干——复述不出或复述含糊 = 问题定义或方案主干不清晰，回 Step 0 / Step 3 修

Step 6 完成后进 Step 7 业务用例走查（T1 确认点前的最后一环），走查收尾即到达 T1 确认点（见 Step 7.4）。

## Step 7：业务用例走查（T1 确认点前必做）

设计文档完稿、自检通过后，提交用户确认前先做**业务用例走查**（walkthrough：按用例步骤逐条对照设计推演能否走通）：主 agent 生成业务用例 → 派独立 subagent 走查 → 缺口反哺回设计文档。走查与 T2 对抗式审查互补：T2 按判据审文档质量，走查按场景审设计能否承载真实业务——先走查后审查，避免文档过审后才发现核心场景走不通。

### 7.1 方向确定性检查（大方向未定不生成用例）

生成用例前先判定**大方向是否基本确定、是否影响业务用例生成**。三个判定点（全部可从文档自身回答）：

1. **问题定义成立**：§0 复述的问题与用户意图一致（用户给的就是明确问题，或复述已被用户确认）
2. **方案方向已定**：§3 方案对比有明确推荐，且全文没有方向级「待裁决」标注（推荐曾被用户否决的，须已完成重选并给出新推荐）
3. **前提不卡用例**：§2 末前提清单没有「影响用例期望结果」的 ⏳ 待裁决项——前提两可，期望结果就写不出唯一答案

任一不成立 = 影响生成 → **停下，把方向级待决点交给用户确认与裁决**（每条带：待决问题 / 影响 / 候选），按裁决修订文档后回本步重判。待决点属行为 × 状态组合类时，裁决材料按 `references/enumeration-matrix.md` 形态准备（穷举矩阵 + 视觉元素 HTML demo），不止纯文字方案描述。全部成立 → 7.2。前期授权（全托管）时不等待：按推荐方案自裁决，决策记入清单随 T1 确认点一并呈现。

### 7.2 生成业务用例（先核心后边界）

用例从设计文档与现状代码派生，**不引入文档外的新需求**（走查验证设计，不是扩大范围）。使用者视角按层适配：面向用户的功能 = 用户场景；基础设施/内部机制 = 其使用者（调用方、运维方）场景。落 `<runDir>/use-cases.md`，每条含：id（UC-N）/ 场景 / 前置 / 操作步骤 / 期望结果（按当前设计应该发生什么 + 设计依据章节）。

1. **核心用例先行**：覆盖 §1 目标与产品核心价值的主干场景；§3.1 终态交互样例对应的场景必须在内
2. **边界用例随后**：失败路径与恢复 / 空数据与极端数据 / 并发与中断 / 权限与越界 / 状态残留与重入 / 跨模块边界——每条标注它攻击的设计点，攻击点说不清的不收

纯文案/纯参数调整类设计（无行为与数据流变化）跳过 7.2-7.4，在 T1 确认点声明跳过理由。T2 打回重写后重进本步：只重走重写触及的用例，不整单重走。

### 7.3 派 subagent 走查

按组并行派独立 subagent（审查与写作分离，主 agent 不自走查）：核心用例一组、边界用例一组；单组超 10 条按模块再拆，同时执行不超 5 个。task 三段式 + structured-output 返回：

```text
背景：对设计 <一句话说明> 做业务用例走查（设计包在 <设计目录绝对路径>）。
目标：
  1. read <use-cases 绝对路径>（只走查分给你的那组）+ <设计目录>/<name>.rendered.md
     （设计文档渲染视图，走查读它；需核对章节结构时读 <设计目录>/ 内的章节 JSON，
     如 s2-status.json 的 artifactTables）
  2. 目标项目根：<绝对路径>——走查推演以设计写明的行为为准；需要核对现状行为时
     read 源码（项目 AGENTS.md 有索引时，先读索引再进入源码）
  3. 逐条走查：按用例步骤对照设计推演「按当前设计这条用例能否走通」。四类缺口都算：
     信息缺失（设计没写到）/ 前后矛盾（两处冲突）/ 边界未定义（设计提到但答案不唯一）/
     走不通（按设计执行到某步无法继续）；每条缺口标注文档位置
  4. V4 交付任务（meta.json 有 acceptanceBinding 时；独立设计任务跳过本条）加做失败反例
     攻击：read 验收包（acceptanceBinding.taskDir 下的 acceptance.json），对关键断言
     （riskAcceptable=false 的判据与 invariant/不变量类优先）各尝试构造一个使设计失败的
     反例——满足验收场景前提、按当前设计执行却产生违反断言结果的具体操作序列。构造成功的
     按第 3 条四类缺口形态登记进 problems（title 带对应断言 id；反例不对应走查用例时
     useCases 留空数组），构造不动的给一句排除理由（为什么按当前设计构造不出来）
  5. 报告写到 <runDir>/walkthrough-core.md（边界组 = walkthrough-edge.md，按组名类推）
验收：
  - 返回 structured-output { reportFile, verdicts[], problems[] }
  - verdicts = 分给你的每条用例 { id, verdict: "pass"|"gap", note }
  - problems = 逐条缺口 { ref, level: "must-fix"|"suggestion", useCases[], title, consequenceRefutation?, consequenceRefutationType?: "will-not-occur"|"not-observable"|"accepted-by-acceptance" }
    （ref = 报告条目锚点 walkthrough-<组名>#N，锚的是报告里该缺口的条目序号；useCases 为
    受影响用例 id；条数合计须等于 must-fix + suggestion。suggestion 必须先标
    consequenceRefutationType（will-not-occur=不会发生 / not-observable=用户不可观察 /
    accepted-by-acceptance=验收明确允许）再给 consequenceRefutation 依据；
    已推演出用户可观察的不正确行为时，不得只按判据字面合规降级）
```

全托管模式附加声明与 T2 派发相同（task 末尾追加同句，见 `flow/review.md`）。

### 7.4 缺口反哺设计文档 → T1 确认点

合并全部 problems（同根因跨用例合并），逐条处置：

| 判定 | 动作 |
|------|------|
| 缺口真实且修法明确（补文档可解：信息缺失 / 矛盾 / 边界未定义） | 直接修进对应章节 JSON，过 Step 8.2 联动同步清单与跨章节引用字段同步，改后重渲染；§4 验收缺的关键场景同步补入 s4-accept.json scenarios |
| 走不通且暴露方向问题（补文档救不了，须改方案） | 回 7.1 方向确定性检查的处置：呈用户裁决，按裁决修订后重走受影响的用例 |
| 拿不准（缺口真实但修法有多个候选） | 列入裁决清单交用户：每条带背景（哪条用例、卡在哪）+ 影响 + 候选 |

处置结论回写 `use-cases.md`（每条用例终态：pass / 缺口已修 / 裁决中 / 登记不修），零缺口也要落走查结论行。走查报告与 use-cases.md 同落 `<runDir>/`。

**T1 完成即阶段确认点**：呈现以「人工审核导航」表为入口——A 级决策逐条列出等用户裁决、B 级一行一条（声明无异议即过），并显式声明导航表外内容为局部实现细节可不审，**不要求用户通读全文**；A 级决策含行为 × 状态组合类的，呈现时附穷举矩阵入口（`<runDir>/` 下矩阵文档路径 + HTML demo 路径），并按 `references/enumeration-matrix.md` 收尾盘点一节主动列出同系统内未穷举的组合清单，随确认点一并呈；随后附用例走查结论（总数 / 通过 / 缺口处置）+ 裁决清单（或已裁决记录）。默认等用户确认「方向与结构合理」→ 授权后进 T2（`flow/review.md`）。全托管连跑时 A 级按推荐自裁决，导航表照常落盘供事后追溯。

## Step 8：审查-修复循环协议（T2 各轮的修复规则）

设计文档过 T1 确认点 → 四席并行审查（方向审席攻击前提层与终态层 + 主审 / 影响面审 / 简洁审；派发见 `flow/review.md`）→ 方向审席 patch 档发现（前提层/产物表/措辞级——问题定义与方案主干不动）随三审发现进当轮问题清单，由修复者按各报告「修复方向」列一并处置后下轮对账；问题定义 / 方案主干 / 分型被击穿（rewrite 档）→ 整循环终止，按修复方向回 Step D 重做诊断再重写，修完重新发起 → 多轮修复循环至全部报告 0 must-fix。**不要自己审——审查与写作分离，避免确认偏差；主 agent 不自审。**

**方向审前移（试点）**：问题定义与方案对比选型定稿后（Step 3 完成、Step 4-7 展开前），先单派一次方向审（tech-design-value-review），不等 T2 四席并行——方向错误在此时改 = 改几段文字，到 T2 才改 = 整篇重写。T2 方向审照常（终审判据不变）；前移审的发现当场修完再继续展开。试点期记录两项：前移审拦截数、T2 方向审 rewrite 档发现数是否下降——连续零增量则前移审降级回 T2 单点（流程环节要能证明收益）。

**高风险契约选择性审**：模块划分与契约涉及跨文件契约（事件 / schema / 接口两侧）、共享状态写入点时，在 T2 之外先派主审 / 影响面审的专项核对——含三类关联声明完整性（该登记 associations 的改动点是否逐项在册，判据见 `flow/plan.md`「三类关联声明」节）；其余情形不触发，不增加固定审查环节。

**轮次唯一形态**：每轮 = 聚焦审 + 修复。R1 = 全面审；R2+ = 聚焦复审——reviewer 只审（a）上轮 must-fix 修复是否成立（fixed 须实证）、（b）修复是否引入新问题（只扫修复触及的章节）、（c）上轮登记不修项的上下文是否被改变（结构化申报复活）。**不做全面重扫，不存在"全面审 + 聚焦审"双重派发**。converged 判定读当轮（聚焦）报告。

### 8.1 每轮修复规则 [MANDATORY]

**循环由 must-fix 驱动：审查只报 must-fix 一个级别，每轮修复全部报告的全部 must-fix，不留尾巴。** 每条 finding 处置三态，逐条记录：

| 处置 | 适用判定线 |
|---|---|
| fixed（修复） | 默认处置：精度歧义 / 边界未声明 / 拆分未同步 / 验收判据不可证伪 / 安全性缺口——当场修进对应章节 JSON |
| deferred（登记不修） | 纯表述 / 措辞 / 偏好性建议且不触发 finding 必填字段——记一句话理由，进交付汇报 |
| archived（归档） | 有价值但不属本文档层——记入设计文档相应节的待办或残留风险 |

**按 finding 必填字段分流**（每条带「影响决策 / 影响交付」两列）：`影响决策 = 是` → 重跑该决策的方案对比 + 8.2 联动同步；`影响交付 = 具体环节` → 修复落点锚定到该环节载体（规划→s5-breakdown.json、开发→s3-solution.json 与 file:line、测试→受影响测试族、验收→s4-accept.json、文档登记→ADR/现行文档）；两字段皆无 → deferred。判定存疑按 fixed 处理（滑坡防护）。

修复时按意见类别选动作：方案性（重跑方案对比 + 联动同步）/ 规格完整性（补齐并查同类缺口）/ 格式可读性（全文统一改）/ 新需求（回 Step 0 判 scope）。

### 8.2 修复纪律

1. **反例重演后再动笔**：must-fix 附反例序列时先重演"修复后行为"；审查给的修复方向也要重演，不照单全收
2. **被击穿的方案记入否决记录**：旧方案连同击穿它的反例写入该决策「不采用」栏（rejected 字段）
3. **决策改动后过联动同步清单**：该决策条目（choice / rejected / evidence）/ 终态形态与公理（终态型）/ s5 拆分单元与文件地图 / s4 验收场景——关联章节 JSON 五处联动，同类缺口全文扫同模式实例一并修；**跨章节引用字段**（decisions 的 gapRefs / unitRefs / axiomRefs、scenarios 的 goalRefs、meta.json reviewNav 的 decisionId）与被引用数组的 id 同步更新
4. **每轮修复后重渲染**：章节 JSON 有任何修改即重跑 `render-design-doc.mjs` 刷新渲染视图（下轮审查与走查读渲染视图；rendered.md 过期会被机器校验告警）
5. **修复轮次做语言回归**：每轮追加的源码锚/否决记录/边界声明会使行文密度上升——新增文本过产物语言自检：流程指令词不当产物小节名；压缩词首次出现必须展开或改用自然词

### 8.3 聚焦复审派发

修订完成后按 findings 归属送回各自审查 agent（方向审的送方向审，主审送主审，影响面审送影响面审，简洁审送简洁审；**修订重写了问题定义 / 方案主干 / 最小形态 / 分型 → 方向审必送**；新增/改变外部接触面或代价声明 → 影响面审必送；增删机制/抽象/扩展点 → 简洁审必送。形态注记：本条是手工循环协议；workflow 形态（tech-review-loop-v4）方向审只在发起时过一次，轮内三席不含方向审——重发起必重过方向审，以「重写主干 / 分型 → 卡断重发起」覆盖同一关注点）。提示词四要素：背景（第 N 轮修订摘要，对照上轮 findings 逐条——每条怎么修的 + 反例重演结果）/ 聚焦（上轮 must-fix 修复是否成立、新机制能否被新反例击穿——修订方自己不放心的场景列出来让审查者优先攻击；交叉引用一致性终检；不重查已确认项）/ 输出（格式同前，新发现标注）。给攻击点建议是提效关键。

### 8.4 终止与交付

方向审通过且三报告均 0 must-fix、上轮处置全部确认，且 V4 判据与机制对账完整、冲突为零、反例场景测试绑定齐全 = **设计就绪（T2 converged）**。不派纯确认轮。交付汇报写明：方向审一句话判定、循环轮数、各报告 must-fix 收敛轨迹、处置清单（fixed / deferred / archived 逐条）、否决记录最终形态。

**T2 完成即阶段确认点**：转述方向审判定 + 收敛轨迹 + 处置清单，默认等用户确认 → 授权后进 T3（`flow/plan.md`）。下一层产物 = 子系统/需求集合的设计到此交付（无 T3）；= 代码任务/技术方案才进 T3。

## 迁移/重写类设计防复发判据 [MANDATORY]

设计对象是「把既有流程/系统重写或迁移到新形态」（老 skill → 新 skill、老管线 → workflow 化等）时，写作期强制过四判据。触发信号除设计对象为重写/迁移类本身外：P4 修复史判定表（Step D 产物，见 `references/principles.md` P4）定性该问题域为「故障密集域重构」或「未修到」且方案含重写/迁移动作时，同样强制适用——修复史是该触发的证据来源：

1. **老能力逐条映射表**：设计必附「老流程能力 → 新形态落点」逐条映射表（老能力全枚举，逐条标注落点 = 新形态某节 / 显式裁决不迁移含理由；禁止只写新形态有什么）
2. **清单条款附条目文本**：设计写「进 XX 清单/登记表/表」类条款时，必须附该清单的条目文本本身（引用条目名而不给内容 = 两个实现各自发明具体化）
3. **双形态契约字段级 SSOT**：同一机制有手工形态与 workflow 形态两个实现时，共用契约（schema 字段名/路径/终态枚举/数字阈值）设计到字段级并声明唯一权威；两实现各自文字化的漂移由该 SSOT 判错
4. **验收含条款对账**：实现完成的验收 = 设计条款逐条对账（每条至少一次触发验证）+ 冒烟按「条款 × 触发条件」矩阵跑——「编译通过 + 主路径跑通」不构成迁移类设计的完成判据
