# 写设计文档流程

> 引导主 agent 按 tech-design 方法论写出设计文档。**结构标准见 `references/doc-structure.md`，写作原则见 `references/design-principles.md`。本文件只给流程步骤，不重复内容。**

> **产物路径约定 [MANDATORY]**：设计文档本体落 `<项目根>/.tmp/tech-design/<name>.md`（项目根 = `git rev-parse --show-toplevel` 解析结果，worktree 解析为各 worktree 根；非 git 仓库落 `/tmp/tech-design/`）。设计文档是 tech-design → dev-flow 的**过程产物，不进项目 docs/、不进 git**——实施落地后的现行设计依据是代码与活性文档（AGENTS.md / docs 索引），过程文档过期即弃，无需退役流程。**只落主文档一个文件**——审查报告、探针、基线数据等流水线伴生产物同落此目录，报告用 `design-review-<时间戳>` 前缀与主文档区分（见 `flow/review.md`）。历史反例：docs/design/ 曾平铺积压 200+ 伴生文件（review-rN / probe / impl-plan），2026-09-12 两轮清理退役 202 个；其后裁决设计文档本体也迁出 docs/——入库的设计文档随实施推进过期成僵尸文档，无人清理。

## Step 0：问题定义先行（设计前必做，禁止跳过）

动笔前先回答三个问题：

1. **用户描述的问题是什么？** 用自己的话复述，确认理解无误
2. **这是不是真正的问题？** 用户描述的现象可能只是症状，不是问题本身（例：用户说"命令太慢"，真问题可能是"每次都全量重算"）
3. **背后有没有隐藏的、用户未明确表达的根本性问题？** 常见信号：用户直接给了方案（"我要加个 X 配置"）而不是问题；触发场景描述得太窄；跳过因果链中间层直接说结论

发现"可能有隐藏问题"时的做法：

- **先提问澄清，不猜**——猜错问题比多问一句贵得多。提问聚焦"根本问题是什么"，不聚焦方案细节（问"你最终要解决 A 还是 B"，不问"配置项放哪个文件"）
- **grill 机制（主动提问澄清，完全自包含）**：发现可能有隐藏问题时，主动向用户提问，等答案再动笔：
  - **grilling（盘问式）**：追问"你真正要解决的是什么"，挖出用户没明确表达的根本问题
  - **research（调研式）**：查证事实性信息（现状、约束、数据来源等）
  - **可多轮追问**：一次问不完就分多次追问，不必一次问全；每轮拿到答案再继续
  - **不带未答问题往下写**：有未答疑点就继续问，直到问题定义收敛再动笔

写方案前最后自问一次：**这个方案解决的是根本问题，还是只让表面症状消失？** 若方案只是吞掉症状（例：加 try-catch 掩盖报错，根因数据模型错误还在），方案不合格——回到问题定义重新设计。

## 前置：判断层性质

动手前先定五件事：

0. **产品边界核对**：项目存在产品愿景文档（如 `docs/PRODUCT.md`，路径以项目 AGENTS.md 索引为准）→ read 并核对本次设计不偏离产品定位/用户画像/核心场景；设计目标与产品愿景冲突时停下向用户澄清，不得自行取舍
1. **本次设计的"当前层 → 下一层"是什么？** 写在文档开头显式声明（准则 10：不跨 2 层）
2. **下一层产物是什么性质？** 套 `doc-structure.md` 的层敏感调节表，确定 §3「解决方案」的侧重点
3. **本次设计是否涉及运行时行为 / 数据流 / 错误处理？** 是 → 准则 5/6/7 全部 P0 适用；否 → 可放宽
4. **领域术语与视觉层核对（条件触发）**：设计引入新领域术语 → read 项目术语表（若存在，典型 `docs/CONTEXT.md`）对齐既有语义或确认待登记，防语义漂移；涉及 UI/视觉层 → read 项目视觉设计权威（若存在，典型 `docs/DESIGN.md`），路径均以项目 AGENTS.md 索引为准
5. **本次设计触及的功能分级（P 级）与风险分是多少？** [MANDATORY] 标注在文档头部：
   - 项目存在功能分级登记（如 `docs/FEATURE-PRIORITIES.md`）→ 查表取本次涉及模块/用例的**最高 P 级**；不存在 → 按「挂掉后果」判据现场评估（P0=项目对用户毫无价值 / P1=大体能用但体验非常差 / P2=基本可用稍可忍受 / P3=影响很少或特定人群）
   - **风险分（1-10）= P 级基数（P0=9 / P1=7 / P2=4 / P3=2）+ 可逆性修正（数据迁移/协议变更/不可逆操作 +1）+ 新颖度修正（仓内无先例机制 +1）**，clamp 1-10
   - 风险分是下游全链路的资源分配锚点：dev-flow 验收计划表的成本倾斜、审查分组（≥7 独享深度审、3-6 且强相关并审、≤3 弱相关打包审）都继承它——分数在这里一次产生，下游不重打

## Step 1：背景目标

写 SCQA 开篇 + 系统是什么 + 设计目标（从使用者体验倒推）+ in/out scope。

- 准则 2：标题下放一句话结论，SCQA 四句开篇
- 受众假设：假设读者会用系统但不懂内部背景，"系统是什么"要补足基本认知

## Step 2：现状与问题分析（禁止跳过）

写使用者视角的现状（真实例子）+ 真实失败模式 + 根因分析 + 物理数据流（若涉及数据）。

- 准则 3：现状放真实系统提示词/接口/界面（**取自代码不编造**）；这是读者理解方案的前提
- 准则 4：本段首次出现的抽象术语（如"元数据""契约"），立刻定义 + 绑本段例子
- 准则 5：若涉及数据流转，画磁盘→用户眼前的物理数据流图
- **禁止**上来讲"哪个文件哪个函数怎么改"（反例 2）

> 这一段最容易被偷懒跳过，也最关键。没有现状和根因，方案就是无源之水。

## Step 3：解决方案

写终态（使用者视角）+ 多方案对比 + 关键决策与权衡。

### 3.1 终态（使用者视角先行）
- 完整交互对话样例（成功路径 + 失败路径）
- 准则 6：失败路径带恢复指引（具体命令/动作）
- 终态在实现机制**之前**讲

### 3.2 多方案对比（准则 9，强制）
- ≥2 个候选方案，每个评「长期架构合理性 / 短期实现成本 / 风险」三栏
- 「风险」栏写按前置第 4 条算出的风险分（1-10）+ 一句主要风险来源；不同方案触及的 P 级不同时分列
- 给明确推荐 + 推荐理由
- 被否方案说明「若用它，§2 的例子会变成什么样」

### 3.3 关键决策与权衡
- 每个决策独立成条：选择 + 被否 + 证据
- 准则 7：运行时行为断言附探针（✅已测/⛔实施期门），探针失败则断言不写
- 准则 8：遇子问题先问减法，别急着加 clever 机制

## Step 4：验收（禁止跳过）

写实施完成后在真实场景里怎么验证功能符合预期。

- **不是单测、不是 mock**：单测只验代码符合设计假设，mock 等于没验真实集成，都不回答"真实工作里好用吗"。验收用真实依赖、真实数据、真实路径
- **写清三要素**：验证场景、步骤、通过标准
- **每个场景回溯 §1 目标**：标注验证 §1「背景目标」的哪一条；无法回溯的场景是多余的，有目标无对应场景是遗漏（SBE「从目标推导范围」）
- **用具体业务例子，不用抽象断言**：写"谁、在什么真实上下文、做什么、看到什么真实结果"，不写"功能正常/响应快"——抽象验收断言和运行时断言同病，不可验证
- **按改动大小匹配投入**：小改动（改文案/调参数/修单点）一句话简化验证即可；大改动（新功能/行为变更/接口调整）必须写多个真实场景
- **设计阶段就定（DoR 门槛）**：验收场景必须 testable 才算设计就绪，指导 Step 5 拆分如何分阶段验收，不是实施后补

> 这是设计最容易被偷懒跳过的一步，也是 review 重点审查项（rubric P0-13/14/15）。验收回答的是"功能在真实工作里符合预期吗"——这是设计文档最该回答的问题。

## Step 5：下一层拆分

写实施路径 + 下一层单元拆分清单 + 每项 justification + 文件改动地图（若涉及代码）+ 待验证检查点。

- 每个拆分必须说明"为什么这么拆"（供审查）
- 拆分尽量呼应 Step 4 验收：让每个拆分单元可独立验收
- 设计阶段无法确定的事诚实标"待验证"，别编

## Step 6：自检

交付前过两份清单：

1. `references/design-principles.md` 末尾的「写前自检清单」（结构和可读性 / 内容主线 / 连贯性 / 方案对比 / 完整性 / scope / 验收）
2. `review/rubric-design-doc.md` 的 P0 项（当作预审，P0 全过再交付；验收 P0-13/14/15 是重点）

**全程贯穿受众假设**：每写一段，问"一个会用系统但不懂内部背景的开发者，能读懂吗？关键概念有例子吗？"

## Step 7：审查-修复循环（对抗式审查回来后）

设计文档写完（Step 1-6），并行派 `tech-design-review`（主审）+ `tech-design-impact-review`（影响面审）+ `tech-design-simplicity-review`（简洁审）三个 subagent 做审查（派发方式见 `flow/review.md`），然后进入**多轮修复循环**，直到三份报告均 0 must-fix。真实案例经 4 轮才收敛（机制级 → 规则级 → 计数语义级 → 0），这是正常收敛信号；轮次问题同级或变宽，怀疑修复方向错了，回到该决策的方案对比重做。

### 7.1 每轮修复规则 [MANDATORY]

**每一轮都必须修复三份报告的全部 must-fix 和所有 suggestion，不留尾巴到下一轮。** 理由：suggestion 里的"实施精度歧义 / 边界未声明 / 拆分未同步"留给实施期就是按歧义实施（文档是实施的 SSOT）；且累积多轮再修会丢失每条意见的上下文。唯一例外：审查方明确标注"不阻塞、随实施带上"且修复成本显著大于当轮收益的项——须在交付汇报中逐条列明未修原因。

修复时按意见类别选动作：

| 意见类别 | 识别信号 | 处理动作 |
|---|---|---|
| **方案性**（推翻决策） | "不用 X，改用 Y"、"这个机制不对" | 重跑该决策的方案对比（新增被指向的候选），过 7.2 联动同步清单 |
| **规格完整性**（缺矩阵/清单/降级） | "没写 X 时怎么办"、must-fix 类缺口 | 补齐对应表格/清单，并检查同类缺口是否还有第二处实例 |
| **格式可读性** | "看不懂"、"分行分 item" | 全文统一改格式（同一模式其他实例一并修） |
| **新需求** | "还要支持 Z" | 走 Step 0 问题定义：确认是同一根本问题还是 scope 变化；scope 扩大回改 §1 目标与 in-scope |

### 7.2 修复纪律（三条，来自真实 4 轮循环的教训）

1. **反例重演后再动笔**：must-fix 附带反例事件序列时，先在修订说明里逐序列重演"修复后行为"，确认反例被消灭。**审查给的修复方向也要重演，不照单全收**——真实案例中审查建议的修复方案（消费点双增）被重演发现仍被同文本场景击穿，改用更稳的方案（单计数确认制）后第 4 轮才真正收敛。
2. **被击穿的方案记入被否谱系**：每轮修复若推翻/替换了自己上一版的机制，旧版连同击穿它的反例一起写入该决策的"被否"栏（`<旧方案> —— <击穿反例>`）。谱系让后续轮次的审查者不必重新发现旧坑，也是最终"设计就绪"结论的论证依据。
3. **决策改动后过联动同步清单**（模式性遗漏高发——真实案例连续两轮在拆分清单上复发"正文已改、§5 未同步"的 must-fix）：
   - [ ] 正文该决策（采用/被否/证据/效果）
   - [ ] 终态数据流图（若画了）
   - [ ] 错误规格表（新边界/新失败路径）
   - [ ] §5 拆分单元表 + 文件改动地图（实施依据，漏同步 = 实施复现已修复的 bug）
   - [ ] §4 验收（新边界是否需要补场景 / 探针降级路径是否受影响）
   - 同类缺口往往不止一处实例——联动修复时扫全文找同模式的其他实例一并修。

### 7.3 复审派发（聚焦复审，不全面重审）

修订完成后**按 findings 归口送回各自的审查 agent**（主审的送 `tech-design-review`，影响面审的送 `tech-design-impact-review`，简洁审的送 `tech-design-simplicity-review`；修订若新增/改变了外部接触面或代价声明，或增删了机制/抽象/扩展点，对应维度的报告都送），提示词四要素：

```text
背景：第 N 轮修订完成（文件路径不变）。修订摘要：对照上轮 findings 逐条——
  每条 must-fix/suggestion 怎么修的 + 反例重演结果（上轮反例序列在新机制下的行为）。
聚焦：
  1. 上轮 must-fix 的修复是否成立；新引入的机制能否被新反例击穿
     （给攻击点建议：修订方自己推演时不放心的场景列出来让审查者优先攻击）
  2. 交叉引用一致性终检（联动同步清单五处）
  3. 不重查已确认项
输出：格式同前（Summary + Findings），新发现标注。
```

给攻击点建议是提效关键——修订方最清楚新机制的薄弱处，点名让审查者攻击比让它全面重扫更快触达深层反例。

### 7.4 终止与交付

- **三份报告均 0 must-fix = 设计就绪**（suggestion 已按 7.1 当轮修完，无遗留）。
- 交付汇报写明：循环轮数、每轮三份报告 must-fix/suggestion 数的收敛轨迹、被否谱系的最终形态、（若有）未修项及原因。
