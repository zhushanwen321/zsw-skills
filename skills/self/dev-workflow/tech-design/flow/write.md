# 写设计文档流程

> 引导主 agent 按 tech-design 方法论写出设计文档。**结构标准见 `references/doc-structure.md`，写作原则见 `references/design-principles.md`。本文件只给流程步骤，不重复内容。**

> **产物路径约定 [MANDATORY]**：设计文档本体落 `<项目根>/.tmp/tech-design/<name>.md`（项目根 = `git rev-parse --show-toplevel` 解析结果，worktree 解析为各 worktree 根；非 git 仓库落 `/tmp/tech-design/`）。设计文档是 tech-design → dev-flow 的**过程产物，不进项目 docs/、不进 git**——实施落地后的现行设计依据是代码与活性文档（AGENTS.md / docs 索引），过程文档过期即弃，无需退役流程。**只落主文档一个文件**——审查报告、探针、基线数据等流水线伴生产物同落此目录，报告用 `design-review-<时间戳>` 前缀与主文档区分（见 `flow/review.md`）。历史反例：docs/design/ 曾平铺积压 200+ 伴生文件（review-rN / probe / impl-plan），2026-09-12 两轮清理退役 202 个；其后裁决设计文档本体也迁出 docs/——入库的设计文档随实施推进过期成僵尸文档，无人清理。

## Step 0：问题定义先行（设计前必做，禁止跳过）

动笔前先过**前置探明门**，再过**产品最小形态三问**，最后回答三个问题：

**前置探明门**：问题是否已探明——症状、触发条件、复现路径三者清楚？未探明（「还不清楚为什么会这样」「需要先加日志/探针观察」）→ **先做调研再回来**：复现实验、日志采集、探针观察都是前置步骤，产物（复现脚本、采集数据、观察记录）落 `.tmp/` 留档，**不进设计文档**。例外：探针体系本身复杂到需要设计（超大项目的采样管道、埋点架构）才可进文档，独立成章并论证复杂度。把「加日志看看再定方案」写成设计内容 = 问题未探明的设计，不合格（准则 0）。

**产品最小形态三问**（准则 13，问题探明后、动笔 §3 前必答，答案写进文档）：

1. **核心价值**：这个功能/产品最最核心的价值是什么（一句话，以项目产品定义文档为锚）？达成这个价值的**最少技术投入**是什么形态？——这个形态就是 §3 方案的主干。
2. **增量收益**：在最小形态之上，有哪些**较少额外投入能换来明显额外收益**的项？逐项独立裁决（投入/收益/不做会怎样），裁决过才进设计，未裁决的不得混入主干。
3. **扩展支持**：架构上如何支持未来更好的扩展？——只保留有**已发生证据**支持的扩展点（已有的第二个使用方/已发生的变化原因）；为想象未来预留的抽象在此阶段砍掉。

最小形态的判别法：**从产品核心价值出发描述这个功能，再对照现状实现——现状的复杂度里有多少是产品天然包含的？多出来的部分每项都要论证「为什么保留」，砍掉是默认候选**。从最小形态倒推设计，不从现状实现倒推（现状实现不是需求）。

三个问题：

1. **用户描述的问题是什么？** 用自己的话复述，确认理解无误
2. **这是不是真正的问题？** 用户描述的现象可能只是症状，不是问题本身（例：用户说"命令太慢"，真问题可能是"每次都全量重算"）
3. **背后有没有隐藏的、用户未明确表达的根本性问题？** 常见信号：用户直接给了方案（"我要加个 X 配置"）而不是问题；触发场景描述得太窄；跳过因果链中间层直接说结论

发现"可能有隐藏问题"时的做法：

- **先提问澄清，不猜**——猜错问题比多问一句贵得多。提问聚焦"根本问题是什么"，不聚焦方案细节（问"你最终要解决 A 还是 B"，不问"配置项放哪个文件"）
- **grill 机制（主动提问澄清，完全自包含）**：发现可能有隐藏问题时，主动向用户提问，等答案再动笔：
  - **grilling（盘问式）**：追问"你真正要解决的是什么"，挖出用户没明确表达的根本问题
  - **research（调研式）**：查证事实性信息（现状、约束、数据来源等）
  - **可多轮追问**：一次问不完就分多次追问，不必一次问全；每轮拿到答案再继续
  - **不带未答问题往下写**：有未答疑点就继续问，直到问题定义收敛再动笔
- **被用户第二次追问「为什么 X」时，主动做前提清点**：连环"为什么"= 设计里有未质疑的隐含前提。不要逐个被动应答——立即列出「本设计默认为真的前提清单」请用户裁决（见 §2 前提清单节）

写方案前最后自问一次：**这个方案解决的是根本问题，还是只让表面症状消失？** 若方案只是掩盖症状，方案不合格——回到问题定义重新设计。掩盖问题的典型形态（准则 12，逐个对照）：加 try-catch 掩盖报错（根因数据模型错误还在）、自动重试/自愈（故障源头还在，重试只是让它间歇性成功）、定时轮询对账补偿（不一致的制造端还在制造）、降级/缓存遮蔽（用户看不见病，病还在）。判别法：删掉方案里的补偿机制，病因还在不在？还在 = 只掩盖了症状。

## 前置：判断层性质

动手前先定五件事：

0. **产品边界核对**：项目存在产品愿景文档（如 `docs/PRODUCT.md`，路径以项目 AGENTS.md 索引为准）→ read 并核对本次设计不偏离产品定位/用户画像/核心场景；设计目标与产品愿景冲突时停下向用户澄清，不得自行取舍
1. **本次设计的"当前层 → 下一层"是什么？** 写在文档开头显式声明（准则 10：不跨 2 层）
2. **下一层产物是什么性质？** 套 `doc-structure.md` 的层敏感调节表，确定 §3「解决方案」的侧重点
3. **本次设计是否涉及运行时行为 / 数据流 / 错误处理？** 是 → 准则 5/6/7 全部 P0 适用；否 → 可放宽
4. **领域术语与视觉层核对（条件触发）**：设计引入新领域术语 → read 项目术语表（若存在，典型 `docs/CONTEXT.md`）对齐既有语义或确认待登记，防语义漂移；涉及 UI/视觉层 → read 项目视觉设计权威（若存在，典型 `docs/DESIGN.md`），路径均以项目 AGENTS.md 索引为准
5. **本次设计触及的功能分级（P 级）与风险分是多少？** [MANDATORY] 标注在文档头部：
   - 项目存在功能分级登记（如 `docs/FEATURE-PRIORITIES.md`）→ 查表取本次涉及模块/用例的**最高 P 级**；不存在 → 按「挂掉后果」判据现场评估（P0=项目对用户毫无价值 / P1=大体能用但体验非常差 / P2=基本可用稍可忍受 / P3=影响很少或特定人群）
   - **风险分（1-10）= P 级基数（P0=9 / P1=7 / P2=4 / P3=2）+ 可逆性修正（数据迁移/协议变更/不可逆操作 +1）+ 新颖度修正（仓内无先例机制 +1）**，clamp 1-10
   - 风险分是下游全链路的资源分配锚点：dev-flow 验收计划表的成本倾斜、审查分组（≥7 独享深度审、3-6 且强相关并审、≤3 弱相关打包审）都继承它——分数在这里一次产生，下游不重打

## Step 1：背景目标

写 SCQA 开篇 + 系统是什么 + 设计目标（从使用者体验倒推）+ in/out scope。

- 准则 2：标题下放一句话结论，SCQA 四句开篇
- 受众假设：假设读者会用系统但不懂内部背景，"系统是什么"要补足基本认知

## Step 2：现状与问题分析（禁止跳过）

写使用者视角的现状（真实例子）+ 端到端大流程图 + 真实失败模式 + 根因分析 + 前提清单。

- 准则 3：现状放真实系统提示词/接口/界面（**取自代码不编造**）；这是读者理解方案的前提
- 准则 5：**§2 开头画端到端大流程图**（从源头到终点的物理视图，本设计涉及的主链路，用户能看懂的粒度）——这张图是全文坐标系，§2 问题点与 §3 决策都用它的环节名锚定
- **问题点锚定格式**：每个失败模式/问题点条目以「**环节**：<大流程> → <环节名>」开头——读者在任何问题点处都能定位「这是流程里的哪个东西」；禁止脱离流程坐标系的机制名词叙事（读者看不懂「指纹跳推优化了推送冗余」，看得懂「环节：widget 推送链 → tick 尾巴的推送步骤，现状每 30s 无条件执行」）
- 准则 4：本段首次出现的抽象术语（如"元数据""契约"），立刻定义 + 绑本段例子
- **前提清单节（§2 末尾，必选）**：列出「本设计默认为真的前提」——设计当作输入而未在本设计中论证的假设（现状行为、外部约束、产品假设），每条标注来源（✅ 已核实代码 / ⏳ 需用户裁决）与「若不成立的影响」；前提错了设计整体作废，清单让读者/审查者可逐一攻击
- **禁止**上来讲"哪个文件哪个函数怎么改"（反例 2）

> 这一段最容易被偷懒跳过，也最关键。没有现状和根因，方案就是无源之水。

## Step 3：解决方案

写终态（使用者视角）+ 多方案对比 + 关键决策与权衡。

**方案形态定型（动笔 §3 前过一遍设计决策序，准则 12 + 准则 13）**：**第 0 步最小形态**——§3.1 终态描述必须先写「最小形态终态」（核心价值的最少投入形态，Step 0 三问的答案落进文档），增量项在此之后逐项列出；①定级——独立/偶发还是同类/架构级（双判据：症状分布 + 根因位置是否在共享路径）？②路线——直接解决还是架构优化？该决策显式进 3.2 方案对比（「修复 vs 重构」本身就是一对候选方案），不允许隐式选择；架构优化路径可分期但每期主体必须是直接解决。③直接解决——方案落在病因环节；掩盖问题类（兜底/自愈/对账/降级遮蔽）不是方案主体。④非功能后置——直接解决完成后才评估，按必要性三问 + 三档（不做/简单/复杂）裁决，档位连验收。暴露问题类（fail-fast、日志）是诊断能力属直接解决的一部分，不受此限。

### 3.1 终态（使用者视角先行）
- 最小形态终态先行（准则 13 第 1 层），增量项随后逐项（第 2 层各带独立裁决）
- 完整交互对话样例（成功路径 + 失败路径）
- 准则 6：失败路径带恢复指引（具体命令/动作）
- 终态在实现机制**之前**讲

### 3.2 多方案对比（准则 9，强制）
- ≥2 个候选方案，每个评「长期架构合理性 / 短期实现成本 / 风险」三栏
- 「风险」栏写按前置第 4 条算出的风险分（1-10）+ 一句主要风险来源；不同方案触及的 P 级不同时分列
- 给明确推荐 + 推荐理由
- 不采用的方案用完整自然句说明「不采用 X 的理由：若用 X，§2 的例子会变成什么样」——产物里用自然中文表述，小节名不用指令性缩略词，照「不采用 X 的理由」式自然句写

### 3.3 关键决策与权衡
- 每个决策独立成条：选择 + 不采用 + 证据
- **决策锚定格式**：每个决策条目以「**环节**：<大流程> → <环节名>」开头（与 §2 问题点同一坐标系）——决策是「在流程哪个环节上装什么/改什么/砍什么」，锚定后读者可定位
- 准则 7：运行时行为断言附探针（✅已测/⛔实施期门），探针失败则断言不写
- 准则 8：遇子问题先问减法，别急着加 clever 机制
- 准则 12：病症明确先直接解决——方案落在病因环节（或架构重设计使病症构造性消失）；掩盖问题类（兜底/自愈/对账/降级遮蔽）不得作为方案主体，出现时逐个过必要性三问 + 三档裁决（不做/简单/复杂），证不出即进不采用栏；档位选择连到 Step 4 验收

## Step 4：验收（禁止跳过）

写实施完成后在真实场景里怎么验证功能符合预期。

- **不是单测、不是 mock**：单测只验代码符合设计假设，mock 等于没验真实集成，都不回答"真实工作里好用吗"。验收用真实依赖、真实数据、真实路径
- **写清三要素**：验证场景、步骤、通过标准
- **每个场景回溯 §1 目标**：标注验证 §1「背景目标」的哪一条；无法回溯的场景是多余的，有目标无对应场景是遗漏（SBE「从目标推导范围」）
- **用具体业务例子，不用抽象断言**：写"谁、在什么真实上下文、做什么、看到什么真实结果"，不写"功能正常/响应快"——抽象验收断言和运行时断言同病，不可验证
- **按改动大小匹配投入**：小改动（改文案/调参数/修单点）一句话简化验证即可；大改动（新功能/行为变更/接口调整）必须写多个真实场景
- **设计阶段就定（DoR 门槛）**：验收场景必须 testable 才算设计就绪，指导 Step 5 拆分如何分阶段验收，不是实施后补

> 这是设计最容易被偷懒跳过的一步，也是 review 重点审查项（rubric P0-13/14/15）。验收回答的是"功能在真实工作里符合预期吗"——这是设计文档最该回答的问题。

## Step 5：下一层拆分

写实施路径 + 下一层单元拆分清单 + 每项 justification + 文件改动地图（若涉及代码）+ 待验证检查点。

- 每个拆分必须说明"为什么这么拆"（供审查）
- 拆分尽量呼应 Step 4 验收：让每个拆分单元可独立验收
- 设计阶段无法确定的事诚实标"待验证"，别编

## Step 6：自检

交付前过两份清单：

1. `references/design-principles.md` 末尾的「写前自检清单」（结构和可读性 / 内容主线 / 连贯性 / 方案对比 / 完整性 / scope / 验收）
2. `review/rubric-design-doc.md` 的 P0 项（当作预审，P0 全过再交付；验收 P0-13/14/15 是重点）

**全程贯穿受众假设**：每写一段，问"一个会用系统但不懂内部背景的开发者，能读懂吗？关键概念有例子吗？"

## Step 7：审查-修复循环（对抗式审查回来后）

设计文档写完（Step 1-6），**先派 `tech-design-value-review`（价值评审，第一道门）**——一句话复述测试、问题值不值得这么解、产品最小形态检查（派发方式见 `flow/review.md`）。价值审有 must-fix → 按其修复方向重写问题定义或方案主干（通常是「回到最小形态重排主干」「砍伪需求」「补保留行为论证」），修完重过价值审；**价值审通过后才并行派三 reviewer**（`tech-design-review` 主审 + `tech-design-impact-review` 影响面审 + `tech-design-simplicity-review` 简洁审）——不对方向存疑的设计做精致化审查（对抗式审查挑得出方案缺陷，挑不出方向错误）。然后进入**多轮修复循环**，直到全部报告 0 must-fix。真实案例经 4 轮才收敛（机制级 → 规则级 → 计数语义级 → 0），这是正常收敛信号；轮次问题同级或变宽，怀疑修复方向错了，回到该决策的方案对比重做。

### 7.1 每轮修复规则 [MANDATORY]

**循环由 must-fix 驱动：每一轮都必须修复三份报告的全部 must-fix，不留尾巴到下一轮。** 理由：must-fix 是方案或事实级缺陷，累积多轮再修会丢失每条意见的上下文。

**suggestion 逐条处置，处置完即可终止，不为 suggestion 单独驱动循环**（2026-09-19 markdown HTML 支持实测：must-fix 收敛后为清 suggestion 又续 2 轮确认，占收敛期约 1/4 时长）。处置三选一，逐条记录：

| 处置 | 适用判定线 |
|---|---|
| 修复 | 实施**精度歧义 / 边界未声明 / 拆分未同步 / 验收判据不可证伪 / 安全面缺口**——这些不修 = 实施期按歧义实施（文档是实施的 SSOT），实质是 must-fix 级内容，核实时可升级 |
| 登记不修 | 纯表述 / 措辞 / 锦上添花 / 偏好性建议——记一句话理由，进交付汇报 |
| 归档 | 有价值但不属本文档层的意见——记入设计文档相应节的待办或残留风险 |

**按 finding 必填字段分流**（审查报告每条带「影响决策 / 影响交付」两列——处置时先读这两列再选动作）：`影响决策 = 是` → 按方案性意见处理（重跑该决策的方案对比 + 7.2 联动同步清单），不得只改字句；`影响交付 = 规划/开发/测试/验收` 的具体环节 → 修复落点锚定到该环节的载体（规划→§5 拆分与文件地图、开发→§3 机制描述与 file:line、测试→受影响测试族清单、验收→§4 场景与断言、文档登记→ADR/活性文档回写项），修完自检该载体已变；`影响决策 = 否 且 影响交付 = 无` → 登记不修（措辞级），不进修复。

判定存疑（分不清修/登记）时按修复处理——把可修的 suggestion 登记掉是滑坡，反向多修一条的成本可接受。唯一例外：审查方明确标注"不阻塞、随实施带上"且修复成本显著大于当轮收益的项——须在交付汇报中逐条列明未修原因。

修复时按意见类别选动作：

| 意见类别 | 识别信号 | 处理动作 |
|---|---|---|
| **方案性**（推翻决策） | "不用 X，改用 Y"、"这个机制不对" | 重跑该决策的方案对比（新增被指向的候选），过 7.2 联动同步清单 |
| **规格完整性**（缺矩阵/清单/降级） | "没写 X 时怎么办"、must-fix 类缺口 | 补齐对应表格/清单，并检查同类缺口是否还有第二处实例 |
| **格式可读性** | "看不懂"、"分行分 item" | 全文统一改格式（同一模式其他实例一并修） |
| **新需求** | "还要支持 Z" | 走 Step 0 问题定义：确认是同一根本问题还是 scope 变化；scope 扩大回改 §1 目标与 in-scope |

### 7.2 修复纪律（三条，来自真实 4 轮循环的教训）

1. **反例重演后再动笔**：must-fix 附带反例事件序列时，先在修订说明里逐序列重演"修复后行为"，确认反例被消灭。**审查给的修复方向也要重演，不照单全收**——真实案例中审查建议的修复方案（消费点双增）被重演发现仍被同文本场景击穿，改用更稳的方案（单计数确认制）后第 4 轮才真正收敛。
2. **被击穿的方案记入否决记录**：每轮修复若推翻/替换了自己上一版的机制，旧版连同击穿它的反例一起写入该决策的「不采用」栏（格式 `<旧方案> —— <被什么反例推翻>`）。记录让后续轮次的审查者不必重新发现旧坑，也是最终「设计就绪」结论的论证依据。
3. **决策改动后过联动同步清单**（模式性遗漏高发——真实案例连续两轮在拆分清单上复发"正文已改、§5 未同步"的 must-fix）：
   - [ ] 正文该决策（采用/不采用/证据/效果）
   - [ ] 终态数据流图（若画了）
   - [ ] 错误规格表（新边界/新失败路径）
   - [ ] §5 拆分单元表 + 文件改动地图（实施依据，漏同步 = 实施复现已修复的 bug）
   - [ ] §4 验收（新边界是否需要补场景 / 探针降级路径是否受影响）
   - 同类缺口往往不止一处实例——联动修复时扫全文找同模式的其他实例一并修。
4. **修复轮次做语言回归（多轮循环的隐性退化）**：每轮 must-fix 修复都在往正文追加源码锚、否决记录、边界声明——行文密度逐轮上升，实际写作对象从「不懂内部背景的开发者」漂移成「有全部上下文的下一轮审查者」。每轮修复后对新增文本过一遍产物语言自检：流程指令词不直接当产物小节名（写「不采用 X 的理由：若用 X，……」）；为省字数发明的压缩词首次出现必须展开定义，或改用自然句（「保留原 id」「逐项判定」式自然表述优先于任何缩略）——对作者是压缩，对读者是黑话；修复追加宁可句子长一点，不引入读者需要解析的缩略语。

### 7.3 复审派发（聚焦复审，不全面重审）

修订完成后**按 findings 归属送回各自的审查 agent**（价值审的送 `tech-design-value-review`，主审的送 `tech-design-review`，影响面审的送 `tech-design-impact-review`，简洁审的送 `tech-design-simplicity-review`；修订若重写了问题定义/方案主干/最小形态 → 价值审必送；新增/改变了外部接触面或代价声明，或增删了机制/抽象/扩展点，对应维度的报告都送），提示词四要素：

```text
背景：第 N 轮修订完成（文件路径不变）。修订摘要：对照上轮 findings 逐条——
  每条 must-fix/suggestion 怎么修的 + 反例重演结果（上轮反例序列在新机制下的行为）。
聚焦：
  1. 上轮 must-fix 的修复是否成立；新引入的机制能否被新反例击穿
     （给攻击点建议：修订方自己推演时不放心的场景列出来让审查者优先攻击）
  2. 交叉引用一致性终检（联动同步清单五处）
  3. 不重查已确认项
输出：格式同前（Summary + Findings），新发现标注。
```

给攻击点建议是提效关键——修订方最清楚新机制的薄弱处，点名让审查者攻击比让它全面重扫更快触达深层反例。

### 7.4 终止与交付

- **价值审通过且三份 reviewer 报告均 0 must-fix，suggestion 全部处置（修复 / 登记不修 / 归档，见 7.1）= 设计就绪**。不派纯确认轮——must-fix 已清零后不再为复核 suggestion 处置而重审（2026-09-19 实测：此类确认轮零发现，纯消耗）。
- 交付汇报写明：价值审的一句话复述（转述给用户做理解校验）、循环轮数、各报告 must-fix/suggestion 数的收敛轨迹、suggestion 处置清单（修了哪些 / 登记了哪些及理由）、否决记录的最终形态。

## 迁移/重写类设计防复发判据 [MANDATORY]

设计对象是「把既有流程/系统重写或迁移到新形态」（老 skill → 新 skill、老管线 → workflow 化等）时，写作期强制过四判据——起因：一次流程重写设计经三轮审查仍丢 13 条老能力，复盘归因后固化：

1. **老能力逐条映射表**：设计必附「老流程能力 → 新形态落点」逐条映射表（老能力全枚举，逐条标注落点 = 新形态某节 / 显式裁决不迁移含理由；禁止只写新形态有什么）
2. **清单条款附条目文本**：设计写「进 XX 清单/登记表/表」类条款时，必须附该清单的条目文本本身（引用条目名而不给内容 = 两个实现各自发明具体化）
3. **双形态契约字段级 SSOT**：同一机制有手工形态与 workflow 形态两个实现时，共用契约（schema 字段名/路径/终态枚举/数字阈值）设计到字段级并声明唯一权威；两实现各自文字化的漂移由该 SSOT 判错
4. **验收含条款对账**：实现完成的验收 = 设计条款逐条对账（每条至少一次触发验证）+ 冒烟按「条款 × 触发条件」矩阵跑——「编译通过 + 主路径跑通」不构成迁移类设计的完成判据
