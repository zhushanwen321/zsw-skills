# tech-design

教**如何写好可被对抗式审查通过的技术设计文档** + **如何对抗式审查设计文档**。

层无关——无论你在哪一层做设计（需求规格 / 技术方案 / 实现计划），都套同一套方法论；差异只在"解决方案"章节的侧重点（见层适配）。

## 产物路径与决策登记 [MANDATORY]

1. **设计文档本体落 `<项目根>/.tmp/tech-design/<name>.md`**（项目根 = `git rev-parse --show-toplevel`，worktree 解析为各 worktree 根；非 git 仓库落 `/tmp/tech-design/`）——设计文档是 tech-design → dev-flow 的**过程产物，不进项目 docs/、不进 git**（实施落地后的现行设计依据是代码与活性文档；入库设计文档会过期成僵尸文档）。伴生流水线产物（审查报告/探针/impl-plan）同落此目录。完整约定见 `flow/write.md` 产物路径节
2. **重要设计决策必须登记 ADR**：项目存在 ADR 登记处（如 `docs/adr/decisions.md`，路径以项目 AGENTS.md 索引为准）时，设计中拍板的重要决策（机制取舍 / 架构选择 / 行为语义变化）须登记或更新 ADR——设计文档本身可弃，决策必须活在其权威登记处；dev-flow 收尾有 ADR 复审兜底

## 核心红线（11 条，详解见 references/design-principles.md）

1. **[MANDATORY] 问题定义先行**：动笔前先过**前置探明门**——问题已探明（症状/触发条件/复现路径清楚）才有写设计的资格；未探明先做调研（复现实验/日志采集/探针观察），调研产物（复现脚本/采集数据/观察记录）不进设计文档，落 `.tmp/` 留档（例外：探针体系本身复杂到需要设计才可进且独立成章）。然后回答——用户描述的问题是什么？这是不是真正的问题？背后有无隐藏的、用户未明确表达的根本性问题？发现可能有隐藏问题时，**先提问澄清再设计，禁止猜**——用 grill 机制主动向用户提问（grilling 盘问根本问题 / research 查证事实，可多轮追问，操作见 flow/write.md Step 0）。方案必须打到根本问题——只解决表面问题 = 不合格。**前提清单**：设计当作输入而未在本设计中论证的假设（现状行为、外部约束、产品假设）必须集中列出成「本设计默认为真的前提」节，每条标注来源（已核实/需用户裁决）——文档自洽不等于前提成立，前提错了设计整体作废
2. **[MANDATORY] 产品最小形态前置**：动笔 §3 前先回答三层——**第一层（主干）**：这个功能最核心的价值是什么（一句话，以项目产品定义为锚）？达成这个价值的**最少技术投入**是什么形态？§3 方案的主体必须是这个最小形态，不是「修复/优化现状实现」——现状实现不是需求，现状的每个被保留行为都要有「为什么需要」的论证，砍掉是默认候选；**第二层（增量）**：最小形态之上，较少额外投入能换来哪些额外收益——逐项独立裁决（投入/收益/不做会怎样），未论证的增量不得混入主干；**第三层（扩展）**：为未来预留的抽象/扩展点只保留有已发生证据支持的（已有第二个使用方/已发生的变化原因），不为想象未来预付。从最小形态倒推设计，不从现状实现倒推——判别法：从产品核心价值描述这个功能，现状实现的复杂度里有多少天然包含？（详解准则 13）
3. **[MANDATORY] 五段骨架**：背景目标 → 现状与问题分析 → 解决方案（多方案对比）→ 验收 → 下一层拆分，缺一不可
4. **[MANDATORY] 方案对比 ≥2 个**：每个评「长期架构合理性 + 短期实现成本 + 风险」，给明确推荐；风险栏按「P 级基数 + 可逆性 + 新颖度」打 1-10 分，文档头部标注触及的最高 P 级与风险分（锚定项目功能分级登记，打分规则见 `flow/write.md` 前置第 4 条——分数设计期一次产生，dev-flow/审查/验收全链路继承）
5. **[MANDATORY] 使用者视角为主线 + 抽象锚定例子**：受众假设是"会用系统但不懂内部背景的开发者"，关键概念补背景 + 最小例子
6. **[MANDATORY] 自包含 + 结论先行**：每版完整可独立读懂（不写 delta 链）；SCQA 开篇 + 每章首句结论
7. **[MANDATORY] scope = 当前层 → 紧邻下一层**，不跨 2 层设计
8. **[MANDATORY] 全流程坐标系**：涉及运行时/数据流/错误时——文档前部（§1 末或 §2 头）画一张**端到端大流程图**（从源头到终点，用户能看懂的物理视图）；全文每个**问题点**和每个**决策**必须锚定到「大流程的哪个环节」（问题点/决策条目以环节锚定开头，如「环节：widget 推送链 → tick 尾巴」）——读者在任何段落都能定位「现在讨论的是流程里的哪个东西」，禁止脱离流程坐标系的机制名词叙事；运行时断言附探针、每个错误配恢复指引
9. **[MANDATORY] 验收用真实场景**：不是单测、不是 mock，是实施后在真实场景验证功能符合预期；每个场景回溯 §1 目标、用具体业务例子而非抽象断言；小改动可简化，大改动多场景。review 重点审查（见 `review/rubric-design-doc.md` P0-13/14/15，业界依据见 `references/acceptance-practices.md`）。验收章节还须含 **e2e 影响面评估**：列出现有 e2e / 真实进程 / 真实 LLM 测试面中受本次改动影响者，圈定开发阶段需跑的子集（e2e 只在开发阶段按改动面跑、空载执行；PR/merge/CI 门禁不跑 e2e——执行准则 SSOT = 项目 AGENTS.md 测试节；自动化回归的长期方向 = e2e 逐步单测化，可 mock/fixture 重放等价覆盖的圈定项应标注定单测化路径）
10. **[MANDATORY] 陈述四分类，推断必核实 + 绝对化断言禁令**：关键陈述区分事实（已核实）/ 推断（未核实）/ 知识（通用领域认知，影响决策时视同推断）/ 决策（人为拍板的选择），推断核实后才写为依据，核实不了的标注「未核实」；核实优先代码逻辑推演，确需跑代码时用独立局部临时代码（与项目无关、只复现局部场景，核实后删除）——见准则 7。**绝对化断言禁令**：「做不到 / 帮不上忙 / 不行 / 没有 X」类断言一律改写为取舍表（可行形态 + 代价 + 何时值得何时不值得）——断言的正确部分与边界部分分开写；把「有取舍」压成「一个不字」会迫使读者追问多轮才能拿到真实边界
11. **[MANDATORY] 直接解决优先（设计决策序）**：写 §3 前依次过——①定级：独立/偶发 → 按独立问题直接修；多个同类症状/高频发生，或根因落在共享路径 → 架构级问题。②路线：「直接解决 vs 架构优化」显式进方案对比，不允许隐式选择；架构路径可分期但每期主体必须是直接解决。③直接解决：方案落在病因环节（修数据流/契约/状态模型，或架构重设计使病症构造性消失）；掩盖问题类（兜底 catch 吞掉/降级遮蔽、自愈、轮询对账）禁止作为方案主体——判别法：删掉补偿机制，病因还在 = 不合格。④非功能后置：直接解决完成后才评估，必要性三问（日常高频已覆盖？极端场景？破坏性×概率×不可检测性）→ 三档裁决（不做——验收证高频覆盖 / 简单——暴露问题类 fail-fast·日志优先，掩盖问题类兜底须「极端情况+正常路径已根治+触发可观测」/ 复杂——须证复杂度<事故代价并写升档条件），档位连验收。暴露问题类（fail-fast、日志）是诊断能力属直接解决，不受此限——详解准则 12

> 这 11 条是写作时的红线。完整 14 条准则见 `references/design-principles.md`。

## 层适配（每一层都能用）

本 skill 不绑定任何特定的"层"概念（如 cw 的 epic/feature/slice/wave）。五段骨架任何层通用，差异只在 §3「解决方案」和 §4「验收」的侧重点——按**本次设计的下一层产物性质**调节：

| 下一层产物 | §3 解决方案重点 | §4 验收重点 | 层敏感准则(5/6/7) |
|---|---|---|---|
| 子目标/子系统 | 划分边界、依赖、优先级 | 子系统协同达成目标、边界契约真实场景成立 | 弱适用 |
| 可验收的需求集合 | 问题陈述、out-of-scope | 需求达成后真实场景验证（非单测） | 弱适用 |
| 可实现的接口/数据模型/技术方案 | 接口先行、数据模型、错误规格、选型对比、物理数据流 | 真实环境跑通关键路径（非 mock 集成） | **全适用（最严格）** |
| 具体测试用例 + 代码任务 | TDD、任务拆分、文件清单、运行时断言探针 | 端到端真实流程验证、断言探针实跑 | 全适用 |

完整调节表见 `references/doc-structure.md` 末尾。判断方法：问自己"本次设计的下一层产物是什么"，映射到上表。

## 审查：价值评审先行 + 三 reviewer 并行

审查分两阶段。**第一道门（价值评审）**：`tech-design-value-review` 先行——一句话复述测试、问题值不值得这么解、产品最小形态检查。价值审有 must-fix → **打回重写（通常是问题定义或方案主干），不派三 reviewer**（避免对错误方向做精致化审查——对抗式审查能挑出方案缺陷，挑不出方向错误，精致化反而延缓推翻）。价值审通过 → **第二阶段三 reviewer 并行**（agent 文件都在 `agents/`）：

- **`tech-design-review`（主审）**：对抗式审查者——默认怀疑方案不成立，专注：① 逼方案自证（找反例/攻击面）② 回溯"目标→方案"因果链是否真达成 ③ 核实关键事实 ④ 验收章节是否真实场景验证（非单测非 mock）
- **`tech-design-impact-review`（影响面审）**：影响面枚举者——专注副作用/遗漏：改动辐射到哪些其他功能与系统面（代码面/数据面/宿主外部系统面/用户工作流面），每个面的影响是否被量化、被显式判定可接受、有无清理或恢复通道（rubric P0-12/19/20）
- **`tech-design-simplicity-review`（简洁审）**：过度设计守门员——专注机制必要性：§3 每个机制/抽象/扩展点是 §1/§2 已发生证据逼出来的，还是为想象未来预付的复杂度；语义四问（Parnas/认知压缩/Rule of Three/反模式清单）+ 砍建议必须三段论证（小取舍/大简化/核心价值不变的判据），误报控制靠「已核实非过度」节（rubric P0-22/23、P1-6）

审查与修复分离：所有 agent 都只报告 must-fix/suggestion，不代改文档；主 agent 拿到报告后按 `flow/write.md` Step 7 的审查-修复循环处理（循环由 must-fix 驱动——每轮全修 must-fix 循环复审至 0；suggestion 逐条处置后即终止，不为它派确认轮）。
