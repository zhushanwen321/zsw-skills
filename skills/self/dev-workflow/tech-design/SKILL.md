# tech-design

教**如何写好可被对抗式审查通过的技术设计文档** + **如何对抗式审查设计文档**。

层无关——无论你在哪一层做设计（需求规格 / 技术方案 / 实现计划），都套同一套方法论；差异只在"解决方案"章节的侧重点（见层适配）。

## 核心红线（9 条，详解见 references/design-principles.md）

1. **[MANDATORY] 问题定义先行**：动笔前先回答——用户描述的问题是什么？这是不是真正的问题？背后有无隐藏的、用户未明确表达的根本性问题？发现可能有隐藏问题时，**先提问澄清再设计，禁止猜**——用 grill 机制主动向用户提问（grilling 盘问根本问题 / research 查证事实，可多轮追问，操作见 flow/write.md Step 0）。方案必须打到根本问题——只解决表面问题 = 不合格
2. **[MANDATORY] 五段骨架**：背景目标 → 现状与问题分析 → 解决方案（多方案对比）→ 验收 → 下一层拆分，缺一不可
3. **[MANDATORY] 方案对比 ≥2 个**：每个评「长期架构合理性 + 短期实现成本 + 风险」，给明确推荐；风险栏按「P 级基数 + 可逆性 + 新颖度」打 1-10 分，文档头部标注触及的最高 P 级与风险分（锚定项目功能分级登记，打分规则见 `flow/write.md` 前置第 4 条——分数设计期一次产生，dev-flow/审查/验收全链路继承）
4. **[MANDATORY] 使用者视角为主线 + 抽象锚定例子**：受众假设是"会用系统但不懂内部背景的开发者"，关键概念补背景 + 最小例子
5. **[MANDATORY] 自包含 + 结论先行**：每版完整可独立读懂（不写 delta 链）；SCQA 开篇 + 每章首句结论
6. **[MANDATORY] scope = 当前层 → 紧邻下一层**，不跨 2 层设计
7. **[MANDATORY] 验收用真实场景**：不是单测、不是 mock，是实施后在真实场景验证功能符合预期；每个场景回溯 §1 目标、用具体业务例子而非抽象断言；小改动可简化，大改动多场景。review 重点审查（见 `review/rubric-design-doc.md` P0-13/14/15，业界依据见 `references/acceptance-practices.md`）。验收章节还须含 **e2e 影响面评估**：列出现有 e2e / 真实进程 / 真实 LLM 测试面中受本次改动影响者，圈定开发阶段需跑的子集（e2e 只在开发阶段按改动面跑、空载执行；PR/merge/CI 门禁不跑 e2e——执行准则 SSOT = 项目 AGENTS.md 测试节；自动化回归的长期方向 = e2e 逐步单测化，可 mock/fixture 重放等价覆盖的圈定项应标注定单测化路径）
8. **[MANDATORY] 涉及运行时/数据流/错误时**：运行时断言附探针、画物理数据流图、每个错误配恢复指引
9. **[MANDATORY] 陈述四分类，推断必核实**：关键陈述区分事实（已核实）/ 推断（未核实）/ 知识（通用领域认知，影响决策时视同推断）/ 决策（人为拍板），推断核实后才写为依据，核实不了的标注「未核实」；核实优先代码逻辑推演，确需跑代码时用独立局部临时代码（与项目无关、只复现局部场景，核实后删除）——见准则 7

> 这 9 条是写作时的红线。完整 12 条准则见 `references/design-principles.md`。

## 层适配（每一层都能用）

本 skill 不绑定任何特定的"层"概念（如 cw 的 epic/feature/slice/wave）。五段骨架任何层通用，差异只在 §3「解决方案」和 §4「验收」的侧重点——按**本次设计的下一层产物性质**调节：

| 下一层产物 | §3 解决方案重点 | §4 验收重点 | 层敏感准则(5/6/7) |
|---|---|---|---|
| 子目标/子系统 | 划分边界、依赖、优先级 | 子系统协同达成目标、边界契约真实场景成立 | 弱适用 |
| 可验收的需求集合 | 问题陈述、out-of-scope | 需求达成后真实场景验证（非单测） | 弱适用 |
| 可实现的接口/数据模型/技术方案 | 接口先行、数据模型、错误规格、选型对比、物理数据流 | 真实环境跑通关键路径（非 mock 集成） | **全适用（最严格）** |
| 具体测试用例 + 代码任务 | TDD、任务拆分、文件清单、运行时断言探针 | 端到端真实流程验证、断言探针实跑 | 全适用 |

完整调节表见 `references/doc-structure.md` 末尾。判断方法：问自己"本次设计的下一层产物是什么"，映射到上表。

## 审查：三 reviewer 并行

审查设计文档时**并行派三个 subagent**（agent 文件都在 `agents/`）：

- **`tech-design-review`（主审）**：对抗式审查者——默认怀疑方案不成立，专注：① 逼方案自证（找反例/攻击面）② 回溯"目标→方案"因果链是否真达成 ③ 核实关键事实 ④ 验收章节是否真实场景验证（非单测非 mock）
- **`tech-design-impact-review`（影响面审）**：影响面枚举者——专注副作用/遗漏：改动辐射到哪些其他功能与系统面（代码面/数据面/宿主外部系统面/用户工作流面），每个面的影响是否被量化、被显式判定可接受、有无清理或恢复通道（rubric P0-12/19/20）
- **`tech-design-simplicity-review`（简洁审）**：过度设计守门员——专注机制必要性：§3 每个机制/抽象/扩展点是 §1/§2 已发生证据逼出来的，还是为想象未来预付的复杂度；语义四问（Parnas/认知压缩/Rule of Three/反模式清单）+ 砍建议必须三段论证（小取舍/大简化/核心无损锚），误报控制靠「已核实非过度」节（rubric P0-22/23、P1-6）

审查与修复分离：三个 agent 都只报告 must-fix/suggestion，不代改文档；主 agent 拿到三份报告后按 `flow/write.md` Step 7 的审查-修复循环处理（循环由 must-fix 驱动——每轮全修 must-fix 循环复审至 0；suggestion 逐条处置后即终止，不为它派确认轮）。
