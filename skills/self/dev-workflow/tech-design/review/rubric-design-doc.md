# 设计文档审查清单（对抗式）

> **本清单是 `tech-design-review`（主审）、`tech-design-impact-review`（影响面审）、`tech-design-simplicity-review`（简洁审）三个 agent 的共同审查依据，分工见下。** 基调是**对抗式**——默认怀疑方案不成立，除非被证据说服。每一项都要主动找反例、攻击面，逼方案自证。
>
> **为什么必须对抗式**：设计文档最贵的错误（运行时断言靠推理、方案不解决根因、关键事实编造）在中立审查下会蒙混过关。本清单的全部检查项，都来自真实案例里被对抗审查（多轮独立攻击 + 实测）才逼出来的问题。中立 = 放过 = 实施期翻车。
>
> 原则编号对应 `design-principles.md`；结构标准对应 `doc-structure.md`；反例对照 `anti-patterns.md`。

---

## 审查纪律

1. **默认怀疑**：拿到文档先假设"这方案有问题"，逐项找证据反驳自己，反驳不了才放行
2. **事实必须验证 + 火力聚焦**：声称"事实错误/API 不存在"前，必须 `read` 源码核实，不得臆断。只报影响核心决策的问题——核心决策是否成立、决策依赖的事实证据是否真实、表达是否妨碍读者理解决策。编号/序号错乱、行号偏移、笔误、格式措辞等**不改变语义的机械性细节不报**：不进 Findings 表、不计数；确有现成证据时至多报告末尾一句话 INFO 带过。不平均用力
3. **只报告不修复**：发现问题给修复方向，不代写方案
4. **每个判定有依据**：引用具体准则编号 + 文档位置（章节号/行号），不凭感觉

---

## 审查分工（价值评审先行 + 三 reviewer 分工）

审查分两阶段：**第一道门 = 价值评审**（`tech-design-value-review`，方向级——must-fix 打回重写，不派三 reviewer）；通过后三个独立 agent **并行**执行深审，本清单按分工划分，各自只判自己的条目：

| reviewer | 负责检查项 |
|---|---|
| **价值审**（`tech-design-value-review`，先行门） | P0-V1 ~ P0-V3 |
| **主审**（`tech-design-review`） | P0-1 ~ P0-11、P0-13 ~ P0-18、P0-21、全部 P1（除 P1-6） |
| **影响面审**（`tech-design-impact-review`） | P0-12、P0-19、P0-20 |
| **简洁审**（`tech-design-simplicity-review`） | P0-22、P0-23、P1-6 |

价值审通过后同一文档产出三份报告，修复时合并处理（见 `flow/write.md` Step 7）。任何一方发现他方职责范围的线索时，标 INFO 交接，不重复判定。

## P0-V 价值评审（第一道门，must-fix = 方向级打回）

> 审的是「方案值不值得做、做的是不是这个量级」——三 reviewer 再严也审不出「不该这么做」。价值审 must-fix 的修复方向通常是「回到最小形态重排主干」「砍伪需求」「补保留行为论证」，不是局部修补。

### V1 一句话复述测试

| # | 检查项 | 怎么查 | 准则 |
|---|---|---|---|
| P0-V1 | **一句话复述测试不通过** | 审查者用自己的话把设计复述成一句外行能懂的话（复述本身写入报告）。复述不出来（机制名词堆砌、一句话装不下）/ 复述很复杂（「以及/同时/再加上」超过一次 = 多目标耦合或核心机制数超标）/ 复述含机制黑话（外行听不懂的自造词/协议名 = 文档缺物理流程坐标系）→ 不通过 | 5/13 |

### V2 问题值不值得这么解

| # | 检查项 | 怎么查 | 准则 |
|---|---|---|---|
| P0-V2a | **现状保留行为未论证** | §2 描述的现状中被 §3 保留并兼容的每个行为，文档是否论证过「为什么需要」？逐个列未论证项，问「砍掉用户失去什么」——答不出实际损失 = 候选砍除项 | 13 |
| P0-V2b | **伪需求** | 方案复杂度是否在服务一个由现状实现引入、而非产品本质需要的行为？判别法：从产品核心价值出发描述这个功能，是否天然包含该行为——不包含 = 伪需求 | 13 |
| P0-V2c | **求解量级与问题不匹配** | 问题的破坏面/频率/用户感知，与方案的机制量级是否匹配（小问题配大机制 / 大问题配小补丁均不通过） | 12 |

### V3 产品最小形态

| # | 检查项 | 怎么查 | 准则 |
|---|---|---|---|
| P0-V3a | **最小形态未显式作答或不是主干** | 文档必须显式回答三层——①核心价值（一句话，锚项目产品定义）+ 最少技术投入形态 = §3 主干；②增量收益逐项独立裁决（投入/收益/不做会怎样），未论证的增量混入主干 = 不通过；③扩展点只保留有已发生证据支持的（第二使用方/已发生变化原因），为想象未来预留 = 不通过 | 13 |
| P0-V3b | **前提清单缺失** | §2 末尾必须有「本设计默认为真的前提」节——设计当作输入而未论证的假设（现状行为/外部约束/产品假设）逐条列出（来源 + 若不成立的影响）；缺失 = 文档自洽但前提不可攻击 = 不通过 | 0 |

## P0 致命（must_fix）—— 不修不能实施

### 结构与可读性

| # | 检查项 | 怎么查 | 准则 |
|---|---|---|---|
| P0-1 | **五段骨架缺失任一段**（背景目标/现状问题/解决方案/验收/下一层拆分） | 对照 `doc-structure.md` 五段，任一段缺失或不完整 | 结构 |
| P0-2 | **delta 链引用** | grep 正文有无「vN」「Rxx-finding」「参见上版」「变更摘要」 | 1 |
| P0-3 | **结论不先行** | 抽查 3 个章节，首句是否该章结论；标题下有无一句话结论；有无 SCQA 开篇 | 2 |

### 内容主线

| # | 检查项 | 怎么查 | 准则 |
|---|---|---|---|
| P0-4 | **问题定义错误或现状未触根因** | §1 定义的问题是否忠于用户的真实问题（还是只复述表面现象/用户给的方案）？有无隐藏的、未表达的根本问题未被识别？§2 是否只有表象（"体验差"）没挖根因；是否有真实例子。**显式形态——调研混进设计**（准则 0 探明门）：文档主体是探明问题的手段（加日志观察 / 加探针复现 / 先收集数据再定方案的步骤）= 问题未探明就写设计，设计不成熟——例外仅限探针体系本身复杂到需要设计且独立成章 | 0/结构§2 |
| P0-5 | **重实现轻体验** | §2/§3 是否上来就讲"哪个文件哪个函数"，缺使用者视角例子 | 3 |
| P0-6 | **抽象术语无定义/无例子** | 抽全文抽象词（元数据/契约/中间件…），首次出现有无定义+绑例子 | 4 |

### 方案对比（对抗式重点）

| # | 检查项 | 怎么查 | 准则 |
|---|---|---|---|
| P0-7 | **无方案对比或仅 1 方案** | §3.2 是否 ≥2 方案 | 9 |
| P0-8 | **对比缺长期架构评估或缺短期成本评估** | 每方案是否两维度都评 | 9 |
| P0-9 | **无明确推荐** | 对比后是否给出"选哪个+为什么" | 9 |

### 对抗式核心三问（最重要）

| # | 检查项 | 怎么查 | 准则 |
|---|---|---|---|
| P0-10 | **方案是否真正解决目标问题** | 回溯 §1 问题定义 → §3 方案的因果链：方案实现了，问题真的解决吗？解决的是根因还是表象？只让症状消失、根因还在 = 不通过。**三种显式形态**（准则 12 设计决策序）：①**兜底替代根治**——§2 病症/根因明确，方案主体是掩盖问题类（catch 吞掉/降级遮蔽/重试自愈/轮询对账/缓存遮蔽），判别法：删掉补偿机制病因仍在；②**架构级问题逐个打补丁**——§2 显示多症状共点或根因在共享路径，§3 却只修单症状不在架构层做统一修复，「直接解决 vs 架构优化」决策未显式进方案对比；③**非功能设计无必要性论证**——掩盖问题类机制未回答「日常高频是否已覆盖、极端场景破坏性×概率×可检测性」、未过三档裁决（不做/简单/复杂）就上强自愈/强兜底/对账；复杂档未证「复杂度<事故代价」、未写升档条件。回收层兜底豁免条件（三者齐备）：极端情况而非正常路径 + 正常路径已根治 + 触发可观测 | 0/12/对抗 |
| P0-11 | **影响决策的关键事实错误** | 文档引用的 API/字段名/类型/方案成立依赖的事实，`read` 源码逐一核实；错误**影响决策或架构** → P0；行号偏移/编号序号等不影响决策的机械性细节 → 不报（审查纪律 2）。**含外部 API 时序/返回形态**（可 await、fire-and-forget、超时行为）——只看函数名不读实装签名 = 命中此项 | 对抗 |
| P0-12 | **是否有副作用/遗漏** | 改 A 是否影响 B？有无遗漏连带改动（schema 变了没提 migration）？边界场景/迁移/向后兼容是否覆盖？**接管/替换既有流程的决策**：read 被接管的原实现，逐段核对"接管点之后的内部步骤"是否被静默绕过且接管方未复刻/未声明放弃（入口复用 ≠ 全程复用）。涉及外部共享状态写入时联动 P0-19 | 对抗 |

### 影响面（影响面审专查）

| # | 检查项 | 怎么查 | 准则 |
|---|---|---|---|
| P0-19 | **共享/宿主状态写入的投影面未分析**（层敏感：设计写入项目不拥有的持久状态时触发——宿主 DB / GUI 状态 / OS 全局状态 / 第三方服务） | 先 ⓪**穷举全部写入面**：方案每次运行/操作对外部系统的所有落盘/落库/发请求点（主存储、日志、临时产物、统计/遥测表、缓存——真实跑一遍后 diff 文件系统与宿主各表增量来兜底，不靠想象列举）；再逐面枚举：①消费方及其过滤/投影规则（谁读这些写入、按什么条件展示——从对方源码/文档核实，非推测）；②写入速率与是否单调累积；③清理/归档/删除通道是否存在（无 = 显式登记风险）；④对方 schema/接口中控制可见性/归类/生命周期的字段（全量枚举，非最小可用集） | 对抗 |
| P0-20 | **「已接受代价」未量化** | grep 全文「已接受/已知代价/权衡/可控」逐条核对四要素：**量级**（多少次/多大体积/多高速率）、**恢复路径**（代价兑现后怎么回来、通道是否存在）、**重审触发条件**（到什么程度不再可接受）、**显式判定**（可接受/不可接受 + 依据）。一句话接受代价 = 未评估 = 不通过 | 9/对抗 |

### 验收（重点审查）

| # | 检查项 | 怎么查 | 准则 |
|---|---|---|---|
| P0-13 | **无验收章节 / 验收不可测试** | §4 是否存在验收章节；验收场景是否 testable（有明确通过标准、可在真实环境执行）；是否每个场景回溯 §1 业务目标。无 testable 验收 = 设计未就绪（DoR） | 11/结构§4 |
| P0-14 | **验收=单测或 mock / 抽象断言** | 验收是否只写"单元测试通过/覆盖率"，或用 mock/桩替代真实依赖；或用抽象断言（功能正常/响应快）而非具体业务例子；验收不回答"真实工作里好用吗" | 11 |
| P0-15 | **验收投入与改动大小不匹配** | 大改动（新功能/行为变更/接口调整）验收是否只一句话敷衍；小改动可简化但不等于没有 | 11 |
| P0-21 | **验收缺宿主/邻居系统不变量场景**（层敏感：方案写入或挂接外部共享系统时触发——对照 P0-19 的接触面） | §4 场景集是否含至少一个「宿主/邻居系统既有表面不被改变」的反向场景（例：实施 N 次后重启宿主，列表/索引/存储无异常残留、无写入堆积）；只验「我的功能工作」不验「宿主表面不变」= 不通过 | 11 |

### 层敏感（仅当设计涉及运行时/数据流/错误时）

| # | 检查项 | 怎么查 | 准则 |
|---|---|---|---|
| P0-16 | **运行时断言无探针** | 找"会自清理/在X之前/不丢类型/高命中"等断言，是否附探针（✅/⛔）；无探针 = 不诚实。**⛔ 实施期门探针无降级路径**（失败时方案怎么调整没写）= 单点依赖，同样不通过 | 7 |
| P0-17 | **涉及数据流但没画物理数据流图** | §2/§3 若有"A 读取 B"，B 物理位置是否标出 | 5 |
| P0-18 | **错误无恢复指引** | 每个失败场景是否配具体恢复动作（不是"请检查"） | 6 |

### 简洁性（简洁审专查）

| # | 检查项 | 怎么查 | 准则 |
|---|---|---|---|
| P0-22 | **投机通用性：机制无已发生证据支撑** | 抽 §3 每个新机制（抽象层/组件/配置项/扩展点/保证机制）问四问①③④：它赌的设计决策是什么、会真变吗？§1/§2 有无**已观察到的第 2-3 个真实变体/需求方**？答不出具体决策、或依据是想象未来（「以后可能要」「顺便做通用」）= 不通过。对照设计版反模式清单：second-system / inner-platform / pass-through / leaky abstraction / abstraction inversion / Greenspun（清单全文见 `agents/tech-design-simplicity-review.md`，判定须引用 §1/§2 原文位置） | 8 |
| P0-23 | **概念数净增：间接成本超过认知压缩** | 四问②：新机制让读者多理解的**独立概念数** vs 它压缩掉的复杂度。接口复杂度≈实现复杂度（浅模块）、引入派生态/执行顺序依赖/纯胶水而未消除本质状态、调用方被迫穿越用不到的层 = 不通过。注意反向同样成立：复杂度高但四问通过的机制是本质复杂度，**不判**（进简洁审「已核实非过度」节） | 8 |

## 判定四态

对每个检查项，输出下列四态之一（必须有依据）：

| 判定 | 含义 | 何时用 |
|---|---|---|
| **通过** | 该项达标 | 需引用文档里达标的证据位置 |
| **不通过** | 该项违反，必须修 | 需解释违反点 + 引用对应准则 + 指出导致的失败模式 |
| **可能不完整** | 存疑，证据不足以判定 | 列出还需要什么信息才能定论 |
| **不适用** | 本项不适用于本次设计类型 | 说明为什么（如层敏感准则对纯需求规格不适用） |

**核心纪律**：不凭感觉。每个"不通过"都要能指向具体准则 + 失败模式（对照 `anti-patterns.md` 的 3 病根：认知懒惰/视角错位/结构失序）。

## 审查输出格式

```markdown
## Summary
<must-fix 数量> must-fix, <suggestion 数量> suggestions.

## Findings

| 优先级 | 位置 | 维度 | 描述 | 修复方向 |
|--------|------|------|------|----------|
| MUST_FIX | §3.2 | P0-10 对抗 | 方案只解决表象，未触及§2根因 | 重新设计要打到根因层 |
| MUST_FIX | §3.3 | P0-11 事实 | 引用的 API 签名与源码不符，方案成立依赖该 API 的行为 | read 源核准后修正或改方案 |
| SUGGESTION | §4 | P1-2 | 拆分无 justification | 每项补"为什么这么拆" |
```

并附 structured-output JSON：`{ "report_file": "<路径>", "must_fix": <数>, "suggestion": <数> }`
