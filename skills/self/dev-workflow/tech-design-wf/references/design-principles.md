# 技术设计文档写作原则

> **本文件是 tech-design skill 的方法论主干。** 共 13 条准则——问题定义先行（0）+ 4 条通用（1-4）+ 3 条层敏感（5-7）+ 减法优先（8）+ 4 条本 skill 专属（9-12），每条配「为什么 / 怎么做 / ✅❌」+ 正例片段。正反例均取自一次真实重构设计文档的 4 版迭代——初稿犯了所有典型错误，经多轮对抗审查修正后归纳出这些准则。

## 怎么用本文件

- **写之前**：通读一遍，建立"好设计文档长什么样"的判断
- **写作中卡壳**：查对应准则
- **写完自检**：用文末「写前自检清单」
- **被审查翻车**：对照 `anti-patterns.md` 找同类反例

## 准则 0：问题定义先行（最优先，先于一切写作）

**为什么**：设计文档最贵的错误不是方案写得差，而是**解决了一个不是问题的问题**。用户描述的现象往往只是症状（"命令太慢"），背后藏着未表达的根本问题（"每次都全量重算"→ 根因是缓存策略错误）。动笔就写方案，等于把"用户说的是什么"当成了"用户真正需要什么"。审查能挑出方案缺陷，但挑不出"问题定义错了"——文档自己定义的问题看起来总是自洽的。问题定义错了，五段骨架写得再好也是白费。

**怎么做**：
- ✅ **问题定义的资格 = 问题已探明**：症状、触发条件、复现路径三者清楚才动笔写设计。未探明（「还不清楚为什么会这样」「先加日志看看」）→ 先做调研（复现实验 / 日志采集 / 探针观察），探明后回来写设计——**调研是前置步骤，其产物（复现脚本、采集数据、观察记录）不进设计文档**，落 `.tmp/` 留档即可。例外：探针体系本身复杂到需要设计（超大项目的采样管道、埋点架构）才可进文档，且独立成章并论证其复杂度
- ✅ 动笔前先回答三问：① 用户描述的问题是什么？② 这是不是真正的问题（现象 vs 症状）？③ 背后有无隐藏的、未明确表达的根本性问题？
- ✅ 怀疑有隐藏问题 → **先提问澄清再设计**（禁止猜）：用 grill 机制主动向用户提问（见下），等答案再动笔

> **grill 机制（主动提问澄清，完全自包含）**：向用户提问时遵循——
> - 提问聚焦"根本问题是什么"：问"你最终要解决 A 还是 B"，不问"配置项放哪个文件"
> - grilling（盘问式）：追问"你真正要解决的是什么"，挖用户没明确表达的根本问题
> - research（调研式）：查证事实性信息（现状、约束、数据来源等）
> - 可多轮追问：一次问不完就分多次追问，每轮拿到答案再继续
> - 有未答疑点不带入设计——直到问题定义收敛再动笔
- ✅ **前提清单**：设计当作输入而未在本设计中论证的假设（现状行为、外部约束、产品假设）集中列出成「本设计默认为真的前提」节（§2 末尾），每条标注来源（✅ 已核实代码 / ⏳ 需用户裁决）与「若不成立的影响」——文档自洽不等于前提成立，前提错了设计整体作废；清单让读者与价值审查者可逐一攻击
- ✅ 写方案前最后自问：这个方案打到根因，还是只让症状消失？
- ✅ 问题定义写进文档 §1（SCQA 的 Q 就是定义后的问题），让 reviewer 可回溯验证
- ❌ 把用户给的方案当成问题（"用户要加个 X 配置"——真问题是"Y 场景下 Z 做不了"，X 只是用户猜的一个解法）
- ❌ 带着未答的问题往下写设计（"先按猜的写，有问题再说"）
- ❌ 方案只解决表面问题（加 try-catch 吞掉报错，根因数据模型错误还在）
- ❌ 把探明问题的手段写成设计内容（"第一步加日志观察，第二步根据观察结果定方案"）——这是调研计划不是设计；问题没探明就写不出方案，回前置调研

> **反例**：用户报"agent 生成的文档没人能读懂"。直接设计"格式化排版、加目录"是解决表面问题；提问澄清后才发现真问题是"文档是 delta 链，没参与讨论的人缺上下文"，方案变成"自包含 + 结论先行"——与最初设想的方案完全不同。

## 一、通用准则（任何设计文档都必须遵守）

这 4 条与设计类型无关——无论你在写需求规格、技术方案还是实现计划，都要遵守。

### 准则 1：自包含，不写 delta 链

**为什么**：设计文档会被没参与迭代的人读——新成员、未来的你、reviewer。写成「v5 = v4 + 变更」、正文引用前序版本或审查编号（「R7-finding」「参见 v2 §4」），对没上下文的人是天书。

**怎么做**：
- ✅ 每一版是完整自包含文档：问题 → 分析 → 方案 → 决策 → 实施，从头读到尾能懂
- ✅ 变更历史 / 审查溯源降级为**附录**（一句话各版本），不占正文
- ❌ 正文出现「v3 §4.2.1 主张被推翻」「上一轮审查发现」「参见 v2」
- ❌ §0 是「这版改了啥」的变更摘要表

### 准则 2：金字塔原理——结论先行 + SCQA 开篇

**为什么**：读者最想先知道「结论是什么」，再决定要不要深读支撑。证据先行让人读到细节还不知道你要说啥。

**怎么做**：
- ✅ 标题下放**一句话结论**（全文 governing thought）
- ✅ 开篇 **SCQA**：情境(S) / 冲突(C) / 问题(Q) / 答案(A) 四段，一段一句
- ✅ **每章第一句是该章结论**（加粗），再给支撑证据
- ✅ 归类分组 **MECE**（如失败模式分 A/B/C、决策逐条、风险成表）
- ❌ 章节以「先看证据」开头，结论埋在末尾或没有
- ❌ 大段辩解性 prose 代替结论句

> **正例片段**（SCQA 开篇）：
> ```
> - S（情境）：系统给 agent 提供 workflow 和 subagent，核心是「资源暴露」。
> - C（冲突）：现状资源暴露既不准也不全——agent 靠猜用法频繁出错，维护改一处要同步三处。
> - Q（问题）：怎么做到「看得全、用得对、传错立刻知道怎么改、维护只动一处」？
> - A（答案）：元数据驱动 + 发现/契约分离 + 单一校验。本文展开这个答案。
> ```
> 四句话，读者立刻知道全文要解决什么、答案是什么。

### 准则 3：使用者视角为主线，例子先行

**为什么**：实现机制（改哪个文件/函数）是给已懂系统的人看的。不了解项目的人要先看到「用户/agent 实际看到什么、怎么做、出错时怎样」，才能理解「所以我们要这么改」。只写构建者视角（代码怎么改）是设计文档最常见的反模式。

**怎么做**：
- ✅ **现状章**：放真实的系统提示词 / 输入输出 / 界面片段（**取自代码，不编造**）+ 真实失败模式
- ✅ **终态章**：放完整交互对话样例（用户说什么 → 系统返回什么 → 下一步怎么做）
- ✅ 实现机制章放在使用者视角**之后**，作为「怎么把行为设计落地」的支撑
- ❌ 上来就是「`config-loader.ts` 的 `toCachedMeta` 改整对象透传」
- ❌ 只写构建者视角，漏了使用者「能不能完成目标」

这与本 skill 的**受众假设**一致：假设读者会用该系统但不懂内部背景，必须先让他看到"长什么样、怎么用"，再讲"怎么改"。

> **正例片段**（终态章的完整成功路径，使用者视角）：
> ```
> [用户] 帮我对 src/auth.ts 做多轮 review，发现问题就修，直到干净
> [agent 读注入段] → review-fix-loop 的 when 匹配
> [agent 调用] workflow info review-fix-loop
> [工具返回] { name, description, parameters: {...JSON Schema}, parametersFriendly: [...], usage: "..." }
> [agent 据参数构造 args]
> [agent 调用] {"action":"run","name":"review-fix-loop","args":{...}}
> [工具返回] Started workflow ... do NOT poll status.
> ```
> 读者无需懂代码就能看懂"改造后 agent 怎么成功完成一次调用"。

### 准则 4：抽象术语锚定具体例子

**为什么**：抽象词（元数据、资源、契约、SSOT、中间件、pipeline）对不了解项目的人是无意义的音节。必须首次出现就定义 + 绑到已展示的例子，否则读者读到 §6 还不知道 §2 提的概念长什么样。

**怎么做**：
- ✅ 术语首次出现：**明确定义 + 「就是 §X 例子里那个 Y」**
- ✅ 后续章节（决策/机制/格式/探针/阶段）每个都标注「影响 / 产出 / 验证 §X 例子里的哪部分」
- ✅ 不采用的方案说明「**若用它，§X 的例子会变成什么样**」（让取舍可感知）
- ✅ **自造压缩词纪律**：不把流程指令词（「被否说明」）、审查行话或为省字数发明的缩略词（「保号」「过堂」类）直接写进产物——产物用自然中文（「不采用 X 的理由」「保留原 id」「逐项判定」）；确需保留的领域原词（源自代码注释，如「宁合不裂」）首次出现时展开定义——对作者是压缩，对读者是黑话（与准则 5 对机制名词叙事的判定同族）
- ❌ 抽象术语反复使用却从不绑定例子
- ❌ §6 之后抽象论述与 §2/§5 例子脱节

> **正例片段**（术语定义 + 物理位置 + 数据流，三者绑定）：
> ```
> 元数据 = 资源的自我介绍（name/description/when/parameters/usage）。
> 物理上声明在每个资源文件顶部：workflow 是 .js 的块注释，agent 是 .md 的 frontmatter。
>
> 磁盘 [.js 顶部 @pi-meta 块] → extension 读取解析 → 每 turn 注入路由段 / agent 调 info 时返回完整契约
>
> 关键：workflow info 不是凭空知道参数的——它就是去读那个 .js 文件、抽出顶部注释块、
> 解析出来的。元数据只有一个源头，两条读取路径都指向它。
> ```
> 「元数据」这个抽象词，被定义 + 被钉到物理位置 + 被画进数据流，读者再也不会迷糊。

## 二、层敏感准则（涉及运行时 / 数据流 / 错误的设计才适用）

**先判断**：本次设计是否涉及「数据怎么流转 / 错误怎么处理 / 运行时行为断言」？
- **是**（如系统重构、技术方案、接口设计）→ 下面 3 条全部适用，且是 P0
- **否**（如纯需求规格、纯架构划分）→ 可跳过，但准则 1-4 仍必须遵守

具体哪些设计层适用哪些准则，见 `doc-structure.md` 的「层敏感侧重点调节表」。

### 准则 5：全流程坐标系——大流程图 + 问题点/决策锚定

**为什么**：「A 读取 B」这类描述如果不展示 B 物理上在哪（哪个文件、什么位置）、A 怎么找到它，读者串不起「数据从哪来、到哪去」。更进一步：设计文档描述的每个问题点、拍板的每个决策，如果不在一条可定位的流程上，读者（包括未来的实施者）就无法知道「现在讨论的是哪个东西」——机制名词叙事（「指纹跳推优化推送冗余」）对作者是压缩，对读者是黑话，用户看不懂就只能逐轮追问。

**怎么做**：
- ✅ 文档前部（§1 末或 §2 头）画一张**端到端大流程图**：本设计涉及的主链路，从源头到终点，用户能看懂的物理粒度——这张图是全文坐标系
- ✅ 画一张从**存储到用户眼前**的完整数据流图：磁盘文件（标具体路径 + 文件内位置）→ 读取/解析 → 用户/agent 看到的内容（数据类设计的最低要求）
- ✅ **每个问题点条目以「环节：<大流程> → <环节名>」开头**（§2），**每个决策条目同样锚定**（§3.3）——决策是「在流程哪个环节上装什么/改什么/砍什么」，锚定后读者在任何段落都能定位讨论对象
- ✅ 图里标注「这一步产出 §X 的 Y」；关键论断点明（把命令和文件物理地连起来）
- ❌ 只说「`info` 返回参数」不说参数从哪个文件的哪个位置来
- ❌ 脱离流程坐标系的机制名词叙事——读者看不懂「X 优化了 Y」，看得懂「环节：主链 → 第 3 步，现状每 30s 无条件执行」
- ❌ 让读者自己猜「那个注释块写在什么文件里」

### 准则 6：错误要给出路（recovery 指引）

**为什么**：错误不只是「什么会坏」，更是「用户/agent 接下来该做什么」。只描述失败不指恢复，读者拿到错误仍不知如何继续。若有权威信息源（如某个查询命令），所有错误应统一指向它，形成「错误 → 权威源 → 重试」的闭环。

**怎么做**：
- ✅ 每个失败场景配**恢复指引**（具体命令/动作，不是「请检查」「请排查」这类空话）
- ✅ 若有 canonical 源（如 `info`），错误文案统一追加「👉 用 `X` 重看/重试」
- ✅ 把「错误 → 恢复」定成**贯穿原则**写进设计目标，不只是某一处错误文案的细节
- ❌ 只描述「会失败/会崩/报错」不说怎么恢复
- ❌ 不同错误指向不一致的恢复路径

> **正例片段**（fail-fast 带恢复指引）：
> ```
> review-fix-loop 参数校验失败：
>   - targetType: 必填，缺失
> 参数 schema: {...,"required":["targetType","target"]}
> 收到: {"target":"main"}
> 👉 用 `workflow info review-fix-loop` 重新查看完整参数与用法示例。
> ```
> 错误不只告诉"错了"，还给"去哪看对的"。

### 准则 7：运行时断言附探针（不写未验证的行为声明）

**为什么**：设计文档常含「X 会自清理」「Y 命中率高」「Z 在 W 之前执行」「跨进程不丢类型」等运行时行为断言。**靠推理写出的断言命中率极低**（实战观察近 0%），会严重误导实施者。这是设计文档的**诚实性**问题——把「应该这样」当「就是这样」，是准则里最贵的一类错误。四分类（事实/推断/知识/决策）是这条纪律的上游形态：每句关键陈述先归性质，推断的去核实，知识影响决策时按推断对待。

**怎么做**：
- ✅ **关键陈述先四分类**：事实（已核实）/ 推断（由已知推导、未核实）/ 知识（通用领域认知，影响决策时视同推断）/ 决策（人为拍板）。推断核实后才写为依据，核实不了的显式标注「未核实」——读者必须能分辨哪些可信
- ✅ **核实手段按成本分级**：优先读代码逻辑推演（顺调用链读实装）；确需跑代码时用**独立局部临时代码**模拟——与项目无关、只复现局部场景现象的最小代码，核实后删除；不搭完整项目复现
- ✅ 每条运行时行为断言配一个**探针**（已跑通标 ✅ 带结果 / 实施期门标 ⛔ 哪阶段前必跑）
- ✅ **⛔ 实施期门探针必须同时写降级路径**（探针失败时方案怎么调整——换形态 / 回退 / 砍掉该能力）。写不出降级路径的探针，说明方案对该断言是单点依赖，设计不完备
- ✅ **探针失败则断言不写进文档**（先验证再声称，而非先声称赌实施时验证）
- ✅ 探针清单单独成节，可审计、可回归
- ✅ 对「靠推理的断言被实测推翻」的教训显式记录（避免重蹈）
- ✅ **外部 API 的时序与返回形态也是运行时断言**：sync 还是 async、返回值还是 void+回调（fire-and-forget）、有无超时/中途 abort——"能在 X 里 await 它"必须实测，不能从函数名推断
- ❌ 裸断言「WeakMap 自清理」「对象引用稳定」「在副作用前执行」「跨进程保留类型」不经实测
- ❌ 把「应该这样」当「就是这样」
- ❌ 假设外部 API 可 await / 同步返回 / 不会被超时打断（`compact()` 这类名字不保证它返回 Promise）
- ❌ 以「复现成本高」为由跳过核实，把推断留在文档里
- ❌ **绝对化断言**：「做不到 / 帮不上忙 / 不行 / 没有 X」——一律改写为取舍表（可行形态 + 代价 + 何时值得何时不值得），断言的正确部分与边界部分分开写；把「有取舍」压成「一个不字」会迫使读者追问多轮才能拿到真实边界（对话同理：被问第二次「为什么 X」= 设计里有未质疑的隐含前提，应立即列出前提清单请对方裁决，而非逐个被动应答）

> **正例片段**（探针清单，每条标注验证的行为 + 状态）：
> ```
> | ID | 验证的行为 | 探针 | 状态 | 失败时的降级路径 |
> | P-order | 错误在 worker 启动前返回 | 校验失败时断言 addEventListener spy 未被调 | ⛔ M3 | 失败 → 校验移到 worker 启动后同步等待 |
> | P-no-eval | discovery 不执行作者代码 | grep discovery 无 new Function/eval | ✅ M2 后 | — |
> | P-cache | 注入段与执行读到同一份 meta | 改 mtime 断言三处读同一份 | ⛔ M5 | 失败 → 收敛为单一读取点，其余消费缓存 |
> ```
> ⛔ = 实施期必须跑通的门槛；✅ = 已实测；⛔ 行必须带降级路径（没有降级 = 单点依赖）。没有探针的运行时断言 = 不诚实。

> **⚠️ 反例警告**：同一案例的早期版本，**每一条运行时断言实测命中率 0%**——「两点接入」实为 3 处、「flow mapping 兼容」实测 5/5 FAIL、「WeakMap 自清理」被 ajv 强引用击败。详见 `anti-patterns.md` 第一节。

## 三、设计哲学准则

### 准则 8：减法优先于加法

**为什么**：遇到子问题，本能是「加个机制解决它」。但每个 clever 机制 = 新的运行时断言（准则 7）= 新的失败面 = 新的审查翻车。正确性应优先靠「by construction」（结构上不可能错），而非「by clever mechanism」（靠精巧机制保证）。

**怎么做**：
- ✅ 遇到子问题先问「能不能砍掉/简化」，再问「加个机制」
- ✅ 选方案时，结构简单的优先——即使它有已知的小代价
- ❌ 为每个子问题加独立机制（每个都是新断言源）
- ❌ 用精巧机制保证正确性（机制一崩全崩）

> **反例**：某案例 v4 为解决 4 个子问题加了 4 个 clever 机制（WeakMap 缓存 / 自动生成示例 / 错误分类 / 空格形态匹配），每个都引入新断言，全部被审查推翻。v5 全砍后，**设计反而比 v4 短 1/3，且所有断言都站得住**（砍掉了未验证的，剩下的 by construction 正确）。

## 四、本 skill 专属准则（来自 tech-design 的定位）

### 准则 9：方案对比必带长期架构 + 短期成本

**为什么**：解决方案章节如果只给一个方案，就是事后合理化（先选了再编理由）。必须 ≥2 方案对比，且每个方案都要评「长期架构合理性」和「短期实现成本」两个维度——只谈一个维度会误导决策。

**怎么做**：
- ✅ ≥2 个候选方案，每个评「长期架构合理性 / 短期实现成本 / 风险」三栏
- ✅ 给明确推荐 + 推荐理由（不是"都可以"）
- ✅ 不采用的方案说明「若用它，前文例子会变成什么样」（让取舍可感知，呼应准则 4）
- ✅ **每个「已接受代价 / 已知风险」必须量化四要素**：量级（多少次/多大体积/多高速率）、恢复路径（代价兑现后怎么回来、通道是否存在）、重审触发条件（到什么程度不再可接受）、显式判定（可接受/不可接受 + 依据）。一句话接受代价（「可见」「可控」）= 未评估——真实案例中这类代价以「GUI 列表可见」一句话被接受，实施后膨胀为数千条残留 + GB 级存储 + 用户手动逐条清理
- ✅ 方案写入本项目不拥有的持久状态（宿主 DB / GUI 状态 / OS 全局状态 / 第三方服务）时，风险栏必须先**穷举全部写入面**（主存储、日志、临时产物、统计/遥测表、缓存——真实跑一遍后 diff 文件系统与宿主各表增量兜底），再逐面枚举**消费方及其过滤/投影规则**（谁读、按什么条件展示）与**清理通道存在性**，再谈代价
- ❌ 只给一个方案
- ❌ 方案对比只写"选了什么"不写"为什么不选别的"
- ❌ 长期成本/短期成本混为一谈，或只谈一个
- ❌ 「已接受代价：X」一句话带过——无量级、无清理通道、无重审条件

### 准则 10：scope = 当前层 → 紧邻下一层，不跨 2 层

**为什么**：一次设计试图跨多层（如从业务目标直接设计到代码实现），必然每层都浅、抓不住重点。聚焦"当前层 → 下一层"，深度才够。

**怎么做**：
- ✅ 明确本次设计的"当前层"和"下一层"是什么
- ✅ 设计深度止于下一层的拆分计划，不越层
- ❌ 一份文档从战略目标写到函数签名

### 准则 11：验收用真实场景验证，不是单测、不是 mock

**为什么**：设计文档常把"有单元测试覆盖"当成"验收通过"。但单测只验证代码逻辑是否符合设计者的假设——它证明不了功能在真实工作里符合预期。mock 同理：把外部依赖 mock 掉，等于把真实集成路径绕过了，验证的是一个想象中的世界。验收要回答的是设计最该回答的问题：**用户/真实环境里，这个功能真的好用、真的解决了 §1 的目标吗？** 没有验收章节的设计，是"设计完了却不知道怎么证明做对了"，实施完只能靠运气判断成败。

这是准则 7（运行时断言附探针）在"整体验证"层面的延伸：准则 7 管"某条行为断言要不要附探针"，准则 11 管"整个功能实施后拿什么证明它符合预期"。两者都反"靠推理声称"。

业界测试金字塔给这个区分权威框架：单元测试（金字塔底层）验证"单个函数逻辑对不对"，验收测试（顶层）验证"用户能否达成业务目标"——**单元测试防止发布有 bug 的代码，验收测试防止发布"满足技术要求但不满足真实需求"的软件**。完整业界依据（ATDD/BDD/SBE/DoR）见 `acceptance-practices.md`。

**怎么做**：
- ✅ 定义**实施完成后在真实场景里怎么验证**：跑什么真实流程、走什么真实数据/环境、看什么真实结果，写明验证场景、步骤、通过标准
- ✅ 按改动大小匹配验收投入——小改动（改文案/调参数/修单点）可一句话说明简化验证（如"改完跑 X 命令看输出"）；大改动（新功能/行为变更/接口调整）必须投入真实场景验证，明确多个验证场景
- ✅ 验收用**真实依赖、真实数据、真实路径**，不用 mock/桩/假数据替代；依赖项无法在验证环境获取时，明说替代方式带来的验证缺口
- ✅ **每个验收场景回溯 §1「背景目标」的哪一条**：标注它验证哪个业务目标。无法回溯到目标的验收场景是多余的，有目标却无对应验收场景的是遗漏（来自 SBE「从目标推导范围」）
- ✅ **验收用具体业务例子，不用抽象断言**：写"谁、在什么真实上下文、做什么操作、看到什么真实结果"，不写"功能正常/响应快/系统稳定"（后者与准则 7 的运行时断言同病：不可验证、靠推理）。可借 Given-When-Then 三段式思路组织，但设计文档层不必上严格 Gherkin 语法
- ✅ 验收章节是设计**就绪门槛（DoR）**：验收场景必须 testable（有明确通过标准、可在真实环境执行）才算设计就绪、可进入实施，并指导 §5 拆分如何分阶段验收——不是实施完才想
- ✅ **方案触达外部共享系统（宿主存储 / GUI / OS 全局状态 / 第三方服务）时，场景集必须含「邻居系统不变量」场景**：实施后宿主的既有表面不被改变（例：跑 N 次后重启宿主，列表/索引/存储无异常残留、无写入堆积）——只验「我的功能工作」不验「宿主表面不变」会漏掉投影面污染类问题
- ❌ 把"单元测试覆盖率"或"mock 测试通过"当验收
- ❌ 验收只写"测试通过"不写真实场景/步骤/标准
- ❌ 验收用抽象断言（"功能正常/性能达标/体验好"）而非具体业务例子
- ❌ 设计时不写验收，留到实施后凭感觉判断

> **正例片段**（验收章节，按改动大小区分）：
> ```
> 验收（真实场景，非单测）：
> - 改动规模：中等（修改 cw design 阶段 guidance 拼装逻辑）
> - 回溯目标：§1 目标"agent 拿到 guidance 能正确驱动下一步"
> - 场景 1（验证上述目标）：在真实已开发项目里跑 cw design <feature>，对比输出 guidance 是否含新增段 → 跑通则通过
> - 场景 2：把输出 guidance 交给真实 agent 消费，看能否正确驱动下一步
> - 通过标准：两个场景都拿到预期 guidance；单元测试仅作回归辅助，不计入验收
> - 依赖说明：cw 自身是真实运行，无需 mock
> ```
> 区分"代码对不对"（单测）和"功能好不好用"（真实场景验收）——验收是后者。

### 准则 12：直接解决优先——设计决策序

**为什么**：病症明确后最容易写出的方案不是「消除病因」，而是「在病症下游挂补偿机器」（catch 吞错降级 / 自动重试自愈 / 定时轮询对账 / 缓存遮蔽）——不动现状、实现局部、看起来「稳健」，本质是**让病症的可见性消失而病因存续**：正常路径依旧 broken，兜底从此成为事实主路径，且每个兜底都是新的运行时断言源（准则 7）与失败面。绝大多数业务逻辑，直接解决（修数据流/契约/状态模型）或架构层重设计（使病症构造性不可能发生）已经足够。非功能性设计（鲁棒性/自愈/对账）排在功能正确之后按必要性评估，不是方案的前菜。

**怎么做（设计决策序，写 §3 前逐步过）**：

1. **问题定义**（准则 0）：问题已探明（症状/触发条件/复现路径清楚），SCQA 的 Q 已收敛。
2. **产品最小形态**（准则 13）：核心价值 + 最少技术投入形态已定，§3 主干 = 最小形态（不是修复现状实现）。
3. **定级：独立问题还是架构问题**——双判据：①症状分布（事后证明）：独立/偶发 → 按独立问题对待；存在多个同类症状、高频发生 → 架构层不合理的信号。②根因位置（事前预测）：偶发问题的根因若落在共享路径（公共数据流/契约/状态模型的环节），修症状不修根因，下次换症状再来——「偶发 + 静默失败 + 根因在共享路径」三者齐备时按架构问题对待。多个症状落到流程图同一环节 = 同类问题的空间证明（配全流程图逐环节落位使用）。
4. **路线：直接解决还是架构优化**——该决策**显式写进方案对比**（准则 9 承载「修复 vs 重构」的对比与理由），不允许隐式选择。架构优化路径允许实施分期，但**每一期的主体都必须是直接解决**——「先兜底顶一版等重构」是第 5 步禁止的形态。
5. **直接解决**（无论哪条路线）：方案落在病因所在环节——修数据流/契约/状态模型，或架构重设计使病症 **by construction** 消失（优于 by clever mechanism 补偿，准则 8 同族）。判别法：删掉方案里的补偿机制，病因还在 = 方案不合格；直接解决是什么答不出 = 根因没挖到，回第 1 步。
6. **非功能设计后置**：直接解决完成后才开始评估。非功能设计分两类，准入不同——**暴露问题类**（fail-fast、快速失败提醒、日志记录：让病因**可见**）属诊断能力，是直接解决的一部分，几乎总是值得做，不需要过兜底准入；**掩盖问题类**（兜底、自愈、对账、降级遮蔽：让病因**不可见**）受第 7-8 步严格评估。
7. **必要性评估**（掩盖问题类才需要）：三问——①直接解决完成后，日常高频路径是否已覆盖（残余的是什么）？②是否存在值得处理的极端场景？③极端场景的风险 = 破坏性 × 发生概率 × 不可检测性（低频但静默的故障——坏了没人知道——危险度上浮，优先补暴露问题类检测而非掩盖问题类兜底）。
8. **三档裁决**（逐风险面裁决，可不同面选不同档）：
   - **不做**：日常高频已被直接解决覆盖、极端场景风险可接受——验收须含日常高频路径的真实验证，这是「不做」的资格。
   - **简单设计**（低成本、好维护、无副作用高收益）：暴露问题类（fail-fast 提醒、日志）优先；掩盖问题类简单兜底须三条件齐备——覆盖极端情况而非正常路径、正常路径已根治、触发可观测（日志/计数/告警）。
   - **复杂设计**（强自愈、强兜底、对账）：额外论证两项——自愈机制本身是新故障源，复杂度与维护成本必须小于它防的事故代价；写明**升档触发条件**（简单档兜底的触发频率超阈值 = 该升档，或说明正常路径仍 broken）。
9. **验收挂钩**（准则 11）：档位选择连到验收场景——选「不做」→ 高频路径验证在场；选简单/复杂档 → 「兜底/自愈触发可观测」场景在场。档位选完验收无回声 = 决策序未闭合。

- ❌ 病症明确可直接根治，方案主体是兜底/自愈/轮询对账/降级遮蔽（掩盖问题类任何一种）
- ❌ 多症状共点（架构级问题）被逐个打补丁，不在架构层做统一修复
- ❌ 未回答「日常高频是否已覆盖、极端场景破坏面多大」就上强自愈/对账
- ❌ 用「更稳健」「容错性更好」「高可用」论证兜底必要性——稳健性论证必须先证明「正常路径无法根治」
- ❌ 兜底静默生效（无日志无计数）——用户永远不知道系统在带病运行
- ❌ 把探明问题的调研手段（加日志观察/加探针复现）写成设计内容——那是准则 0 的前置调研

> **反例**（形态识别）：§2 已写明「X 链路在 Y 环节断裂，信号被吞」，§3 方案却是「增加自动重试 + 失败降级 + 每小时对账修复任务」——三个机制全挂在病症下游，§2 指认的断裂环节一个没修。删掉三个机制，断裂还在 = 方案不合格。正确形态：修复 Y 环节的传输/契约，兜底（若有）只覆盖修完后的极端残余场景并过三档裁决。完整反例见 `anti-patterns.md` 反例 14。

### 准则 13：产品最小形态前置——从核心价值倒推，不从现状实现倒推

**为什么**：技术设计最常见的方向性错误，是把「现状实现」当成需求——现状的每个行为都被当作必须兼容的约束，方案于是围绕「如何修复/优化现状」展开，为现状引入的伪需求做正向设计。而对抗式审查能挑出方案缺陷，挑不出方向错误（文档自己定义的问题看起来总是自洽的）——错误方向的设计可以被多轮审查打磨得非常精致，精致感还会让所有人更确信方向对。最小形态前置就是在精致化开始之前锚定方向：先问「产品最核心的价值是什么、达成它的最少投入是什么」，再谈其余。

**怎么做（三层递进，顺序不可倒置）**：

1. **主干（必答）**：这个功能/产品**最最核心的价值是什么**（一句话，以项目产品定义文档为锚，不凭 agent 个人偏好）？达成这个价值的**最少技术投入**是什么形态？——§3 方案的主体必须是这个最小形态。判别法：从产品核心价值出发描述这个功能，对照现状实现——现状的复杂度里有多少是产品天然包含的？多出来的部分每项都要论证「为什么保留」，**砍掉是默认候选**；论证不出的 = 伪需求（现状实现引入、产品本质不需要的行为）。
2. **增量（逐项裁决）**：最小形态之上，看**能否用较少的额外投入达成更多额外收益**——每个候选项独立论证（投入 / 收益 / 不做会怎样），裁决过才进设计；未论证的增量混入主干 = 不合格。
3. **扩展（证据门槛）**：**架构上如何支持未来更好的扩展**——只保留有已发生证据支持的扩展点（已存在的第二个使用方 / 已发生的变化原因）；为想象未来预留的抽象在此阶段砍掉（与准则 8 减法优先同族，但管的是产品形态层而非机制层）。

- ✅ §3.1 终态先写最小形态终态，增量项随后逐项（各带独立裁决）
- ✅ 现状的每个被保留行为在 §2 有「为什么需要」论证（答「砍掉用户失去什么」，答不出实际损失 = 候选砍除）
- ❌ 从现状实现倒推设计（「现状每 30s 推一次，如何让它推得少」），而不问「这个行为该不该存在」
- ❌ 未论证的「兼容现状行为」混入方案主干
- ❌ 为想象未来预付扩展点（没有第二个使用方就抽通用层）
- ❌ 增量收益打包论证（「顺便一起做了」）

> **反例**（形态识别）：现状 widget 每 30s 全量重推且行文本嵌倒计时。直接进入「如何减频」的工程问题 → 衍生出去重、保活、恢复一整族机制设计；先问最小形态（「这个功能 = 到点触发 + 一个静态任务列表 + 前端自己算倒计时」）→ 倒计时从底层同步本身是伪需求，推送天然该是「状态变了推一次」——大半机制设计从未被需要。核心价值三问在 §3 动笔前完成，方向锚定后工程问题小一个量级。

**问题定义（准则 0，最优先）**
- [ ] 问题已探明（症状/触发条件/复现路径清楚）才动笔；探明调研的产物未混进设计文档
- [ ] 动笔前确认过：用户描述的问题是什么、是不是真问题、有无隐藏的根本问题
- [ ] 有疑点时用 grill 机制向用户提问澄清过（grilling 盘问 / research 查证，可多轮），未带未答问题往下写
- [ ] **前提清单**在 §2 末尾成节：设计默认为真的假设逐条列出（来源标注 已核实/需裁决 + 若不成立的影响）
- [ ] **关联登记面**在 §1 头部成字段：触及/修改/推翻的存量权威文档（决策记录/排障文档/功能分级等）逐项登记（无关联时显式写「无」）——它是 design-code-sync 核对回写的登记处
- [ ] 方案打到根本问题，不是只让表面症状消失

**产品最小形态（准则 13）**
- [ ] 三问已答并写进文档：核心价值（一句话）+ 最少技术投入形态 = §3 方案主干
- [ ] 现状的每个被保留行为都有「为什么需要」论证（从产品核心价值描述功能，现状复杂度里天然不包含的部分逐项质询）
- [ ] 增量收益逐项独立裁决（投入/收益/不做会怎样），未论证的增量未混入主干
- [ ] 扩展点只保留有已发生证据支持的（第二使用方/已发生变化原因）

**全流程坐标系（准则 5）**
- [ ] 文档前部有端到端大流程图（源头到终点，用户看得懂的物理粒度）
- [ ] §2 每个问题点、§3.3 每个决策以「环节：<大流程> → <环节名>」锚定开头
- [ ] 无脱离流程坐标系的机制名词叙事（拿任一段落问读者「现在讨论的是流程里哪个东西」，答得出）

**设计决策序（准则 12）**
- [ ] 已定级：独立/偶发还是同类/架构级（双判据：症状分布 + 根因位置）；「直接解决 vs 架构优化」决策显式进了方案对比
- [ ] 病症明确的每个问题，方案落在病因所在环节（删掉掩盖问题类机制，病因还在 = 不合格）
- [ ] 掩盖问题类兜底/自愈/对账逐个过三问（日常高频已覆盖？极端场景？破坏性×概率×可检测性）+ 三档裁决（不做/简单/复杂）+ 档位论证（复杂档证复杂度<事故代价、写升档条件）
- [ ] 档位选择连到了验收场景（不做→高频验证在场；做→触发可观测场景在场）

**陈述纪律（准则 7/9）**
- [ ] 关键陈述已四分类，无未标注的推断冒充事实
- [ ] 决策证据条目带核实状态（✅ 已核实——锚点/探针；⏳ 推断——显式标注待核）
- [ ] 代码锚点写「符号名 + 设计时坐标」且全文头部声明坐标系——符号名是承重结构，裸行号不是（实施后必漂移，追着刷是纯损耗）
- [ ] 无绝对化断言（「做不到/不行/帮不上忙」全部改写为取舍表）

**结构与可读性（准则 1/2/4）**
- [ ] 不读前序版本/审查记录也能懂（无 delta 引用，无审查编号）
- [ ] 无自造压缩词与流程术语残留：拿任一节问「不懂内部背景的读者能解析每个词吗」——答不出的词已展开定义或改自然词（多轮审查修复后的文档尤其要重查，密度随轮次单调上升）
- [ ] 标题下有一句话结论 + SCQA 开篇
- [ ] 每章首句是该章结论（加粗）
- [ ] 章节内分组 MECE

**内容主线（准则 3）**
- [ ] 现状章有真实例子（提示词/界面/输入输出，取自代码不编造）
- [ ] 终态章有完整交互对话样例
- [ ] 实现机制在使用者视角之后

**连贯性（准则 4/5）**
- [ ] 每个抽象术语首次出现有定义 + 绑定已展示例子
- [ ] 后续章节回指前文例子
- [ ] 不采用的方案说明「若用它例子会怎样」
- [ ] 涉及数据流时，画了从存储到用户眼前的物理数据流图

**方案对比（准则 9）**
- [ ] ≥2 方案，每个评长期架构 + 短期成本 + 风险
- [ ] 有明确推荐 + 理由
- [ ] 决策条目用「采用/不采用/证据/效果」四件套 item 化，无连排段落
- [ ] 每个「已接受代价/已知风险」量化四要素（量级/恢复路径/重审条件/显式判定）
- [ ] 写入外部共享状态时，已枚举消费方投影规则与清理通道再谈代价

**完整性（准则 6/7，层敏感）**
- [ ] 每个失败场景配恢复指引（具体命令/动作）
- [ ] 关键陈述已四分类，无未标注的推断冒充事实；探针优先独立局部临时代码（核实后删除）
- [ ] 运行时行为断言都附探针（✅/⛔ 标注），⛔ 行带降级路径
- [ ] 外部 API 的时序/返回形态假设（可 await、不超时）有探针
- [ ] 接管/替换既有流程的决策，被绕过段的副作用逐段有归属（复刻或声明放弃）
- [ ] 探针清单单独成节

**scope（准则 10）**
- [ ] 明确了当前层 → 下一层，未跨 2 层

**验收（准则 11）**
- [ ] 有验收章节，定义了实施完成后的验证方式
- [ ] 验收用真实场景（非单测、非 mock），写明场景/步骤/通过标准
- [ ] 场景表带「核实」列：断言具体命令/文本/形态的行已核实（附代码锚点）或标注 ⏳ 未核实（审查按推断对待，实施前升级或降级为形态判据）；步骤的操作前提（命令存在/候选数/通道可达）设计期核实过
- [ ] 验收投入与改动大小匹配（小改动可简化，大改动多场景）
- [ ] 关键负面行为（不该发生的不发生）至少一个场景反向验证
- [ ] 触达外部共享系统时，含「宿主/邻居系统表面不变」场景（重启后列表/索引/存储无残留）
