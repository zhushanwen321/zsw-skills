# 穷举矩阵（行为 × 状态组合类决策的裁决材料生产法）

> 目的：当关键决策的行为全集 = 「用户动作 / 输入信号 × 系统状态」的有限组合，且现状行为分散在代码各处、无单一文档可引时，纯文字方案描述无法支撑用户裁决——先派 subagent 把组合全集逐格核实现状行为，产出穷举矩阵（决策涉及界面视觉元素时配 HTML demo），用户基于事实矩阵逐格裁决。本文件是方法唯一来源——`flow/write.md` Step 3.3 / 7.1 / 7.4 引用它，方法修订只改这里。

## 触发判据（三条同时成立才用）

1. 决策对象是用户可见行为 × 系统状态的有限组合（按钮形态 / 消息呈现 / 恢复行为），组合可枚举
2. 现状行为分散在代码里、无单一权威描述——用户对该机制没有概念，纯文字方案描述读了无法裁决
3. 用户需要逐格（或逐类格）裁决新行为，不是只裁「值不值得做 / 风险多大」

## 反判据（命中任一就不用）

- 纯内部机制决策（数据流 / 协议 / 算法）：用户裁决的是方向与风险，走方案对比
- 组合行为已有状态机 / 转移表完整定义：直接对照定义，不重新枚举
- 新设计对全部组合拟用统一一条规则覆盖、且无可见分流维度——**软判据**：统一规则覆盖多状态组合时，建议轻量穷举一遍验证规则真成立。实战教训：「所有可发送状态都是发送按钮」看似一条统一规则，穷举后才发现「输入框有无内容」需要分流，规则当场改写

## 与既有机制的边界

| 机制 | 时序 | 产出 | 与本方法的关系 |
|------|------|------|---------------|
| Step 0 前置探明门 | 动笔前 | 问题症状 / 触发条件 / 复现路径 | 问题没探明时穷举救不了，先探明 |
| 穷举矩阵（本方法） | 决策前 | 组合全集的现状行为事实 → 辅助裁决「每格该怎么行为」 | — |
| Step 7 用例走查 | 决策后 | 验证「按当前设计这条用例能否走通」 | 同一设计可两者都用：先穷举裁决，定稿后走查验证 |
| T2 审查 | 文档完稿后 | 按判据挑文档毛病 | 穷举矩阵是审查的证据输入，不替代 reviewer |

## 操作流程

### 1. 定维度（成败点）

穷举维度 = 用户动作 / 输入信号 × 系统状态的全集。维度清单从代码事实推导（状态字段、布尔标记、模式变体），不从方案描述推导。完整性自检三问：

1. 输入侧：用户能做什么动作？输入框 / 控件有无内容算不算一个维度？（实战教训：第一版漏了「输入框有无内容」被打回补全——内容有无往往改变控件职责）
2. 状态侧：全部正交状态维度都进来了吗？（例：回合状态 × 压缩 × 后台任务 × 交接态 × 变体——漏一个维度，矩阵就少一轴）
3. 变体侧：同一状态的不同进入路径行为不同吗？不同则单列

### 2. 派 subagent 穷举

单方向 1 个 subagent；一次盘点出多个方向时并行派发，同时执行不超 5 个。task 三段式（背景 / 目标 / 验收）+ 三条纪律：

1. **只读分析，禁止修改仓库文件**
2. prompt 开头指明先读已定稿文档（设计文档 / 已裁决决策），避免把已覆盖内容当盲区重复穷举
3. 报告落设计产物目录（`<runDir>/`），命名 `<主题>-matrix.md`

全托管模式附加声明与用例走查派发相同（task 末尾追加同句）。

### 3. 事实标准

矩阵每格的行为描述以源码核实为准（读过代码 = 事实）；读不到代码证实的格子显式标「未核实」，禁止推断填格。发现现状不一致的格子（界面显示与实际行为不符）逐格标注——这些格子往往正是方案推荐的证据。

### 4. 抽验核实后才汇总

主 agent 对 subagent 报告抽验（至少核对关键格的源码引用真实存在、结论与代码一致）后再汇总呈用户——subagent 会产伪问题（凭空造状态名、把已存在的机制当缺失），不抽验不采信。

## 呈现形态

### 矩阵文档（默认）

三张表结构：

- 表 A：呈现形态全集（如按钮的全部形态）
- 表 B：输入信号全集（全部状态字段 / 用户动作，每个注明来源 file:line）
- 表 C：组合矩阵（行 = 状态组合，列 = 呈现形态 / 实际行为，逐格填事实 + 不一致标注）

矩阵超约 30 格时按维度分组呈现（如「无交接态组 / 有交接态组」），不一次性全摊给用户。

### HTML demo（界面视觉元素确认时必备）

决策涉及视觉形态（角标 / 图标 / 颜色 / 布局 / 徽标）且用户对该元素没有实物概念时，做 HTML demo：

1. **视觉参数从源码取**（真实色值 / 尺寸 / 圆角 / 定位），不凭空画
2. **页签对比**：现状 / 方案 A / 方案 B 各一页签，矩阵按方案着色区分
3. zcode 宿主：走 Gen UI 可视化通道渲染（visualize 技能）；pi / 其他宿主：落 HTML 文件给绝对路径链接

## 收尾盘点（T1 确认点前必做）

单个方向穷举完成、准备进 T1 确认点前，主动盘点：同一交互系统内是否还有其他「用户动作 × 系统状态」组合未穷举？逐条列出清单（每条：组合是什么 / 相对已定决策是否盲区 / 建议处置），随确认点一并呈用户裁决——不等用户想起来问。（实战原型：穷举定稿后用户主动问「我们应该不只是遗漏了这部分」，盘点出 6 个未穷举方向。）

## 产出归宿

- 穷举矩阵 = 过程产物，落 `<runDir>/`，不进设计文档正文；用户裁决结果写进设计文档决策节（五件套），矩阵文档作为该决策「证据」栏的引用
- HTML demo 是一次性确认材料，裁决完成后不进任何权威文档
