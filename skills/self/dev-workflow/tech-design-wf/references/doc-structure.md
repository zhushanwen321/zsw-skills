# 设计文档结构标准

> **本文件定义一份合格技术设计文档的骨架。** 五段式结构 + 每段的「写什么 / 为什么 / 怎么写好」。骨架层无关——无论你在哪一层做设计，都套这五段；差异只在「解决方案」「验收」两段的侧重点（见文末层敏感调节表）。
>
> 思考原则（怎么想：七原则与产物表规格）见 `principles.md`；写作准则（怎么表达）见 `design-principles.md`；本文件只管"结构长什么样"，含产物表在各节的落位。

---

## 五段骨架

```
1. 背景目标       → 为什么做、要做到什么
2. 现状与问题分析 → 现在长什么样、问题根因是什么
3. 解决方案       → 改成什么样、为什么这么改（多方案对比）
4. 验收           → 实施后怎么证明功能真的符合预期（真实场景，非单测非 mock）
5. 下一层拆分     → 怎么落地、拆成哪些下一层单元
```

**约束（准则 10）**：scope = 当前层 → 紧邻下一层，不跨 2 层。一份文档只负责"从当前层设计到下一层"。

**章节 JSON 语义（权威结构）**：五段骨架的权威载体是设计目录内六个章节 JSON（渲染产物的 md 形态仍按五段展示，语义不变）；字段规格的权威定义见 `references/design-doc-schema.md`，对应关系：

| 渲染视图章节 | 章节文件 | 承载字段 |
|---|---|---|
| 头部（分型 / P 级 / 风险分） | `meta.json` | designType / typeRationale / priority / riskScore / riskRationale |
| 人工审核导航 | `meta.json` | reviewNav（decisionId 集与 s3 decisions 的 id 集一致） |
| 关联登记 | `meta.json` | relatedDocs（本设计触及的存量权威文档清单，可空） |
| §1 背景目标 | `s1-context.json` | background / goals / outOfScope |
| §2 现状与问题分析 | `s2-status.json` | currentBehaviour / flowDiagram / problems / assumptions / artifactTables（四张产物表） |
| §3 解决方案 | `s3-solution.json` | terminalForm（终态型）/ options / decisions / migrationWaves（终态型） |
| §4 验收 | `s4-accept.json` | scenarios / assertionRedlights / e2eImpact |
| §5 下一层拆分 | `s5-breakdown.json` | units / fileMap |

下文各段「写什么 / 怎么写好」对五段骨架语义逐段展开，同样适用于对应章节 JSON 的字段填写；修改一律回章节 JSON，改后重跑渲染脚本（命令与产物地位见 `references/design-doc-schema.md` §10）。

**文档头部声明行**（三件并列 + 一行坐标系，落在 `meta.json`，渲染为头部表）：

- **设计分型**：终态型 / 演进型（`flow/write.md` Step D 判定，判定结论与理由落 designType / typeRationale 字段）。终态型附触发依据（用户显式要求终态/不计成本、修复史判定表输出「未修到」、设计对象为架构级）；演进型附一句辩护「为什么不需要终态视角」——分型是方向审判据 D1 的攻击对象
- **功能分级（P 级）与风险分**：落 priority / riskScore / riskRationale 字段，判定规则见 `flow/write.md` 前置「判断层性质」第 5 条
- **全文锚点坐标系**：代码锚点写「符号名 + 设计时坐标」（如 `useExtensionUI.ts:373 respond 分型锚点`），全文声明一行「本文行号是设计时坐标，实施后以代码为准」（落在长文本字段值内，如 background 开头）。**符号名是承重结构**（它是回同步环节的核实对象——符号还存在、语义还对，就没漂移）；裸行号不是——实施加几行代码行号必然漂移，把行号当承重结构会导致实施后整批无意义的回写

每段都要遵守准则 2（首句结论先行）。下面逐段展开。

---

## §1 背景目标

**写什么**：SCQA 开篇 + 系统是什么 + 设计目标。

**为什么**：读者（会用系统但不懂内部背景的开发者）必须先知道"为什么做、要达到什么"，才能理解后面的方案。跳过背景直接讲方案，读者不知道你在解决什么。

**怎么写好**：
- **问题定义先行（准则 0）**：§1 的 Q 必须是验证过的真问题——复述用户问题 → 判断是否真问题 → 识别隐藏根本问题。有疑点用 grill 机制先提问澄清（grilling 盘问根本问题 / research 查证事实，可多轮追问），禁止把用户给的方案/表面现象当问题
- **关联登记清单（落 `meta.json` 的 relatedDocs 字段）**：本设计触及、修改、推翻的存量权威文档逐项登记——决策记录（ADR）、产品定义、领域模型等，每条 = 文档相对路径 + 一句关系说明（行内字段规格见 `references/design-doc-schema.md` §3）。设计者写设计时最清楚自己动了什么语义，此时登记最准；该字段是后续 design-code-sync 核对回写的登记处（登记了没同步 = 可立项的遗漏）；无关联时留空数组
- 开篇 SCQA 四句（情境/冲突/问题/答案）——准则 2
- "系统是什么"：一两段介绍被设计的系统/模块，让没接触过的人建立基本认知
- "设计目标"：从使用者体验倒推（用户/agent 要能做到什么），不是功能清单
- 显式声明 in-scope / out-of-scope（防止 scope creep）

**正例参照**：SCQA 开篇 → `design-principles.md` 准则 2 正例；设计目标"从 agent 体验倒推四件事"。

## §2 现状与问题分析

**写什么**：使用者视角的现状（真实例子）+ 端到端大流程图 + 真实失败模式 + 根因分析 + Step D 产物表 + 前提清单（增强版）。

**为什么**：这是设计文档最容易偷懒跳过的一段，也是读者最需要的——不讲清"现在有什么问题"，方案就成了无源之水。准则 3（使用者视角）和准则 5（全流程坐标系）的主战场。

**怎么写好**：
- **问题定义先行（准则 0）**：§1 的 Q 必须是验证过的真问题——复述用户问题 → 判断是否真问题 → 识别隐藏根本问题。有疑点用 grill 机制先提问澄清（grilling 盘问根本问题 / research 查证事实，可多轮追问），禁止把用户给的方案/表面现象当问题
- **开头画端到端大流程图（准则 5）**：本设计涉及的主链路，从源头到终点，用户看得懂的物理粒度——这张图是全文坐标系，下文所有问题点与 §3 所有决策都用它的环节名锚定
- **产物表落字段（Step D 生成，触发了才有行）**：修复史判定表 → `artifactTables.repairHistory`、状态副本清单 → `artifactTables.stateCopies`、信号-蕴涵表 → `artifactTables.signalImplications`、上游依赖清单 → `artifactTables.upstreamDeps`、前提清单（增强版）→ `assumptions`——全部在 `s2-status.json`。列级规格与触发条件见 `principles.md` 末尾「产物表落点表」；未触发的原则不执行、对应表为空数组
- **现状用真实例子**：系统提示词 / 接口请求响应 / 界面片段，**取自代码不编造**——准则 3
- **失败模式锚定流程环节**：每个失败模式/问题点条目以「**环节**：<大流程> → <环节名>」开头——读者在任何问题点处都能定位"这是流程里的哪个东西"；禁止脱离流程坐标系的机制名词叙事
- **失败模式要真实**：列出当前实际怎么出错（不是想象中的），最好附触发条件
- **根因分析**：从症状挖到根因（不是停留在"用户体验差"这种表象）
- **画存储到用户眼前的物理数据流**（数据类设计）——准则 5
- **前提清单（`s2-status.json` 的 assumptions 字段，必选，增强版）**：「本设计默认为真的前提」——设计当作输入而未在本设计中论证的假设逐条列出，标注分类（事实/推断/知识/决策）、核实动作（✅ 附读了什么位置 / ⏳ 待裁决附「若不成立的影响」），否定性断言（「无 X」形态）附排除记录——规格见 `principles.md` P5；前提错了设计整体作废，方向审判据 D2 逐条攻击
- **抽象术语在此定义并锚定例子**：后面章节会反复用的关键概念（如"元数据""契约"），首次出现就定义 + 绑本段的例子——准则 4

**正例参照**：现状（agent 视角 + 真实系统提示词 + 失败模式 A/B/C）→ `design-principles.md` 准则 3；大流程图 + 前提清单定义 → 准则 4/5 正例。

> **禁止**：上来就讲"config-loader.ts 的某某函数怎么改"（反例 2）。先让读者看到"使用者眼里现在长什么样、怎么出错"。

## §3 解决方案

**写什么**：终态 + 方案对比 + 关键决策与权衡。**形态由设计分型决定**（Step D 判定，头部声明）：

| 节 | 演进型（默认） | 终态型 |
|---|---|---|
| 3.1 终态 | 最小形态终态先行（使用者视角） | 公理清单 + 终态形态 + 终态-现状差距表 |
| 3.2 对比 | 多方案对比（长期/短期/风险 + 明确推荐） | 迁移路径对比（一次到位 vs 分波次；成本只呈现，不作推荐依据） |
| 3.3 决策 | 关键决策与权衡（四件套 item 化 + A/B 定级） | 差距-波次映射决策（条目形态与定级同左） |

**为什么**：这是设计文档的核心。要回答两个问题：① 改造后使用者眼里变成什么样（终态）；② 为什么这么改而不是别的（方案对比）。终态型再答第三个：现状怎么迁过去（差距与波次）。

**怎么写好**：

### 3.1 终态（使用者视角先行）
- **最小形态终态先行（准则 13）**：先写核心价值的最少投入形态终态，增量项随后逐项（各带独立裁决）——方案主干 = 最小形态，不是"修复现状实现"。**终态型变体**（落 `s3-solution.json` 的 terminalForm 字段组）：公理清单（P1 产物：每条 = 不变量陈述 + 推导依据，不写实现细节）先行立骨 → 终态形态（结构 / 不变量 / 职责归属，从理想形态倒推）→ 终态-现状差距表（每条差距标注由哪一步消除），列级规格见 `principles.md` P1
- 放完整交互对话样例（成功路径 + 失败路径）——准则 3
- 失败路径要带恢复指引——准则 6
- 终态要在实现机制**之前**讲，让读者先理解"行为设计"，再看"怎么落地"

### 3.2 多方案对比（准则 9，强制）
- **≥2 个候选方案**
- 每个方案评三栏：**长期架构合理性 / 短期实现成本 / 风险**
- 给**明确推荐 + 推荐理由**（不是"都可以"）
- 不采用的方案用自然句说明「不采用 X 的理由：若用 X，§2/§3.1 的例子会变成什么样」——让取舍可感知（准则 4；产物小节名不用流程指令词缩略，照本句的自然句式写）
- **终态型变体**：对比对象换成迁移路径，候选至少覆盖「一次到位」与「分波次」两型，逐路径评三件事——每步消除哪条差距、中间态边界（该期完成后系统处于什么形态）、有无制造新差距。**成本只呈现，不作推荐依据**：推荐按差距消除的完备性与不制造新差距判定，成本信息如实列出供用户知悉
- 用表格呈现最清晰：

  | 方案 | 长期架构 | 短期成本 | 风险 | 裁决 |
  |---|---|---|---|---|
  | 方案 A（选） | ... | ... | ... | ✅ |
  | 方案 B | ... | ... | ... | ❌ |

### 3.3 关键决策与权衡
- 每个关键决策独立成条，用**固定四件套 item 化格式**——「采用 / 不采用 / 证据 / 效果」各成一个 bullet，不写成连排段落（连排段落里读者分不清哪段是采用、哪段是不采用）：

  ```
  **D1：<决策标题>（选定）**
  - **环节**：<大流程> → <环节名>（本决策落在流程哪个环节——与 §2 问题点同一坐标系）
  - **采用**：<选了什么、怎么工作>
  - **不采用**：<不选什么、为什么不行>
  - **证据**：<符号名+设计时坐标 / 先例 / 探针编号>，带核实状态——✅ 已核实（读码/探针拿到）或 ⏳ 推断（显式标注，禁止未标注的推断冒充证据）
  - **效果**：<这个决策让 §1 哪个目标 / §3.1 哪个场景成立——本决策的交付影响面>
  ```

- **终态型变体**：决策对象换成差距-波次映射——终态-现状差距表逐条映射到波次（每条差距有归属波次，每波次至少消除一条差距），条目形态与定级机制同上
- 涉及运行时行为的决策，断言落在断言-红灯映射表（准则 7 / `principles.md` P6）
- 遇到子问题先问减法——准则 8
- **接管/替换既有流程的决策**：逐段枚举被绕过路径的全部副作用——"接管入口"不等于"接管了原流程的每一段"（hook 拦截、装饰器包装、流程替换都会让原实现的后半段静默失效）。每段显式写"接管后谁负责"：要么复刻、要么声明放弃，禁止默认沿用（见 `anti-patterns.md` 反例 12）

**正例参照**：终态对话样例 → 准则 3 正例；fail-fast 带恢复 → 准则 6 正例；决策表（方案/证据/裁决/不采用的方案若被选用会怎样）→ 准则 9。

> **禁止**：只给一个方案（事后合理化）；方案对比只写"选了什么"不写"为何不选别的"；长期/短期成本混为一谈。

## §4 验收

**写什么**：实施完成后，在真实场景里怎么验证功能符合预期。

**为什么**：设计最容易漏的就是"做完了怎么证明做对了"。验收回答 §1 目标是否真的达成——单测只验证代码符合设计假设，mock 等于没验证真实集成，都不回答"真实工作里它好用吗"。没有验收，实施完只能靠运气判断成败。设计阶段就定验收，还能反向指导 §5 拆分（让每个拆分单元可分阶段验收）。

**怎么写好**：
- **用真实场景**：真实依赖、真实数据、真实路径，**不用 mock/桩/假数据**替代——准则 11
- **断言-红灯映射表（条件触发，P6 产物，落 `s4-accept.json` 的 assertionRedlights 字段）**：设计含运行时行为断言（自清理 / 在 X 之前执行 / 不丢 / 有界这类假设，触发判定见 `principles.md` P6）时逐行登记——每条运行时假设 × 假设被破坏时哪个机器检查变红（测试名 / CI 步骤 / 探针，写具体名字）× 无对应检查时的补建项（挂进 T3 验收计划）。主审 P0-27 逐行核对
- **「e2e 影响面评估」固定子节（`s4-accept.json` 的 e2eImpact 字段承载）**：渲染视图小节标题逐字为「e2e 影响面评估」（下游 T3 按标题检索继承，措辞漂移会检索失败——渲染脚本固定输出该标题）——列出受影响的既有 e2e / 真实进程测试资产清单与开发阶段需跑子集；无受影响项时 items 为空数组且 noneReason 填依据，禁止留空或省略（约定全文见 `flow/write.md` Step 4）
- **场景表带「核实」列**：断言具体命令、界面文本、界面形态的场景行，核实状态逐行标注——「✅ 已核实 + 代码位置（grep/读源码拿到的锚点）」或「⏳ 未核实」（允许存在，但审查按推断对待；实施前必须升级为已核实，或降级为形态判据——不写具体文本，写可判定的状态如「非完结形态」）。前提清单三态模式的场景表版；未核实的具体文本断言进了验收剧本，会拖到真机验收才暴露口径错误
- **步骤可行性核实**：场景步骤的每个操作前提（命令存在、候选数足够、通道可达）设计期机械核实——写「输入 X 后按方向键选其他项」前先确认该输入下确有多条候选
- **写清三要素**：验证场景、步骤、通过标准
- **每个场景回溯 §1 目标**：标注验证哪个业务目标；无法回溯的场景是多余的，有目标无对应场景是遗漏
- **用具体业务例子，不用抽象断言**：写"谁、在什么真实上下文、做什么、看到什么真实结果"，不写"功能正常/响应快"
- **按改动大小匹配投入**：小改动（改文案/调参数/修单点）一句话简化验证即可；大改动（新功能/行为变更/接口调整）写多个真实场景
- **关键负面行为也要验**：设计了"不该发生就不发生"的行为（如"提醒不强制"、"仅跨界时注入一次"、"去重后不重复发"），至少一个场景反向验证——只验正向会漏掉"一有信号就过度反应"这类回归
- **设计阶段就定（DoR 门槛）**：验收场景 testable 才算设计就绪，指导 §5 拆分如何分阶段验收

**正例参照**：准则 11 正例（验收章节按改动规模区分投入）。

> **禁止**：把"单元测试通过/覆盖率达标"当验收；只写"测试通过"不写真实场景步骤标准；用抽象断言（功能正常/响应快）而非具体业务例子；大改动只用一句话验收敷衍。

## §5 下一层拆分

**写什么**：实施路径 + 下一层单元拆分清单 + 每个拆分的理由。

**为什么**：设计文档要能落地。拆分清单告诉实施者"下一步做什么"，拆分理由让拆分可审查（为什么这么拆而不是别的）。拆分还应呼应 §4 验收——尽量让每个拆分单元可独立验收。

**怎么写好**：
- **实施路径**：分阶段交付，每阶段交付 §3 终态的一部分，各自可独立验证/回滚。**终态型**：拆分单元 = 迁移波次（来自 3.3 差距-波次映射），波次可标注目标 dev 版本形成跨版本队列——一份设计文档对应一份实施计划，各期共用同一设计与同一审查终态（约定全文见 `flow/write.md` Step 5）
- **拆分清单**：每个下一层单元列出 + justification（为什么这么拆）
- **文件改动地图**（若涉及代码）：新增/改写/收敛哪些模块，让实施者有清单可循
- **待验证检查点**：设计阶段无法确定的、留给实施期验证的点（诚实标注）

## 层敏感侧重点调节表

五段骨架通用，但 §3「解决方案」和 §4「验收」的**侧重点**按"本次设计的下一层性质"调节。先判断本次设计属于哪类，再套对应侧重点：

| 本次设计性质 | §3 解决方案重点 | §4 验收重点 | 涉及准则 | 典型层序（仅示例） |
|---|---|---|---|---|
| **子目标/子系统拆分** | 划分边界、依赖关系、优先级、为什么这么切 | 拆出的子系统能否协同达成 §1 目标、边界契约在真实场景是否成立 | 1-4, 9-11 | epic→feature |
| **需求规格** | 问题陈述、out-of-scope、边界场景 | 需求达成后用真实场景验证（真实场景验证，非单测） | 1-4, 9-11 | feature |
| **技术方案设计** | 接口先行、数据模型、错误规格、技术选型对比、物理数据流 | 真实环境跑通关键路径（非 mock 集成）、性能/正确性达 §1 目标 | **全部 1-11** | slice |
| **实现计划** | 测试先行(TDD)、任务拆分、文件清单、测试范围收敛、运行时断言探针 | 实施后端到端真实流程验证、运行时断言探针实跑 | 1-4, **5-7**, 9-11 | wave |

**判断方法**：问自己"本次设计的下一层产物是什么"——
- 下一层是"一组子目标/子系统" → 子目标拆分类
- 下一层是"可验收的需求集合" → 需求规格类
- 下一层是"可实现的接口/数据模型/技术方案" → 技术方案设计类（准则 5/6/7 全适用，最严格）
- 下一层是"具体的测试用例 + 代码任务" → 实现计划类

**技术方案设计类最严格**：它同时涉及数据流（准则 5）、错误处理（准则 6）、运行时行为断言（准则 7），三条层敏感准则全部适用；准则 11（验收）也在这类设计上最严格（要求真实环境跑通）。其他类型可酌情放宽 5-7，但 1-4/9-11 始终必须。

> 表中 epic / feature / slice / wave 四层仅作示例（一套分层交付流程的层名）。项目用自己的层名，按"下一层产物性质"映射到上表即可——本 skill 不依赖任何特定项目的层概念。
