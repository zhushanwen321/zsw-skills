# 技术设计七原则（原则层）

> **本文件是 tech-design-wf 技能的原则层，回答「做设计时怎么想」。** 技能分三层：原则层（本文件）管怎么想，机器层（可脚本判定的硬约束）管怎么查，循环层（T1 → T2 → T3 流程文档）管怎么收敛。七条思维原则，每条五节：陈述 / 为什么 / 思考操作子 / 可证伪产物 / 触发条件。
>
> 两个使用期：
> - **T1 设计期**（Step D 诊断 → 写作 → 自检 → 用例走查）：执行触发原则的思考操作子（执行这条思考的编号步骤），产出对应产物表（原则执行结果的落表形态）。触发扫描在 Step D（诊断期，动笔之前的步骤）完成。
> - **T2 审查期**（方向审 + 主审 / 影响面审 / 简洁审 + 修复循环）：七原则是攻击方向。审查者不读原则宣言，只攻击产物表——逐行验证真实性、找漏行、抽行复核。
>
> **为什么每条原则必须绑定产物表**：纯原则有已知的失败模式——原则表演：写一段「从终态考虑」，方案照旧缝补。对策是每条原则的执行结果必须落成可证伪产物（审查者能对照它逐行指出错误的表）。没有产物表的原则执行视同未执行。
>
> **与设计文档骨架的关系**：产物表不是独立文件，按文末「产物表落点表」嵌入设计文档对应章节。章节定义与嵌入格式以 `flow/write.md` 为准，本文件只约定原则本体、产物表列级规格与落点概览。

## 使用总则

1. **全部条件触发**：七条原则各自按「触发条件」生效，不逐条全量强制。纯文案、参数调整类设计只强制 P5（推断核实，七条中唯一全量强制的地基原则），防止小设计被七套操作子压垮。
2. **触发扫描在 Step D 做**：动笔之前逐条对照七条「触发条件」，判定本次设计适用哪些原则，产出触发清单（写入 runDir，即本次设计的运行产物目录）。触发了的原则必须执行操作子并产出产物表；未触发的不执行、不产出。
3. **产物表落盘按 write.md 约定**：落点章节、嵌入格式、生成步骤（Step D 生成还是写作期生成）以 `flow/write.md` 为准；文末落点表给出概览。
4. **审查期只认产物**：T2 各审查角色把触发了的原则当作攻击方向，攻击对象是产物表本身。宣言式陈述（「本设计贯彻了终态优先」）不可审，不采信。

## P1 终态优先

### 陈述

设计从「系统应该是什么形态」倒推，不从「现状哪里坏了」缝补。先定终态与不变量，再谈现状怎么迁过去。

### 为什么

真实案例两条：

- **反复缝补的演进史**：对一个多次重构仍问题不断的子系统做全历史回溯，根因不是哪一次修错了，而是每次修复的目标都只是「够到下一个能用的形态」。修完到达的是中间形态而非理想形态；下一个问题到来时，又以这个中间形态为起点继续缝补。没有终态参照，缝补可以无限继续。
- **审查从不质疑框架**：对 27 个设计包、669 条审查处置的统计显示，推荐方案被整体推翻的案例为 0；18 例决策翻转全部发生在设计内部（删一个属性、化简状态机、换一个谓词）。审查机制天然在既有框架内打磨，不质疑框架本身。终态视角不能指望审查补上，必须在 T1 写作期自己带上。

### 思考操作子

1. 假设历史包袱为零，写下该域的理想形态：结构、不变量、职责归属。
2. 对照业界已收敛形态校准（同领域的标准协议、成熟实现怎么解这个问题）：与理想形态冲突之处，要么吸收要么写明不吸收的理由。
3. 对照理想形态逐维度列终态-现状差距表。
4. 迁移路径按差距表编排：每一步缩小至少一条差距，且不制造新差距。

### 可证伪产物

**公理清单 + 终态-现状差距表**（落 §3.1，写作期 Step 3 生成）。

公理清单——公理指设计不可妥协的不变量（invariant，系统任何时刻必须恒真的性质）：

| 列 | 填写要求 |
|---|---|
| 编号 | 公理序号（A1、A2……），供差距表与审查引用 |
| 不变量陈述 | 一句话写「什么必须恒真」，不写「怎么实现」。写成某种具体做法的条目会被「这是实现细节不是不变量」打回 |
| 推导依据 | 从理想形态的哪项职责或哪条业界收敛形态推出。答不出推导的公理是拍脑袋，审查可攻击 |

终态-现状差距表：

| 列 | 填写要求 |
|---|---|
| 编号 | 差距序号，供迁移路径引用 |
| 维度 | 理想形态的哪个维度：结构 / 不变量 / 职责归属 |
| 终态 | 该维度在理想形态下是什么，引用公理清单编号 |
| 现状 | 该维度当前实际形态，附代码或文档位置 |
| 消除步 | 由迁移路径的哪一步消除——每个差距必须有归属步骤 |

攻击点：公理逐条问「违反它系统会出什么问题」，答不出 = 不是不变量；差距表与迁移路径对账——有差距无消除步、有迁移步不消除任何差距、或某步制造新差距，均判设计未完成。

### 触发条件

设计分型判定为终态型。分型信号（用户显式要求终态或不计成本；修复史判定表输出「未修到」；设计对象为架构级）与判定机制见 `flow/write.md`。

## P2 权威唯一

### 陈述

每份核心运行态数据必须答得出三问：唯一权威在哪、其余全部副本是谁、靠什么保持一致。答不出 = 设计未完成。

### 为什么

真实案例两条：

- **写者侧落盘推翻「无落盘」前提**：一份设计的前提写着「该状态无任何落盘」。核实时只查了读取侧代码；而落盘线索当时已经在 grep 输出里，因核实没覆盖写入侧被放过——写者侧（写入这份数据的代码一方）早有落盘实现，前提整体不成立。
- **4 副本 3 管道**：同一份核心状态散布在跨进程的四个副本上，靠三条管道互相同步，是六周返工的总根因。状态不止一个权威时，每条同步管道都是新的不一致来源。

### 思考操作子

1. 枚举该状态的全部持有者：跨进程、跨包、磁盘 / 内存 / 派生视图，一个不漏。
2. 每份标注性质：权威 / 派生视图 / 缓存。
3. 审查派生视图的同步手段：凡靠对账、巡检、定期比对这类对齐代码维持一致的，都是多份权威的嫌疑——顺着它找出这份代码在费力对齐的是哪两份数据，把其中一份降级为派生视图，或合并两份数据。
4. 新增任何持久化之前，跨包跨进程排查既有落盘层，必须包含写者侧。

### 可证伪产物

**写者枚举表**（落 §2 现状与问题，Step D 生成）：

| 列 | 填写要求 |
|---|---|
| 状态 | 被枚举的核心运行态数据名。一份数据可占多行——每个持有者一行 |
| 持有者 | 谁持有这份副本：进程 / 包 / 磁盘或内存，具体到模块或文件 |
| 性质 | 权威 / 派生视图 / 缓存，三选一。每个状态必须恰好一行「权威」；出现两行权威、或多行互相对齐 = 多份权威，设计未完成 |
| 同步手段 | 非权威副本靠什么跟随权威：单读源 / 事件订阅 / 重建。靠对齐代码维持的必须单独标注，并给出操作子第 3 步的追查结论 |

派生视图（projection）：从权威数据推算出的只读副本，本身不产生新事实。

攻击点：审查者抽行验证「同步手段」的真实性（读代码确认该手段存在且如描述）；攻击漏持有者——任何一个未被枚举的副本都算 must-fix（必修）级问题。

### 触发条件

设计涉及持久化状态、多进程或多视图共享状态、新增落盘格式。

## P3 蕴涵审讯

> 蕴涵（implication）：A 蕴涵 B，即 A 成立时 B 必然成立。审讯 = 对每个信号从两个方向追问到底。

### 陈述

凡「以 X 变化触发 Y」的机制，必答「X 变化在蕴涵上等于 Y 需要重算吗」。信号变化不等于目标变化，反之亦然。

### 为什么

真实案例：一份设计用文件 mtime（修改时间戳）变化判定「记录已变、需要重算」。核实写者侧后发现：用户只是发一条消息也会改 mtime——信号变了，记录内容没变。失效判定的粒度与信号的实际含义错配，全套设计由此重建。这是一次成本极低（读几行代码）、产出极深的核实。

### 思考操作子

1. 列出设计中全部触发信号：mtime / 事件 / 回调 / 计数 / 超时。
2. 对每个信号问两个方向：①它变了、但不该触发的情况存在吗（假阳性：信号变而目标没变）？②该触发、但它不变的情况存在吗（假阴性：目标变而信号不变）？
3. 任一方向成立 = 失效粒度错配：换信号，或收窄判定条件。两个方向都不成立的信号，才允许作为失效判定依据。

### 可证伪产物

**信号-蕴涵表**（落 §2 现状与问题，Step D 生成）：

| 列 | 填写要求 |
|---|---|
| 信号 | 机制依赖的变化信号：mtime / 事件 / 回调 / 计数 / 超时 |
| 设计假设的蕴涵 | 设计默认「信号变化 ⇒ 什么失效 / 重算」，一句话写清机制把它当成了什么的证据 |
| 实际蕴涵 | 顺写者与读者两侧代码核实后，信号变化真正代表什么，附核实位置 |
| 错配形态 | 无错配 / 假阳性 / 假阴性。非「无错配」的行必须写处置：换信号或收窄判定 |

攻击点：抽行验证「实际蕴涵」的核实位置真实存在且结论如实；攻击漏信号——设计里出现而表里没有的触发信号算 must-fix。

### 触发条件

设计含基于信号变化的失效判定、缓存失效或增量同步机制。

## P4 历史模式

### 陈述

同一问题域修过多次仍出问题，是结构性信号。设计前先解释「为什么之前的修复没收敛」，再决定窄修还是重构。

### 为什么

真实案例：对某子系统全部历史提交与 PR 做全样本回溯，产出四类事实，全部读当前代码看不到：

1. PR 描述与实际改动存在系统性偏差——描述说改了 A，双亲 diff 显示实际改的是 B。PR 描述不可信。
2. 有核心机制上线两周即被推倒。
3. 57% 的修复来自审查流程而非开发自检。
4. 回摆（修复收敛后又退回旧形态）检测能区分资产域（修复历史显示稳定、值得保留的部分）与故障密集域（反复出问题的部分）。

不回溯历史就动手设计，等于无视该域已经公开的失败模式。

### 思考操作子

1. 对该问题域做 git log 与 PR 全样本回溯：取证一律用 merge 提交的双亲 diff（该 merge 的两个父提交之间的真实差异），不信 PR 描述。
2. 追同一机制的修复链：修复收敛之后有无回摆。
3. 统计 fix 集中在哪一层：接口形状返工（结构性问题）还是逻辑错误（局部问题）。
4. 输出定性判定，填修复史判定表。

### 可证伪产物

**修复史判定表**（落 §2 现状与问题，Step D 生成）：

| 列 | 填写要求 |
|---|---|
| 机制 | 被反复修复的问题点，写符号名与位置 |
| 修复次数 | 全样本统计，取证方式为双亲 diff |
| 回摆 | 收敛后是否又退回旧形态：无 / 有（附来回翻转的提交对） |
| 修复层次 | 集中在接口形状返工（结构性）还是逻辑错误（局部） |
| 定性 | 三选一：资产域不动 / 故障密集域重构 / 未修到（历次修复都没触及根因）。判定依据必须能从前四列读出 |

该表直接驱动设计分型：定性为「未修到」的，分型判为终态型（与 P1 联动）。

攻击点：审查者抽一条机制，用双亲 diff 复核修复次数与回摆结论；攻击「定性」列——前四列支撑不出定性的行打回。

### 触发条件

问题域有 ≥3 次修复记录，或用户表述「反复出现 / 修过多次」。

## P5 推断核实

> 地基原则：其余六条的产物表都依赖核实动作的真实性。七条中唯一全量强制。

### 陈述

设计依赖的关键陈述先分四类：事实（已核实）/ 推断（由已知推导、未核实）/ 知识（通用领域认知，影响决策时视同推断）/ 决策（人为拍板）。推断核实升级为事实后才能作为设计依据。否定性断言（「无 X」「没有任何 Y」形态的断言）的核实范围必须覆盖全部写者与持有方——只查读侧不算核实。

### 为什么

真实案例两条：

- **「全双工」转述断言**：设计转述某底层通道是全双工（双向同时收发），被一句「要给出原因和证据」追问后核实，发现根本不是。从别处转述来的结论，是推断冒充事实的典型形态。
- **落盘线索被放过**（同 P2 案例一的另一层教训）：线索当时已在 grep 输出里，因为核实只查了读侧、没有枚举写者侧而被放过。核实的执行方式决定核实是否有效。

### 思考操作子

1. 前提清单逐条标注：✅ 必须附核实动作（读了什么文件的什么位置、跑了什么探针）；⏳ 待裁决。
2. 否定性断言专项：先枚举「谁可能在写、谁可能持有」，再逐个排除，排除记录留档。
3. subagent、记忆、外部会话给出的结论，进设计文档前主 agent 亲自核实一次。

### 可证伪产物

**前提清单（增强版）**（落 §2 末，Step D 生成、写作期持续更新）。由两部分组成。

前提主表：

| 列 | 填写要求 |
|---|---|
| 陈述 | 设计默认为真的一条前提，一句话 |
| 分类 | 事实 / 推断 / 知识 / 决策 |
| 核实动作 | 读了什么文件的什么位置、跑了什么探针。留空 = 未核实；未核实的推断不得作为设计依据 |
| 状态 | ✅ 已核实 / ⏳ 待裁决。⏳ 条目必须写「若不成立的影响」 |

否定性断言排除记录：

| 列 | 填写要求 |
|---|---|
| 断言 | 「无 X」「没有任何 Y」形态的前提 |
| 候选写者 | 谁可能写入或持有 X——先枚举再排除，枚举范围跨包跨进程、包含写者侧 |
| 排除证据 | 逐个候选的排除依据（读了哪里、确认什么），全部排除完才允许断言成立 |

攻击点：审查者抽样复核 ✅ 条目——亲自读源码验证核实动作真实发生过；攻击全部否定性断言——专找写者侧反例；⏳ 条目逐条判定是否影响设计方向。

### 触发条件

所有设计（唯一全量强制）。

## P6 防护网

### 陈述

设计依赖的每条运行时假设，必须存在「假设被破坏时变红」的机器检查（红灯 = 检查失败时给人看的失败信号）。没有红灯的假设等于未来的一次线上事故。

### 为什么

真实案例：架构审计发现 on-diff 检查（基于代码 diff 增量运行的检查）机制存在、也能发现真问题，但没有任何 CI 流水线消费它的结果——机制红了没人看。「修复靠人看」等于防护网有洞：假设被破坏的发现依赖某人恰好路过，而没有人会永远路过。

### 思考操作子

1. 列出设计全部运行时假设：自清理、在 X 之前执行、不丢、有界、命中率高之类。
2. 逐条映射现有机器检查：测试 / lint / CI 步骤 / 探针。
3. 无对应检查的登记补建项，挂进 T3（实施计划阶段）验收计划。

### 可证伪产物

**断言-红灯映射表**（落 §4 验收，写作期 Step 4 生成）：

| 列 | 填写要求 |
|---|---|
| 假设 | 设计依赖的一条运行时行为断言，一句话（如「worker 退出时队列必被清空」） |
| 变红通道 | 假设被破坏时哪个机器检查会失败：测试名 / CI 步骤 / 探针，写具体名字。填「无」= 该假设没有任何机器检查覆盖 |
| 补建项 | 通道为「无」的行登记：补建什么检查、挂进 T3 验收计划的哪个阶段。已有通道的行填「—」 |

攻击点：审查者逐行验证「变红通道」真实存在，且构造该假设被破坏的场景时它确实失败；「无 + 补建项为空」的行判设计未完成。

### 触发条件

设计含运行时行为断言。

## P7 上游约束

### 陈述

依赖不可修改的上游（第三方运行时 / 平台 / 框架）时，每个接触点（调用或依赖上游的具体代码位置）必须显式声明：这是上游保证的契约，还是只是当前版本恰好如此，还是押注上游未来会改。押注项单独成清单，带退场条件。

### 为什么

真实案例：对一个跨进程应用的 18 条上游消息通道盘点发现，9 处状态标记借道一条 UI 交互通道传递——上游从未保证这条通道可承载状态标记，只是当前版本恰好可行。这属于观察级依赖（当前版本如此、无契约保证）却被当契约用。不显式声明接触点性质时，设计的正确性会被无意识地押在上游行为上。

### 思考操作子

1. 枚举对上游的全部行为依赖——写行为，不写包名（「某条 UI 交互通道返回的标记会随选择结束清理」是行为依赖，「依赖某上游运行时」不是）。
2. 逐个标注性质：契约级（上游文档明文保证，附出处）/ 观察级（当前版本如此，无保证）/ 押注（期望上游未来版本如此）。
3. 观察级转入前提清单，按 P5 核实管理；押注项列退场条件（押注失效时换什么替代形态、什么信号触发切换）。

### 可证伪产物

**上游依赖清单**（落 §2 末或 §3.3，Step D 或写作期 Step 3 生成）：

| 列 | 填写要求 |
|---|---|
| 依赖 | 依赖了上游的什么行为，一句话 |
| 接触点 | 本项目哪些代码依赖它：符号名与位置，全部列出 |
| 性质 | 契约级（附上游文档出处）/ 观察级 / 押注 |
| 退场条件 | 押注行：失效信号与替代路径。观察级行：填「已转前提清单 #N」。契约级行填「—」 |

攻击点：审查者攻击漏接触点（用 grep 核对上游符号的全部调用点与清单一致性）；抽查契约级条目的文档出处真实存在。

### 触发条件

设计依赖非本项目代码的运行时行为。
