# T1 写设计文档流程

> 引导主 agent 按 tech-design 方法论写出设计文档（Step 0-6），审查循环协议见 Step 7（T2 执行细节见 `flow/review.md`），T3 实施计划见 `flow/plan.md`。结构标准见 `references/doc-structure.md`，写作原则见 `references/design-principles.md`——本文件只给流程步骤，不重复内容。

> **产物路径约定 [MANDATORY]**：设计文档本体落 `<项目根>/.tmp/tech-design/<name>.md`（项目根 = `git rev-parse --show-toplevel`，worktree 解析为各 worktree 根；非 git 仓库落 `/tmp/tech-design/`）。设计文档是 tech-design-wf → dev-flow-wf 的**过程产物，不进项目 docs/、不进 git**。只落主文档一个文件——审查报告、探针等伴生产物同落此目录（T2 报告在 `<name>/round-N/` 子目录，见 review.md）。

> **ADR 沉淀 [MANDATORY]**：项目存在 ADR 登记处（如 `docs/adr/decisions.md`，路径以项目 AGENTS.md 索引为准）时，设计中拍板的重要决策须登记或更新——设计文档可弃，决策必须活在其权威登记处。

## Step 0：问题定义先行（设计前必做，禁止跳过）

动笔前先过**前置探明门**，再过**产品最小形态三问**，最后回答三个问题：

**前置探明门**：问题是否已探明——症状、触发条件、复现路径三者清楚？未探明 → **先做调研再回来**：复现实验、日志采集、探针观察都是前置步骤，产物落 `.tmp/` 留档，不进设计文档。把「加日志看看再定方案」写成设计内容 = 问题未探明的设计，不合格。例外：探针体系本身复杂到需要设计（多探针编排/结果归因），独立成章并论证复杂度。

**产品最小形态三问**（问题探明后、动笔 §3 前必答，答案写进文档）：

1. **核心价值**：这个功能最核心的价值是什么（一句话，以项目产品定义文档为锚）？达成该价值的**最少技术投入**是什么形态？——这个形态就是 §3 方案的主干
2. **增量收益**：最小形态之上，哪些**较少投入换明显收益**的项？逐项独立裁决（投入/收益/不做会怎样），未裁决的不得混入主干
3. **扩展支持**：只保留有**已发生证据**支持的扩展点（已有第二个使用方/已发生的变化原因）；为想象未来预留的抽象砍掉

判别法：**从产品核心价值出发描述这个功能，再对照现状实现——现状复杂度里天然不包含的部分，每项论证「为什么保留」，砍掉是默认候选**。从最小形态倒推设计，不从现状实现倒推。

三个问题：

1. **用户描述的问题是什么？** 用自己的话复述，确认理解无误
2. **这是不是真正的问题？** 用户描述的现象可能只是症状（例：用户说"命令太慢"，真问题可能是"每次都全量重算"）
3. **背后有没有隐藏的、用户未明确表达的根本性问题？** 常见信号：用户直接给了方案而不是问题；触发场景描述得太窄；跳过因果链中间层直接说结论

发现"可能有隐藏问题"时的做法：**先提问澄清，不猜**——提问聚焦"根本问题是什么"，不聚焦方案细节；grill 机制（grilling 盘问式 / research 查证式，可多轮追问）；**不带未答问题往下写**；被用户第二次追问「为什么 X」时，主动列出「本设计默认为真的前提清单」请用户裁决。

写方案前最后自问：**这个方案解决的是根本问题，还是只让表面症状消失？** 掩盖问题的典型形态：加 try-catch 掩盖报错、自动重试/自愈、定时轮询对账补偿、降级/缓存遮蔽。判别法：删掉方案里的补偿机制，病因还在不在？还在 = 不合格。

## 前置：判断层性质

动手前先定五件事：

0. **产品边界核对**：项目存在产品愿景文档（如 `docs/PRODUCT.md`）→ read 并核对不偏离产品定位；冲突时停下向用户澄清
1. **本次设计的"当前层 → 下一层"是什么？** 文档开头显式声明（不跨 2 层）
2. **下一层产物性质？** 套 `doc-structure.md` 层敏感调节表确定 §3 侧重点
3. **是否涉及运行时行为 / 数据流 / 错误处理？** 是 → 准则 5/6/7 全部 P0 适用
4. **领域术语与视觉层核对（条件触发）**：新术语 → 项目术语表对齐；涉及 UI → 项目视觉设计权威对齐，路径以项目 AGENTS.md 索引为准
5. **本次设计触及的功能分级（P 级）是多少？** 项目存在功能分级登记（如 `docs/FEATURE-PRIORITIES.md`）→ 查表取涉及模块/用例的**最高 P 级**；不存在 → 按「挂掉后果」现场评估。**P 级标注在文档头部**（一致性审查按分级核对错误处理策略——P0/P1 fail-fast、P2/P3 接入点降级边界）

## Step 1：背景目标

SCQA 开篇 + 系统是什么 + 设计目标（从使用者体验倒推）+ in/out scope。受众假设：会用系统但不懂内部背景的开发者。

## Step 2：现状与问题分析（禁止跳过）

使用者视角现状（真实例子，**取自代码不编造**）+ **端到端大流程图**（§2 开头，全文坐标系）+ 真实失败模式 + 根因分析 + **前提清单节**（「本设计默认为真」的假设逐条列：来源标注 ✅ 已核实 / ⏳ 需用户裁决 + 若不成立的影响）。问题点条目以「**环节**：<大流程> → <环节名>」开头锚定。禁止上来讲"哪个文件哪个函数怎么改"。

## Step 3：解决方案

**方案形态定型（动笔前过设计决策序）**：第 0 步最小形态终态先行 → ①定级（独立/偶发 vs 同类/架构级）→ ②路线（直接解决 vs 架构优化，显式进 3.2 对比）→ ③直接解决（方案落病因环节；掩盖类不作主体）→ ④非功能后置（必要性三问 + 三档裁决，档位连验收）。

- 3.1 终态：最小形态终态先行，增量项随后各带独立裁决；完整交互对话样例（成功 + 失败路径带恢复指引）；终态在实现机制之前讲
- 3.2 多方案对比（强制）：≥2 候选，各评「长期架构合理性 / 短期实现成本 / 风险」，给明确推荐；不采用方案用完整自然句说明理由
- 3.3 关键决策与权衡：每条「**环节**」锚定开头 + 选择 + 不采用 + 证据；运行时断言附探针

## Step 4：验收（禁止跳过）

真实场景验证（非单测非 mock）；三要素（场景/步骤/通过标准）；每场景回溯 §1 目标；具体业务例子不用抽象断言；按改动大小匹配投入。**e2e 影响面评估**：列出受影响的现有 e2e/真实进程/真实 LLM 测试面，圈定开发阶段需跑子集（执行准则 SSOT = 项目 AGENTS.md 测试节；能 mock/fixture 等价覆盖的标单测化路径）。

## Step 5：下一层拆分

实施路径 + 单元拆分清单 + 每项 justification + 文件改动地图 + 待验证检查点。每个拆分说明"为什么这么拆"；拆分呼应 Step 4（单元可独立验收）；设计阶段无法确定的诚实标"待验证"。

## Step 6：自检

交付前过两份清单：`references/design-principles.md` 末尾「写前自检清单」+ `review/rubric-design-doc.md` 的 P0 项（预审）。全程贯穿受众假设：每写一段问"不懂内部背景的开发者能读懂吗"。

**T1 完成即阶段确认点**：呈现文档 + 摘要，默认等用户确认「方向与结构合理」→ 授权后进 T2（`flow/review.md`）。

## Step 7：审查-修复循环协议（T2 各轮的修复规则）

设计文档写完 → 先派价值审（派发见 `flow/review.md`）→ must-fix 打回按其修复方向重写问题定义/方案主干，修完重过价值审 → 通过后三 reviewer 并行 → 多轮修复循环至全部报告 0 must-fix。**不要自己审——审查与写作分离，避免确认偏差；T2 派发三 reviewer，主 agent 不自审。**

**轮次唯一形态**：每轮 = 聚焦审 + 修复。R1 = 全面审；R2+ = 聚焦复审——reviewer 只审（a）上轮 must-fix 修复是否成立（fixed 须实证）、（b）修复是否引入新问题（只扫修复触及的章节）、（c）上轮登记不修项的上下文是否被改变（结构化申报复活）。**不做全面重扫，不存在"全面审 + 聚焦审"双重派发**。converged 判定读当轮（聚焦）报告。

### 7.1 每轮修复规则 [MANDATORY]

**循环由 must-fix 驱动：每轮修复全部报告的全部 must-fix，不留尾巴。** suggestion 逐条处置，处置完即终止，不为 suggestion 单独驱动循环。处置三选一，逐条记录：

| 处置 | 适用判定线 |
|---|---|
| 修复 | 精度歧义 / 边界未声明 / 拆分未同步 / 验收判据不可证伪 / 安全面缺口——实质是 must-fix 级内容 |
| 登记不修 | 纯表述 / 措辞 / 锦上添花 / 偏好性建议——记一句话理由，进交付汇报 |
| 归档 | 有价值但不属本文档层——记入设计文档相应节的待办或残留风险 |

**按 finding 必填字段分流**（每条带「影响决策 / 影响交付」两列）：`影响决策 = 是` → 重跑该决策的方案对比 + 7.2 联动同步；`影响交付 = 具体环节` → 修复落点锚定到该环节载体（规划→§5、开发→§3 与 file:line、测试→受影响测试族、验收→§4、文档登记→ADR/活性文档）；两字段皆无 → 登记不修。判定存疑按修复处理（滑坡防护）。

修复时按意见类别选动作：方案性（重跑方案对比 + 联动同步）/ 规格完整性（补齐并查同类缺口）/ 格式可读性（全文统一改）/ 新需求（回 Step 0 判 scope）。

### 7.2 修复纪律

1. **反例重演后再动笔**：must-fix 附反例序列时先重演"修复后行为"；审查给的修复方向也要重演，不照单全收
2. **被击穿的方案记入否决记录**：旧方案连同击穿它的反例写入该决策「不采用」栏
3. **决策改动后过联动同步清单**：正文该决策 / 终态数据流图 / 错误规格表 / §5 拆分单元表 + 文件地图 / §4 验收——五处联动，同类缺口全文扫同模式实例一并修
4. **修复轮次做语言回归**：每轮追加的源码锚/否决记录/边界声明会使行文密度上升——新增文本过产物语言自检：流程指令词不当产物小节名；压缩词首次出现必须展开或改用自然词

### 7.3 聚焦复审派发

修订完成后按 findings 归属送回各自审查 agent（价值审的送价值审，主审送主审，影响面审送影响面审，简洁审送简洁审；**修订重写了问题定义/方案主干/最小形态 → 价值审必送**；新增/改变外部接触面或代价声明 → 影响面审必送；增删机制/抽象/扩展点 → 简洁审必送。形态注记：本条是手工循环协议；workflow 形态（tech-review-loop）价值审只在发起时过一次，轮内三席不含价值审——重发起必重过价值审，以「重写主干 → 卡断重发起」覆盖同一关注点）。提示词四要素：背景（第 N 轮修订摘要，对照上轮 findings 逐条——每条怎么修的 + 反例重演结果）/ 聚焦（上轮 must-fix 修复是否成立、新机制能否被新反例击穿——修订方自己不放心的场景列出来让审查者优先攻击；交叉引用一致性终检；不重查已确认项）/ 输出（格式同前，新发现标注）。给攻击点建议是提效关键。

### 7.4 终止与交付

价值审通过且三报告均 0 must-fix、suggestion 全部处置 = **设计就绪（T2 converged）**。不派纯确认轮。交付汇报写明：价值审一句话复述、循环轮数、各报告 must-fix/suggestion 收敛轨迹、suggestion 处置清单、否决记录最终形态。

**T2 完成即阶段确认点**：转述价值审复述 + 轨迹 + 处置清单，默认等用户确认 → 授权后进 T3（`flow/plan.md`）。下一层产物 = 子系统/需求集合的设计到此交付（无 T3）；= 代码任务/技术方案才进 T3。

## 迁移/重写类设计防复发判据 [MANDATORY]

设计对象是「把既有流程/系统重写或迁移到新形态」（老 skill → 新 skill、老管线 → workflow 化等）时，写作期强制过四判据——起因：一次流程重写设计经三轮审查仍丢 13 条老能力，复盘归因后固化：

1. **老能力逐条映射表**：设计必附「老流程能力 → 新形态落点」逐条映射表（老能力全枚举，逐条标注落点 = 新形态某节 / 显式裁决不迁移含理由；禁止只写新形态有什么）
2. **清单条款附条目文本**：设计写「进 XX 清单/登记表/表」类条款时，必须附该清单的条目文本本身（引用条目名而不给内容 = 两个实现各自发明具体化）
3. **双形态契约字段级 SSOT**：同一机制有手工形态与 workflow 形态两个实现时，共用契约（schema 字段名/路径/终态枚举/数字阈值）设计到字段级并声明唯一权威；两实现各自文字化的漂移由该 SSOT 判错
4. **验收含条款对账**：实现完成的验收 = 设计条款逐条对账（每条至少一次触发验证）+ 冒烟按「条款 × 触发条件」矩阵跑——「编译通过 + 主路径跑通」不构成迁移类设计的完成判据
