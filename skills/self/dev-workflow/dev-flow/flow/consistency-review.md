# 一致性对抗审查、修复循环与全量测试验收

> 阶段 3+4。审查对象 = `git diff <基线>..HEAD` 与设计文档章节的对照。收敛方向只有两个：实现回归文档，或文档经确认后演进（进登记表）。reviewer 只报告不修改。
>
> 原阶段 5 Gate A（全量测试验收）已并入本阶段尾部：审查清零 + 全量套件绿一起构成阶段 5 端到端验收的入口证据——两层验证同类相邻，合并省一轮派发冷启动；diff 量大时的拆分规则见「全量测试验收（原 Gate A）」节。

## 派发规模判定

- diff 总量 ≤500 行或单元 ≤2 → 单个全局 reviewer 审全部，**且任务书附带跑全量测试套件 + lint/typecheck + 覆盖矩阵**（一次读完 diff 顺手全验，Gate A 不再单独派发）
- 否则按顶层模块分区，每区一个 reviewer（相互独立、禁止引用彼此结论，避免盲区共谋）；全量测试套件**不由 reviewer 承载**，见「全量测试验收（原 Gate A）」节

reviewer 同样用 general-purpose + task 内嵌指令，独立上下文；一律后台异步派发，通知到达即收报告（多分区先到先读，聚合去重待全齐）。

## reviewer task 模板

```text
背景：你是对抗式一致性审查者——只报告，绝不改代码改文档。仓库 <cwd>，
  变更区间 <基线hash>..HEAD；领地映射与基线见实施计划 <绝对路径>
  （其「0 章节映射」给出设计文档各内容的实际位置）；设计文档 <绝对路径>。
目标：
1. read 实施计划的章节映射 → 按映射 read 设计文档对应节 + diff 全量。
   映射指向的节不存在或与节名原文对不上 → 立即返回「映射失效」说明，禁止按猜的节继续审
2. 逐章比对：终态是否被完整实现；机制层与实现是否一致
   （数据流/错误处理/共享接线点）；验收场景表的通过标准是否当前即可检验。
   错误处理契约：项目存在功能分级登记（如 `docs/FEATURE-PRIORITIES.md`）时，
   按改动触及模块的分级核对错误处理策略——P0/P1 改动应 fail-fast + 结构化日志
   （静默吞错/兜底掩盖 = unreasonable）；主流程衔接 P2/P3 的接入点应有降级边界
   （catch + 日志 + 关闭/占位），P2/P3 异常向上传播可打断主流程 = unreasonable；
   无日志的静默降级同样 = unreasonable（降级 ≠ 吞错）。
   声称事实前必须 read 原文件核实到行级；禁止凭目录名想象
3. 三分类输出，每条附 file:line 或 diff hunk 证据 + **两必填字段（影响决策 / 影响交付）**：
   reasonable[]    实现优于设计/合理演化且不破坏设计声明的目标 — 给理由 + 文档同步建议
   unreasonable[]  违背设计 / 遗漏未做 / 越权多做了设计外功能 — 给严重度 + 修复建议
   doc_errors[]    文档自身错了（实现是对的）— 逐条列出应修正处
   两字段判定口径（unreasonable 与 doc_errors 必填，reasonable 可省）：
   - 影响决策：`是——<违背的是设计哪条机制决策（D几/§几），不修则该决策落空>` 或 `否——<半句理由>`
   - 影响交付：`<环节>——<什么会出错>`；环节枚举对准交付链：`开发`（实现偏离设计须回改代码）/ `测试`（行为与设计断言不符致用例错位）/ `验收`（验收场景按设计写但实现已偏离，场景不可检验）/ `文档登记`（doc_errors 本体——设计文档须回写否则误导后来读者）/ `无`
4. 返回 {reasonable, unreasonable, doc_errors}（宿主无 structured-output 工具时，
   在回复中用 json 代码块返回同构对象，解析失败视同无效需重报）；
   空数组必须显式说明「在 XX 区未发现」，含糊的整体性断言无效
验收：每条结论可回溯到具体章节与文件位置
```

## 结论处理

| 分类 | 归宿 | 执行者 |
|------|------|--------|
| unreasonable | 组成修复批次并按领地分组并行派发（规则见「修复批次并行规则」节）：原 dev 会话仍存活则续聊定向修，否则按 execute.md「接替程序」补派并附前任证据包。修后走 execute.md 第 4 步核验 + 定向复审（只审本批影响面，不做全文重审） | subagent |
| doc_errors | 主 agent 亲自修订设计文档对应措辞，并在计划「残留风险与变更历史」节记一笔（主 agent 持有审查全景，此项不是编码，允许亲为） | 主 agent |
| reasonable | 写入计划「合理偏差登记表」节；涉及机制层面的同步设计文档「终态/机制」实际节的表述（按章节映射定位），保证后来读者不被过时描述误导 | 主 agent |

**按必填字段分流**（消费 reviewer 报告时先读每条的「影响决策 / 影响交付」）：`影响决策 = 是` 的 unreasonable 优先级最高（设计决策落空——先评估是否须改设计文档再修代码，防代码向偏离方向固化）；`影响交付 = 验收` 的条目修复后必须重核对应验收场景的可检验性（实现已偏离时场景断言跟着失效）；`影响决策 = 否 且 影响交付 = 无` 的条目降级为登记项，不进修复批次。

## 修复批次并行规则 [MANDATORY]

unreasonable 清单默认并行修，禁止把领地互斥的多组打包给单个 subagent 串行消化（2026-09-09 实测：5 条修复单发耗时 48 分钟，按组并行约 15 分钟）：

1. **按领地分组**：指向同一文件/同领地的条目归一组——组内串行，组间领地互斥即并行派发（并发 ≤5）
2. 每组一个修复 dev，三段式 task 附该组全部条目 + file:line 证据
3. 组完成先到先核验先 commit（同 execute.md 第 4/5 步），不等全批齐
4. 定向复审按组并行收口：每组修完即派只审该组影响面的复审，不攒轮
5. **微修复合并**：复审/Gate 回流中发现的单条小修（预计 <5min）不单独占一轮派发——攒入下一个待派修复批次；仅当它是 Gate 通过的唯一阻塞项时才单独派发并即刻重验
6. 例外：全部条目落在同一领地 → 单组串行修，无并行空间，属正常

## 数字阈值 [MANDATORY]

- 审查累计 ≥3 轮仍不收敛，或 unreasonable 规模不减反增 → 整线暂停，向用户呈报残余风险矩阵，裁决后再继续
- 单条 unreasonable 的修复走「打回定向修」，超 2 轮未解决同样升级

## 全量测试验收（原 Gate A，并入本阶段尾）[MANDATORY]

审查清零 commit 之后、转阶段 5 之前执行，产出 = 阶段 5 入口门的测试证据：

1. **主 agent 直跑计划约定的全量套件**：跑哪些范围以实施计划 §4「测试与验收计划」的约定为准——计划期按改动面圈定并写明命令（Gate A 防的是跨单元叠加回归，防线集中在改动面 + 依赖闭包；改动面外包的测试零回归信息，纳入只增耗时）；计划未明确约定时回退项目全量命令。命令 + lint/typecheck 从项目配置真实读取（AGENTS.md / package.json scripts），禁止凭记忆编命令；输出落盘（`<项目根>/.tmp/dev-flow/<plan-name>.gate-a.log`），不污染审查上下文
2. **零容忍绕过**：任何 SKIP_* 类变量、test.skip、跳过的 lint 规则——发现即记为失败项而非忽略
3. **全绿** → 在计划「变更历史」记一笔（命令 + 关键输出行），进入「清零后」流转
4. **有 failures** → 单独派一个归因 subagent 读落盘输出：逐条归因到单元/修复批次，产出处置清单（回 execute.md 补修 / 用户签认转残留风险登记）。微修复（预计 <5min）按「修复批次并行规则」第 5 条攒批，不单独占轮
5. **覆盖矩阵**（小 diff 合并场景由 reviewer 顺带；分区场景由归因 subagent 或主 agent 从落盘输出整理）：单元领地 × 实际测试用例，列出无人认领的改动区——uncovered 区要么补测试要么显式登记理由
6. **前置产物并行预备 [MANDATORY]**：全量段清单中「产物类」条目（e2e 产物构建 / fixture 生成 / bundle 构建——特征：命令确定、结果确定、被后续「验证类」条目消费）在全量段开始时作为第一波并行启动，禁止按清单顺序现用现建（2026-09-19 实测：real 轨首跑因磁盘产物过期被 launch 探针拒绝，重跑付一次全轮成本）。计划 §4 圈定全量段时逐条标注「产物类 / 验证类」；产物类条目就绪时点记入 gate-a.log

## 清零后

更新计划状态表、登记全量测试证据并 commit（该 commit 即阶段 5 入口门第 2 条所指标记），转入 `flow/acceptance.md`。
