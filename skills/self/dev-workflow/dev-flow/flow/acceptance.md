# 端到端验收

> 阶段 5。输入：一致性审查清零 + 全量测试绿（原 Gate A 已并入阶段 3，见 consistency-review.md）。本阶段只做机器替代不了的验证：真机场景验收。排序三原则：**核心先行、依赖解锁、共享状态互斥并行**。subagent 一律后台异步派发、完成通知驱动。

## 验证方式分级（全流程成本排序 [MANDATORY]）

| 级 | 方式 | 成本分 | 执行者 |
|----|------|--------|--------|
| L0 | 静态规则：lint / typecheck / 项目既有守卫脚本 / grep 机械信号 | 1-2 | 主 agent 直跑 |
| L1 | 增量单测（单元领地内） | 2-3 | dev subagent 自跑 |
| L2 | 全量测试套件 + lint/typecheck + 覆盖矩阵 | 4 | 主 agent 直跑落盘；failures 才派 subagent 归因 |
| L3 | 脚本化端到端：预编译剧本（操作 + 断言 + 全页截图 + console 抓取） | 5 | 脚本多实例并行跑 + 一个汇总 subagent 判定 |
| L4 | agent 端到端：真机逐步操作 | 8-9 | 验收 subagent |

铁律：L0 未清不进 L2；L2 不绿不派任何端到端；L3 能覆盖的场景不升 L4。机器可判定的修复（lint 报错、守卫红灯、悬空引用）在任何 agent 端到端之前清零——把它们留到 L4 才发现是最贵的返工路径。

**e2e 执行边界 [MANDATORY]**：e2e / 真实进程 / 真实 LLM 用例（含项目既有的真实 pi 等价性基线、真机轨、real E2E）只在开发阶段**按改动面**执行——清单从设计文档「e2e 影响面评估」继承、由 impl-plan §4 验收计划表圈定（见 plan.md），空载串行跑，禁止全量扫跑；PR/merge/CI 门禁只跑单测，不承担 e2e（SSOT = 项目 AGENTS.md 测试节）。圈定项里能以 mock / fixture 重放等价覆盖的，随所属单元沉淀为 L1/L2 单测（e2e 逐步单测化）。

## 入口门 [MANDATORY]

机械核验四条，任一不过 → 退回对应环节，不接受口头豁免：

1. 计划状态表全部 committed（或存在用户明示豁免的单元，逐个列名）
2. 一致性审查清零 + 全量测试绿的 commit 在 `git log` 可见（阶段 3 出口证据）
3. L0 静态守卫全绿：lint / typecheck / 项目既有守卫脚本零报错（命令从项目 AGENTS.md / package.json scripts 真实读取）
4. 若处于 fail 回流的重验场景：先声明本轮重验范围——failures 未触及共享接线点 → 只重验影响面；触及 → 全量重来

## 剧本预编译（进入即做，先于任何场景派发）

把验收场景表逐行分两类：

- **可脚本化**：操作序列确定 + 通过标准可机器断言（testid 存在 / 计数数字 / 文本出现）→ 编译 Playwright 脚本，固定抓三样落盘：全页截图、console 告警、断言结果日志
- **需判断力**：视觉形态是否符合设计规范 / 体验流畅性 / 探索性检查 → 保留 L4，由验收 subagent 亲自跑
- **混合行拆行**：一行场景同时含确定性断言与判断性断言时拆成两行——确定性部分降级 L1/L3 先行执行（产物落盘），判断性行的「依赖」列指向它；L4 agent 任务书附「确定性产物已就绪」，只做判断与签收。计划期 impl-plan 验收计划表的 L4 行必须在「优化判定」声明"机器判不了的部分是什么"（视觉形态 / 交互过程 / LLM 行为）——声明不出 = 强制拆行或降级（2026-09-19 实测：A9 纯文件断言被场景级定级拖进真实 LLM 组，白付组内串行等待）

**采样管道复用检查 [MANDATORY]（写任何采样/探针脚本之前）**：真机采样（连接 CDP → 定位选择器 → 注入样本 → 等待渲染信号 → DOM/截图采样 → 落盘）是所有场景共用管道，禁止每次现场重写。写脚本前依次核：① read 项目采样管道文档（如 `docs/testing/render-sampling.md`，路径以项目 AGENTS.md 索引为准）——已有可复用脚本的，直接复用，只写场景专属断言；② 本次踩出的新采样姿势（新选择器 / 新等待信号 / 新注入方式）沉淀为管道脚本资产回写该目录；③ 发现现有脚本有失效/重复/可合并的，优化整合删减——管道是资产，随用随养，不养尸体。

**预飞自检 [MANDATORY]（写场景剧本之前，两步零 LLM）**（2026-09-17 增补，源自 taiji 批量 tool 验收实测：环境未知 ×2 + 剧本低级错误 ×3 共烧掉 5 轮真实 LLM 轮次）：

1. **环境 smoke**：场景依赖的每个环境面（引擎/依赖发现、资产/模板可寻址、工具注册、端口/服务可达）先跑无 LLM 探针（模块直 import 断言 / CLI --print / 一次 dry 请求）逐项验证可用；探针 fail 即先修环境——把「环境未知」收敛成一张已知清单，禁止用真实 LLM 轮次踩环境坑
2. **剧本 dry-run**：剧本内的机械断言（grep 模式 / 正则 / JSON 解析路径）必须先对已有样本数据（前序轮事件流 / fixture）跑通再上真机；bash 语义歧义点（管道子 shell 的 cwd 隔离、`$()` 剥尾换行、引号嵌套）逐行过一遍；prompt 骨干措辞（被验证过的否定句/指令形态）跨剧本复制时保持逐字——真实 LLM 轮次只验业务行为，不验脚本自身正确性

**一次性 vs 可复用分流 [MANDATORY]**：

| 判定 | 落点 | 登记 |
|------|------|------|
| 功能面会反复回归（核心 UI / 主链路 / 长期维护面）→ 可复用 | 项目 e2e 目录（如 `e2e/*.spec.ts`） | 同 commit 登记对应测试静态文档（如 `docs/testing/11-real-e2e-specs.md` spec 清单）——验收产出沉淀为回归资产 |
| 一次性场景（迁移 / 特殊环境 / 本设计特有） | `<项目根>/.tmp/dev-flow/<plan-name>.acceptance/`（与 impl-plan 同目录） | impl-plan「变更历史」记一笔 |

**多实例并行**：互斥场景组各绑独立 dev 实例（项目有装配器时用其端口段派生 + 独立数据目录 + `--print` 取 CDP 端口；无装配器的项目手动分配端口 + 临时数据目录，`mkdtemp` 自建自删），脚本并行执行；全部产物集中给**一个汇总 subagent**：判 pass/fail + 扫全页截图与 console 兜底（脚本的断言盲区由这一步补偿）+ fail 归因定位到场景与日志行。

## 场景排序与派发 [MANDATORY]

1. **分组**：场景表逐行标 `核心` / `非核心`（核心 = 主链路功能，走不通则其余验收无意义）。表无此标记时主 agent 补标，依据（设计目标节的达成链）随验收汇报呈现
2. **依赖标注**：每行标前置场景 id；前驱 pass 才解锁后继（复用 execute.md 就绪集思想）。注意依赖（逻辑先后）与共享状态互斥（并行资源冲突）是两个正交维度，都要排；第三个维度是**修复独立性**——出现核心组缺陷时，逐场景标注三态：`无已知缺陷`（默认）/ `独立于缺陷 N`（预期行为不受该缺陷修复影响 → 可在「归因+修复」窗口内于旧实例前置跑，产物按旧实例标记）/ `依赖缺陷 N`（阻塞等修复）。前置跑的两条硬边界：修复后实例必须重启 → 前置场景必须在重启前跑完否则作废；同实例调试操作天然串行 → 前置跑只占用修复 agent 工作期间的实例空闲。仅在「已出现核心组缺陷 + 修复窗口时长 > 前置场景预估耗时」时启用，不满足条件一律串行等修复
3. **派发次序**：核心组先行——组内按依赖拓扑排序 + 无共享状态的场景并行（并发 ≤5，共享状态/状态累积链归串行组）；核心全绿后非核心组按依赖解锁
4. **核心短路 [MANDATORY]**：任一核心场景 fail → 非核心场景挂起不派发（已派出的收结果但不追加），先进修复循环——核心修复后非核心可能连带作废，先跑等于白验
5. fail → 先查项目排障文档（若存在，典型 docs/TROUBLESHOOTING.md，路径以 AGENTS.md 索引为准）匹配已知症状，再进入修复循环（领地互斥多组并行，规则见 consistency-review.md），修后只重验受影响场景（或其所在互斥组）；blocked → 如实报告环境/权限原因，禁止用 mock 变通冒充通过

## 收尾

1. 全绿后向用户交付汇总：目标达成对照表 + 合理偏差登记表 + 残留风险 + 覆盖概览 + 剧本分流结果（沉淀了哪些可复用 spec / 丢弃了哪些一次性脚本）
2. 主 agent 最终 commit（验收产物、可复用 e2e spec 与文档登记）。**impl-plan 不入本 commit**——台账/计划文档全程是盘面产物（`.tmp/`，plan.md 文档头 [MANDATORY] 禁令），终态回填写盘即闭环，禁止 `git add -f` 入库
3. **功能分级登记同步 [MANDATORY]**：交付引入了新功能/新用例，或既有功能的「挂掉后果」变化导致分级依据改变 → 同 commit 更新项目功能分级登记（如 `docs/FEATURE-PRIORITIES.md`）对应行 + 受影响 extension 包内文档头注（仅包内有 ARCHITECTURE.md / docs/ 的）；纯内部重构/等价修复不触发。项目无分级登记时跳过并在交付汇报注明
4. **重要文档资产更新检查 [MANDATORY]**：对照项目 AGENTS.md 文档索引登记的资产文档（典型：`docs/PRODUCT.md` / `docs/ARCHITECTURE.md` / `docs/CONTEXT.md` / `docs/DESIGN.md` / `docs/STANDARDS.md` / `docs/TEST-STRATEGY.md` / `docs/TROUBLESHOOTING.md`），按变更内容判定是否同 commit 更新——产品边界/用户画像变化 → PRODUCT；进程拓扑/分层/数据流变化 → ARCHITECTURE；新领域术语或语义漂移 → CONTEXT；视觉范式/token 结构变化 → DESIGN；编码规范变化 → STANDARDS；回归基线/测试分层变化 → TEST-STRATEGY；新增排障规则/日志路径 → TROUBLESHOOTING。路径以项目 AGENTS.md 索引为准（项目可能不同名）。**项目维护了采样管道资产目录时（见「剧本预编译」采样管道复用检查），本验收期新增/修改/淘汰的管道脚本同 commit 回写资产目录并同步其资产清单表**。零触发也必须在交付汇报注明「文档资产零同步」，禁止静默跳过
5. [OPTIONAL] 用户指示时做产物清理（临时 worktree 删除、调试存档归置、一次性验收脚本目录）
6. **自动衔接终态同步（阶段 6）[MANDATORY]**：最终 commit 落地后 read `../design-code-sync/SKILL.md` 按其流程执行——输入直接给出本流水线的设计文档与 impl-plan 路径（跳过该 skill 的「找文档」步），审查基线 = 本流水线最终 commit，审查对象 = 当前 HEAD 终态。其循环内 code-right/doc-right 修复按该 skill 自身验证纪律执行（增量测试绿、一轮一 commit）；修复触及验收场景表覆盖行为时重跑受影响场景（局部重验，不重开整门）。仅用户明示跳过可免，跳过须在计划「变更历史」记录

## 失败状态的可视边界

任一环节不绿时，交付口径必须是「未完成 + 差距清单」，禁止以部分通过的事实宣称整体完成。
