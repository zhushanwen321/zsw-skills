# 执行计划 — 预检门与 DAG 规划

> 阶段 0+1。输入：一份设计文档绝对路径。产出：自检通过、已基线落盘的 `<设计文档同名>.impl-plan.md`（全程不停等用户确认）。
>
> **产物路径约定 [MANDATORY]**：impl-plan 统一落 `<项目根>/.tmp/dev-flow/<basename>.impl-plan.md`（项目根 = `git rev-parse --show-toplevel`，worktree 解析为各 worktree 根；目标非 git 仓库时落 `/tmp/dev-flow/`）。`.tmp/` 是临时产物目录、在项目 `.gitignore` 中（全局 ignore 模板已含 `/.tmp/`）——**禁止 `git add`（含 `git add -f`）把该目录任何文件入 git**（全局 AGENTS.md「提交策略」同款禁令；gitignore 只对 untracked 文件生效，force-add 一次即永久入库）。基线 = 计划文件落盘完成，不依赖 git 跟踪。

## 阶段 0：预检门 [MANDATORY 不可跳过]

### 0.1 结构完整性

read 设计文档全文，核对四类内容存在。**编号不可依赖**——tech-design 两代结构并存（完整版 11 节：验收=§8、拆分=§10；精简版五段制：验收=§4、拆分=§5），一律按实质特征定位：

| 必备内容的实质特征 | 用途（缺失即打回） |
|--------------------|-------------------|
| 背景/目标：陈述要解决什么、达成什么 | 单元验收条款的回溯锚点 |
| 终态/机制：实现后是什么样、如何落到代码层（数据流/错误处理/共享接线点） | dev 实现的内容来源 |
| 验收：含「真实流程/通过标准」列的场景表 | 阶段 5 端到端验收的剧本；无此节无法验收 |
| 下一层拆分：unit 列表或等效分解 | 单元切分的种子 |

任一缺失 → 停止，告知用户回 tech-design 流程补文档。本 skill 不接管文档写作。

### 0.2 固化章节映射 [MANDATORY]

把上述四类内容在本文档中的实际位置写成映射表，后续所有 subagent task 从这里拿坐标，禁止自猜编号。此时在对话中呈现映射即可（编排者对照原文机械核对，不等用户）；阶段 1 建立计划文件时落入其「## 0 章节映射」节：

```markdown
## 0 章节映射
| 内容 | 本文实际位置 |
|------|--------------|
| 背景/目标 | §N <节标题原文> |
| 终态/机制 | ... |
| 验收场景表 | ... |
| 下一层拆分 | ... |
| 待验证检查点（无则记「无」） | ... |
```

### 0.3 对抗式审查通过的证据

向用户询问，或在以下位置依次查找旁路报告：`<项目根>/.tmp/tech-design/design-review-*.md`（现行产物路径）→ 设计文档所在目录 → 项目根（旧版位置 `.review/design-review-*.md`）：

报告格式兼容：若报告不含 tech-design 标准的 must_fix 字段，按其结论节人工判定「有无未解决的必修项」；判定不了 → 当作从未审查，现场补审。

- **有记录且 must_fix == 0** → 通过；把报告路径写进计划
- **有记录但 must_fix > 0** → 停止；列出问题清单，等文档修复后重来
- **从未审查过** → 现场补一轮完整对抗式审查再继续。派发方式按 tech-design 的 `flow/review.md`（主审 `tech-design-review` + 影响面审 `tech-design-impact-review` + 简洁审 `tech-design-simplicity-review` 三审并行；其 SKILL 与 rubric 的绝对路径从 available_skills 中 tech-design 的 location 解析，报告落 `<项目根>/.tmp/tech-design/`）。补审后仍 must_fix > 0 → 同样停止

门设在此处的原因：拿未经审查的设计直接开发，问题会在阶段 3 以「设计与实现双重返工」的代价暴露。

### 验收计划表（§4 内，阶段 1 产出 [MANDATORY]）

把设计验收场景表逐行编译成本表，**在流水线最早期就给出提速评估**，而不是到阶段 5 才发现可优化项：

```markdown
| # | 验收项（场景表行） | 方式(L0-L4) | 成本(1-10) | 收益(1-10) | 组 | 依赖 | 优化判定 |
|---|--------------------|-------------|------------|------------|----|------|----------|
| A1 | 计数口径与渲染 | L3 脚本 | 4 | 9 | 核心 | - | 可脚本化（testid 已有）；沉淀 e2e |
| A2 | 体验流畅性 | L4 agent | 8 | 5 | 非核心 | A1 | 无法降级 |
```

- **方式/成本**：按 SKILL.md 核心原则 3 的 L0-L4 分级；成本分 = 执行耗时量级 + 环境搭建 + 派发轮次综合（1=秒级静态规则，10=十分钟级多轮 agent 端到端）
- **收益分**：抓缺陷概率 × 缺陷逃逸代价（越晚发现的缺陷修复越贵；核心组主链路缺陷逃逸代价最高）
- **组**：核心 / 非核心（主链路 = 核心，走不通则其余验收无意义）
- **依赖**：前置验收项 id——功能依赖链上不先验前面的，后面的没法验
- **优化判定**：本项的提速手段——可降级（L4→L3）、可合并（与他项同领地/同环境并跑）、可脚本化（操作确定 + 标准可机器断言）、静态规则可消化（L0 守卫能覆盖的部分）

**提速结论 [MANDATORY]**：表后附一段——可降级 N 项 / 可合并 N 项 / 可脚本化 N 项 / L0 静态守卫清单（项目既有守卫脚本逐个列出），预计节省的派发轮次。随计划一并呈现给用户备查（陈述性展示，不构成等待点）。

**e2e 影响面圈定 [MANDATORY]**：§4 必须从设计文档「e2e 影响面评估」（tech-design 验收章节）继承并落成清单——现有 e2e / 真实进程 / 真实 LLM 测试面中受本次改动影响者逐个列出，每一项落到「跑（开发期，执行时点 = 所属单元 committed 后 / 阶段 5，空载串行）/ 不跑（理由）」之一；按改动面选择，禁止全量扫跑。PR/merge/CI 门禁不承担 e2e（与项目 pre-merge-check / CI 的 unit 轨同口径，SSOT = 项目 AGENTS.md 测试节）；圈定项里能以 mock / fixture 重放等价覆盖的，随所属单元顺手单测化（e2e 逐步单测化）。

**e2e 影响面机器对账 [MANDATORY]**：上清单必须与 `node scripts/select-affected-e2e.mjs --base <基线 ref>`（项目须有 `docs/testing/e2e-map.json` e2e 资产登记表；无此表的仓库跳过本步）的输出双向对账，差异逐条披露——机器输出有人工清单没有的 rule → 补进清单或落「不跑（理由）」；人工清单有机器输出没有的项 → 属人工判断（如新增能力尚无 e2e 资产登记），在计划中注明判断依据。对账是防漏的护栏、非替代人判断：脚本只按 scope 命中选 rule，看不见设计语义，最终清单以人工裁决为准。

### 计划自检 [MANDATORY]

主 agent 对着 DAG 图与单元表自检三件事，全部通过即开工，**不停等用户确认**（设计文档已经过对抗式审查收敛，计划评审由编排者自担）：

1. 切分粒度合理：无跨领地耦合、无空转单元、依赖方向与 DAG 一致
2. worktree 标记符合预期：隔离判据逐单元复核（见 `references/dag-authoring.md`）
3. 验收条款无遗漏：每个单元至少一条可机械核验的证据条款（命令输出/diff 形态），设计验收场景表的每一行都能落到某单元的验收条款**且出现在验收计划表中**（含方式/成本/收益/组/依赖五列与优化判定）
4. 验收计划表自洽：核心组覆盖主链路；依赖列无环；优化判定与提速结论已给出
5. e2e 影响面圈定无悬空：设计文档「e2e 影响面评估」的每一项都落到验收计划表或「不跑（理由）」之一，圈定子集已标注执行时点与空载串行要求；已与 select-affected-e2e 输出完成机器对账（差异双向披露，无登记表的仓库除外）

自检结论随计划一并呈现给用户备查（陈述性展示，不构成等待点）。仅当出现真正无法机械判定的歧义——如两个单元的领地必须重叠、设计文档内部自相矛盾——才停下问用户；其余情况直接进入基线落盘。

### 并行度复审（门槛触发 [MANDATORY]，基线落盘前）

自检通过后、**基线落盘前**，按门槛派 `parallelism-reviewer`（agent 定义见本 skill `agents/`，zcode 环境直接以该 subagent_type 派发；无 agent 注册机制的环境用 general-purpose + task 内嵌该 agent 文件全文）审一遍计划的并行度——自检清单管"对不对"，这步管"快不快"：串行边里的假货（测试依赖当代码依赖、保守默认边、零依赖资产后置、构建产物现用现建）从自检眼皮底下溜走的实测代价是整单元时长（2026-09-19 markdown HTML 支持实测：U2 仅因"测试可跑"边多串行 24 分钟）。

- **触发门槛**：实现链关键路径深度 ≥3 或单元数 ≥4。门槛内的两单元小计划不派（仪式感零收益）
- **派发**：task 给 impl-plan 绝对路径 + 设计文档绝对路径 + 项目根（三段式）；报告落 `<项目根>/.tmp/tech-design/` 同级或 `<项目根>/.tmp/dev-flow/`，一 plan 一报告
- **处置**：reviewer 只报告——主 agent 逐条裁决（采纳即改 DAG/单元表/验收计划表，改完重跑一遍「计划自检」；不采纳的记理由），裁决结果在计划「变更历史」记第一笔
- 头两个使用并行度复审的项目交付后回看其产出：连续零 finding 则降级为自检清单条目、砍掉派发（流程环节要能证明收益）

### 基线落盘

Write 计划文档到产物路径（见文档头 [MANDATORY] 约定）并校验可读回，即完成基线——**不 commit、不 `git add`**（`.tmp/` 是 gitignored 产物目录，force-add 一次即永久入库）。工作区若有本会话之外的改动一律不碰、不裹挟。

## 中断恢复

依赖 = 计划文件 + 状态表（落 `.tmp/dev-flow/`，不依赖 git hash）。程序见 SKILL.md「状态恢复」；计划期回本文档「计划自检」步续走，执行期转 `flow/execute.md` 第 1 步。
