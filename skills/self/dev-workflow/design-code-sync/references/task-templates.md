# Task 模板与条目 Schema

派 subagent 时按全局 AGENTS.md 三段式（背景/目标/验收）组装 task；以下模板可直接填充。

## 差距条目 Schema

每条 finding 必含八字段：

| 字段 | 说明 |
|---|---|
| id | F1、F2…（聚合与复审追踪用） |
| location | file:line 或 文档§章节（证据锚点，禁模糊指向） |
| gap | 差距是什么：现实与文档各自怎么说 |
| direction | doc-right（文档更合理 → 修代码）/ code-right（代码更合理 → 修文档）/ contested |
| severity | must-fix / suggestion / info |
| impact | 对整体交付的影响——这个问题误导了什么交付判断 / 会造成什么返工；**写不出影响 = 不立项或降 info**（纯时点细节不算差距，例：行号坐标漂移在符号仍可定位、语义仍成立时不立项） |
| rationale | 方向裁决理由；contested 时写明两边论点 |
| fix-hint | 修复建议（修复 agent 须重演验证，不照单全收） |

severity 判据（按"是否误导后来者"划线）：

- **must-fix**：误导后续开发/运维——过时的风险登记、悬空符号引用、行为与文档矛盾、状态表与现实不符、变更历史缺关键 commit。
- **suggestion**：不同步但不误导——措辞过时、新旧口径混用、命名不一致。
- **info**：知晓级——风格、可选改进。

direction 判据：

- **doc-right 默认**：设计文档过对抗式审查，是意图 SSOT；实现偏离默认视为漂移。
- **code-right**：实现期发现的文档盲区/错误，且实现行为有证据（测试、真实运行输出）确认更合理。
- **contested**：两边都有实质道理且影响公开 API / 行为语义 / 数据格式 → 必标，不得自行裁决。

## Reviewer Task 模板（三段式）

```text
背景：你是对抗式一致性审查者——只报告，绝不改代码改文档。
  仓库 <cwd>，审查基线 = 当前 HEAD（终态全量对照，不是 diff 区间——
  交付后的修复 commit 不在任何流水线记录里，只有全量对照能抓到）。
  设计文档 <绝对路径>；impl-plan <绝对路径或"无">。
目标：
1. read 设计文档全文 +（若有）impl-plan，对照当前代码实现逐章比对。
   审查关系五条：
   a. 代码 ↔ 设计文档：终态是否被完整实现；机制层（数据流/错误处理/
      共享接线点）是否一致
   b. 现实 ↔ impl-plan：状态表是否反映真实进度；残留风险登记是否已过时
      （已修复的风险仍标"待处理" = must-fix）；变更历史是否缺关键 commit
   c. impl-plan 内部：单元表 vs 状态表 vs 变更历史互相矛盾处
   d. 注释口径：测试文件头、生产文件注释声称的行为是否与当前实现一致
   e. 设计「关联登记面」× 存量文档同步：设计头部登记的关联面（决策记录/
      排障文档/功能分级等）逐项核对是否已按本次交付同步；设计无该字段时
      按交付语义扫描「声称行为被推翻/被修改」的登记面兜底，并立项提示补登记
2. 机械验证：文档/注释中反引号引用的标识符逐一 grep 验证存在，
   悬空引用/改名残留直接立项（severity 按"是否误导"判）；
   行号坐标漂移不立项（符号仍可定位、语义仍成立 = 无影响——核实目标
   是交付一致性，不是时点细节）；声称任何事实前必须 read 原文件核实到行级，
   禁止凭文件名想象
3. 逐条输出 finding（八字段 schema，impact 必填——写不出交付影响的不立项
   或降 info），每条附 file:line 或 grep 证据；
   某审查关系无发现必须显式说"在 X 关系未发现"，含糊的整体断言无效；
   多 reviewer 分区时只审自己的区，禁止引用其他 reviewer 的结论
验收：每条 finding 可回溯到具体文档章节与代码位置；方向裁决有理由；impact 说得清交付影响
```

## Fixer Task 模板（三段式）

```text
背景：你是修复执行者。仓库 <cwd>，第 N 轮修复。审查报告见 <粘贴全文或文件路径>。
目标：
1. 按 direction 执行：doc-right → 改代码；code-right → 改文档；
   所有等级（must-fix/suggestion/info）全部当轮修复，不留尾巴
2. 每条修复前先重演 fix-hint：推演修复后行为是否真解决 gap，
   建议方案站不住就换更稳方案，并在修复摘要中说明换法与理由
3. 波及扫描：每修一处，grep 同模式实例（同类注释、测试文件头、
   其他文档引用点）一并修；标识符删除/改名后确认无悬空引用残留
4. 改代码 → 跑增量测试必须绿（附命令与输出）；
   改文档 → 过联动自检五处（正文 / 数据流图 / 错误规格 / 拆分清单 / 验收场景）
约束：只动 finding 指向及波及扫描命中的文件；范围外必改时停下上报，禁止顺手改；
  禁止一切 git 写操作
验收：逐条 finding 列修复结果（改了什么 / 怎么验证的 / 波及点扫到几处），
  禁止无证据的"已完成"
```

## 聚合与复审

- 主 agent 聚合多 reviewer 报告时去重（同一 gap 多区命中合并为一条，location 并列）。
- 聚合后维护收敛表，逐轮更新：

| 轮 | must-fix | suggestion | info | contested | 备注 |
|---|---------|-----------|------|-----------|------|

- 复审（Step 4）task 背景附上轮 findings 全文 + 本轮修复摘要，目标只写三条：上轮各条是否真修复（含重演验证）、修复是否引入新差距、不重查已确认项。
