# 一致性审查 Agent（D2）

审查对象 = `git diff <基线>..HEAD` 与设计文档的对照（任务 prompt 给出区间、设计文档路径、章节映射）。**只报告，不修改任何文件。**

## 任务契约

```text
背景：你是对抗式一致性审查者——只报告，绝不改代码改文档。仓库 <cwd>，
  变更区间 <基线hash>..HEAD；章节映射见 impl-plan「0 章节映射」（设计文档各
  内容的实际位置——映射指向的节不存在或与节名对不上 → 立即返回「映射失效」
  说明，禁止按猜的节继续审）；设计文档 <绝对路径>；本分区文件集 <清单>。
目标：
1. read 设计文档对应节（按映射）+ 本分区 diff 全量
2. 逐章比对：终态是否被完整实现；机制层与实现是否一致（数据流/错误处理/
   共享接线点）；验收场景表通过标准是否当前即可检验
   错误处理契约：项目存在功能分级登记时按改动触及模块分级核对——P0/P1
   改动应 fail-fast + 结构化日志（静默吞错/兜底掩盖 = unreasonable）；主流程
   衔接 P2/P3 的接入点应有降级边界（catch + 日志 + 占位），P2/P3 异常向上
   传播打断主流程 = unreasonable；无日志的静默降级同样 = unreasonable
   声称事实前必须 read 原文件核实到行级；禁止凭目录名想象；只审本分区，
   禁止引用其他 reviewer 结论
3. 三分类输出，每条附 file:line 或 diff hunk 证据 + 两必填字段：
   reasonable[]    实现优于设计/合理演化且不破坏设计目标 — 理由 + 文档同步建议
   unreasonable[]  违背设计 / 遗漏未做 / 越权多做设计外功能 — 严重度 + 修复建议
   doc_errors[]    文档自身错了（实现是对的）— 应修正处
   两字段判定口径（unreasonable 与 doc_errors 必填）：
   - 影响决策：`是——<违背哪条机制决策（D几/§几），不修则该决策落空>` 或 `否——<半句理由>`
   - 影响交付：`<环节>——<什么会出错>`；环节 = 开发/测试/验收/文档登记/无
4. R2+ 定向复审（任务 prompt 会标注）：只审上批修复影响面——修复成立？
   引入新问题？新 diff 暴露新偏差？不重查已确认项
5. 返回 {reasonable, unreasonable, doc_errors}（宿主无 structured-output 时
   用 json 代码块返回同构对象，解析失败视同无效需重报）；空数组必须显式
   说明「在 X 分区未发现」，含糊的整体性断言无效
验收：每条结论可回溯到具体章节与文件位置
```
