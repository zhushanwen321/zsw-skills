# 流水线后修复与按需对抗审查

> 阶段 5 之后的持续守护。dev-flow 是一次性流水线：交付后任何独立 commit 不再触发
> 阶段 3 审查——本文件补上「何时必须回写文档、何时必须重跑对抗审查」的触发纪律。

## [HISTORICAL] 起因

2026-08-31 update 模块事故：流水线交付（时称 Gate B 双绿，即端到端验收全绿）后，用户授权修复一个登记过的
残留风险（UPDATE_DIR import 期烤死真实目录）。修复 commit 只改了代码与测试，未回写
impl-plan——事后对抗审查抓出 9 条漂移：残留风险登记仍标「待裁决」、变更历史断档、
已删除符号在设计文档 3 处悬空引用、6 个测试文件头注释仍描述已不存在的「import 期
求值」机制。教训固化为下方两条纪律。

## 触发条件 [MANDATORY]

流水线交付后，出现以下任一动作时必须走本流程（二者通常同时发生）：

1. 修复 impl-plan「残留风险」节登记过的任何条目
2. 独立 commit 触及设计文档声明机制所在的模块（注释级除外）

## 修复纪律 [MANDATORY]

1. **登记即债务，修复后同批标记完成**：修复登记过的残留风险时，同 commit 回写该登记
   （改写为已修复态 + 引用修复 commit + 修复触发依据），并在「变更历史」追加条目。
   禁止只修代码不回写登记；禁止跨 commit 回写（回写动作与修复同批提交）。
2. **符号形态变更同批清扫**：修复涉及符号删除/改名/常量改函数时——
   - grep 该符号在 docs/ 与全部测试注释中的引用，悬空引用同批清理（注释里描述
     已失效机制的段落一并改写，不只换符号名）
   - 项目配置了符号漂移守护（如 xyz-agent 的 `scripts/check-doc-symbol-drift.mjs`，
     约束登记 C-proc-10）时必须跑过
3. **收尾自检**：修复 commit 的验证面是类型 + 测试 + lint——注释与文档正确性不在
   机器信号内，靠下方对抗审查兜底，不靠「我改干净了」的自感。

## 按需对抗审查 [MANDATORY]

修复 commit 落地后，后台异步派发独立 reviewer（general-purpose + task 内嵌指令，封闭上下文）
做**定向**审查——只审该 commit，不重开全文审查：

- 审查对象：`git diff <修复commit>^..<修复commit>` × 设计文档 + impl-plan
- 审查模板复用 `flow/consistency-review.md` 的 reviewer task 模板，变更区间改为
  单 commit 范围；如 impl-plan 登记表/状态表与该 commit 相关，一并纳入对照
- 三分类输出（reasonable / unreasonable / doc_errors），处理链同 consistency-review：
  doc_errors 主 agent 修，注释级可派 subagent 批量修， unreasonable 打回修复
- 审查结论（**即使零发现**）回写 impl-plan 变更历史——零发现也是有效证据，
  证明该 commit 经过了独立审查。回写是写盘动作（`.tmp/` 不入 git），不产生 commit

## 与既有环节的关系

| 环节 | 审查对象 | 本文件补充 |
|------|----------|-----------|
| 阶段 3 一致性审查 | 流水线内 diff（基线..HEAD）× 设计文档 | 流水线外 commit 无对应环节 → 本文件补上 |
| 阶段 6 终态同步（design-code-sync） | 交付时点 HEAD 终态全量 × 设计文档（双向校准） | 交付后独立 commit 无对应环节 → 本文件补上（定向单 commit 审查，不重开全量校准） |
| 符号漂移守护（机器） | 文档符号 × 源码导出表 | 只抓符号存在性，抓不住机制描述失真 → 仍需本文件的对抗审查 |
