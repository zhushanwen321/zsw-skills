# 风险分级与执行深度

风险分级决定流程成本，不改变 accepted 的语义。不要因为任务小就省略证据，也不要因为任务新就堆叠所有审查。

## 判定输入

按实际失败后果评估，不按文件数量或预期工作量评估：

- 是否修改持久数据、权限、安全边界或不可逆状态；
- 是否跨模块、跨进程或接入外部宿主；
- 是否有多个生命周期、异步任务或共享状态；
- 是否是项目没有先例的新机制；
- 失败能否快速发现、回滚和恢复。

## 路由

| 等级 | 典型情况 | 最小执行深度 |
|------|----------|--------------|
| low | 局部、可逆、已有测试基线的 bug 修复 | 简短契约；一个实现增量；独立覆盖核对；探索性审查可 not-required |
| medium | 普通功能、跨两个以上模块、新增外部接口 | 完整契约与设计审查；独立覆盖核对；按缺口决定探索维度 |
| high | 新子系统、持久状态、安全、异步生命周期、共享宿主状态 | 优先实施增量；强制探索性审查；强制相关场景证据 |

## 探索维度

维度名由任务自行选择，常见通用维度：

- assembly：模块是否真实装配并连接；
- data：写入、序列化、读取、迁移是否满足同一契约；
- lifecycle：启动、重载、恢复、关闭及异步交错；
- control：开关、配置、权限是否覆盖所有相关路径；
- security：不可信输入、越权、隔离与信息泄露；
- failure：异常、降级、重试、部分失败是否按声明传播；
- host：宿主及相邻功能是否保持原有不变量。

只选择与本任务风险相关的维度，不为了形式完整全选。

## 用户裁决点

以下情况必须呈现给用户，不能由 agent 自行拍板：

- 修改用户目标、非目标或不可接受风险的行为；
- 接受 unknown、partial、failed 或 open finding；
- 方案之间存在不可逆或高代价取舍；
- 探索审查发现原契约遗漏了重要行为。

全托管授权只表示主 agent 可以连续执行流程，不表示可以替用户接受事后才出现的具体风险。
