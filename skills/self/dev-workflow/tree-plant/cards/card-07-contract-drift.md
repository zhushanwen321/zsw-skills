# 判据卡 7：契约漂移（修剪类别攻击收尾必做）

## 攻击目标

实现与外部接口核实表（fact-check.md）的逐行对账：实现里用了表外的接口形态、表里登记的形态被实现改掉、表外私增依赖。这张卡是唯一保留的「一致性」检查——对象是接口核实表（事实登记），不是设计文档措辞。

## 历史实证

- V5 场五处契约错（cwd 形态/registerCommand 单对象签名/含空格命令名/工具参数/usageNote）：mock 与实现同错，三份同构假契约互相背书，一路验收到 accepted、真实宿主全失效——本卡存在的理由
- bare 场反例证明：实现前逐行核 SDK（行号级），五处全对——本卡的通过形态

## 探针形态

0. **表 vs 真实源码（先做这条）**：逐行打开依据列登记的源码位置，比对真实签名与登记的「形态」——若核实表本身是虚构的，表与实现会对得上（两边同错），只有这个方向能抓到；抽查发现表错即回扎根重核全部同簇行
1. 逐行对账：接口核实表每行 → grep 实现里该接口调用点 → 比对调用形态（参数个数/顺序/返回处理）与登记一致
2. 反向扫描：实现中全部外部调用点（grep 宿主 API 前缀）→ 每个点必须能指回表内某行；指不回 = 表外私增
3. case 重跑：表内每行关联的实机 case 当前代码下仍绿
4. 只写不读字段审计（清单驱动）：先列 diff 范围内全部 export 符号 + 落盘字段/状态变量清单，再逐个 grep 调用点/读取点，清单项零命中 = 零引用导出/死字段——不列清单逐个发现会漏（历史实证：攻击驱动漏 2-4 处）
5. 平台契约项枚举对账：枚举交付物触达的全部平台契约项（注册函数的全部可选字段/呈现与输出通道/模式变体/补全回调），比对实现实际采用情况
6. 声明对账：design/api 声明的可构造行为与声明的文件/字段，逐条对实现核对

## 判别判据

- 登记形态与依据列源码位置的真实内容不符 = 核实表虚构（最高优先级，回扎根重核）
- 调用形态与登记不一致 = 缺陷（以真实源码为准修实现，或回扎根重核修表）
- 实现存在表外调用点 = 缺陷（补核入表或删除调用）
- 同一落盘文件/状态存在多个写入实现（同义双函数互为条件跳过、先到者定内容）= 重复保险式缺陷，收敛为单一写入入口
- 零引用导出/死字段（清单式全量 grep 零命中）= 发现（导出但全仓零调用点）
- 平台契约项已枚举而实现未采用且无登记取舍 = 半成（弃用合法，静默弃用不合法）——枚举范围限「交付物触达的契约项」，不得扩为平台每个可选字段全量登记
- 声明的可构造行为或声明的文件/字段存在性，经对账无实现支撑 = 半成——锚定形态五类：格式版本处置（构造高版本条目断言跳过/保留行为）/ 未知字段保留 / 降级路径 / 恢复通道 / 声明文件与字段存在性
- 交付入口与验证入口不一致 = 缺陷：package.json scripts（test 等）对外部用户必须可跑——验证走了自配入口而交付入口在干净环境必败 = 声明的可用性与实态不符

## 修复模式与回归

漂移修复后重跑关联 case；若登记本身错（源码核实推翻），回种子扎根更新表并重跑 root gate——不静默改表。
