# 判据卡 7：契约漂移（P1 收尾必做）

## 攻击目标

实现与外部接口核实表（fact-check.md）的逐行对账：实现里用了表外的接口形态、表里登记的形态被实现改掉、表外私增依赖。这张卡是唯一保留的「一致性」检查——对象是接口核实表（事实登记），不是设计文档措辞。

## 历史实证

- V5 场五处契约错（cwd 形态/registerCommand 单对象签名/含空格命令名/工具参数/usageNote）：mock 与实现同错，三份同构假契约互相背书，一路验收到 accepted、真实宿主全失效——本卡存在的理由
- bare 场反例证明：实现前逐行核 SDK（行号级），五处全对——本卡的通过形态

## 探针形态

1. 逐行对账：接口核实表每行 → grep 实现里该接口调用点 → 比对调用形态（参数个数/顺序/返回处理）与登记一致
2. 反向扫描：实现中全部外部调用点（grep 宿主 API 前缀）→ 每个点必须能指回表内某行；指不回 = 表外私增
3. case 重跑：表内每行关联的实机 case 当前代码下仍绿

## 判别判据

- 调用形态与登记不一致 = 缺陷（以真实源码为准修实现，或回扎根重核修表）
- 实现存在表外调用点 = 缺陷（补核入表或删除调用）

## 修复模式与回归

漂移修复后重跑关联 case；若登记本身错（源码核实推翻），回种子扎根更新表并重跑 root gate——不静默改表。
