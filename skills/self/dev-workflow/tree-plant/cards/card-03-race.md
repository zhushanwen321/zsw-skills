# 判据卡 3：状态机竞态

## 攻击目标

多进程/并发读写同一存储时的四问：双持锁可能吗？接管会破坏互斥吗？同内容会写两条吗？读会不会踩到半写状态？

典型形态：O_EXCL 建锁文件后写 owner 元数据——两步间崩溃留空锁，接管逻辑对空 payload 立即拆锁 = 双持；无条件删锁放行第三进程；并发 edit 同一 id 终态撕裂；read 攒着写者刚截断的文件。

## 历史实证

- ds41fe-sv2 场：v1 锁双持真竞态（both locked=true 实测复现），模型自发压力循环 3 分钟抓到
- V2 场 F-A42→A45：锁属主自查缺失（无条件删锁）→ 修复 → 登记缺口再补
- step5-sv4 场 F-X35 修复引入 claim 机制直接产生 4 条新 finding（修复自我供养的样本）
- V2 场 F-A23→A33→A48：config 写读撕裂窗口族（原子写→同 fd 配对读→写侧收尾锚）

## 探针形态

1. 真实子进程并发（≥4 写者 ×N 条互异内容）：断言终态全量、零丢失、零重复——不是 mock 并发
2. 同文本并发写：断言恰好一条（内容寻址/锁内查重）
3. 锁竞争中途 SIGKILL 一方：断言存续方可安全接管且互斥不破
4. 并发 edit/delete 同一 id：断言终态一致性（新内容或删除，不撕裂）

## 判别判据

- 互斥原语与元数据两步分离 = 竞态缺口（应单步原子原语：mkdir/改名）
- 「锁内检查-写入」必须是同一原子段
- 两进程并发改写同一 id 的终态语义（后写覆盖/版本条件写/拒绝）未声明、删除留痕取舍未声明 = registered 发现（声明级缺口，登记不阻塞）

## 修复模式与回归

并发用例进验收 case（真实子进程形态）；变异验证 = 摘掉查重/接管判定，并发用例必红。
