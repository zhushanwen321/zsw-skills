## 核心挑战

Tool description 设计最大的陷阱：**把它写成功能说明书而不是行为约束器。** 模型已经从工具名称和参数 schema 知道工具能做什么，它需要知道的是什么时候不能做、什么时候必须做。

第二个陷阱：**给所有工具写一样长的 description。** 风险等级不同，深度必须不同。给一个只读查询工具写 400 字的 description = 浪费 context 且可能稀释真正高风险工具的约束权重。

## 设计维度

### 维度 1：调用条件（When to Use）— 精确到场景级别

**为什么重要**：模型不会天然知道"这个场景应该调这个工具"。如果触发条件太模糊，模型要么没调（该用时没用），要么调了不该调的（[F4 工具误用]）。

**决策指南**：

- 信号驱动的触发条件：不只是"什么时候用"，而是**什么信号触发调用**
  - 用户说了什么关键词？
  - 系统处于什么状态？
  - 前置条件是否满足？
- [P1 行为约束] 调用条件和系统状态绑定：`"Use this tool only after X completes successfully."` — description 的重心在约束行为，不是描述功能
- 数量规则：触发条件超过 3 条 → 可能这个工具职责太宽，考虑拆分。只有 1 条且太宽泛 → 加上排除条件缩小范围
- 来源：观察模型**实际漏调**或**误调**的场景——那些场景就是调用条件需要加固的地方

**验证问题**：一个新上手的开发者读了这个 description，能不能在 5 秒内判断出"当前应该调这个工具吗"？

### 维度 2：反模式（When NOT to Use）— 具体场景枚举

**为什么重要**：[F4 工具误用] 是整个系统中最常见的失败模式。模型会在错误场景调用工具——不是因为它"不知道更好"，而是因为它不知道"这不是那个工具的职责"（[P4 反模式枚举]）。

**决策指南**：

- 反模式来源不是凭空想象，而是观察模型的实际误用行为。**先跑一段时间不加反模式的版本，记录实际误用，再补齐反模式**
- 每个反模式的写法：
  - 描述一个具体的误用场景：`"Do not use this tool to check file existence — use list_items instead."`
  - 解释为什么会被误用：模型可能产生什么错觉？（如：模型认为 update + check 是同一件事）
  - [P3 数字阈值] 用精确数字消除歧义：`"after at least 3 consecutive failed attempts"` 而非 `"after multiple failures"`
- [P2 风险∝密度] 反模式数量与风险成正比：低风险 1-2 条，中风险 2-4 条，高风险 4+ 条
- 反模式的排序：最频繁发生的误用场景放在最前面——模型更可能记住第一条

**验证问题**：如果把反模式列表全部删除，模型下一步最可能在什么场景误用这个工具？

### 维度 3：能力边界 — "你不能用这个工具来 X"

**为什么重要**：[P6 能力边界] 模型会基于工具名称和功能**推断**它的能力范围，而这种推断往往是错的。`update_goal` 听起来像能做一切和 goal 相关的事，但如果它不能 pause/resume，必须声明。

**决策指南**：

- 判断标准：工具的名称或功能描述是否可能让模型联想出超出实际范围的操作？
- 格式：`"You cannot use this tool to [具体操作]."`
- 和反模式的区别：[F4 工具误用]（反模式）说的是"在错误场景用对了工具"，[F5 范围蔓延]（能力边界）说的是"用了这个工具做它不支持的操作"。两者独立但互补
- 能力边界必须**白名单式**声明——不能说"你只能用这个工具做合理的事"，模型不知道什么算合理
- 不需要为每个功能声明能力边界——只声明"看起来像但实际不是的"操作

**验证问题**：给 5 个不同的人读工具名称和参数 schema（不看 description），问他们"这个工具能做什么"。如果某人的答案超出了实际能力，那就是需要声明的能力边界。

### 维度 4：跨工具约束 — 建立工具链

**为什么重要**：[P9 工具链约束] 模型不会自动推断工具间的调用顺序。如果不声明 A 在 B 之后才能用，模型会直接调用 B——然后因为数据不完整而失败（[F8 工具链断裂]）。

**决策指南**：

- 三种约束类型：
  - **前置条件**：必须先调用哪个工具？`"Use this tool only after list_items returns results. Do not guess item IDs."`
  - **互斥关系**：不能和哪个工具同时使用？`"Do not call this and X in the same turn — their effects conflict."`
  - **优先级**：两个工具都能做时优先用哪个？`"If both this tool and X could solve the problem, prefer X."`
- **双向原则**：如果工具 B 必须在 A 之后调用，在 A 的 description 中不需要反向声明"B 可以在你之后调用"。但如果是全局优先级规则，必须在 System Prompt 中也声明一次协同——防止模型从另一个方向看不到优先级（[F12 优先级网络断裂]）
- **只在有真实依赖时声明**。不要为了"完整"而编造不存在的工具链关系——多余的声明和没有声明一样有害

**验证问题**：把所有工具名前两字遮住，只读跨工具约束，能否还原完整的工具调用流程图？

### 维度 5：正反面示例 — 示例优于规则

**为什么重要**：[P5 示例驱动] 模型通过示例学习"边界在哪"比通过规则推断更准确。一条反模式 + 一个具体的正反面示例 = 模型真正理解了规则的意思。

**决策指南**：

- 高风险工具必须至少各 1 个正反面示例；低风险工具可选
- 每个示例附 `<reasoning>` 解释为什么——模型不是看示例的结果，而是看推理过程
- 示例的选择：选最容易被模型误用的场景，而不是最典型的场景。典型的场景模型自己也会做对
- 示例不是"写对了长什么样"，而是"这里有个难以判断的边界，正确做法是 X"
- 示例的更新：观测到新的误用 → 添加新示例。示例集应该随时间增长

**验证问题**：删掉所有规则文本，只留示例，模型的行为会不会比"只留规则没有示例"更准确？

### 维度 6：参数级约束 — 双重冗余

**为什么重要**：[F1 规则被忽略] 关键参数（如 status 的 complete/blocked 值）如果只在参数 description 中出现一次，模型可能忽略。核心约束需要在多个位置重复声明。

**决策指南**：

- 不是所有参数都需要参数级约束——只对**行为影响大**的关键参数做
- 双重冗余策略：参数 enum/description 中声明一次 + 工具 description 中的"调用条件"或"反模式"中重复一次
- 例如：`status` 参数的 `blocked` 值，在参数 description 中说"blocked: work cannot proceed"，在工具 description 的反模式中说"Do not use blocked because work is hard or uncertain"
- 注意冗余 ≠ 复制粘贴。两个位置的措辞不同但含义相同——模型从不同角度接受同一个约束

### 维度 7：生命周期结构 — 高风险工具专用

**为什么重要**：[P10 生命周期结构] 涉及多阶段操作的工具（如 goal 管理工具），模型在每个阶段需要不同的行为指导。平铺式 description 让模型在不同阶段都看到同样的文本，无法针对性引导。

**决策指南**：

- **适用条件**：工具操作后有明确的后继步骤（如 goal update 后需要 completion audit），且不同步骤需要不同行为约束
- 结构：按 before → during → after 组织
  - before：前置条件检查
  - during：操作本身的行为约束
  - after：操作后的验证和收尾
- **这不是必须项**。如果工具只有单一操作（如 read 文件），生命周期结构反而增加认知负担
- 生命周期结构放在工具 description 中，而不是分散到 steering prompt 中——确保模型在调用这个工具**之前**就看到了整个流程

## 风险驱动的分级

| 风险 | 长度 | 反模式 | 示例 | 是否需要生命周期 | 适用 |
|------|------|--------|------|----------------|------|
| 低 | <60 字 | 1-2 | 可选 | 否 | 只读查询 |
| 中 | 60-150 字 | 2-4 | 建议 | 否 | 轻量操作 |
| 高 | 150-400 字 | 4+ | 必须 | 按需 | 状态变更/编排 |

**[P14 约束衰减] 越级惩罚**：低风险工具写了 300 字 description → 浪费 context，稀释高风险工具的注意力权重。所有工具的 description 都很长 → 核心约束被淹没，整体服从率下降。

### 动态 Description（实现考虑）

[Codex 原则 11] 当工具的可用性或行为依赖运行时配置时，description 应该动态生成，确保约束与实际环境一致。

**什么时候需要动态生成**：
- 工具只在特定 mode 下可用（如只在 goal mode 下可用）
- 工具的行为因配置不同而不同（如 sandbox 模式下的额外限制）
- 工具的调用条件中包含运行时数据（如当前可用的插件列表）

**实现方式**：description 用函数而非静态字符串，运行时注入当前状态。如 `"This tool is only available in goal mode. Current mode: ${getCurrentMode()}."`

**注意事项**：动态内容不应改变核心约束的语义，只应改变"当前是否可用"和"当前的行为参数"——核心反模式和能力边界始终不变。

## 最致命的 3 个失败案例

1. **缺少反模式** → [F4 工具误用]。最典型：把 update 工具当 create 用，跳过创建阶段直接调用更新
2. **缺少能力边界** → [F5 范围蔓延]。如认为 `update_goal` 能 pause/resume goal
3. **缺少跨工具约束** → [F8 工具链断裂]。如不先搜索就直接安装一个包

## 与其他载体的协作

- **System Prompt**：全局工具优先级和编码规范不放在单个工具 description 中。如果一条规则对 3 个以上工具都有影响，它应该在 System Prompt 中
- **Steering Prompt**：运行时行为引导（如 completion audit）放在 steering prompt 中，在 goal turn 完成时注入，不放在工具 description 中——工具 description 是静态的，不随系统状态变化
- **Error Message**：工具失败后的行为引导放在工具返回值中，不放在 description 中。description 告诉模型"调用前该知道什么"，error message 告诉模型"失败后该做什么"
- **Safety Policy**：高风险工具在 description 的调用条件中标注"此操作需 Guardian 审批"，但不写 Guardian 的具体规则——那是 Safety Policy 独立的职责

## 设计走查

完成 Tool Description 设计后，按此顺序自检：

1. **功能说明书测试**：删掉所有"能做什么"的描述（因为工具 name + params 已经说了），description 还能约束模型行为吗？
2. **反模式真实性**：每条反模式是不是来自实际观察到的误用？还是你自己猜的？
3. **能力边界测试**：5 个不同的人读了工具 name + params 会推断出哪些操作？它们都在你的能力边界声明中了吗？
4. **跨工具依赖测试**：从 description 中提取所有其他工具的名称——如果有的工具只在这里提了一次，全局没有，检查是否有遗漏
5. **风险匹配检查**：工具的风险等级和 description 长度/反模式数量匹配吗？
6. **约束衰减检查**：这个工具 description + system prompt 和其他 tool description 的总约束是否超过阈值？如果是，system prompt 中可能有规则应该移到具体的 tool description 中
