# 证据信号清单（三层）

> audit 模式第 2 步的完整规格。三层证据各自独立产出，主 agent 聚合后才进排序——禁止用单一层结论直接定候选。语义层结论不得由主 agent 单方拍板（见 SKILL.md 约束）。

## 第一层：可计算信号（确定性工具，bash 并行，只读）

| 信号 | 工具 | 阈值/口径 | 降级路径 |
|------|------|-----------|----------|
| 无调用方导出/依赖 | knip（若项目已配） | 列表输出；测试引用**排除**（Fowler 豁免——audit 层口径，见下「两处口径差异」） | grep `export` × `git grep` 引用计数（word-boundary，排除注释/re-export 行） |
| 纯转发方法占比 | grep 签名匹配（方法体仅委托调用，无校验/变换/语义增值） | 转发方法数/总方法数 >20% 报候选 | 无（grep 零依赖） |
| 单实现接口/抽象类 | grep implements/extends + 实现计数 | 实现数 =1 报候选（需语义层确认非刻意取舍） | 同左 |
| 抽象链深度 | code-review-graph（可用时优先）调用链静态追踪 | 单链 >4 层报候选 | grep import 链近似 |
| 认知复杂度热点 | eslint-plugin-sonarjs（若项目已配） | 仅作定位辅助，**不单独成候选**——复杂度高可能是本质复杂度 | 跳过，报告标注「证据等级：降级」 |

**两处「引用」口径差异（有意相反）**：audit 可计算层**测试引用排除**（speculative generality 判定看真实调用方，测试不是）；pre-commit 断言**测试算引用**（自动拦截宁宽松防误拦）。前者防漏报、后者防误拦。

**已知漏拦（pre-commit 断言的四类，audit 层负责兜底捕捉）**：①撞名符号（含 `.open()` 成员访问形态——正则剔除必误杀真引用）②import 占位（声明即被计为引用）③动态引用/字符串拼接 ④default/别名导出（提取失真）。audit 层用 knip 精确分析 + 语义五问补充捕捉，不依赖 grep 计数。

## 第二层：语义层（subagent 并行扫，五问框架）

每个可疑抽象必须回答五问，输出带证据行号，无证据的怀疑丢弃：

| 问 | 判定动作 | 理论出处 |
|----|----------|----------|
| ① 它赌的决策是什么？会真变吗 | 每个抽象必须能指出「它隐藏的困难且预计会变化的设计决策」；答不出具体决策（只说「以后可能换实现」而无真实变更证据）= 投机抽象 | Parnas information hiding (1972) |
| ② 间接成本是否超过认知压缩 | 接口复杂度 ÷ 实现复杂度接近 1 = 浅模块；引入新派生态/执行顺序依赖/纯胶水而未消除本质状态 = 净增偶然复杂度；读者被迫经过用不到的抽象层才能干活 = abstraction 强加 | Ousterhout 深浅模块；Out of the Tar Pit；Cognitive Dimensions |
| ③ 依据是已发生证据还是想象未来 | 抽象合法依据是已发生 ≥3 次的真实变体（Rule of Three）；两段代码只因同一变化原因同时变才该合并（DRY 是关于知识不是文本）；无当下真实需求方的能力在持续收持有税 | Rule of Three；DRY-knowledge；YAGNI 四成本 |
| ④ 反模式信号 | 见下方反模式清单，逐条核对 | Fowler/Gabriel 等 |
| ⑤ **SDK 影子层** | 底层 SDK/宿主 API **已直接提供**该能力（同步返回值、可订阅事件、getter、既有常量），却又自造一层轮询/重试/守卫/状态跟踪/归一化去拿**同一事实**。判据须同时满足：(a) 指出 SDK 等价面（事件名/方法名/返回语义 + 行号）；(b) 自造层无新增信息（同样的事实换个更贵的方式拿到）；(c) 防御类机制还须回答：防御所针对的外部行为，写防御之前验证过真的会发生吗——未验证 = 按想象失败处理。**打不开行号证据的指控降级为「疑似」** | 源头案例 C（SSOT §2.4）、案例 D（SSOT §2.5）|

### 反模式信号清单（问 ④ 的核对表）

- **inner-platform effect**：配置项组合图灵完备（有条件/循环/变量）；出现「元表」「字段自定义」机制；用户用 DSL 表达的东西等价于几十行宿主语言代码
- **abstraction inversion**：调用方在「更高层」重建「更低层」已有的能力；分层方向与依赖方向倒挂
- **leaky abstraction**：使用者必须同时理解抽象层和底层才能正确使用；修 bug 必然穿透抽象层；文档必须教抽象之下的原理
- **pass-through / middle man**：一个模块大部分方法只是原样转发；「该层被删除后调用方直接调目标，行为不变」；装饰器常是浅转发
- **second-system effect**：重写/重构方案里出现大量「这次顺便把通用性做进去」「支持以后可能的所有 X」；当前真实调用方数为 0 的能力占比过高
- **Greenspun's tenth rule**：渐进式重造运行时设施（自制 GC/动态分发/闭包对象/反射）——单看每个都合理，合并看是在重写语言
- **SDK 影子层（ reinvented capability / polling-for-a-known-fact ）**：底层已给出事实，却又造一层延迟版或副本版去重新获得它。四种典型形态：
  1. **轮询替事件**：SDK 有可订阅事件直接表达该事实，却用 `setTimeout`/`setInterval` 过一段时间回来看一眼（例：pi 的 `message_start` 即「轮次已启动」，却用 30s 定时器确认）；
  2. **镜像替 getter**：SDK 有 getter/返回值直接给当前状态，却手工维护一份状态跟踪再对账（例：有 `getCurrentModel()` 却自建 model 状态机）；
  3. **重试替幂等**：被包调用本身已幂等或已由 SDK 保证，却又包一层 try/catch + 重试 + 兜底；
  4. **归一化替契约**：SDK 类型已收窄为单一形态，却保留运行时 `Array.isArray` 之类的容差分派。
  **与「本质复杂度」的分界**：若 SDK 确实**没有**等价面（能力真缺口），绕法是合理的——判定必须落到行号证据，不能凭「感觉有更简单的路」。
  **与「双重保险防线」的分界**：事故登记只是第二道防线合法的必要条件，还须**事故根源已修复**。根源未修、靠补偿机制（对账函数、定时巡检、状态守卫、重发机制这类）撑着的，补偿机制本身进简化候选——判别法：把补偿机制删掉，问题还在 = 它只遮症状不治病。为**想象中的失败**加的是影子层（源头案例 D，SSOT §2.5）。

### 豁免（不进候选）

- **Fowler 豁免一**：框架代码可为使用者保留未用功能（判定：库/框架的公共 API 面）
- **Fowler 豁免二**：被测试引用的能力（audit 层口径；但注意测试只证明「可被调用」不证明「有人需要」——大量仅测试引用的导出仍是候选，降级为「疑似」）
- **本质复杂度**：问题本身难的代码（五问 ② 通过）——列入「已核实非过度」，不进候选
- **有变更证据的隐藏决策**：平台绑定、供应商 SDK、已知格式迁移等有真实变更史的 Parnas 合法隐藏

### 通用性边界（五问 ①③ 的裁决线）

Ousterhout「模块应略通用」与 YAGNI「别提前设计」的冲突，裁决线：为**同一问题域内已观察到的第 2-3 个变体**泛化（证据驱动，合法）；为**想象中的其他场景**泛化（YAGNI 兜底，投机）。

## 第三层：业务层（LLM 读文档，主 agent 执行）

每个复杂机制映射三件事：**保证什么**（它向调用方承诺的完备性/一致性/兼容性保证）→ **服务谁**（真实调用方/场景清单）→ **用量证据**（该场景的调用证据）。输入优先级：项目设计文档 > ADR > README > 代码注释 > 问用户。产出是候选卡片「小取舍」段的原料：牺牲这个保证，哪些调用方/场景受影响。

## subagent 派发规格 [MANDATORY]

- **清单内联**：subagent 不自动加载 skill——主 agent 先 read 本文件，把五问问句与反模式清单**逐字内联**进派发提示词，禁止让 subagent 凭空扫。
- **规模**：单 subagent ≤5 文件 / 3000 行；超限模块按子目录再拆；并行 ≤5。
- **三段式提示词模板**（占位符由主 agent 填充）：

```text
## 任务背景
你在审查仓库 <仓库绝对路径> 的模块 <模块路径>，找「过度设计/过度抽象」：
为边缘需求或想象场景付出不成比例复杂度的构造。本审查只报告，绝不修改任何文件。

## 目标
对范围内每个可疑抽象（单实现接口、纯转发层、无调用方导出、注册表/工厂、
投机扩展点、完备性保证机制、**SDK 影子层**），逐字核对以下五问并回答：
① 它赌的决策是什么？会真变吗？（答不出具体决策 = 投机）
② 间接成本是否超过认知压缩？（浅模块信号：接口复杂度≈实现复杂度；
   引入派生态/顺序依赖/胶水而未消除本质状态；调用方被迫穿越用不到的层）
③ 依据是已发生的证据（≥3 真实变体/真实调用方）还是想象未来？
④ 反模式核对：<粘贴上方反模式清单全文>
⑤ SDK 影子层：该事实/能力，底层 SDK 或仓内共享层是否已直接提供（同步返回/
   可订阅事件/getter/既有常量）？若判「已提供」，必须给出等价面的**行号级**
   证据（实际打开实装或类型定义确认），并说明自造层为何没有新增信息；
   打不开证据的必须降级为「疑似」而不能进候选。防御类机制另答两问：
   它防的外部行为，验证过真的会发生吗（未验证 = 影子层）；事故驱动的
   防线，事故根源修了吗（未修而靠它撑着 = 补偿机制，进候选）。

## 验收
- 每条发现必须附：位置（file:line）+ 五问逐条回答（第五问 = SDK 影子层）+ 调用方清单（grep 结果）
- 对每个「SDK/共享层已提供」的指控，必须实际打开对应实装/类型定义确认并给**行号级**证据；打不开证据的降级为「疑似」并注明
- 无证据行号的怀疑丢弃；五问全过的高复杂度代码列入「疑似本质复杂度」并给理由
- 以结构化文本返回：每条一个块（位置/五问/调用方清单/初步方向建议
  doc-right|code-right|contested），此记录将存档进审计报告附录
```

- **派发后**：后台异步，通知到达即收报告，多分区先到先读、聚合去重。主 agent 对每条「投机」结论抽验 ≥1 个调用方（实际读调用点代码）后才进候选。
