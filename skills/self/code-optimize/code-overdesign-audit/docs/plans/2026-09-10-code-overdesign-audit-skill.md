# 过度设计审计 skill（code-overdesign-audit）技术设计

> 一句话结论：独立 skill `code-overdesign-audit`，以「三层证据 → 杠杆排序 → 卡片报告 → 裁决后执行」五步流程识别过度设计并论证「小取舍 → 大简化 → 核心价值不变」，配套 pre-commit 可计算信号断言防新增；不改造现有 skill，不做全自动修改。

**层声明**：当前层 = skill 行为规格设计；下一层产物 = SKILL.md + references/*.md + pre-commit 断言配置（可实现的接口/技术方案层）。

---

## 1. 背景目标

### 1.1 SCQA 开篇

- **Situation**：本仓库的 skill 体系里，`code-simplify` 管代码级行为不变的简化（死代码/重复/复用，默认只扫最近改动），`improve-codebase-architecture` 管架构级「做深模块」（Ousterhout 风格 deepening）。
- **Complication**：真实项目里反复出现第三类问题——**需求/设计级的过度设计**：系统为边缘需求、极端场景或完备性保证付出不成比例的复杂度。两个真实案例（详见 §2.2）：session-reader 设计为「唯一解析入口 + 三副本全修 + 迁移窗口期全可见」三层完备性保证叠出 v9.2 版设计文档；subagent 通知机制靠人工直觉做对了取舍（零载荷/弃镜像帧/推送不轮询），但这套判断无法复用。
- **Question**：如何把「发现过度设计 + 论证高杠杆简化（简化一点点设计，可维护性/可理解性大幅提升，且核心价值无损）」工具化为可复用的 skill？
- **Answer**：新建 `code-overdesign-audit` skill，用三层证据（可计算信号 + 语义五问 + 业务保证映射）定位候选，按杠杆排序产出带完整论证的候选卡片，用户裁决后才执行；同时把可计算信号落成 pre-commit 断言阻止新增投机复杂度。

### 1.2 系统是什么（受众背景补足）

读者假设：会用 zcode/pi 类 CLI coding agent 和其 skill 机制，但不知道本次调研背景的开发者。

- **skill 机制**：每个 skill 是一个 `SKILL.md`（frontmatter 触发词 + 正文流程约束）+ 可选 `references/` 子文档，按需 read。源码在 `<skills 源码仓库>/skills/`，symlink 到 `~/.agents/skills/` 供 agent 发现。
- **两个现有 skill 的精确边界**（取自各自 SKILL.md，不概括）：
  - `code-simplify`：「把最近改动的代码变更容易读懂而非更短，行为严格不变」——范围收敛在本次改动，明示「Not for 架构重构」。
  - `improve-codebase-architecture`：「Surface architectural friction and propose **deepening opportunities** — refactors that turn shallow modules into deep ones」——产出方向是把浅模块做深（加法侧）。注意它并非与减法完全绝缘：其词汇表已含 deletion test（「If complexity vanishes, it was a pass-through」）与「One adapter = hypothetical seam」这类可删性判据种子——与减法侧共享部分判据，差异在**产出方向**：它不产出「删除候选 + 功能取舍论证」。
- **市场调研结论（2026-09-10，三轮）**：无知名现成 skill 覆盖此缺口；高匹配实现（rbwsam/abvx/brooks-lint 等全仓 over-engineering 扫描）均在 0-16 star 个人仓库，可借鉴其扫描维度与排序思想但不直接安装（用户已决策自建）。
- **理论调研结论**：代码层判定可归为五问（详见 §3.3.2），需求层「小取舍→大简化→核心价值不变」可由 YAGNI 四成本 + SRE error budget + Kano indifferent + Concierge 测试拼装论证；需求层的「功能级复杂度会计」与「出场判定」是公认空白，需自建启发式。

### 1.3 设计目标（从使用者体验倒推）

1. **G1 发现**：用户说「审计一下这个仓库/模块的过度设计」，得到一份按杠杆排序的候选报告——每张候选卡片含：位置、复杂度来源（哪个保证/抽象导致的）、简化方案、功能取舍内容、核心价值影响评估、推荐强度。排序保证「最值得先看的在最上面」。
2. **G2 论证**：每张卡片的三段论证完整——牺牲什么保证（小取舍）、省下什么机制（大简化）、为什么核心价值无损（核心价值不变的判据）。用户看完能直接做决策，不需要再自己去论证。
3. **G3 裁决权在人**：skill 绝不自动改代码。报告之后进入裁决对话（grilling 式），用户挑选候选、确认取舍边界后才进入执行；执行时架构级删减由本 skill 做，代码级简化移交 `code-simplify`。
4. **G4 防新增**：pre-commit 断言拦截新增的投机复杂度（无调用方导出、纯转发层、单实现接口），有显式豁免通道（豁免需写理由，理由可被本 skill 下次审计复核）。
5. **G5 误报可控**：对「正确的设计」不误报——本质复杂度高（问题本身难）的代码、有真实多调用方的抽象、Fowler 两豁免（框架代码、测试引用）不进候选或标注「已核实非过度」。

### 1.4 Scope

**In scope**：
- skill 本体：SKILL.md + references 子文档（信号清单、排序模型、报告与裁决协议、执行协议）
- pre-commit 断言配置模板（目标仓库可复制使用，首版支持 TS/JS，Python 信号降级子集）
- 两个真实案例（§2.2）作为验收 golden case

**Out of scope**：
- `improve-codebase-architecture` 的 YAGNI filter 回植（独立小任务，**排为本 skill 实施后的紧邻下一步**；回植完成前的中间态风险：两 skill 对同一投机抽象可能给出方向相反的建议——拆除 vs 做深，此时以本 skill 判定优先，已在 §3.3.9 声明）
- 多语言全覆盖（Rust/Go 等的工具信号适配，首版后按需扩）
- skill 的实战迭代调优（实施后用真实项目跑出来的问题驱动，不在本设计内预答）
- CI 侧全量扫描 workflow（首版只做 pre-commit 本地断言，CI 化待首版验证后）

## 2. 现状与问题分析

### 2.1 使用者视角的现状（真实例子）

现在用户面对一个「感觉过度复杂」的项目时，可用的工具与效果：

| 动作 | 实际效果 | 缺口 |
|---|---|---|
| 跑 `code-simplify`（scan 模式） | 默认只扫最近改动（触发词含「全仓去重」，但全仓产出仍是死代码/重复/复用等语句级机会） | 不判断「这个抽象/保证该不该存在」 |
| 跑 `improve-codebase-architecture` | 产出 HTML 报告，候选是「把浅模块做深」的重构 | 方向是加法（做深），不是减法（拆除）；不评估「砍需求换简化」 |
| 跑 knip / eslint cognitive complexity | 各自报「未使用导出」「函数太复杂」的原子告警 | 告警≠判定：cognitive 高可能是问题本身难；knip 命中可能被测试引用；没有排序、没有论证、没有取舍评估 |
| 人工读设计文档 + 凭经验判断 | 效果取决于个人（§2.2 案例 B 的作者做对了，但不可复制） | 判定知识在个人脑中，无流程、无记录 |

### 2.2 源头案例 A/B（验收 golden case——已知正确答案、用来验证审计能否得出同样结论的仓库）

**案例 A（反面——完备性保证型过度设计）**：session-reader「唯一解析入口」设计。
原始证据（ground truth）文档：`<internal-repo>/extensions/universal/session-reader/docs/2026-09-10-session-root-discovery-and-env-transparency.md`（v8→v9.2，1101 行）。
目标是「session_read 是唯一入口」（agent 无需 bash find/grep），为此叠了三层完备性保证：①唯一入口覆盖（doctor 自诊断、候选根探测、错误信息重写、uuid 归一化——为对齐所有历史布局形态建了一层运行时探测机制）；②三副本（extension/npm/CLI）全修且功能对齐（文档 545 行起）；③迁移窗口期内所有固定路径扫描器不失明，其中「一律旧赢+新避让」统一合并策略被审查击穿，最终凭据域与记录域分策略（文档 704-706 行）——复杂度最高的部分正来自完备性保证本身（根因 bug 是 `src/discovery/roots.ts:84` 的路径假设，文档 553 行）。该设计里最有价值的决策恰恰是需求级的：**「根修（B 方案）先行后，护栏（A 方案）的环境注入与专项修复可整体删除」（文档第 3 行决策区）**——砍掉「兜住所有历史布局」这个保证，换掉一整层机制。这正是本 skill 要系统性产出的那类发现。

**案例 B（正面——正确取舍的判定结构，但靠人工直觉）**：subagent 通知机制设计。
原始证据文档：`<internal-repo>/docs/design/subagent-agent-end-recovery-replay.impl-plan.md`（F3 节，195 行起）。
取舍决策表：activity 事件刻意零载荷（宿主只要活性信号，stdoutBytes 富数据无消费者）；telemetry 路径不加同款回调（镜像帧同 eventId = 同一知识，双发只增噪声）；推送而非轮询（服务端天然 ~1.01s cadence）；一切取舍有红线（activity 不得削弱杀链——真无进展仍必须可回收）。这套判断每条都命中理论（YAGNI 持有成本 / DRY-knowledge / boring tech / error budget 下界），但当时是人工逐条推导，不可复用。

**两案例合起来的教训**：判定结构已存在且被验证有效（案例 B 是正确答案的样本，案例 A 含已被识别的正确简化），缺的是把它工具化。

### 2.4 源头案例 C：SDK 影子层（taiji scheduler）

**案例 C（反面——SDK 已给出事实，却又造一层延迟版去重新获得）**：scheduler「命令路径建任务后任务持久化」机制里的 **30s 写盘自检定时器**。

原始证据文档：taiji workspace `extensions/universal/scheduler/src/ack-turn.ts`（已删除该定时器，merge `f289d6c24`）+ 设计文档 §3.3 D7 v6.3。

- **绕的圈**：注入合成轮打开会话落盘开关后，挂一个 30s `setTimeout` 回来看「会话文件是否已创建」，未创建则发如实通知。配套还有 `pending` 标志位 + 顶部去重守卫 + 「定时器回调必须清 pending」的修复（F1）。
- **SDK 等价面（行号级）**：`pi.on('message_start')` 事件本身就是「该轮次已启动」的直接信号（`extensions/types.d.ts` 事件枚举含 `message_start`；实装 `agent-session.js` 的 `_runAgentPrompt` 路径会发射它）⇒ **成功本就同步可观测，无需轮询**。
- **失败侧同样有出口**：`pi.sendMessage` 返回 `void`，其 rejection 被 `bindCore` 的 `.catch` 转 `runner.emitError`，RPC 模式转成 `extension_error` output 事件给宿主（`rpc-mode.js:259`）——扩展收不到，但宿主看得到，用户并非无感。
- **判定结论**：定时器的独特价值只是**通知延迟**（30s vs 下一个 session 边界），不是覆盖度——`handleSessionBoundary` 在 `session_start`/`session_shutdown` 两处本就跑同一落盘判定。而它自身是长生命周期进程里唯一的有状态定时器，且正是 F1 类 bug（陈旧 `pending` 永久挡住本会话后续创建）的来源。
- **删除后的连带简化**：`pending` 字段整个删除，去重守卫只认 `window` ⇒ 触发器静默失败时下一次创建**重新注入**（重试）而非被永久挡住——原来需要「定时器 + F1 修复」共同维持的性质变成结构性成立。
- **教训**：这条不在原四问的射程内（它不是浅模块/纯转发/无调用方，单点复杂度低、有真实消费者、注释也写了理由）。它逃过前一轮 9 候选审计的原因正是**缺少「SDK 是否已给出该事实」这一问**。故增补为第五问与「SDK 影子层」反模式。

### 2.5 源头案例 D：修 bug 堆出的补偿机制与防不存在场景的守卫（taiji subagent-workflow）

2026-09-25 taiji subagent-workflow 全链路审查（63 条问题）暴露三个判定标准缺口与一个待决信号：

- **防线豁免边界缺口**：63 条中的最大族是补偿机制（对账函数、送达水位比对、15s 定时巡检、状态守卫、重发机制）——每一层都有真实事故登记，按「有事故登记即合法」的旧边界全部豁免，而事故根源均未修复，补偿机制在持续交税。由此修正边界：**事故登记只是必要条件，还须根源已修复**；判别法 = 删掉补偿机制后问题是否还在（终态条文落 evidence-signals.md「与双重保险防线的分界」）。
- **防御前提缺口**：防 pi compaction 删除 entry 的守卫，实装核实 pi 0.84.4 的 compaction 只追加条目、从不删除——守卫防的外部行为结构上不存在，永不触发。同族实例：恒真谓词（候选过滤覆盖两态全集）、恒等式校验（两个分支同值）、签名与实现不符（参数被丢弃）。由此在 SDK 影子层判据补 (c)：**防御所针对的外部行为，写防御之前验证过真的会发生吗**。
- **检测恒不命中缺口（同项目第二实例，2026-09-25 补）**：嵌套 workflow 循环检测拿绝对路径比裸名，生产形态下恒不命中（A↔B 互调无限递归无人拦）；锚定它的测试用生产不可达形态构造，所以常绿。与防御前提缺口互补：那边是「防的场景结构上不存在」，本条是「场景真实存在、检测逻辑本身死了」——防线活着但永远不打响，且常绿测试持续供给安全感。由此在 SDK 影子层判据补 (d)：**检测条件在生产形态输入下能命中 + 锚定测试用生产可达形态构造**（终态条文落 evidence-signals.md 第五问）。
- **待决可计算信号：枚举成员无生产/消费**——事件词表 7 个成员 1 个无生产者、输出动作 6 个成员 1 个无执行者（同一案例两处实例）。单一独立案例不满足「同类判定反复发生」的信号下沉准入（SKILL.md「核心骨架与演进框架」扩展点②），暂不落地；第二个独立案例出现后把该判定从语义层下沉为可计算信号。

### 2.3 根因分析

1. **判定知识未工具化**：五问（§3.3.2）和三段论证（§3.3.3）散在理论文献和个人经验里，没有变成 skill 的信号清单与检查规则。
2. **可计算信号未持续执行**：knip/转发检测等信号有工具但没进任何 hook，投机复杂度长驱直入。
3. **复杂度排序维度错位**：直觉排序按「复杂度分」，但复杂度高 ≠ 过度（可能是本质复杂度），且分层转发型过度设计单点复杂度都很低——需要「投机信号 × 变更热度」合流（§3.3.4）。
4. **需求层判定无现成方法**：「这个保证值多少复杂度」「砍了用户在乎吗」没有理论化的会计方法，必须设计成人机协作环节而非全自动扫描。

## 3. 解决方案

### 3.1 终态：使用者视角

**成功路径（全仓审计 → 裁决 → 执行）**：

```text
用户：审计一下 ~/projects/xyz-agent 的 session-reader extension，最近感觉过度设计了

skill：
  [定范围] 检测 git 近 30 天活跃路径 + 用户指定模块 → 圈定 extensions/universal/session-reader
  [证据收集]
    可计算层（并行 bash）：knip 未使用导出 11 处；转发方法占比 34%（阈值 20%）；
      抽象链平均深度 2.8（含 2 条 >4 的链）
    语义层（2 个并行 subagent，按五问 + 反模式清单扫）：命中「候选根探测」
      （赌的决策=布局会变，但方案 B 根修后该决策已被消灭 → 投机）；
      「uuid 归一化」（单调用方）；「doctor 自诊断」（inner-platform 信号：配置探测面）
    业务层（读项目设计文档）：三层完备性保证逐一映射到调用方清单
  [杠杆排序] 输出 5 张候选卡片，按杠杆分排序
  [报告] 写 markdown 报告到 <项目根>/.tmp/code-overdesign-audit/code-overdesign-audit-<ts>.md，节选：

  # 候选 1（高杠杆）｜候选根探测层
  - 位置：src/discovery/roots.ts:84 周边 + doctor 命令
  - 复杂度来源：保证③「迁移窗口期固定路径扫描器不失明」+ 保证①的布局对齐
  - 简化方案：方案 B（根修对齐 pi 布局）落地后，整层探测/兜底删除
  - 功能取舍：失去「布局漂移时自动适配」——迁移完成后该场景不存在
  - 核心价值影响：无（KL888 调用方走标准布局；牺牲的是历史形态兼容）
  - 三段论证：小取舍=放弃自动适配历史布局｜大简化=删除探测+兜底 ~600 行
    与 doctor 专项｜核心价值不变的判据=根修后布局唯一，JTBD「读 session」不受影响
  - 推荐强度：Strong（前置条件：方案 B 已落地）

  # 候选 2（中杠杆）｜uuid 归一化包装 …（略）
  # 候选 3（已核实非过度）｜状态域/记录域分策略合并 …
    （两轮审查击穿统一策略的反例 = 该复杂度是本质的，标注不可砍及原因）

用户：候选 1 有个前置条件没满足，先看候选 2

skill：[裁决对话] 就候选 2 grilling：取舍边界（uuid 不归一化时哪些输入会 miss？
  调用方实测有几种格式？）→ 用户确认「只保留连字符标准格式」
  [执行] 删包装层 + 改 2 处调用点 + 跑相关测试 → 通过 → 代码级清理移交 code-simplify
```

**失败/降级/挂起路径**：
- knip 不可用（非 JS 仓库/未安装）→ 可计算层降级为 grep 系信号（§3.3.2 降级表），报告标注「证据等级：降级」；
- 扫描无候选 → 报告明说「0 候选」并列出已核实非过度的高复杂度点（G5），不是硬凑候选；
- **挂起模式（夜间托管兼容）**：报告落盘后 skill **结束回合等用户裁决**，明示恢复入口（「回来后说『继续审计裁决』+ 报告路径即可从报告继续」）——不在等待裁决上空转，与全局约定「确认后进入执行态不中途停问」兼容（裁决属于执行前必须的用户决策，非中途确认）；
- 用户裁决「都不砍」→ 裁决结论（含「已核实非过度」清单）写入持久基线文件（`<项目根>/.tmp/code-overdesign-audit/baseline.md`，见 §3.3.5），下次审计增量复用；报告本体保留在 `.tmp/` 仅作快照，丢失可由基线重建要点。

### 3.2 多方案对比

| 维度 | 方案一：独立 skill 五步流程（推荐） | 方案二：改造 improve-codebase-architecture 加减法模式 | 方案三：scan-only 极简报告 skill |
|---|---|---|---|
| 长期架构合理性 | 高：与两个现有 skill 构成三分工——**意图层互斥**（产出方向：代码级减法 / 架构级做深 / 设计级拆除，判据部分共享，见 §1.2），触发词边界以 description Not for 段显式声明（§3.3.9 冲突矩阵）；references 结构可随实战迭代 | 低：它的 deletion test / one-adapter 判据确实已是减法种子，加一节即可复用判据——但减法的**产出**（删除候选卡片 + 功能取舍论证）与其 deepening 产出方向相反，单 skill 双方向稀释 description 触发精度；且它是 mattpocock 上游拷贝件，改动越大将来同步越难；需求层业务取舍超出其纯代码视角 | 中：能发现不能裁决——需求层三段论证必须有人机对话环节，scan-only 砍掉后产出的是「告警清单」回到 §2.1 缺口 |
| 短期实现成本 | 中：SKILL.md + 5 个 references + 断言模板，跨 2-3 个会话 | 低：在现有文档上加一节 | 低：单文件 |
| 风险 | 排序模型与信号清单首版可能过/欠敏感——用两个 golden case 验收兜底（§4） | 触发串扰：用户说「简化架构」时两个模式抢路由 | 价值不完整：用户还是得人工做三段论证 |

**推荐方案一**。不采用其余方案的理由：若用方案二，§2.2 案例 A 的「候选 1」（删探测层）会以「deepening 候选」的卡片形态出现（把探测层做深？），方向性错误；若用方案三，案例 B 那样的取舍边界确认（「uuid 只保留标准格式行不行」）没有发生的地方，执行无从谈起。

### 3.3 关键决策与权衡

#### 3.3.1 命名：`code-overdesign-audit`

选：品类语义一致（over-engineering 审计），且与 code-simplify 构成 `code-` 前缀家族，触发词自然（过度设计/过度抽象/审计复杂度/高杠杆简化/YAGNI 审计）。不采用：`complexity-audit`（误导为度量工具，与认知复杂度混淆）、`simplification-leverage`（自造词，无生态对应）。中文名「过度设计审计」进 description。

#### 3.3.2 三层证据与信号清单（references/evidence-signals.md 的规格）

**可计算层**（确定性工具，bash 并行，每项带降级路径）：

| 信号 | 首版工具 | 阈值/口径 | 降级 |
|---|---|---|---|
| 无调用方导出/依赖 | knip | 列表输出；测试引用排除（Fowler 豁免） | grep `export`×引用计数 |
| 纯转发方法占比 | grep 签名匹配（方法体仅委托调用） | >20% 报候选 | 无（grep 本身零依赖） |
| 单实现接口/抽象类 | grep implements/extends + 实现计数 | =1 报候选 | 同左 |
| 抽象链深度 | 调用链静态追踪（code-review-graph 可用时优先） | 单链 >4 层报候选 | grep import 链近似 |
| 认知复杂度热点 | eslint-plugin-sonarjs（若项目已配） | 仅作定位辅助，**不单独成候选**（§2.3 根因 3） | 跳过，标注降级 |

**语义层**（subagent 并行扫，按维度分组，学 rbwsam 六维度但换成五问框架）：每个可疑抽象回答五问——①赌的决策是什么、会真变吗（Parnas）②间接成本 vs 认知压缩（深浅比）③依据是已发生证据还是想象未来（Rule of Three：真实变体数 ≥3 才算证据）④反模式信号（inner-platform/abstraction inversion/leaky/Greenspun 清单）⑤SDK 影子层（判定与形态见 evidence-signals.md；源头案例 C §2.4、案例 D §2.5）。**输出必须带证据行号**，无证据的怀疑丢弃。
**派发规格 [MANDATORY]**：subagent 不自动加载 skill——主 agent 须先 read `references/evidence-signals.md` 再把五问问句与反模式清单**内联进派发提示词**（不允许让 subagent 凭空扫）；单个 subagent 规模 ≤5 文件/3000 行（全局约定），超限模块按子目录再拆；提示词须三段式（背景含仓库路径、目标、验收含「输出带证据行号」）。

**业务层**（LLM 读项目设计文档/ADR + 调用方清单）：每个复杂机制映射「保证什么 → 服务哪些真实调用方/场景 → 该场景的用量证据」。输入优先级：项目设计文档 > ADR > README > 代码注释 > 问用户。

**[MANDATORY] 语义层结论不得由主 agent 单方拍板**：subagent 报告的「投机」判定必须附调用方清单，主 agent 抽验 ≥1 个调用方真实存在后才进候选——防 LLM 幻觉调用方缺失。三类已知易错点：测试文件算不算调用方、动态调用/字符串拼接引用、跨包 re-export（grep 计数与语义判断在这些点上天然分歧，抽验必须实际读调用点代码）。

#### 3.3.3 三段论证与推荐强度（references/report-format.md 的规格）

每张候选卡片固定字段：位置（file:line）/ 复杂度来源（哪个保证或抽象）/ 简化方案 / 功能取舍 / 核心价值影响 / 三段论证 / 推荐强度。三段论证的锚：

- **小取舍**：明确写出牺牲的保证/功能/便利，量化到「哪些调用方/场景受影响」（YAGNI 四成本框架的持有成本侧）
- **大简化**：预估删除的机制量（行数/模块数/概念数——概念数优先，DHH conceptual compression：度量读者需理解的独立概念）
- **核心价值不变的判据**：三选一——调用方证据（受影响调用方 = 0 或均有替代路径）/ 感知线论证（牺牲维度在用户感知线之下，error budget 思想）/ 替代路径（人工/既有工具可兜底，Concierge 测试）

推荐强度三级：Strong（三段论证全闭环）/ Worth exploring（缺一段，通常是核心价值不变的判据待补）/ Speculative（仅投机信号，无业务证据）。**「已核实非过度」单独成节**：高复杂度但五问通过（本质复杂度）的点名列出 + 不可砍理由——这是 G5 误报控制的落点。
**基线的持久化与重审**：「已核实非过度」条目在裁决结束后写入持久基线文件 `<项目根>/.tmp/code-overdesign-audit/baseline.md`（项目维度临时产物目录，`.gitignore` 覆盖不污染 diff；与 tech-design/dev-flow 产物路径规则统一）。基线条目**必须附证据快照**（当时的调用方清单与计数）；下次审计时，调用方计数较快照变化的条目强制重验（判定可能过期），未变的直接复用——增量审计的复用边界以此为准。

#### 3.3.4 杠杆排序（references/ranking-model.md 的规格）

**刻意用定性三档评分，不造公式**（避免排序模型本身成为过度设计）：投机判定为**入围门槛**（语义五问命中附证据行号 + 主 agent 抽验调用方真实存在，缺一不进候选，记入「已核实非过度」），门槛通过才进三维各打 0-3 分——简化收益（删机制量/概念数；变更热度为修正因子，死区收益半档）/ 执行成本（调用方改动面与回归风险）/ 综合（裁决推荐度；前置条件未满足封顶 1）。综合降序 + 成本升序 tie-break；「高杠杆」标记 = 综合 3 且成本 ≤1。复杂度分不进排序键，只在卡片里作「简化收益」的输入之一（§2.3 根因 3 的直接落实）。

#### 3.3.5 报告与基线：双层载体

**报告（呈现层）**：markdown 写 `<项目根>/.tmp/code-overdesign-audit/code-overdesign-audit-<ts>.md`（项目根 = `git rev-parse --show-toplevel`，worktree 解析为各 worktree 根；目标非 git 仓库时落 `/tmp/code-overdesign-audit/`）并给绝对路径。不采用 HTML：improve-codebase-architecture 用 HTML 是因为要画 before/after 结构图；本 skill 卡片的核心是论证结构，markdown 表达完整且生成便宜、可粘贴进 issue/ADR 复用。代价四要素：`.tmp/` 是临时产物目录、随时可被清理（量级）；无需恢复路径——**报告是有意的一次性快照，所有跨会话状态不依赖报告**（见下）；无需重审条件（非持久资产）。用户裁决后由用户决定是否把某候选登记为 ADR（呼应 grill-with-docs 惯例）。

**基线（持久层）**：`<项目根>/.tmp/code-overdesign-audit/baseline.md`——存裁决结论、已核实非过度清单（附证据快照，§3.3.3）、豁免复核队列（§3.3.7）。跨会话三条链路（增量复用/基线复验/豁免复核）全部挂在这层，不挂报告。共享粒度（项目维度）：基线随各 worktree 的 `.tmp/` 独立持有，不跨 worktree/clone 共享——正确性由「快照计数变化强制重验」兜底（不会错误复用，最多重复审计一次）；目标非 git 仓库时基线写 `/tmp/code-overdesign-audit/<repo 标识>/baseline.md`（repo 标识 = 绝对路径哈希）。显式代价：`.tmp/` 被清理或换机重装 = 基线丢失 = 下次 audit 退化为全量重审（恢复路径：重跑 audit 重建，无数据损失仅时间成本；audit 低频，代价可接受）。

#### 3.3.6 执行边界与移交

裁决确认后：架构级删减（删抽象层/删机制/改调用方）由本 skill 主导执行 + 跑受影响测试；执行中冒出的语句级清理（死代码/重复）**移交 code-simplify**（路由：报告「另有 N 处代码级清理点」）；行为变更类取舍必须在执行前把「取舍后的新行为」写进裁决确认（用户已确认的边界就是验收标准）。改测试迁就简化 = 撤销（继承 code-simplify 铁律）。

#### 3.3.7 pre-commit 断言（references/ci-assertions.md 的规格，D 配套）

选 pre-commit 而非 CI workflow（不采用 CI：反馈慢且本仓库无 CI 基建依赖；首版验证断言信噪比后再 CI 化——已在 out-of-scope 声明）。断言集（快速子集，单次提交断言耗时预算 <10s，验收探针见 §4 场景 4e）：

| 断言 | 实现 | 拦截口径 |
|---|---|---|
| 新增无调用方导出 | **git diff --cached 自解析**：提取本次暂存新增的 export 符号 → 逐符号全仓引用计数（**`git grep` 实现，天然限定 tracked 文件**——不扫 node_modules/生成物/文档，堵住「全仓 grep 字面扫一切」的搜索范围未定义漏拦）。**符号提取口径**：拦截面仅限具名非别名导出——`export default`（匿名无符号；有名 default 的消费侧导入名与源符号无字面关系，grep 计数天然失效）与 `export { x as y }` 别名重命名**不进拦截面**（提取即失真，强行拦截必违宁漏勿拦），由 audit 细网兜底。**计数最小机械规则**：word-boundary 匹配（`grep -w`）；排除注释行；排除 re-export 行（`export ... from` 模式——barrel 转发行是假引用，且其本身即转发信号）；排除定义文件本身 | 新增 export 全仓零引用即拦 |
| 新增单实现接口 | grep 暂存 diff 中 implements/extends | 新增接口仅 1 实现即拦 |
| 新增纯转发方法 | 签名匹配（同可计算层） | 暂存新增方法体纯委托即拦 |

不采用的实现：「knip diff 模式（只查暂存区新增导出）」——knip CLI 无 diff/staged 能力（已核实官方 CLI reference 与 v6.35.1 源码，2026-09-10），引用不存在的能力作为实现路径 = 设计不可实施；knip 全仓跑（秒级以上）也超 pre-commit 预算，只用于 audit 流程的可计算层。自解析方案单符号 grep 毫秒级、新增导出单次提交通常 <10 个，预算内可达。

**已知漏拦类目（断言一的显式接受代价）**：机械规则与拦截面无法覆盖的四类漏拦——①**撞名符号**：`export function open()` 这类通用动词命名，成员访问 `.open()`、字符串、部分注释形态仍会使计数虚高 → 漏拦，而通用动词命名恰是投机包装导出的高频形态（`.open()` 归此类而非规则可消解类：成员访问同时是真引用与假引用的载体，正则剔除必连带误杀真引用，与宁漏勿拦矛盾——已实测 `grep -w open` 命中 `mod.open()`；全局 API 撞名（fetch/init）、存量同名符号、解构导入等形态语义同源，由本类涵盖不独立设类）；②**import 占位**：同一提交新增导出 + `import { open } from ...` 但从不调用——import 声明行被计为引用 → 永久放行，此为投机导出最典型的产生方式，频率大概率高于撞名；③**动态引用/字符串拼接调用**；④**default/别名导出**：拦截面外（符号提取口径，见断言一行）——不强行拦截，由 audit 细网兜底。判定：接受宽松口径（pre-commit 拦截是打断开发流的高代价动作，宁漏勿拦），量级为「未知但存在」；重审/兜底条件：**audit 层是细网**——knip 全仓精确分析 + 语义层五问不依赖 grep 计数，断言一漏掉的撞名/占位/动态/default 符号由低频 audit 兜底捕捉；若实战发现某类漏拦高频出现，将该模式升级为专项 grep 规则（监控分类以本清单四类为准）。两处「引用」口径差异的理由（落 evidence-signals.md 规格）：pre-commit 断言**测试文件算引用**（自动拦截宁宽松防误拦）；audit 可计算层**测试引用排除**（speculative generality 判定看真实调用方，测试不是）——前者防误拦、后者防漏报，方向相反均有意。
**拦截输出与监控口径**：断言拦截必须带原因码（`no-reference` / `single-impl` / `pass-through` / `expired-exempt`）；「月误拦 >5 次触发口径重审」的计数**仅统计 `no-reference` 类**（预期内正常使用被拦 = 口径过宽信号），`expired-exempt` 是设计预期行为单列计数——不混入误拦数据，避免污染后续 CI 化决策输入。

**时序性误拦的显式代价（已接受）**：分步提交（先提交导出、下一步提交调用方）的正常工作流会被断言一拦截——真投机与 WIP 在 pre-commit 时点不可区分，此摩擦**显式登记为已接受代价**：量级预估成熟仓库月均 <2 次；每次用 `wip` 类豁免（见下）30 天短期豁免；重审条件：月误拦 >5 次 = 断言口径过宽信号，触发口径重审（计数口径见上「拦截输出与监控口径」：仅 no-reference 类；此数据是后续 CI 化决策的输入，误拦污染会误导该决策——因此必须监控而非容忍）。

**豁免通道 [MANDATORY]**：行内标记 `// oe-exempt:<yyyymmdd>:<类目>:<理由>`，类目枚举与期限：`wip`（时序性，30 天）/ `test`（测试引用豁免，90 天——复验收益：测试是否仍引用、该导出是否已有真实调用方）/ `framework`（框架代码为使用者保留，Fowler 豁免本义即常驻合法，**不设期限**，仅在 audit 步骤 0 汇总中列出保持可见——复验收益是确认框架代码仍被使用，挂期限无意义）。
生命周期四要素：①量级——断言口径窄（仅新增面三信号），成熟仓库预期存量 <20 条，>50 条 = 信噪比失败信号；②**期限触发面双通道**——pre-commit 断言每次提交都解析标记，**日期过期即视为无豁免重新拦截**（wip 30 天到期还挂着 = WIP 语义已消失，恢复动作：复核移除标记，或确属长期豁免改类目并补理由；选拦截而非警告的理由：豁免是显式债务，债务到期必须处理而非提示后继续挂着不处理）；audit 步骤 0 固定 grep 全部 oe-exempt 汇总（按日期排序，过期标红）作为深度复核通道——即使两次 audit 间隔超期，期限校验也以提交粒度持续生效；③清单化通道——复核队列由 audit 步骤 0 重建后写入基线文件，**pre-commit 对 `.tmp/code-overdesign-audit/` 保持只读**（无即时写盘动作，无并发/失败语义问题）；④清理通道——复核通过改期/改类目或移除标记，候选被删则标记随代码消失，下次 audit 汇总自然不再命中。豁免是显式债务：随代码进版本库永久可见（消费方除本 skill 外还有代码评审者与 grep 工具，标记格式保证可被机器汇总）。

**安装写入面穷举**（每面给安装/卸载路径；安装步骤 0 强制 hook 环境检测）：
- **步骤 0：`git config core.hooksPath` 检测，三分支**——(a) 未设置（hooks 在 `.git/hooks/`）→ 走下述 append 模式；(b) 设置为重定向型框架（husky `.husky/_`、lefthook、python pre-commit 等——实测 husky v9.1.7 安装即 `git config core.hooksPath .husky/_`，`.git/hooks/` 内一切不被 git 执行，真实执行链是 `.husky/_/pre-commit` shim → `sh -e .husky/pre-commit`）→ **显式二选一**：向框架用户 hook 文件（如 `.husky/pre-commit`）append 带 marker 行，并显式登记「写入面进入工作区、一行 diff 随版本库」的代价，征得用户同意；或打印 skipped + 手动接入指引后放弃——两支都必须可见，**禁止静默安装到永不被执行的 `.git/hooks/`**（那比不装更糟：无任何信号的真实失效）。该确认是安装流程的一次性分叉点（非执行态中途停问），交互走 §3.1 挂起模式同构语义：给出代价说明与**默认推荐项**（U5 模板内置：推荐「登记代价并安装」——工作区一行 marker 注释的可见债务，优于断言缺失；仓库明确禁工作区写入时推荐放弃）后结束回合等用户选择；(c) 目标 hook 文件不存在 → 创建最小 hook。**marker 互斥声明**：oe-exempt 汇总用 `grep -r "oe-exempt:"`（带冒号锚定），与调用行 marker `# oe-audit-assert` 前缀互斥——hook 调用行不会被 audit 步骤 0 误认为豁免标记；两标记格式在任何一端演进时必须维持互斥。
- `.git/hooks/oe-assert.sh`（断言脚本本体，新增；重定向框架时脚本放框架目录或保留 `.git/hooks/` 由 hook 文件调用）——卸载即删文件；
- hook 调用行：append 模式，行带特征 marker 注释（`# oe-audit-assert`）——**卸载按 marker 识别删行**，不碰他人内容；
- 无独立配置文件（阈值内嵌脚本默认值）；**零外部依赖**——断言全部用 git/grep/node 内置能力实现，不引入 knip 依赖、不改 package.json/lock（lock 文件纪律不受影响）；
- clone 仓库（如 zcode 引擎仓）：分支 (a) 下全部写入面在 `.git/` 内，不污染工作区；分支 (b) 下接入点在工作区 hook 文件（一行 marker 注释），显式登记该 diff——唯一进工作区的其余内容是 oe-exempt 标记本身（有意为之——债务可见性）。
工具级故障（如 grep 异常）→ 断言跳过并打印 skipped（不阻塞提交，与 AGENTS.md「失败要出声」一致：skip 必须可见）。误报率验收见 §4 场景 4。

#### 3.3.8 流程编排与 subagent 拆分

模式识别（audit/复核豁免/裁决后执行）在 SKILL.md 主文件；语义层扫描按「五问 × 模块分组」拆 subagent 并行（≤5 个，模型路由：探索/扫描用 flash 级，裁决对话与执行在主 agent）；业务层读文档在主 agent（需要全局视野）。学 code-simplify 的路由表结构：SKILL.md 只放触发词 + 流程骨架 + [MANDATORY] 约束，细节全部下沉 references。

#### 3.3.9 触发词冲突矩阵（U1 description 规格的一部分）

与既有 skill 触发词的逐词对照（已 read 三者 SKILL.md 核实）。原则：**产出方向定归属**——产出「删除候选 + 取舍论证」归本 skill，其余显式让渡：

| 本 skill 触发词 | 竞争 skill（共享语义场） | 归属裁决 |
|---|---|---|
| 过度设计 / 过度抽象 / over-engineering | improve-codebase-architecture（architecture review / refactoring） | 本 skill：产出方向是**拆除**；若用户意图是做深模块（「把这个模块做深/加深」）→ 让渡给它。Not for：「模块做深、deepening、可测试性重构」 |
| 高杠杆简化 / 大简化 | code-simplify（简化 / simplify / 找简化机会 / 全仓去重） | 本 skill：**设计级**简化（删抽象/删机制/功能取舍）；语句级（死代码/重复/复用/本次改动清理）→ 让渡。Not for：「简化最近的代码、清理本次改动、死代码、去重、复用优化」 |
| 复杂度审计 / 复杂度过高 | code-quality-tool（代码审查 / 检查代码 / quality check） | 本 skill：复杂度**归因与取舍论证**；规范性质量检查（lint 级、规范符合性）→ 让渡。Not for：「代码规范检查、lint 级问题」 |
| YAGNI 审计 / 投机抽象 / speculative generality | 无直接竞争（rethink 是思维框架不扫代码；code-link 是调用链追踪工具） | 本 skill 独占 |

过渡期风险（YAGNI filter 回植前）：本 skill 与 improve-codebase-architecture 对同一投机抽象可能给出方向相反的建议（拆除 vs 做深），此时**以本 skill 判定优先**（见 §1.4 out-of-scope 声明）。

## 4. 验收

（大改动，多场景；每个场景回溯 §1.3 目标）

**场景 1：golden case 正检——session-reader 仓库全仓审计**（验证 G1/G2/G5）
步骤：在 xyz-agent 仓库（session-reader extension 所在）实跑 skill 全流程（audit 模式）。
通过标准：①报告产出候选卡片且按杠杆排序；②「方案 B 落地后探测/兜底层可删」这一已知正确简化出现在候选中且推荐强度 ≥ Worth exploring（该简化的取舍边界被正确陈述）；③「状态域/记录域分策略合并」出现在「已核实非过度」节（两轮审查击穿统一策略的反例被识别为本质复杂度）；④无凭空调用方（抽查候选卡片引用的调用方真实存在）。

**场景 2：golden case 反检——subagent 通知机制代码不误报 + 0 候选报告形态**（验证 G5）
步骤：对已合入三 PR 的通知机制代码（zcode 引擎仓）跑**两遍**完整 audit 流程——**前置（单一权威动作）**：删除该仓库基线文件 `<项目根>/.tmp/code-overdesign-audit/baseline.md`，并在第一遍跑批前机器断言 `test ! -f <项目根>/.tmp/code-overdesign-audit/baseline.md` 通过（把「无基线」从动作承诺变成可验证状态，顺带消除清错路径的执行风险）。不采用「未审计过的仓库副本」作为替代——基线按项目维度挂各 worktree 自己的 `.tmp/`，新副本天然无基线，该选项技术上重新可行但仍不采用：副本引入 HEAD 一致性等额外变量，删除基线文件是变量最少的单一动作。**第一遍（带阳性对照）**：跑批前在工作区（不提交）暂加已知投机构造（无引用导出 + 单调用纯转发方法各一），完整跑批出报告；**第二遍（还原后）**：还原对照后重跑完整流程。**裁决时序 [约束]**：两遍报告均先于任何裁决动作产出；「已核实非过度 / 都不砍」裁决**仅对第二遍报告执行一次**——若第一遍后即裁决，基线已建立，第二遍按增量模式从基线复用出报告，「0 候选」不再经过本轮扫描，② 被静默架空。
通过标准：①第一遍阳性对照**必须进候选**（灵敏度证明——排除「扫描未发生仍全绿」的假通过：0 候选 + 阳性对照也 0 命中 = 扫描失败而非正确放行）；②第二遍对照**从候选消失**（双向灵敏度）且候选数 0 时明说 0 候选、**不硬凑**——两遍分别证明「该报的报」与「不该报的不报」；③零载荷 activity 事件、telemetry 路径无回调、推送透传这三处「刻意的不做」两遍都**不出现**在候选中——skill 能识别「单实现但有明确设计理由」（读了设计文档/ADR 中的取舍记录）而非机械报「单一路径」；④「已核实非过度」节非空且每条附证据快照（调用方计数）+ **反向抽查证据行号真实存在**（**第二遍报告判分**，与场景 1④ 对称，防「凭设计文档放行、编造快照」通路）；⑤语义层 subagent 五问记录随报告存档可追溯（**两遍报告均判分**）；⑥基线文件正确落盘 `.tmp/code-overdesign-audit/`（**第二遍裁决后判分**，依据上方裁决时序约束）；⑦对照还原后 `git status` 校验工作区干净（阳性对照零残留）。

**场景 3：端到端裁决与执行**（验证 G2/G3）
步骤：任选场景 1 报告的一个中杠杆候选，走完裁决对话（grilling 取舍边界）→ 用户确认 → 执行删减 → 受影响测试全绿。
通过标准：①执行前「取舍后的新行为」已写入裁决确认；②删除后调用方行为与裁决确认一致（无超范围删减）；③冒出的语句级清理点被移交 code-simplify 而非顺手改。

**场景 4：pre-commit 断言多向验证**（验证 G4）
步骤：在目标仓库配置断言后——a) 暂存一个新增无调用方**具名非别名**导出提交（构造须避开 default/别名——拦截面外，否则验收误判失败），预期被拦；b) 暂存正常修改连续 10 次（含既有导出的编辑，其中至少一次为 `export default` 修改），预期全部放行（同时验证拦截面收窄不误拦 default）；c) 带 `oe-exempt:<今日>:wip:<理由>` 标记再提交，预期放行且标记可被 `grep -r "oe-exempt:"` 汇总到；d) **时序用例（WIP 两步提交）**：第一步提交新增导出（带 wip 豁免）→ 放行；第二步提交调用方并移除标记 → 放行；随后跑一次 audit 步骤 0 的等效 grep 汇总，断言汇总中无该豁免残留（队列由 audit 重建的语义，pre-commit 不写盘）；e) **耗时探针**：连续 10 次真实提交实测断言耗时，单次 <10s；f) 模拟脚本级故障（PATH 清空）→ 打印 skipped 不阻塞提交；g) **husky/重定向型仓库安装**：在 `core.hooksPath=.husky/_` 的仓库跑安装 → 走显式分支（登记工作区写入代价或 skipped+指引，可见），真实提交一次验证断言输出实际出现（不静默失效）。
通过标准：a-g 全部符合预期；b 类正常提交连续 10 次零误拦（e 的耗时数据同时是「CI 化」后续决策的输入）。
