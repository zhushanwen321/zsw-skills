# 凑数测试识别与治理

> 配合 SKILL.md 场景 C 使用。诊断现有测试套件的健康度——哪些是真测出问题的、哪些是凑数。

## 凑数测试的 5 个信号

按严重度排序。出现任意一条都值得审查该测试是否值得保留。

### 信号 1：弱断言密度高

```
grep -rc "toBeDefined\|toBeTruthy\|toBeFalsy" tests/ | sort -t: -k2 -rn
```

`toBeDefined` 数量是套件腐败的头号指标。某文件出现 20+ 个 `toBeDefined`，几乎可以确定是"写了测试但没测任何东西"。这些测试让覆盖率好看，但 mutation 100% 存活——删掉被测逻辑它们照样绿。

**治理**：逐个问"改成错的实现它会红吗？"不会红的删掉或改成强断言。

### 信号 2：集成测试测纯逻辑

表现：测试文件起 `createMockBackend` + `buildApp` + `app.inject`，但断言的是纯计算结果（计数、状态、解析输出）。

诊断：
- 文件耗时 >2s 但只含 <20 个用例
- `ms/用例 > 300`（纯逻辑层 1 应 <50ms）
- 用例标题含"计算"/"计数"/"解析"/"格式化"但仍走 HTTP

**治理**：把被测逻辑抽成纯函数导出，下沉层 1。整套耗时从秒级降到毫秒级。

### 信号 3：每用例重建 app / DB

表现：`beforeEach` 里 `buildApp()` + `initDatabase()`。N 个用例 = N 次完整应用启动。

**治理**：`beforeAll` 建一次 app；每用例只 `db.exec("DELETE FROM table")` 清数据（或用事务回滚）。单个 app 实例 + 数据清理比每用例重建快 5-10 倍。

### 信号 4：测试第三方库的行为

表现：断言 `JSON.parse` 能解析、`Date` 能格式化、`fetch` 能请求——这些是库的责任，不是你的代码。库一升级测试就挂，但挂的不是你的 bug。

**治理**：删掉。只测"你对库的使用方式"（你传给库的参数、你对库输出的处理），不测库本身。

### 信号 5：CRUD happy-path 重复

表现：`GET 返回列表` / `POST 创建` / `PUT 更新` / `DELETE 删除` 各一个用例，每个都完整 HTTP round-trip。这些测的是框架（Fastify 路由通不通），不是业务逻辑。

**治理**：保留 1 个"路由+鉴权+基本CRUD通"的烟雾测试，其余删掉或合并成 `it.each` 表驱动。业务逻辑（校验、并发、边界）才值得单独用例。

## Mutation Testing：凑数的唯一客观裁判

覆盖率能骗（一个 `toBeDefined` 让行覆盖达 100%），mutation 骗不了。

**原理**：工具（Stryker）自动把生产代码做微小变异——`+`→`-`、`>=`→`>`、`<`→`<=`、删一行、改布尔常量。每个变异跑一遍测试套件：
- 变异后测试红了 = **mutant 被杀死**（测试有效）
- 变异后测试仍绿 = **mutant 存活**（测试对这个分支是凑数的）

**mutation score = 杀死 / 总变异**。低于 60% 的文件就是凑数重灾区。

**何时跑**：一次性诊断，不改代码。报告会精确指出"哪些测试存活了 mutant"——比凭感觉清理准得多。日常不跑（慢），作为季度体检或大重构前的基线测量。

```bash
# Node/TS 项目示例（Stryker）
npx stryker init
npx stryker run --mutate "src/core/**/*.ts"
# 报告在 reports/mutation/，按文件看存活 mutant
```

## 慢测试帕累托优化

80% 耗时集中在 20% 文件。定位它们：

```bash
# vitest 输出每个文件的 endTime-startTime
npx vitest run --reporter=json --outputFile=/tmp/vitest.json
# 解析 json.testResults，按 duration 降序，标红 >1s 的
```

**优化优先级**（按 ROI）：

1. **纯逻辑误放层 2** → 下沉层 1（收益最大：秒级→毫秒级）
2. **每用例重建 setup** → 改 `beforeAll` + 清表（收益大：5-10x）
3. **不必要的外部依赖**（真起端口、真连网络）→ mock 或 app.inject（收益中）
4. **超时/重试默认值过大** → 测试专用调小（收益中）
5. **串行可并行** → 拆文件并行跑（收益取决于核数）

**不要做的"优化"**：
- 跳过慢测试（`it.skip`）——掩盖问题，测试债务只增不减
- 降低断言来加速——本末倒置
- 给凑数测试加缓存——凑数测试该删不该缓存

## 真实诊断案例

某项目 158 个测试文件、1906 个用例、总耗时 150s。实测分布：

- 35 个慢文件（≥1s）占 132s（88% 耗时），但只含 24% 的用例
- 83 个快文件（<0.2s）含 62% 的用例，几乎零成本
- 全仓 229 个 `toBeDefined()`，集中在 stream-bridge（43）、modality-redirect（20）等文件
- 慢文件特征：`beforeEach` 重建 app + 每用例 `app.inject` 完整 round-trip

**结论**：测试数量（1906）不等于测试价值。治理方向不是加更多测试，而是把 35 个慢文件里的纯逻辑下沉层 1、弱断言改强断言——同样的回归保护力，耗时砍到 1/4。
