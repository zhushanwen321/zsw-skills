# 测试质量方法论

测试的唯一价值是**抓到未来的回归**。覆盖率、数量、绿色对勾都不是目的——一个能抓住真实 bug 的断言，胜过一百个 `toBeDefined()`。

## 核心原则

1. **有效性优先于覆盖率** [MANDATORY]：测试的存在理由是"代码改坏了时它会红"。判断好坏的唯一标准：删掉或改坏被测代码，它会不会失败？不会 = 凑数。Mutation testing 是客观裁判。
2. **纯逻辑下沉到层 1** [MANDATORY]：状态机、计数器、解析器、序列化、排序、过滤等无副作用的纯逻辑，**禁止用集成测试测**。用纯函数单元测试或 property-based 测试，速度快 100 倍且覆盖更多边界。
3. **集成测试只测集成**：集成测试验证"模块协作是否正确"（DB 读写、HTTP 状态码、跨层数据流）。把纯逻辑塞进集成测试 = 既慢又脆，且 mutation 存活率高。
4. **一个 property-based 顶一百个 example**：能表达为"对所有合法输入，X 恒成立"的不变量，用 `fast-check` 自动生成上百个输入。example-based 测 20 个例子都可能漏掉的边界，property-based 一次覆盖。
5. **慢往往是凑数的信号**：80% 耗时集中在 20% 文件。慢测试多源于"用集成测试测纯逻辑"或"每用例重建 setup"。优化它们，而不是容忍慢。

## 写测试时的强制自检 [MANDATORY]

每写完一个测试，提交前必须过这 3 条；任一不通过禁止提交：

1. **mutation 自检**：把被测代码的 `<` 改成 `<=`、`+` 改成 `-`、删一行——这个测试会失败吗？不会 → 断言太弱，重写。
2. **层归属自检**：这个测试有副作用吗（DB/HTTP/文件系统）？没有 → 它是层 1，不该起 server。有 → 它验证的是协作还是纯逻辑？纯逻辑 → 下沉层 1。
3. **断言强度自检**：用了 `toBeDefined` / `toBeTruthy` / `toBeFalsy` / `toBe(true)` / `length > 0` 吗？用了 → 能否换成具体值断言（`toBe(expected)` / `toMatchObject` / `toEqual`）？
