# 范围确定与自适应策略

## 范围确定（优先级从高到低）

1. 用户显式指定了文件/目录/模块 → **以用户指定为准**。
2. 否则：本次提交的代码（`git diff` 覆盖工作区 + 已暂存；或相对 HEAD 的已提交改动）。
3. 本次无提交 → 取当前 `git diff origin/main` 的差集。
4. 以上都为空 → 最近修改/提到的文件。

## 负载指标采集

用 `git diff --stat` 或 `git diff <base> --stat` 估算三个指标：

- **代码量**：新增/改动总行数（不含空白/注释）
- **文件数**：涉及文件数、目录分布
- **架构复杂度**：单层，还是存在模块间依赖 / 跨包耦合 / 深调用链

## 自适应策略决策表

按三指标判定负载等级，任一命中即取较高等级（L1 < L2 < L3）。拿不准就升级（并行更稳）。

| 负载等级 | 判定（任一命中即升级） | 执行策略 |
|---|---|---|
| **L1 轻微** | 改动 ≤ ~150 行，且文件数 ≤ 3，且架构简单（单模块、无跨文件耦合） | **单 agent**：一个简化专家直接处理全部文件，减少协调开销 |
| **L2 中等** | 改动 > 150 行，或文件数 4–10，或存在跨文件逻辑耦合 | **多 agent · 按问题类别拆**：复用 / 质量 / 效率，三个并行审查 agent（各拿完整 diff） |
| **L3 重** | 文件数 > 10，或改动 > ~800 行，或架构复杂（多模块、深依赖、跨包调用） | **多 agent · 按文件/模块拆**：文件/模块分组，每组一个 agent 并行；组内复杂再按问题类别补一轮 |

### 策略理由（为什么）

- **单 agent（L1）**：改动小，一个 agent 上下文足够，减少协调与聚合开销。
- **按问题类别拆（L2）**：三个专注 agent 各管一类，各自深挖代码库里同类问题，比一个全能 agent 覆盖更深（对抗上下文稀释）。
- **按文件/模块拆（L3）**：文件多时单 agent 上下文被稀释；按文件分组并行才能各自保住上下文。组间共享/交叉逻辑用"按问题类别"补充一轮，并由主 agent 聚合冲突。

### 冲突消除

多 agent 可能给出冲突建议（如"复用 agent 建议用工具 X" vs "效率 agent 建议 X 低效手写"）。**由主 agent 基于代码意图判定**，丢弃明显误报，不逐个争论。

### 用户覆盖

用户可强制指定（"用单 agent" / "全部按文件并行" / focus 参数如"侧重内存效率"），以用户为准。
