# Scan 模式 — 找简化候选（不改代码）

处理「找找哪里能简化 / 找死代码 / 清理重复」类请求：把宽泛的「找简化点」转化为**有证据的简化候选**，产出 TODO/FIXME/XXX 注释或提案文本，**不修改任何代码**。用户确认候选后，行为不变的安全清理转 `workflow.md`（fix 模式）执行；涉及行为/API 决策的候选保持提案形态，等人拍板。

## 模式判定

| 用户意图 | 模式 | 产出 |
|---------|------|------|
| "找简化机会"、"哪里能简化"、"找死代码"、"清理重复"、"全仓去重"、"沉淀工具"、"扫一遍简化候选" | **scan** | 候选清单（TODO/提案），不改码 |
| "简化这段代码"、"清理本次改动"、"review my changes" | **fix**（默认） | 修改后的 diff，确认后改 |

涉及重复检测的意图（"清理重复"/"全仓去重"/"沉淀工具"）：**必读 `reuse-optimization.md` 走两层检测**（确定性工具打底 + 纯 LLM 语义级补漏），产出统一为重复簇；簇的复用判定与归宿按同文件三分法。只靠肉眼读文件找重复 = 未完成。

## 步骤 0：项目上下文（不硬编码任何项目）

读目标项目根 `AGENTS.md` 的硬约束与架构文档（`docs/architecture.md`、`docs/design/` 等），识别该项目的踩坑护栏：

- 哪些结构是踩坑换来的硬约束（session 隔离、emit 契约、适配层等），与已记录架构打架的简化需要额外证据。
- **护栏：镜像结构默认是有意设计**。同一事实的双表示、双实现、双后端（本地/远端双 provider、双传输路径等）默认视为有意设计，不得作为「低成本的」简化候选提议删除，除非用户明确推翻该约束。受保护设计内部的未用方法或 hook 仍可清理，只要不拆掉受保护结构本身。

## 什么算强候选（5 条硬性条件）

满足其一即进入候选，但每条都必须有证据：

1. **无生产消费者** — 公开方法、事件、配置项、注册通知、helper、包、持久化事件或测试产物没有任何生产调用者。
2. **双表示镜像同一事实** — 两套结构表达同一个事实（尤其跨持久化状态与运行时事件两套通路），维护两套必会失步。
3. **投机泛化** — 为想象中的产品需求做的通用化：多会话/运行时注册失效、没有产品负责人的通用抽象等。
4. **手写可换依赖** — 手写代码重实现了维护良好的第三方包或运行时内置能力，换掉能删除实现加其专属测试。
5. **added-then-removed 全取代** — 功能加了又被完整移除：代码、配置、schema、测试均无存活痕迹时，残留引用（死文档、注释里的历史叙述）可安全清除。只要还有存活行为、兼容处理或测试钉住，就不是简化候选，而是有主的行为决策。

## 附加信号与薄候选

附加信号（配合硬性条件使用，不单独成立）：

- 测试或文档是唯一消费者，且它们钉住的行为不承重。
- 一个 seam 有每个实现都必须支持、但无消费者使用的方法。
- 独立包只承载测试/demo/支持代码，纯增发布与依赖开销。
- 不变量、回滚路径、期望输出集、特例测试只为保护一个未用 API。
- 简化后的行为可能有细微差异，但新行为仍然合理且更好解释。

薄候选通常不够格：删一个 typo、跑一次工具、删掉有意记录的某实现、没有调用点证据就说「这里看着复杂」。

## 广泛扫描

用户要广度或数量时用并行 subagent，每个 agent 一个域、要求证据不要猜测。域按目标项目的目录结构动态划分（核心运行时、UI、共享类型/协议、扩展/插件、打包与脚本），不写死任何项目的布局。

subagent 不可用时自己模拟同样的广度。**不要被第一个好候选拦住**；从最大的生产代码 delta 开始——只扫未用符号会漏掉重复生命周期/防御机制最重的地方。

## 证明或否决每个候选

写结论前先给每个符号/行为分类消费者：

- 生产语料：`src`、配置与脚本。
- 非生产语料：测试、README/docs、快照、生成的期望输出、注释。
- 模糊语料：demo、工具脚本——先看用法再分类。

用 `rg` 先搜：精确符号名、事件名、包名、配置键、方法名的 `.name(` 与 `name(` 两种写法、线上字符串；然后读调用点。类型检查能报未用导出，但不能替代理解公开接口、动态事件名、测试与文档。

否决或降级：

- 存在生产调用者，简化会变成功能决策而不是清理。
- 该 API 被明确的架构决策或踩坑经验保护，新证据不足以推翻。
- 移除会造成无关连锁改动，却没实际减少公开 API 或必需行为。
- 想法正确但太小：落成带标签的 TODO/FIXME/XXX 注释。

## 产出

### 内联 TODO/FIXME/XXX 注释（小清理）

只用于小、局部、明确有用且不需要设计决策的清理。保持简短可执行：

- 用稳定标签命名问题，如 `TODO(double-default)`、`XXX(unused-default)`。
- 说明为什么现在安全、什么动作能简化它。
- 不给投机抱怨加 TODO，不给需要决策的行为加 TODO。

紧迫度语义按目标项目根 `AGENTS.md` 的约定；无约定时用通用语义：`TODO` 低、`FIXME` 中、`XXX` 高。

### 简短提案文本（涉及决策的候选）

涉及行为或 API 变化、需要人拍板的候选，写一段简短提案文本，放 PR 描述或 issue，不落地为正式文档。结构：

- **问题**：指出现状 API/结构，引用相关文件，给出消费者证据（生产调用者与测试/文档分开列）。
- **提案**：精确说明删什么、折叠什么、降级什么；涉及测试、文档、JSDoc、快照清理时一并列出。
- **代价**：最强的反对理由——放弃什么能力、行为差异、未来产品诉求，以及为什么取舍仍然合理。
- **验收**：可观察的结束状态。

足够具体到实现 PR 能照着走。不要写「简化这个包」这种模糊提案。多个提案重叠时合并进既有提案，不重复建。

## 与 fix 模式的衔接

- 用户确认后，行为不变的安全清理（TODO 类）→ 按 `workflow.md` 的 fix 流程执行（报告、确认后改、增量验证）。
- 涉及行为/API 决策的候选 → 保持提案形态，等用户拍板，不擅自执行。

## 合并其他分支的简化想法（可选）

Diff 兄弟分支用远端主分支做基准（不是当前分支），才看得到它的独立贡献：

- 只移植达标的候选（注释或提案文本）。
- 重叠内容合并进既有提案/注释，不重复。
- 不为了凑数移植低置信候选。
- 更新 PR 描述，让 reviewer 看到真实候选数与范围。
- 只有用户要求时才关重复的 PR。
