# quota-wait：额度等待与守望

套餐额度问题的两种处理，共享同一套机制：**落盘任务状态 + 后台 bash 跑 quota-wait CLI（轮询额度至恢复或到点）**。

| | 模式 A：挂起恢复 | 模式 B：守望检查 |
|---|---|---|
| 触发前提 | 额度已耗尽或即将耗尽，任务必须停 | 额度还够，任务继续跑，先留一个到点保险 |
| 是否停当前任务 | 立即停 | 不停 |
| 等待载体 | 后台 bash 跑 CLI 守到恢复或到点 | 后台 bash 跑 CLI 守到第一个检查点时刻 |
| 醒来后动作 | 无条件按状态文件继续原任务 | 三态分流：已完成收工 / 被额度错误打断则接管 / 仍在进行则起下一个检查点（默认行为） |
| 落盘重点 | 完整接续信息（「下一步」具体到可直接执行） | 在 A 的基础上增加 status 与心跳时间戳 |

后台 bash 里的 CLI 退出时，完成通知回到发起它的会话，CLI 的标准输出（stdout）随通知一起可读：逐行轮询日志 + 末行 JSON 摘要（reason=recovered/deadline、nextFiveHourResetLocal 下一次 5h 窗口结束时刻、三窗口已用状态）。本会话醒来时上下文还在，直接按当时状态判定；会话已关闭则通知丢失，此时唯一凭据是落盘的状态文件。所以 Step 2 落盘不是可选步骤，两种模式都必须做。

## 触发条件（硬性，不可自行放宽）

本 skill 只在用户明确指示时执行——用户说出「quota-wait」「等额度恢复再继续」「X 点再继续」「设个检查点」「额度快用完了」，或直接点名本 skill 时，才走本流程。用模式 A 还是模式 B 由用户的话决定：用户说等恢复再继续 / 任务必须停 → 模式 A；用户说设个检查点到点看看 / 任务继续跑 → 模式 B。

- 用户只说「继续」「开干」「接着做」「额度恢复了」或类似意思 → 直接恢复原任务（读进度文件/状态表接着干），禁止走本 skill、禁止起任何等待任务
- **禁止 agent 自行触发**：不得自行判断「额度快耗尽了，我应该挂起/设个检查点」。额度报错（如 1308 限额错误）发生后的默认动作 = 如实汇报中断点与已完成进度，然后按用户指示行动；用户未明确要求等待时，一个后台 bash 都不许起
- 额度报错且确实需要等待时：先把进度落盘（防丢工作）再汇报——**落盘 ≠ 走本 skill**，起等待任务才是本 skill 的本体；是否起由用户裁决

## 输入

- 必需：当前 agent（pi / zcode）与当前 provider 名——pi 传 taiji provider id（如 `zai-coding-cn`）；zcode 传模型引用的 provider 段（如 `account:bigmodel-individual-coding-plan`）。名字映射表在技能 `config/provider-map.json`，对不上时按 CLI 报错里的指引补一行映射。
- 可选：目标时刻（模式 A 的恢复时刻 / 模式 B 的检查点时刻），如 `18:11`、`3小时后`，作为 CLI 的 `--until` 传入；未给时不问不猜，直接省略（CLI 缺省 6 小时后到点返回）。
- 恢复时刻由 CLI 查询套餐额度接口得出，**禁止自行推算 5h 窗口**；CLI 查询失败（非零退出）时才回落用户口述时刻。

### 前提与 Harness 适配

核心机制在 pi 与 zcode 上完全一致：后台 bash 睡到点退出 → 完成通知自动回到发起会话 → stdout 随通知一起可读。差异只在工具调用形态，按下表取用：

| 操作 | pi | zcode |
|---|---|---|
| 判别特征 | 环境变量 `PI_CODING_AGENT=true`（`env` 输出中可见 PI_ 前缀） | Bash 工具有 `run_in_background` 参数，配套 TaskOutput / TaskStop |
| 启动后台 bash | bash { command, background: true } | Bash { command, run_in_background: true } |
| 返回的任务标识 | task_id | task_id |
| 完成通知 | 自动送达会话并唤醒下一回合 | 自动送达会话 |
| 主动查进度（少用） | bash_output { task_id } | TaskOutput(task_id) |
| 用户取消等待时终止 | bash_kill { task_id } | TaskStop(task_id) |

- 判别以**手头 bash 工具的实际参数签名**为准（参数名是 `background` 还是 `run_in_background`）——工具签名是最终事实，环境变量只作辅助确认；两种签名都不存在时说明当前环境不支持后台 bash，告知用户本 skill 依赖它，停止执行
- 两种 harness 的完成通知都是自动送达，一律禁止用第二个 bash 或循环查询去等第一个（busy-wait）
- pi 环境若装的是 bash-async 扩展而非内置后台 bash，以其签名为准（启动同为 `background: true`，查进度用 pollJobId，终止用 killJobId）

## Step 1：确定 CLI 调用参数

后台 bash 直接调用本技能自带 CLI（要求 node ≥ 18、本机有 taiji 数据目录）：

~~~text
node ~/.agents/skills/quota-wait/scripts/quota-wait.mjs --agent <pi|zcode> --provider <名> [--until <目标时刻>]
~~~

- `--until` 形态：`18:11`（今天已过取明天）、`+3h`、`+40s`、ISO 串均可；用户给了时刻就传，没给就省略
- CLI 行为：首查一次额度，随后每 15 分钟轮询；额度恢复（较上一轮变多：已用百分比下降 / 已用量下降 / 窗口剩余重置秒数跳升）或到点即退出（exit 0），末行输出 JSON 摘要；连续 4 轮查询失败或无 5h 窗口数据时非零退出，stderr 带恢复指引
- CLI 非零退出时不硬等：把 stderr 指引与中断点一并汇报用户，等用户处理（如去 taiji 设置页刷新 Cookie）

## Step 2：落盘任务状态 [MANDATORY]

覆盖写入 `<workspace>/.zcode/quota-wait-state.md`（固定路径与文件名，两种 harness 统一，与平台无关；本场景全局只有一个等待任务）。

两种模式共用字段：

- 模式：A 挂起恢复 / B 守望检查
- 暂停/守望开始时间：<当前时间>
- 预定恢复/检查时刻：<目标时刻>
- 原始请求：<用户最初的任务描述，尽量原文>
- 已完成：<已完成步骤、关键文件路径、commit hash（若已提交）>
- 下一步：<具体到可直接执行的下一步动作；模式 B 被接管时也靠它恢复>
- 注意事项：<约束、坑、未决问题；没有则写"无">

模式 B 追加字段，随任务推进更新（心跳（heartbeat）= 主会话还活着、最近一次活跃的时间戳，是会话上下文丢失后唯一的状态证据）：

- status：running / done / interrupted
- updated_at：<最近一次心跳的本地时间>
- 当前步骤：<正在做什么，供误判排查>
- 检查点次数：<已延后几个检查点，用于排查递延链>

内容从当前会话上下文提取（同一会话挂起时上下文就在手边）；用户在新会话只贴了一句话时按用户提供的写，缺失项如实标"未知"，禁止编造进度。

## Step 3：起后台 bash 等待

### 模式 A：挂起恢复

起后台任务（参数按上方 Harness 适配表：pi 用 `background: true`，zcode 用 `run_in_background: true`，语义相同）：

~~~text
node ~/.agents/skills/quota-wait/scripts/quota-wait.mjs --agent <pi|zcode> --provider <名> [--until <Step 1 的目标时刻>]
~~~

CLI 退出（恢复或到点）即完成通知回到本会话，末行 JSON 的 reason 与 nextFiveHourResetLocal 就是醒来后的行动依据。醒来后的动作（上下文还在时直接做；若醒来时上下文已丢失，按状态文件做同样的事）：

1. 读 `.zcode/quota-wait-state.md`，核对「已完成」与实际磁盘状态是否一致——磁盘比状态文件新时以磁盘为准，防止按过期状态重复劳动
2. 按「下一步」继续执行原任务
3. 完成后按全局规范收尾（测试、commit、汇报）

### 模式 B：守望检查

起第一个检查点：

~~~text
node ~/.agents/skills/quota-wait/scripts/quota-wait.mjs --agent <pi|zcode> --provider <名> [--until <Step 1 的目标时刻>]
~~~

然后**立即继续执行原任务，不做任何停留**。任务执行期间，每个回合末顺手更新状态文件的 `updated_at` 与 `当前步骤`（一次小写，成本忽略不计）。

检查点 bash 退出、通知到达时，按以下优先级判定：

1. **任务已完成**（状态文件 status=done，或自己上下文里任务已收尾）→ 收工，向用户汇报任务已完成、守望结束，不做任何其他动作
2. **被额度错误打断**（自己上下文里有额度耗尽报错、状态文件 status=interrupted，或 updated_at 距现在超过 45 分钟——最后一条是上下文丢失时的兜底判据）→ 接管恢复：按状态文件「下一步」继续执行原任务
3. **仍在进行**（无完成证据、无打断证据、心跳新鲜）→ 任务自己会继续，本次检查点收工；同时**起下一个检查点**：按 CLI 返回 JSON 的 `nextFiveHourResetLocal` + 1 分钟（对齐该套餐 5h 窗口的真实结束时刻再加 1 分钟防边界竞争；JSON 读不到时回落上一个 bash 结束时间 +5 小时 1 分钟）作为 `--until` 起新的后台 bash，命令模板同第一个检查点，状态文件检查点次数 +1

起下一个检查点是默认行为：只要任务未完成，每个检查点醒来都按判据 3 起下一个，直到——任务完成（走判据 1 收工）、被额度错误打断（走判据 2 接管）、或用户明确说不需要继续守望。用户在任何时刻叫停，后续检查点醒来即收工、不再起新的。

## Step 4：汇报后立即停止 [MANDATORY，仅模式 A]

汇报三件事：状态文件路径、预计恢复时刻（可先用 CLI `--dry-run` 查一次得出）、后台任务的 task_id（两种 harness 返回的都是 task_id；pi 与 zcode 的完成通知都附带输出文件路径，CLI 的 stdout 从那里读）。然后**停止，不再执行原任务的任何动作**——额度已经不足，多余动作既烧剩余额度又可能中途被掐断，止血是本 skill 的首要目标。

模式 B 无此步骤：任务一直在跑，没有"停"这个动作。

## 已知限制

- 后台 bash 的存活边界：跨回合必然存活（退出时通知回到会话）；跨应用重启或会话关闭后是否存活未经验证——模式 A 若要等数小时，先确认这段时间会话不会关，否则恢复通知会丢失
- 检查点链条随会话存活而延续：通知回到会话才能起下一个检查点，会话关闭则链条中断、守望静默失效（与模式 A 同一边界）——长时间无人值守时，这条限制决定保险是否真的有效
- CLI 依赖：node ≥ 18；本机 taiji 数据目录（`~/.taiji`，可用环境变量 `TAIJI_AGENT_DATA_DIR` 覆盖）且该 provider 已在 taiji 设置页配置额度查询凭证——缺失时 CLI 非零退出并给指引，此时按 CLI 报错处理，不硬等
- 系统休眠会暂停轮询定时器（与 sleep 同边界），唤醒后自动继续轮询
- CLI 退出后 bash 自动结束，无需手动清理；用户取消等待时终止该后台任务（终止命令按 Harness 适配表：pi 用 bash_kill、bash-async 扩展用 killJobId，zcode 用 TaskStop）

## 禁止

- **禁止在用户未明确指示时触发本流程**——典型违规：「额度报错了，我自己起个后台任务等恢复」「用户说继续，我顺手起个 bash 保险」。用户说继续就直接继续，不起任何等待
- 模式 A 禁止起等待后继续执行原任务（含"顺手再改一点"）
- 禁止自行推算恢复时刻——一律用 CLI 查询；CLI 查询失败时才改用用户口述时刻
- 禁止把任务状态只写进对话不落盘——会话一旦丢失，对话里的上下文全部丢失
- 模式 B 禁止跳过三态判定直接起下一个检查点——每个检查点醒来必须先判定再动作
- 模式 B 检查点只做判定与（必要时）接管恢复，禁止做与任务无关的写操作
- 禁止用本 skill 做普通定时任务或定时提醒——那些直接用 CronCreate，无需本 skill
