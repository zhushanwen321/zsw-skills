# SKILL.md 审查清单

审查 SKILL.md 时按此清单逐项判定。SKILL.md 不是普通 prompt 载体——它通过 description 概率匹配决定加载，正文做路由不做内容。

> 前置知识：审查前必须已读 patterns/skill-design.md 的 6 个设计维度、references/design-principles.md 的 P1/P2/P5/P11/P14、references/failure-mode-taxonomy.md 的 F1/F10/F13、references/carrier-taxonomy.md 的 SKILL.md 栏目。无此前提的审查 = 凭感觉打分。

## P0 必需检查

缺少任何一项 → skill 触发失败、加载后执行错误流程、细节约束丢失。

### 维度 1：Description（触发开关）

- [ ] **Description 只写触发条件**：用"Use when..."开头 + 第三人称 + 包含用户实际短语。不包含工作流描述（"first does X, then Y"）。验证方法：只读 description，能判断该不该加载但不能判断 skill 具体做什么 → 正确。
  - 无此 → 模型 probability-match 后跳过正文，按 description 简化描述行动
- [ ] **Description 有排除子句**："Not for..." 防止无关场景加载。
  - 违反 F10（缺示例）。无此 → skill 在不该触发时被加载
- [ ] **Description < 500 字符**：name + description 合计不超 1024。
- [ ] **触发短语密度 ≥3 个**：覆盖同一意图的不同表达方式（如"审查"/"review"/"audit"/"检查质量"）。

### 维度 2：正文（路由）

- [ ] **正文 ≤150 行**：超过 150 行 → 重新审视每段是否必须在加载时就读到。每超出 50 行，模型实际阅读深度少一层。
  - 违反 P14（约束衰减）。无此 → F13 约束过载：后面的规则被注意力衰减跳过
- [ ] **正文第一句是路由指令而非概念解释**：不写"提示词设计是至关重要的"，写"按以下路由表选择要 read 的文件"。
- [ ] **路由表按用户意图分类**：不是按文件分类。"用户说写" → read X，"用户说审查" → read Y。
- [ ] **路由表覆盖所有主要意图**：写/审查/问原则/要模板/查失败——至少覆盖 skill description 中声明的所有场景。

### 维度 4：标记系统

- [ ] **文件末尾有标记说明章节**：定义 HISTORICAL/ MANDATORY/ OPTIONAL 的语义和修改约束。
- [ ] **HISTORICAL 标记只来自真实事故**：不因为"觉得重要"就加 HISTORICAL——只有真实发生过的灾难配这个标记。
- [ ] **标记嵌入在内容中**：[HISTORICAL] 前缀必须在规则旁边，不能只在末尾汇总。

### 维度 3：References 组织

- [ ] **References 一层深度**：不嵌套引用（references/ 中的文件不引用其他 references/ 文件描述同一主题）。一次 read 即可加载。
  - 违反 P11（展示独立）。无此 → 审查者需要追多层引用才能找到信息

## P1 建议检查

### 维度 1：Description 深度

- [ ] **Description 使用 YAML 折叠块格式**（`>-`）：防止冒号解析错误。description 用双引号或折叠块包裹。

### 维度 2：正文深度

- [ ] **核心原则精简**：3-5 条，每条 1-2 句。不解释模型已知的概念。
- [ ] **正文不重复其他 skill 内容**：如果 meta-sk-skill-writer 已定义 YAML 规范，引用它而非复制。
- [ ] **文件引用用相对路径**：skill 可能安装在不同目录。

### 维度 5：自由度分级

- [ ] **不同步骤有不同自由度**：脆弱操作（不可逆）→ 低自由度（精确步骤），灵活操作 → 高自由度（文字指导）。不自上而下统一定一个自由度。
- [ ] **低自由度步骤有理由标注**："因为此操作不可逆"。

### 维度 6：Token 效率

- [ ] **1 个精心示例优于 3 个平庸示例**：说明同一件事的示例只保留最好的。
- [ ] **不解释模型已知概念**：不需要定义 JSON/Markdown/YAML 是什么。
- [ ] **低频使用内容移出正文**：10 次加载中只用 1 次的内容 → references/。

## 审查清单自检

审查清单本身也需要质量检查。完成本案审查后，确认：

1. **维度覆盖**：6 个设计维度（Description/正文结构/References/标记系统/自由度/Token效率）是否均有检查项？
2. **P0 判断准确**：每个 P0 项缺失真的会导致 skill 触发失败或执行错误流程吗？description 相关项的 P0 定位是否合理（description 写错 = 整个 skill 废掉）？
3. **P1 判断准确**：自由度分级和 Token 效率的 P1 定位是否合理？还是应该升为 P0？
4. **引用完整**：每个检查项是否标注了违反的原则编号和导致的失败模式编号？
5. **可判定性**："正文 ≤150 行"可以通过 wc -l 判定，但"1 个精心示例优于 3 个"如何判定？需要补充判定方法吗？

## 快速参考

审查完成后对照此表做最终确认：

| 原则 | 此载体语境 |
|------|----------|
| P1 行为约束 | description 是触发唯一入口——只写何时用不写做什么，防止模型跳过全文 |
| P2 风险∝密度 | SKILL.md 不做内容做路由——正文控制在 ~150 行，细节在按需加载的子文档 |
| P5 示例驱动 | 路由表中的示例与用户实际会说的话对齐——触发精度由示例决定 |
| P11 展示独立 | 正文路由结构统一，不每个 skill 自己发明排版 |
| P14 约束衰减 | description 过长 → 匹配权重稀释 → 触发精度下降 |

| 失败模式 | 此载体语境 |
|---------|----------|
| F1 规则被忽略 | 核心约束淹没在长 description 中，模型读取后不执行 |
| F10 缺示例 | 路由规则无示例 → 模型不准确判断该进哪个流程 |
| F13 约束过载 | SKILL.md 全文过长 → 加载后 context 浪费，有效约束不可见 |
