# Prompt 架构与工程管理

提示词在代码中的组织方式、分层架构和缓存策略。回答"这段 prompt 应该放在哪里？怎么分层？如何优化缓存？"

## 一、文件组织决策树

当需要管理一段 prompt 时，按以下决策树选择存储方式：

```
需要提示词？
│
├─ 提示词是否需要运行时变量替换？
│  ├─ 是 → 变量数量 > 3 或结构多段？
│  │  ├─ 是 → 独立 .md 模板文件 + 模板引擎
│  │  │       （变量用 {{variable}} 占位符）
│  │  └─ 否 → 代码生成（如 TypeScript 的模板字符串）
│  └─ 否 → 提示词长度 > 100 词？
│     ├─ 是 → 独立 .md 文件（可独立审查、版本控制）
│     └─ 否 → 内联在代码中
│
├─ 提示词是否需要按条件组合多个片段？
│  ├─ 是 → 动态组装（运行时拼接）
│  │       （每个片段独立管理，按条件选择）
│  └─ 否 → 按上面规则选择
│
└─ 提示词是否是 Tool Description？
   ├─ 是 → 信息密度 < 150 字？
   │  ├─ 是 → 内联在工具定义中
   │  └─ 否 → spec 中放核心约束（精简），复杂指引放独立文件
   └─ 否 → 按上面规则选择
```

## 二、管理方式对比

| 方式 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| 内联字符串 | 简短常量（<100 词）；精简 tool description | 代码和 prompt 修改同步；无需额外文件 | 长文本可读性差；不支持变量替换 |
| 独立 .md 文件 | 复杂模板、Agent prompt、Personality | 可独立审查；支持 Markdown 格式 | 需编译时嵌入；不支持变量替换（需后处理） |
| .md 模板 + 变量替换 | 含多变量的 Steering Prompt | 模板与代码分离；编译时可预览 | 需模板引擎；变量类型错误运行时才暴露 |
| 运行时动态拼接 | 按条件组合多个片段 | 灵活；每个片段独立管理 | 组装逻辑复杂；最终输出难预览 |
| 动态生成函数 | 依赖运行时配置的 description | 可按 feature flag 切换版本；灵活性高 | 调试困难；一致性风险 |（Claude Code 特有） |

## 三、Static/Dynamic 分层

### 原理

将 System Prompt 分为两段：跨会话不变的 Static 段和每轮 API 调用重新计算的 Dynamic 段。

### 分层动机

不只是逻辑清晰——核心动机是 **prompt cache 命中率**。Static 段可以被缓存，跨用户甚至跨会话复用，Dynamic 段每次重算。

### 分层线（Boundary Line）

这条线以上的内容跨会话不变，线以下的内容每次 API 调用重新计算：

```
Static（可缓存）:
  ├─ 身份声明
  ├─ 全局行为规范
  ├─ 编码规则
  ├─ 工具使用优先级
  └─ 输出格式规范
═══════ DYNAMIC BOUNDARY ═══════
Dynamic（每 turn 计算）:
  ├─ 环境信息（cwd、git 状态、OS）
  ├─ Agent/Skill 列表
  ├─ Session 状态
  ├─ CLAUDE.md 内容
  └─ 条件性 section（MCP 指令、语言设置等）
```

### 来源

Claude Code：`SYSTEM_PROMPT_DYNAMIC_BOUNDARY` 标记分隔，`systemPromptSection()` memoize 缓存 dynamic 段直到 `/clear` 或 `/compact`。

## 四、缓存优化策略

### 来自 Claude Code 的工程实践

| 策略 | 做法 | 效果 |
|------|------|------|
| Boundary marker | 单行标记分隔 static/dynamic 段 | 缓存系统识别前缀匹配点 |
| Section memoize | Dynamic 段计算结果缓存，直到显式清除 | 避免相同内容重复计算 |
| 高频变化内容迁移 | Agent/Skill 列表从 tool description 移到 attachment | 列表变更不影响 tool schema 缓存 |
| 标准化路径 | `/private/tmp/xxx` 替换为 `$TMPDIR` | 跨用户 prompt 一致 = 缓存可共享 |
| Budget 控制 | Skill 列表占上下文 1% 上限，超出截断 | 防止动态内容膨胀挤掉缓存 |

### 对我们系统的适用性

- **Boundary marker**：即使不做全球级缓存，本地也可以区分"只需算一次"和"每次都要算"的内容，减少不必要计算
- **高频变化内容迁移**：如果 agent/skill 列表频繁变化，将其从 system prompt 移到 attachment/reminder 中，避免 prompt 每次重建
- **Section memoize**：对含计算逻辑的 dynamic section 做结果缓存，在 `/clear` 时失效

### 不适合过度优化的场景

- 用户量小、会话短的系统：缓存命中率收益不大
- 架构不支持前缀匹配缓存的 API：分层的好处主要是逻辑清晰，不是性能

## 五、分层约束策略（约束冗余的应用）

关键约束在多个层级同时出现——不是重复，是有意的冗余。

| 层级 | 位置 | 粒度 | 用途 |
|------|------|------|------|
| Tool description | 工具注册 | 核心约束（精简） | 第一道防线 |
| 参数 schema | 参数定义 | 参数级约束 | 第二道防线 |
| System prompt | 系统注入 | 行为指引 + 示例 | 补充细节 |
| Tool response | 返回值 | 运行时嵌入指令 | 动态补充 |

选择在哪些层冗余：只冗余"状态转换条件"和"工具调用顺序"等关键约束，不冗余"输出格式"和"身份声明"。

## 六、提示词演化与版本管理

### 原则

- **每个 prompt 文件独立版本控制**：独立的 .md 或 prompt.ts 文件，可以在 git 中独立 diff
- **模板和渲染逻辑分离**：模板文件不含代码逻辑，代码文件只做变量替换，不嵌入大段文本
- **修改 prompt 时同步更新审查清单**：如果 prompt 的行为约束变了，对应的 rubric 也必须更新

### 不建议的做法

- 把所有 prompt 放在一个巨大的配置文件里（如 Claude Code 的 900 行 `prompts.ts`）
- 在代码中硬编码超过 100 词的 prompt
- 用 feature flag 制造过多的 prompt 版本差异（维护负担）

## 七、提示词预算管理

### 为什么需要预算

提示词占用上下文窗口的空间。系统提示词 + 所有工具描述 + 运行时 steering prompt 的总和决定了留给对话历史的剩余空间。没有预算控制，工具数量增长时 prompt 会无节制膨胀。

### 分载体的字数预算

| 载体 | 推荐上限 | 依据 |
|------|---------|------|
| System Prompt（static 段） | 500-800 词 | 需要覆盖身份、全局行为、输出格式；超过则拆到 tool description |
| System Prompt（dynamic 段） | 200-400 词 | 环境信息 + agent/skill 列表；按需注入而非全量 |
| Tool Description（低风险） | < 50 词 | 只读/简单操作 |
| Tool Description（中风险） | 50-150 词 | 轻量状态变更 |
| Tool Description（高风险） | 150-400 词 | 复杂编排/安全敏感操作 |
| Steering Prompt | 200-500 词 | 单次注入，按状态按需 |
| Compact Prompt | 300-500 词 | 独立 session，可稍大 |
| Agent Prompt | 50-150 词 | 极简，继承主 prompt |
| Error Message | 50-100 词 | 极简三要素 |

### 总量控制

- **工具描述总量**：所有工具描述的字数总和不应超过上下文窗口的 20%。30 个工具每个 150 词 = 4500 词，在 200K 上下文中占 2.25%，在 32K 上下文中占 14%——后一种情况已经逼近危险区
- **System Prompt 总量**：static + dynamic 段不超过上下文窗口的 5%
- **Skill/Agent 列表**：不超过上下文窗口的 1%（Claude Code 的做法）
- **优先级分配**：核心工具的约束优先保障，低频工具的约束可以精简

> **token 计算参考**：使用 ChatGPT 的 tiktoken 库（`cl100k_base` 编码）进行 token 计数。粗略估算：英文 1 token ≈ 0.75 词，中文 1 token ≈ 0.5 字。后续开发时集成 tokenizer 工具进行精确预算校验。

## 八、提示词可测试性

### 问题

修改 prompt 后，怎么知道是改进了还是退化了？人工逐场景测试不具可扩展性。

### 测试维度

| 维度 | 测试方法 | 示例 |
|------|---------|------|
| 行为一致性 | 修改前后对同一组输入执行，对比工具调用序列 | 旧 prompt：operation X 触发时调用 A→B→C；新 prompt 也应该是 A→B→C |
| 失败模式覆盖 | 构造已知失败场景，验证修改后是否消除 | 构造"一次失败就 blocked"场景，验证新 prompt 不会触发 |
| 约束服从率 | 在 N 个测试场景中统计关键约束被遵守的比例 | "Do not mark complete without evidence"在 20 个场景中被遵守了几次 |
| 回退检测 | 构造不需要触发约束的正常场景，验证约束不会误触发 | 正常完成任务后，验证 agent 不会无故标记 blocked |

### 测试方法

1. **Golden set 对比**：维护一组"已知正确行为"的测试用例（输入 → 期望的工具调用序列），修改 prompt 后跑一遍对比
2. **对抗性测试**：构造已知的失败场景（如"一次失败后尝试 blocked"），验证 prompt 是否阻止了失败
3. **回归测试**：每次 prompt 修改后，跑全部已知的失败场景确保没有"修一个坏三个"

### 注意事项

- 测试结果受模型版本影响——同一个 prompt 在不同模型上的行为可能不同
- 测试用例需要覆盖边界场景，不只是 happy path
- 建议维护一个 `prompt-tests/` 目录存放测试用例

## 标记说明

| 标记 | 含义 | 修改约束 |
|------|------|----------|
| `[HISTORICAL]` | 历史经验总结 | 不允许删除或削弱 |
| `[MANDATORY]` | 流程强制要求 | 必须严格遵守 |
| `[OPTIONAL]` | 可选步骤 | 可根据需求调整 |
