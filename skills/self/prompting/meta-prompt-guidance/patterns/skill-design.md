# 技能中枢设计方法论

SKILL.md 不是普通的 prompt 载体。它通过 description 的概率匹配来决定是否被加载，正文做路由不做内容。

## 前置知识

设计 SKILL.md 前，必须已掌握以下原则和失败模式。如未读过，请先 read：

```
read {skill_dir}/references/design-principles.md
  # 重点：P1(行为约束)、P2(风险∝密度)、P5(示例驱动)、
  #       P11(展示独立)、P14(约束衰减)
read {skill_dir}/references/failure-mode-taxonomy.md
  # 重点：F1(规则被忽略)、F10(缺示例)、F13(约束过载)
read {skill_dir}/references/carrier-taxonomy.md
  # 重点：SKILL.md 栏目 — description 只写何时用，正文做路由不做内容
```

## 核心挑战

SKILL.md 设计最大的陷阱：**把 description 写成能力摘要而不是触发条件。** 模型看到 description 中的工作流描述后，会跳过正文直接按 description 执行——丢失所有细节。

第二个陷阱：**正文做内容不做路由**。150 行以内是上限——每超出 50 行，模型实际阅读的深度就少一层。SKILL.md 的作用是告诉模型"去读哪个文件"，不是"在这里学会所有东西"。

## 设计维度

### 维度 1：Description — 只写触发条件

**为什么重要**：description 是 skill 的"触发开关"。它通过模型中的概率匹配机制决定 skill 是否被加载。如果 description 写了"做什么"，模型可能跳过正文直接按 description 行动。

**决策指南**：

- 格式要求：
  - 用 "Use when..." 开头
  - 第三人称（description 注入 system prompt 时作为工具描述的一部分）
  - 包含用户会说的**实际短语**（如"审查"、"trace code"、"设计 skill"）
  - 包含排除子句（"Not for..."）
  - < 500 字符
  - 使用 `>-` YAML 折叠块格式（防止冒号解析错误）
- 验证方法：**只读 description，能判断什么时候该加载这个 skill 吗？** 如果能但不知道 skill 具体会做什么，description 正确
- [P4 反模式枚举] 反模式检测：
  - description 中出现流程描述（"first does X, then Y"） → 太像正文
  - description 中没有排除子句 → 可能在无关场景被加载（[F10 缺示例]）
  - description 中用了第一人称 → 描述的不是触发条件而是身份声明
- 触发短语的密度：至少 3 个不同的触发短语，覆盖不同表达方式

### 维度 2：正文结构 — 做路由不做内容

**为什么重要**：正文是 skill 的导航员，不是教科书。正文的核心价值是决策树——根据用户意图判断"去读哪个文件"。

**决策指南**：

- 正文结构（按优先级排序）：
  1. 核心原则（3-5 条精简版，每条一句话）
  2. 路由表（用户意图 → 应 read 的文件路径）
  3. 载体选择/场景映射（如适用）
  4. 强制约束（MANDATORY 标记）
- **150 行硬上限**。[P14 约束衰减] 每超出 50 行，重新审视——"这段内容真的必须在 skill 加载时就被读到吗？"如果 600 行正文，后面的规则因注意力衰减被忽略
- 路由表的设计：按用户意图分类，不是按文件分类。"用户说写" → read X，"用户说审查" → read Y
- 正文中引用文件时**总用相对路径**而非绝对路径——skill 可能安装在不同目录
- 每条路由指令的第一条必须是**最高优先级的强制步骤**

### 维度 3：References 组织 — 一层深度

**为什么重要**：references/ 子目录放详细方法论和知识库。一层深度 = 一次 read 即可加载，不用嵌套引用再嵌套引用。

**决策指南**：

- 拆分时机：当正文的某个章节超过 3 页屏幕时，拆到 references/ 中
- [P11 展示独立] 引用格式：正文中写"详见 references/XXX.md 第 N 节"，不写"详见 XXXXXX 文件的 YYYYY 部分"
- 不嵌套引用——references 中的文件不应引用 references 中其他文件来描述同一主题
- 命名规范：references/ 下的文件名能独立说明内容——文件被单独 read 时读者无需看目录就知道它在说什么

### 维度 4：标记系统 — 内容性质标注

**为什么重要**：SKILL.md 中的内容有不同的修改约束。没有标记，AI（或人类维护者）不知道哪些绝对不能动。

**决策指南**：

| 标记 | 含义 | 修改约束 |
|------|------|----------|
| HISTORICAL | 来自实际事故的规则 | **不允许删除或削弱**，只能补充 |
| MANDATORY | 流程强制要求 | 必须严格遵守 |
| OPTIONAL | 可选步骤 | 可根据需求调整 |

- 标记系统的文档：必须在 skill 文件的末尾有"标记说明"章节定义上述含义
- HISTORICAL 标记的使用：只有来自真实事故的规则才配这个标记。不要因为"觉得重要"就打 HISTORICAL
- 标记的可见性：标记必须嵌入在实际内容中（如 `[HISTORICAL]` 前缀），而不能只在末尾汇总说明

### 维度 5：自由度分级

**为什么重要**：不同场景下，skill 应该给 AI 的自主空间不同。脆弱操作需要精确步骤，灵活操作可以给更高自由度。

**决策指南**：

| 自由度 | 适用场景 | 内容格式 | 示例 |
|--------|---------|---------|------|
| 高 | 多种方案均可 | 文字指导 | "你可以用正则或解析器，取决于复杂度" |
| 中 | 有偏优方案 | 伪代码/模板 | 提供推荐方案但允许替代 |
| 低 | 操作脆弱，失败代价高 | 具体命令/精确步骤 | 直接给出必须执行的命令 |

- 不要为整个 skill 统一定一个自由度——不同章节可以有不同的自由度
- 如果一个步骤的自由度设为"低"，必须在旁边标注为什么（"因为此操作不可逆"）

### 维度 6：Token 效率 — 信息密度

**为什么重要**：skill 加载时消耗固定 context。如果有 100 个 skill 但每个平均 300 行，同时加载 5 个就是 1500 行 context 被占用。

**决策指南**：

- [P5 示例驱动] 一流示例优于多个平庸示例。如果 3 个平庸示例和一个精心挑选的示例说明同一件事，只保留最好的一个
- 不重复其他 skill 已说过的内容。如果 meta-sk-skill-writer 已经定义了 YAML 规范，你的 skill 引用它而不是复制它
- 不解释模型已知的概念。不需要告诉模型"JSON 是什么"或"Markdown 是什么"
- 如果一段内容在 10 次 skill 加载中只有 1 次被用到，它不应该在正文中

## 最致命的 3 个失败案例

1. **Description 写工作流** → 模型概率匹配后跳过正文，按 description 的简化描述行动——丢失所有细节约束
2. **正文做内容不做路由**（[F13 约束过载]）→ 600 行正文，模型加载后仍然不知道第一步该做什么，且后面的规则因约束衰减被忽略
3. **缺少排除子句**（[F10 缺示例]）→ skill 在不该触发时被加载，如写 CLAUDE.md 时触发 skill-writing skill，在错误的上下文中执行错误的流程

## 与其他载体的协作

- **Agent Prompt**：skill 是知识/方法论，agent 是执行者。agent 引用 skill 作为方法论来源——agent prompt 说"你是什么"，skill 说"你该怎么做"
- **System Prompt**：skill 正文注入到主 agent 上下文中，作为 system prompt 的扩展。skill 不修改 system prompt，不覆盖 system prompt 中的全局硬约束
- **Personality**：skill 不定义自己的人格风格——那是 agent 层面的设置。skill 只描述流程和方法

## 设计走查

完成 SKILL.md 设计后，按此顺序自检：

1. **Description 纯触发测试**：只读 description，能判断该不该加载 skill 吗？能但不知道具体怎么做？→ 通过
2. **正文路由测试**：正文的第一句话是不是路由指令（"read X"）而不是概念解释？
3. **行数检查**：正文超过 150 行了吗？超过的部分能移到 references/ 中吗？
4. **标记完整性**：末尾有标记说明章节吗？HISTORICAL 标记只来自真实事故吗？
5. **嵌套引用检查**：references/ 中的文件是否引用了其他 references/ 文件来描述同一主题？（是 → 需要索引入口）
6. **排除子句**：description 中有 "Not for..." 子句吗？测试：把 skill 名称遮住，给一个不相关场景的描述，description 能否告诉模型"不用加载"？
