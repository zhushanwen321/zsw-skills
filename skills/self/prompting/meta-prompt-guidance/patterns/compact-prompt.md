# 上下文压缩设计方法论

## 核心挑战

Compact prompt 设计最大的陷阱：**模型在压缩 session 中调用工具而不是生成摘要。** Compact 的 turn 极其宝贵（通常只有一次），浪费在工具调用上等于压缩失败——用户将在没有任何摘要的情况下失去对话状态。

第二个陷阱：**压缩后的摘要缺乏原文引用，恢复方基于自己的理解重新开始。** 模型会"理解"之前做了什么然后"重新开始"，但它的理解可能和实际完成的偏离 30%[F2 目标降级]。

## 设计维度

### 维度 1：反工具调用围栏 — 位置和频率

**为什么重要**：模型在 compact session 中的工具调用会被拒绝（compact session 通常没有工具权限），但如果模型尝试调用工具，它浪费了唯一可用的 turn——这个 turn 本应用于生成摘要。

**决策指南**：

- **至少两次强调**：开头一次 + 结尾一次。Sonnet 4.6+ 的自适应思维有时会忽略单次弱指令——三次尤佳
- 开头强调的格式：
  - 用 CRITICAL/CRITICAL 声明开头
  - 列出所有被禁用的工具（不只是"不要用工具"）
  - 第二段用不同措辞重申
- 结尾强调的格式：
  - "REMINDER: Tool calls in this session will be REJECTED. Generate summary only."
  - 位置必须紧跟输出章节模板之后——模型此时正在计划"输出什么"，最容易产生"如果我去看一下这个文件..."的冲动
- **不要假设模型会记住开头的禁令**。模型在处理长 prompt 时注意力逐渐分散——中间的章节模板可能让它忘记开头说了不要调工具

### 维度 2：结构化章节模板 — 防止信息遗漏

**为什么重要**：没有章节模板，模型对"什么信息重要"的判断不稳定。有时压缩后丢失了用户的所有原始消息，有时保留了不重要但忽略关键的决策逻辑。

**决策指南**：

必需章节（按优先级排序）：

1. **Primary Request** — 用户最初在做什么。必须引用用户的第一条消息原文
2. **Key Technical Concepts** — 涉及的技术栈和概念。只写当前对话中用到的，不写可能与任务相关的
3. **Files and Code** — 修改了哪些文件，关键代码片段。包含文件路径和修改内容
4. **Errors and Fixes** — 遇到的错误和解决方案。必须记录"试了什么 → 为什么失败 → 最终怎么解决的"
5. **Problem Solving** — 解决思路和决策逻辑。记录"选了哪个方案、为什么没选另一个"
6. **All User Messages** — 所有用户消息，含时间顺序。这是最容易被模型省略但恢复方最需要的
7. **Pending Tasks** — 尚未完成的任务。用原始需求对比
8. **Current Work** — 最近的工作进展，**必须引用原文**而非总结
9. **Optional Next Step** — 建议的下一步

- Current Work 章节中的原文引用要求是**非协商项**。没有原文引用，恢复方基于"摘要模型的理解"重新开始 → 任务漂移
- 如果某章节在本次压缩中没有内容，明确写"N/A"而不是省略——让恢复方知道"不是漏了，是真的没有"

### 维度 3：Analysis 草稿区

**为什么重要**：模型直接输出最终摘要时思考深度不足——它为了"简洁"跳过推理过程。草稿区给模型一个空间展开思考，然后再压缩成最终输出。

**决策指南**：

- 格式：`<analysis>` → 模型自由推理 → `</analysis>` → `<summary>` → 结构化输出
- 必须声明 `<analysis>` 最终被剥离，只保留 `<summary>`。让模型知道分析内容不会被后续看到，不用担心"暴露推理过程"
- 草稿区的引导词：`"In <analysis>, think through what matters and why. In <summary>, produce the compressed output."`——不给具体指引，让模型自己判断
- 草稿区和章节模板的关系：草稿区是 writing process，章节模板是 output format。两者独立——模型先在草稿区想清楚，再按章节模板输出

### 维度 4：Partial Compact 变体

**为什么重要**：全量压缩 50 轮对话 → 时间太长、token 太多、质量下降。部分压缩能聚焦当前最需要保留的内容。

**决策指南**：

三种压缩范围：

| 变体 | 范围 | 适用场景 |
|------|------|---------|
| BASE | 全量 | 对话不超过 30 轮 |
| PARTIAL | 只压缩近期 N 轮对话 | 早期对话已经稳定，只需保留近期动态 |
| PARTIAL_UP_TO | 压缩早期对话 + 保留近期完整 | 早期对话是上下文铺垫，近期是执行阶段 |

- 选择依据：**近期对话的价值密度**。如果近期每轮都在做具体修改，保留完整；如果近期只是确认和总结，压缩
- 不要自动选择 BASE——30 轮以上强制考虑 PARTIAL
- PARTIAL_UP_TO 的"UP_TO"点怎么选？找到第一次 git commit 或第一次具体修改的时刻，往前 5 轮作为分界点

### 维度 5：自定义指令注入

**为什么重要**：用户的关注点因人而异。有些用户关心 TypeScript 类型，有些关心性能，有些关心安全。通用章节模板会漏掉用户特定的关注点。

**决策指南**：

- 支持用户通过配置文件追加指令：`"When compacting, pay extra attention to: [user-defined focus areas]."`
- 自定义指令作为章节模板的**加权因子**，不是额外章节——"如果你发现章节中涉及用户关注的领域，扩展那部分"
- 如果用户没有自定义指令，此维度不激活——不要强制加一个空段落

## 最致命的 3 个失败案例

1. **缺少反工具调用围栏** → 压缩 session 中调用工具，浪费唯一 turn（压缩失败，用户完全丢失对话状态）
2. **缺少原文引用要求** → 恢复后模型基于自己对摘要的理解重新开始，任务偏离 30%[F2 目标降级]
3. **缺少 analysis 草稿区** → 模型为追求"简洁"省略关键技术细节，恢复方基于不完整的上下文做决策

## 与其他载体的协作

- **System Prompt**：compact prompt 在独立 session 中运行，不继承主 agent 的 system prompt。compact prompt 自己定义一个极简的行为边界（只做压缩，不做任何其他事）
- **Steering Prompt**：compact 后的恢复机制引用 [P12 交接framing]。恢复方需要 steering prompt 注入"你正在接手一个压缩后的对话"的状态声明
- **Agent Prompt**：compact 后的摘要可能被注入到新 agent 的上下文中作为前置知识——需要和 agent prompt 的环境信息注入配合

## 设计走查

完成 Compact Prompt 设计后，按此顺序自检：

1. **反工具调用围栏测试**：从 prompt 中删除所有反工具调用围栏内容，模型在这个 prompt 下会不会尝试调工具？如果会，围栏还不够强
2. **章节模板完整性**：模拟一个 30 轮的修复 bug 对话——用章节模板压缩后，恢复方能不能在不知道原始对话的情况下继续工作？
3. **原文引用位置**：Current Work 章节是否明确要求"引用原文"而非"总结"？
4. **草稿区与输出分离**：模型是否被告知 analysis 会被剥离？
5. **压缩范围决策**：有没有基于对话长度自动选择压缩范围的逻辑？还是每次都用 BASE？
