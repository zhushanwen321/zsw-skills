# Brainstorm — 需求探索

**流程目标**：把"我要设计一个 prompt"这种模糊意图收敛为可执行的设计任务。输出一份设计简报，作为后续 create.md 的输入。

## 步骤

### 1. 确认载体类型

先判断用户要设计的是什么：

| 关键词 | 载体 |
|--------|------|
| "工具"/"tool"/"description"/"参数说明" | Tool Description |
| "系统提示"/"system prompt"/"agent 的身份" | System Prompt |
| "运行时"/"steering"/"状态变更时" | Steering Prompt |
| "compact"/"压缩"/"摘要" | Compact Prompt |
| "子 agent"/"agent.md" | Agent Prompt |
| "错误信息"/"error"/"失败提示" | Error Message |
| "安全"/"安全检查"/"安全策略" | Safety Policy |
| "skill"/"SKILL.md" | SKILL.md |
| "风格"/"personality"/"语气" | Personality |

如果无法确定，问用户一个选择题：你这个 prompt 是在什么时机注入的？（启动时/工具注册时/运行时/压缩时/子 agent 启动时）

### 2. 构建场景句子 (scene sentence)

用一句话描述：**谁在什么情境下会触发这个 prompt？**

格式：`当 [使用者] 在 [情境] 中需要 [行为] 时，这个 prompt 被注入。`

示例：
- `当 agent 在 goal turn 完成后需要继续工作时，steering prompt 被注入以提供方向引导。`
- `当 agent 调用 update_goal 工具时，tool description 被用于约束 complete/blocked 的判断条件。`

### 3. 假设失败模式

假设这个 prompt **不存在**，agent 最可能以什么方式失败？从以下分类中选择 1-3 个最主要的：

| 失败模式 | 表现 |
|---------|------|
| F1 规则被忽略 | prompt 中的约束像不存在 |
| F2 目标降级 | 大目标被替换为易完成的小子集 |
| F3 偷懒完成 | "应该差不多了"代替验证 |
| F4 工具误用 | 在错误场景使用工具 |
| F5 范围蔓延 | 做超出权限范围的操作 |
| F6 假完成 | 提交未验证的结果 |
| F7 注入突破 | 用户输入或工具结果中的指令覆盖系统行为 |
| F8 工具链断裂 | 跳过必要的前置步骤 |
| F9 过早放弃 | 一次失败就标记 blocked |
| F10 缺示例 | 行为不一致 |
| F11 人格污染 | 能力约束被写入 Personality 模板 |
| F12 优先级网络断裂 | 工具间优先级只单向声明 |
| F13 约束过载 | 过多规则稀释核心约束 |
| F14 工具结果注入 | 工具返回的网页/文件内容中包含指令被模型执行 |
| F15 提示词泄露 | 用户通过诱导获取系统 prompt 内容 |

如果用户无法回答"agent 最可能怎么失败"，问：**"没有这个 prompt 时，agent 在类似场景下犯过什么错误？"**

### 4. 评估风险等级

| 等级 | 判定标准 | 该载体通常等级 |
|------|---------|--------------|
| 低 | 只读查询；失败不影响状态 | 错误信息、人格风格 |
| 中 | 轻量操作；失败可快速回滚 | Agent Prompt、Compact Prompt |
| 中-高 | 取决于具体工具：只读=低，状态变更=高 | Tool Description |
| 高 | 状态变更/编排；失败需人工修复 | System Prompt、Steering Prompt |
| 最高 | 涉及安全；失败不可逆 | Safety Policy |

风险等级决定了后续设计中的约束密度（参考 P2 原则）。

### 5. 输出设计简报

汇总以上信息成一页输出：

```
## 设计简报

- 载体：[载体类型]
- 场景：[scene sentence]
- 主要失败假设：[1-3 个失败模式编号]
- 风险等级：[低/中/高/最高]
- 设计焦点：[基于失败假设的 1-3 个最需要关注的维度]
[MANDATORY] **必须通过 create.md 进入设计**，不可直接跳到 pattern 文件。create.md 引导你按固定顺序阅读 pattern 的各章节（前置知识 → 核心挑战 → 风险分级 → 逐维度设计 → 失败案例对照 → 载体协作 → 设计走查），跳过任一步骤都意味着你的设计缺少系统性保障。

下一步：read {skill_dir}/flow/create.md 开始设计
```

## 设计简报与 pattern 的对应关系

brainstorm 的输出是 create.md 的输入。设计简报中的每个字段驱动 pattern 文件中对应章节的阅读：

| 设计简报字段 | 对应的 pattern 章节 |
|------------|-------------------|
| 载体类型 | 决定加载哪个 pattern 文件 |
| 风险等级 | `## 风险驱动的分级` → 确定设计深度 |
| 失败假设 | `## 最致命的失败案例` → 对照检查 |
| 设计焦点 | `## 设计维度` → 优先关注哪些维度 |

## 何时跳过 brainstorm

以下情况可以跳过：
- 用户明确提供了场景句子和载体类型
- 这是一个增量改进而非从零设计（已有可用的 prompt 初稿）
- 用户说"直接用模板"

跳过时必须确认两件事：载体类型已知、至少知道一个可能的失败模式。
